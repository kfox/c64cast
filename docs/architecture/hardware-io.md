## `backend.py` — the C64Backend duck type, hardware profiles, and the shared write path

c64cast started life talking to exactly one device, and every consumer — scenes, modes, overlays, the playlist, the audio streamer — was duck-typed on the `Ultimate64API` method surface, injected from a single construction site. [backend.py](../../c64cast/hw/backend.py) is that implicit contract made explicit so a second hardware family (the TeensyROM+) could drop in at the same seam. The split inside the ABC is the design:

* The **write path** (`write_memory*`, `write_regs`, `write_region`, `flush`, plus the cache/listener/stats bookkeeping) is **mandatory** — it carries 100% of rendering and audio programming, so a backend that can't write can't usefully exist.
* Everything that needs a *response* from the machine (`read_memory`), a firmware *runner* (`reset`, `run_*`), the REU, or the Ultimate's config REST surface is **capability-gated**: the ABC ships defaults that raise `BackendCapabilityError`, and callers check the matching `profile.supports_*` flag first. The exception marks a *missed gate* — a programming error — not a runtime condition to catch.

**`HardwareProfile`** is why callers never branch on device family: a scene asks `supports_read` / `supports_run_prg` / `supports_reu` instead of testing `isinstance` or a family string. The flags describe the *connected device*, not the backend class — `TEENSYROM_PROFILE` declares `supports_read` at the protocol level, and `TeensyROMBackend.__init__` probes the actual firmware at connect and downgrades it via `dataclasses.replace` (the profile is frozen, so a downgrade is a new value, never shared mutation). Behavioral facts that would otherwise be scattered family checks ride the profile too: `writes_are_acked` (TR — makes `flush` ~free), `reu_bus_clean` (the U64's REUWRITE is an ARM-side memcpy, no bus halt), `kernal_irq_intact`. The Ultimate 64 and Ultimate II+ are protocol-equivalent for c64cast's purposes and share one profile; a per-variant selector (e.g. differing `max_fps`) can be added without touching the factory contract.

**The connect-time capability probe (`refine_capabilities`).** The shared Ultimate profile is a lie in one place: the U64's multi-SID config surface (`SID_CONFIG_CATEGORIES` — addressing, socket configuration, UltiSID curves) doesn't exist on the U2+, whose emulated stereo SIDs live under `Audio Output Settings` with a different topology. Worse, a GET for a category the device doesn't have reads as an empty category — the firmware answered HTTP 200 and an empty body before 3.15 (C64 Ultimate 1.1.0 still does) and answers 404 with a JSON error naming the category from 3.15 on, and `read_config_category_body` folds both into one "absent" answer — so without a gate every SID config consumer read empty state and planned against it. `supports_sid_config` splits that surface out of `supports_config` (the U2+ has a perfectly good config API — REU, sampler, device info), claimed optimistically by the family profile and revoked at connect by `Ultimate64API.refine_capabilities`: one `GET /v1/configs`, run by cli/doctor only after the startup probe has already proven REST reachable — so `--skip-probe` gains no round-trip and an unprobed run keeps today's optimistic behavior, absorbed per-call as before. The revocation is the TR's `supports_read` downgrade pattern on the Ultimate side, and it logs exactly one line saying SID routing/model/mixer control is unavailable on this device.

Category *presence* is the test, deliberately not the `product` string from `/v1/info`: the category list is the actual contract the config calls are made against — it also tracks firmware differences within one product — while the product string is presentation, and matching on it would mean maintaining a list of product names ("U64", "U64E", "C64 Ultimate", …) that drifts with every new SKU. Every failure mode of the probe (unreachable, unrecognized shape) keeps the optimistic flags: the per-call error handling already absorbs a missing surface, but nothing could absorb SID config wrongly *disabled* on a healthy U64 by a transient read error.

`max_write_rate_hz` is 200.0 on **both** profiles, and on the TR that number is a measured floor, not a wall: the link sustained 188 writes/s of 64 bytes with zero missed slots, and a later run held 557 writes/s with zero underruns (`scripts/diags/audio_fm_probe.py`, 2026-08-05). It is deliberately not raised — spending the headroom measures *worse*, raising the DAC noise floor 2–3 dB for NMI ticks nobody can hear. See [the video-path note in audio.md](audio.md#the-video-path-is-deliberately-not-split-and-lost-ticks-are-not-the-hiss).

**`BufferedWriteBackend`** is one shared implementation of the host-side write path, lifted verbatim from the original Ultimate64API so both families get identical cache/diff semantics; a concrete backend implements a single transport primitive, `_emit(addr, payload)`. Sharing it is the point — the delta strategy is subtle enough to drift if it existed twice. `write_region`'s strategy: no cache or a length change → full push; otherwise a choice between **one write covering the dirty span** and **several writes covering only the dirty `DELTA_CHUNK_BYTES` (256) slabs inside it**, decided by `profile.write_cost_s` — whichever the link charges less for. There is no separate full-push branch: a span write is a subset of the same bytes and cost rises with payload, so the span is never worse, and "everything dirty" is just the case where the span is the whole region.

### The chunking decision is per-link, because the two links are opposites

`HardwareProfile.write_cost_s(nbytes)` models what one write costs the frame budget as `max(floor, intercept + per_byte × nbytes)`. Both terms are HW-measured by [`scripts/diags/link_cost_model.py`](../../scripts/diags/link_cost_model.py), which times bursts flush-to-flush and separates the fixed cost from the marginal one with a two-stage fit (2026-08-12, r² = 1.0000 in every cell, reproduced across runs):

| | fixed per write | marginal | knee | regime |
|---|---|---|---|---|
| Ultimate 64 (socket DMA) | **5.22 ms** | 1.85 µs/B | ~2.1 KB | write-count-bound |
| TeensyROM+ (USB serial) | **0.29 ms** | 1.44 µs/B | ~54 B | byte-bound |

The Ultimate row was re-measured on firmware 3.15a (FPGA `125`, core `1.50`, U64-II) on 2026-10-03, with the 1-second idle close handled, in five runs. The floor and slope fall inside that spread and did not move. The intercept did: four of the five runs fit it at 1.30 – 1.33 ms against the 0.784 ms measured in August, so writes above the knee cost about 0.5 ms more than the old model said (8.80 ms measured at 4 KB, 8.34 ms predicted). The profile now carries the five-run median, 1.328 ms, which moves the knee from ~2.4 KB to ~2.1 KB. The fitted floor spans 5.20 – 6.21 ms with a median of 5.35, the slope spans 1.53 – 1.85 µs/B with four of the five runs at 1.84 – 1.85, and the knee spans 1.2 – 2.7 KB with a median of 2.2 KB. The steady cells are tighter than the fit. At 8 B and at 256 – 2048 B, a 320-write burst costs 5.08 – 5.10 ms per write in every run, and 4 KB and 8 KB cost 8.80 and 16.49 ms. The width of the floor range comes from the 32 – 128 B cells, whose fitted per-write cost wanders between 1.9 and 9.3 ms from run to run while each of the 256 – 2048 B cells' fits holds within 14 µs. The 3.15 bitfile also changes DMA reads of I/O registers (`08c8033d`): before it, a read in the first three cycles after BA fell was served without I/O selected. That changes no constant here, since this model times writes only.

The marginal slopes are within ~30% of each other because both are the same thing — the C64 bus at roughly a cycle a byte. What differs by **18×** is the fixed per-write cost, which is the link protocol. That single number inverts the right answer: on the Ultimate a payload under ~2.1 KB is *free* (an 8-byte write and a 2 KB write both cost ~5.22 ms), so k chunks cost k times one span write and chunking is almost always a loss; on the TeensyROM cost is essentially all payload, so skipping clean slabs genuinely pays.

**This is why the old fixed byte-ratio rule was wrong, and why it looked right.** It chunked whenever the dirty slabs totaled under 60% of the region — a pure byte argument, and by that measure it was always winning. Priced against the Ultimate's actual link it was losing every time it fired: measured through `video_render_probe.py` against real video, **19 of 19 firings across three display modes were slower than not chunking**, one mhires clip losing 1083 ms over 400 frames concentrated into 14 frames that each stalled ~77 ms — a visible hitch on scene cuts, which is exactly when a wide sparse dirty pattern occurs. Making the decision a cost comparison took that clip's mean frame from 18.1 ms to 13.3 ms and its worst frame from 104.4 ms to 26.0 ms. The rule was tuned, accidentally, for the byte-bound link.

Dropping the separate full-push branch is the other half, and on real content the broader one: a span write is a subset of a full push, so a frame whose dirty range is wide now sends the range instead of the region. On hardware (U64, a minute of video per mode, write rate and frame rate unchanged) that is **~25% fewer bytes** on the host-DMA bitmap path — 220 → 166 KiB/s — and **~28%** in the character modes, 41 → 30 KiB/s. Note the write *rate* does not move: the chunked branch fired on only ~3.5% of frames, so its removal shows up in the worst frames rather than in an average, which is why the offline per-frame probe is the tool that can see it and a 10-second heartbeat average is not.

**Where this actually applies on an Ultimate.** With the REU enabled, `[video].use_reu_staged = auto` stages `hires`/`mhires` bitmaps through the REU bank-swap, which does not go through `write_region` at all — so on a default U64 the bitmap figures above describe the host-DMA path (`use_reu_staged = false`), and what improves in the staged configuration is screen and color RAM. Char modes (`petscii`, `mcm`, `blank`) are always on this path, as is everything on the TeensyROM+, which has no REUWRITE.

The chunked branch still earns its place on the TeensyROM, for the reason it was written: a waveform trace's dirty *range* spans the whole region while only a fraction of cells changed, and a span-only strategy would push the whole thing. It simply must not fire on a link where the second write costs more than the bytes it saves. Re-measure with `link_cost_model.py` and update the profile constants if a firmware or transport change moves them — nothing else in the tree needs to know.

`_emit` implementations never raise on transport failure: a transient blip must not crash the playlist, so both backends route failures through the shared escalating log ladder (debug on the 1st consecutive failure, warning at the 10th and 50th, error at the 200th; reset on any success). Write listeners — the software framebuffer behind preview and recording — are synchronous and exception-isolated. The semantic helpers (`silence_sid`, `blank_display`, `disable_case_switch`, `restore_kernal_irq_vector`) are pure writes on the standard memory map, implemented once here so any write-capable backend gets them for free.

**`describe_device()`** is the connect-time identity line — `"Ultimate 64-II B95B01 (firmware 3.15a, FPGA 125, core 1.50)"`, or `"TeensyROM+ 12345678 (full firmware, serial /dev/cu.usbmodem12345678@2000000)"`. The ABC default returns `""`, so a backend that can't tell simply logs nothing; the Ultimate reads `GET /v1/info` and the TR reads the USB serial number of a serial-attached board (a TCP-attached one has no per-unit identifier, so the link description carries the rest). It is best-effort by construction — a device that won't answer costs a log line, not a run.

`describe_device(detailed=True)` adds the firmware build, `"firmware 3.15a build dddd29b2"`. The session asks for it only at `-v` (the root logger at DEBUG), because a commit hash is noise on a normal connect line; `--doctor` always asks, because its output is what goes into a bug report. Every `/v1/info` field is optional and only what the device reported is shown, so one code path reads every firmware without a version check: `git_commit_hash` is new in 3.15a and absent on 3.14e and C64U 1.1.0, `core_version` is reported only by U64-family hardware (the C64U included, never a U2/U2+), and `unique_id` only while the unit's `Unique ID` network setting is non-empty. `fpga_version` is `"1"` followed by two *hex* digits (`sprintf("1%02x", …)` in the firmware), so `"124"` is FPGA 0x24 — it is shown verbatim and never compared as a number. The `ethernet_mac` and `wifi_mac` fields 3.15a added are read but never shown: the identity line goes into logs and pasted bug reports, and a MAC is a second per-unit identifier that names nothing the reader needs.

The connection target alone is not enough to identify what a run talked to. An IP or serial path names an *endpoint*: two devices can trade addresses between runs, and `192.168.2.64` is merely the Ultimate's factory default, so several units on one bench answer to it at different times. The `unique_id` is stable across DHCP re-leases, which is why `dac_calibration_store` already keys per-unit calibrations on it. The sharper reason on the Ultimate family is `product` — the *only* field over this API that distinguishes a U64 from a U2+, and the two expose different config categories. A U2+ run that fails a `SID Addressing` PUT reports a bare `404` against a URL, which reads as a firmware or c64cast bug rather than as "this isn't a U64"; the identity line is what makes that legible from a log alone.

`pause_idle()` encodes a contract that is easy to miss: whatever idle it reaches must keep the kernal keyboard scan alive, or `$028D` freezes and the C=-held-to-resume gesture can never be detected — the stream is stranded paused. The default (`reset()`) satisfies it on the Ultimate, whose reset lands at the BASIC READY prompt with the editor IRQ scanning; the TR must override it (see [teensyrom_api.py](#teensyrom_apipy--the-teensyrom-backend)).

**`make_backend(cfg)`** keeps construction policy out of the CLI: it defaults to the Ultimate family so a config with no `[hardware]` section behaves byte-for-byte as before, and folds the resolved NTSC/PAL rate into `profile.default_fps` (video system is orthogonal to hardware variant, so the playlist reads one number). One subtlety on the TR serial path: when auto-detection resolves the device, the factory writes the resolved port *back into the config* — `dac_calibration_store.resolve_calibration_key` only looks up the board's USB serial number when `serial_port` is set, so leaving it empty would silently key two different TR+ boards on one host to a single shared `"tr-serial-auto"` calibration file. `BACKENDS` is metadata for the CLI/schema `choices` only, not a dispatch table — the actual dispatch is the `if`/`elif` chain here; the two are pinned against each other by `test_backend_choices_match_registry` (CLI side) and by every family's own construction tests (dispatch side). `system.upper()` is applied once, here, before the fps fold — nothing at config load enforces `SYSTEM_CHOICES`' canonical spelling, and `resolve_system` in [hw_provision.py](#hw_provisionpy--live-reu--sampler-auto-provisioning) normalizes the same way when it re-folds the profile after the live probe.

`BufferedWriteBackend._stats["bytes"]` is incremented in both `write_memory` and `write_memory_file` — a write path split for exactly this reason (see below) means either one alone would leave half of all traffic invisible in the byte counter this doc's chunking figures are derived from. `_notify` (write listeners) shares the same escalating-ladder shape as `_emit`'s failure path, keyed on its own `_consecutive_listener_errors` counter, so a listener that fails on every write can't amplify one fault into hundreds of tracebacks a second.

## `api.py` — Ultimate64API + `socket_dma.py` — SocketDMAClient

Split-transport client:

* **Writes** go through [socket_dma.py](../../c64cast/hw/socket_dma.py) — a persistent TCP socket to the U64's Ultimate DMA Service (port 64) sending opcode `0xFF06 DMAWRITE`. Per-connection FIFO ordering at the server, ≈5 ms per write, ≈200 writes/sec sustained. The constructor calls `connect()` immediately so failure (service disabled, auth rejected, etc.) surfaces as `SocketDMAError` at startup, before the playlist runs. `api.flush()` is a trailing IDENTIFY round-trip — when it returns, the server has drained every prior write.
* **Reads, reset, runners, probe** stay on REST via `requests`. These are low-rate and one-shot; the HTTP throughput wall (≈50-70/sec) doesn't apply.

**One network password covers both links.** The firmware keeps a single `Network Password` (`CFG_NETWORK_PASSWORD`) and checks it on the DMA socket's AUTHENTICATE, on FTP and Telnet, and on every REST API route (`routes.h` → `find_api_call`, a 403 `{"errors":["Forbidden."]}` when the `X-Password` header is missing or wrong; 3.15 made the missing-header case a clean 403; 3.14 and C64U 1.1.0 run the same check as `strcmp(NULL, …)`, so there a request with no header against a password-protected device is undefined). So `dma_password` is sent on both: `SocketDMAClient` in AUTHENTICATE, and `Ultimate64API` as a session-wide `X-Password` header, encoded to the same UTF-8 bytes. The config name stays `dma_password` because it is user surface. There is no capability to probe — the firmware ignores the header while no password is set — so it goes on every request whenever one is configured. Four guards keep it out of the places the DMA password was already kept out of. `password_header_value` refuses a password HTTP cannot carry (a control character, a leading or trailing space or tab) or cannot encode as UTF-8 (a non-UTF-8 byte in the env var arrives as a lone surrogate) before the session is built, because `requests`' `InvalidHeader` and the codec's `UnicodeEncodeError` quote the value, and `read_memory` or the startup error would log it; `SocketDMAClient` refuses the same password without echoing it. `_UltimateSession.rebuild_auth` drops the header on a redirect to another host, as `requests` does only for `Authorization`. The session sets `trust_env = False`, because a plain-HTTP request through `HTTP_PROXY` (or the macOS system proxy) hands the proxy every header, and no proxy has a reason to sit between c64cast and a LAN device. And urllib3's `-vv` request lines carry method, URL and status, never headers. `probe()` follows the unchecked web root with `GET /v1/version`, an API route, so a password the REST side refuses fails startup (exit 4) and `--doctor` with a message naming the password sources, rather than surfacing later as scattered 403s. That probe runs after `__init__`'s DMA connect, which already fails on a missing or wrong password, so the header-less request older firmware mishandles is not one c64cast sends to a password-protected device.

Two coalescing/caching layers on top:

1. **`write_regs(base_addr, *values)`** — packs N contiguous register writes into one DMA write (e.g. `D020-D023` border + 3 backgrounds in one packet).
2. **`write_region(address, data, region_id=…)`** — caches the last-pushed bytes per region and only sends the changed sub-range, choosing between one span write and per-slab writes by the link's measured cost model ([above](#the-chunking-decision-is-per-link-because-the-two-links-are-opposites)). Display modes call `api.invalidate_cache()` in `setup()` because a mode switch can repurpose the same address. The cache also drops itself whenever `delivery_epoch` moves ([below](#a-write-the-connection-may-have-lost-drops-the-dirty-cache-c64cast531)).

Latency tracking lives on the DMA client (`socket_dma.latency_summary()` / `format_latency()`); `api.format_write_latency()` is the playlist-facing shim (`teensyrom_api.py` exposes the same method name over `teensyrom_dma`'s own latency tracker, so the playlist calls it backend-agnostically). The heartbeat line and the `--profile` summary both surface this.

`flush()` itself still only logs on failure — every one of its ~10 call sites across `audio.py`/`waveform.py`/`asid_player.py`/etc. ignores the return value, and changing its signature to surface failure would ripple through all of them for no benefit (a transient DMA hiccup shouldn't crash a scene). But three call sites inside `api.py` flush immediately before POSTing to `run_prg` — `launch_program`, `_launch_sid_player`, `dump_char_rom`'s `_kick_char_rom_dump` — and `run_prg` soft-resets the C64, so a write that never landed (the SID payload, the re-INIT stub, ...) is unrecoverable once that POST fires. Those three go through `_flush_or_raise()` instead, which raises `RuntimeError` when the flush it just did (tracked via `self._last_flush_failed`, set by `flush()` itself) failed, aborting the launch rather than racing ahead of it. The three also share `_post_prg()` for the POST-then-404-to-RuntimeError pattern (a 404 there means the firmware lacks `run_prg`/`run_crt`), which used to be duplicated three times.

**Reset listeners.** Every reset the Ultimate performs re-applies part of its configuration (`U64Config::run_reset_task` → `effectuate_settings`), and that wipes volatile state c64cast set over the run, the [pushed palette](video-color.md#hardware_palettepy--pushing-a-scenes-own-16-colors-colorhardware_palette) among it. `add_reset_listener` registers a callback that runs after each reset this API issues: `reset()`, the clear-loop `run_prg` in `run_basic_clear_loop`, and every `_post_prg` kick, since `run_prg` and `run_crt` reset the machine too. A listener runs only when the request succeeded, and one that raises is logged and skipped.

**Routes newer firmware added are probed, not version-gated (`probe_route`).** Firmware 3.15 added REST routes that older firmware — 3.14, and C64 Ultimate 1.1.0 — does not register, and a version or product test would have to be maintained against every release of both lines. `probe_route(path, feature)` asks with one `GET` and `classify_route_answer` reads the answer the way the firmware writes it: 200 is present; 501 is a route the firmware registers but this hardware cannot serve (it says why rather than letting a 404 read as a wrong URL); a 404 with an **empty** body is the router finding no such path; a 404 with a JSON `errors` list is the route itself refusing for a reason of its own (`menu_screen` with the menu closed), so the route is present. Only `GET` is ever used, because a probe must not change machine state. Definite answers are cached per connection; an absent or unsupported route logs one INFO line naming the feature it skips. Anything else — a transport error, a 500, a 404 with a body that is not that JSON — fails closed: the feature stays off, a WARNING says so, and nothing is cached, so the next call asks again.

**`SocketDMAClient`'s own failure invariant: every round-trip that fails closes the socket before returning control, except `flush()` used to be the one exception.** `_connect_locked`'s comment states why: leaving `_sock` assigned after a failed handshake risks a half-open socket whose next command blocks on (or misreads) a reply still in the server's per-connection FIFO. `flush()`'s except arm re-raised without `_close_locked()`, so a timed-out IDENTIFY reply landed on the *next* flush as its own — permanently one reply behind on the barrier every `run_prg`/reset call relies on. It now closes like every other round-trip. The two handshake steps (`_authenticate_locked`, `_identify_locked`) had the same class of gap the other direction: each sent its command *before* entering the try block that maps failures to `SocketDMAError`, so a peer that reset the connection mid-send let a raw `OSError` escape past `connect()`'s documented contract — both sends now sit inside the mapped try.

**A connection the server closed is redialed before the command, not after it (c64cast#520).** Firmware 3.15 gives every DMA connection a one-second receive timeout (`socket_dma_set_timeouts` in `socket_dma.cc`: `SO_RCVTIMEO` and `SO_SNDTIMEO` of 1 s), and a `recv` that times out ends the connection loop, which closes the socket. C64 Ultimate 1.1.0 branched before that change and keeps an idle connection open, as 3.14e does. Measured on a U64-II at 3.15a: the FIN arrives 1.00 s after the last command, whichever command it was (IDENTIFY, DMAWRITE or a zero-length WAIT), and a write sent 2 s after the last one returned from `sendall` without an error and never reached memory; only the write after it raised `BrokenPipeError`. The old recover-on-`sendall`-error path therefore lost exactly one command per pause, and `write_region`'s dirty cache recorded it as delivered. `_ensure_live_locked` now runs before every command and every `flush()`, in two parts:

* **Every command: a zero-timeout `recv(1, MSG_PEEK)`.** A pending FIN reads as `b""` and a reset raises (or, on Linux, which reports the FIN first, a reset after a FIN reads as `b""` and sits in `SO_ERROR`, which the check reads too), so a connection the server has already closed is redialed before the command. A pending byte is also a redial, with a warning, because the server sends nothing unprompted and a stray reply means the stream is out of step. Measured cost: under a microsecond, against the ≈5 ms per-write floor; 300 back-to-back writes ran at 5.07 ms each with the check, 4.93 to 5.62 ms without it.
* **After `idle_verify_after_s` (0.5 s) without a command: an IDENTIFY round trip.** The peek cannot see a close that happens after it and before the command lands, and at 0.999 s of idle that window is real. The round trip either fails (and the client redials) or proves the server is in its `recv` with a fresh one-second timer, which the next command then has in full. It costs about 2.4 ms once per pause.

**A redial does not let `flush()` vouch for commands the old connection may have dropped.** Only the idle close is known to be harmless: the server sends its FIN after reading every byte it was sent, so a FIN that arrives `FIN_SETTLE_S` (0.1 s) or more after the last command, by which time any reset a crossing command drew would be here too, redials quietly. Every other redial (a reset, an earlier FIN, a stray byte, an idle IDENTIFY that goes unanswered, a failed `sendall`) abandons a connection that may have discarded commands, and if any command went out on it since its last answered IDENTIFY, the next `flush()` raises `ConnectionError` once, because its own IDENTIFY on the new connection answers for that connection only. It still sends that IDENTIFY first and raises after the reply: `Ultimate64API.flush()` only logs the failure, and its callers then poll registers over REST (`uci.py`) or start timed playback (`sampler.py`, `asid_player.py`) on the assumption that the writes issued on the new connection have landed. Without this, a write the server dropped unread was followed by a `flush()` that succeeded, and `_flush_or_raise` let a REST runner launch on top of it; before the pre-command check existed, the `sendall` into the reset connection made that `flush()` raise. Any `flush()` that raises clears the pending report, so it is raised exactly once.

**A write the connection may have lost drops the dirty cache (c64cast#531).** `write_region` records a region's bytes as soon as `dmawrite` returns, which is when the kernel has taken them, not when the Ultimate has run them. After a lossy redial the next frame of an unchanged picture used to diff against bytes the machine never received and skip them, and they stayed wrong until that part of the picture changed. `BufferedWriteBackend.delivery_epoch` is the sum of two monotonic counts: failed `_emit` calls (`stats["errors"]`, the only loss an acked transport like the TeensyROM+ can have) and the transport's `_possible_loss_count()`. `write_region` compares it with the epoch its cache was filled under and clears every region when it has moved, including a move during the previous call's own writes, so the next frame resends everything in full. On the Ultimate the count is `SocketDMAClient.possible_loss_count`, which goes up in `_abandon_locked`, the one place a connection holding unconfirmed commands is given up: every non-benign redial, and a `flush()` whose IDENTIFY goes unanswered, which `Ultimate64API.flush()` only logs. A polled counter rather than a callback keeps the transport ignorant of the cache and needs no lock on the cache side.

A static picture sends nothing, so it would learn of the loss only at its next command. `Ultimate64API` therefore reads the count through `SocketDMAClient.check_for_loss()`, which runs the per-command peek without sending: it costs a non-blocking lock attempt and, only while commands are unconfirmed, one `recv(MSG_PEEK)`. A reset or an early FIN there abandons the connection and counts the loss, and the next command redials. The firmware 3.15 idle close is left alone for the next command to redial quietly, and a connection another thread holds is not waited for, since that thread's own command runs the same check. A machine that reboots without sending a reset is not detectable this way; the first command after it draws the reset and the frame after that repaints.

Clearing the cache only helps a region that someone writes again, so anything that skips a write because it believes the bytes are already there has to follow the same epoch. The display modes' color registers (`$D020`-`$D023`) go through `write_region` under `RegionID.VIC_D020`/`VIC_D021` on every push, instead of a mode-side last-value check. Two callers skip a write without going through `write_region` and read `C64Backend.delivery_epoch` themselves (the ABC default is 0, meaning "never resend"). `VideoScene.process_frame` treats a moved epoch like an OSD change and renders the held frame again, so a paused video does not wait for playback to resume. `VoiceScopeRenderer` keeps the regions it paints only on a content change (strip colors, the two text rows) and sends them again from `_render_hires` when the epoch moves. Writes made once at setup (charsets, IRQ handlers, the `$D011`/`$D016`/`$D018` pokes) are not covered: nothing repeats them, so a loss that takes one of them is repaired only by the next scene's setup.

A setup write whose loss would go unnoticed *and* stay wrong uses `hw/delivery.write_confirmed(api, write, tries=3)` instead: it runs the write, flushes, and repeats while `delivery_epoch` moved across the run, so a run that left it unmoved landed. A write that raises a transport error counts as unconfirmed, since `reu_write` is not routed through `_emit` and leaves the epoch unmoved when a redial fails. The REU audio pump's install stages, the sampler's ring prefill and prebuffer, and the ASID player's ring prefill and player install go through it; each caller decides what an unconfirmed write costs.

A redial on 3.15a costs about 7 ms (TCP connect 2 to 4 ms, IDENTIFY 3 to 5 ms), measured both right after a client close and after the server's idle close, so nothing waits seconds for the old connection to clear. A keepalive (a zero-length `WAIT`, opcode `0xFF05`, every half second while idle) also holds the connection open on 3.15a and was measured working, but it was not adopted: it needs a thread, it adds a write under the shared lock during every pause, and it would keep the one connection the server serves held for as long as the process lives, where 3.15a otherwise lets another client in after a second of silence. A reconnect is cheap enough that keeping the connection alive buys nothing measurable. `reconnect_count` counts every implicit redial and the `--profile` latency line prints it as `reconnects=`.

**A failed redial backs off (#542).** Every failed `_emit` moves `delivery_epoch`, so during an outage every region is retried on every frame, and before the backoff each retry dialed. A dial to a machine that is switched off holds the connection lock for the whole `connect_timeout` (5 s), which the audio thread is waiting on too. `_reconnect_locked` now refuses implicit redials for `REDIAL_BACKOFF_MIN_S` (0.5 s) after a failed one, doubling to `REDIAL_BACKOFF_MAX_S` (8 s). A refused redial raises `SocketDMAError` with no network I/O, so the write still counts as failed and the picture still repaints once the link is back. A successful dial or an explicit `connect()` clears the backoff. The first wait is what a blip costs on recovery, against a 7 ms redial when the machine answers. At the cap, a timing-out dial holds the lock for at most 5 s of every 13, and a machine that comes back is redialed within 8 s. Measured on loopback, 10 frames of a hires picture (bitmap changing, screen and color still) with the server gone and `connect_timeout` scaled to 0.5 s: before the backoff, 27 dials and 13.9 s of wall time when every dial times out; after it, 1 dial and 0.74 s. A refused dial is fast either way (0.25 s for both). The base before #531 made 9 dials and took 4.8 s, because the cache still skipped the unchanged regions.

The single-connection behavior was re-measured on 3.15a. A second connection opened while the first is in use is accepted at the TCP level but its IDENTIFY is not answered; it is served as soon as the first connection closes, including by the idle timeout, about one second after the first connection's last command. So on 3.15a a second process can take the machine over after a second of silence, and this client's next redial then waits behind it and fails after `io_timeout` with a `SocketDMAError`.

**Some reconnects are sticky-refused.** A rejected password (`_auth_rejected`) and an explicit `close()` (`_closed`) both make the next implicit reconnect (from `dmawrite`/`flush` finding `self._sock is None`) raise immediately rather than redialing — the credential-harvesting/self-DoS angle (re-offering a known-bad cleartext password to whatever now answers `host:port`, or hammering the firmware's per-failed-AUTHENTICATE `vTaskDelay(1000)`) is specifically what this closes off. A generic transient failure (dead endpoint, network blip) is not sticky: it gets the timed redial backoff described above (#542), and the next redial after the wait dials again. `_recv_exact_locked` now tracks one cumulative `io_timeout` deadline across all its `recv()` calls instead of resetting a fresh per-chunk timeout on every one — a peer dribbling a reply back slower than the timeout but never idle for a full one used to wedge the read (and the lock shared with `AudioStreamer`) far past `io_timeout`.

## `teensyrom_api.py` — the TeensyROM+ backend

The TR-family implementation of `C64Backend`, on top of the token protocol in [teensyrom_dma.py](../../c64cast/hw/teensyrom_dma.py). Nearly everything unusual in it traces to two firmware facts that shipped together in TR+ v0.7.2.5: WriteC64Mem became **cycle-clean** (its /DMA assert gates on a safe VIC cycle), and **ReadC64Mem** (`0x64FD`) appeared. `profile.supports_read` is therefore the proxy for "new enough firmware" throughout the module — it gates not just reads but the choice of idle, SID playback, and the char-ROM dump.

**Connect-time capability probe.** The profile declares read support at the protocol level, but a given device may run older firmware. `__init__` reads 2 bytes at `$FFFC` (the KERNAL reset vector — always mapped, value-stable) and downgrades `supports_read` on failure — version-robust without parsing the ping banner. The failure path drains stale bytes, because an unknown token on old firmware can leave trailing bytes that would desync the next real command.

**Two idles.** On cycle-clean firmware, bring-up launches the same IRQ-enabled BASIC clear-loop the Ultimate runs, keeping the kernal keyboard scan — and so `$028D` — live for the keyboard poller. On older firmware it falls back to the spin stub: `SEI`, 252 × `NOP`, `JMP` back to the top. Pre-cycle-clean DMA perturbs the running 6510, and streaming over a live interpreter corrupts it within seconds (`?UNDEF'D STATEMENT`, `?SYNTAX ERROR`); a perturbed cycle in a NOP sled just lands somewhere in the sled and slides back to the `JMP` — there is no interpreter state to corrupt. The cost is that IRQs stay masked, `$028D` freezes, and physical-keyboard control is gone. The clear-loop path's own repairs — LaunchFile leaving the program un-run, the CURLIN READY probe, draining the loader's post-ack chatter — are the [Startup section's](#startup-basic-clear-and-loop-program) story; the CURLIN constants also record that the usual "high byte `$FF` means direct mode" summary did **not** match on hardware (READY read `$0000`), which had silently disabled the repair until the probe accepted both.

**`pause_idle` — both constraints are hardware, not style.** (1) *Don't reset*: a TR reset boots to the TeensyROM menu, which does not run the kernal keyboard scan, so `$028D` freezes and resume can never be detected. (2) *Don't blank*: DEN=0 removes badlines, and the cycle-clean DMA gates its /DMA assert on a badline — with none, every subsequent read *and* write hangs, which strands resume and wedges the TR until a power-cycle. Since the clear-loop keeps running underneath every scene anyway (the DMA only overwrites screen/VIC RAM, never the BASIC program), pause is simply a DMA screen-clear with DEN left on — the closest possible idle to the working live-scene state.

**Sliced writes, only while an NMI sample player runs.** WriteC64Mem halts the 6510 for the whole payload, and every halt longer than one CIA2 NMI period (85 cycles at 12 kHz NTSC) costs the `$D418` DAC's sample player ticks — the NMI is edge-triggered, so ticks that fire during a halt collapse into one. On firmware that carries WriteC64Spans (TR+ v0.9+, detected by `probe_spans` at connect unless `[teensyrom].dma_slicing` is `off`), `_emit` sends a write as slices of at most `dma_slice_bytes` with `dma_slice_gap_us` of 6510 time between them. Measured on an NTSC C64 (`scripts/diags/halt_shape_probe.py`, 2026-10-03), 32-byte slices with 40 µs gaps lose 3.9× fewer NMI ticks per byte written than WriteC64Mem. With DAC audio under mhires video the NMI rate rose from ~10 630 to ~11 630 Hz (nominal 12 032), and the FM wobble in captured audio fell 2–4× (`audio_fm_probe.py`) with an unchanged noise floor. Tear rate on the double-buffered bitmap did not move (about 1% of frames either way, `doublebuffer_tear_ab.py` with every write sliced, before the gate below existed), and with DAC audio on the displayed frame rate held or rose.

**Off by default anyway.** Those averages hide what slicing costs a bitmap video. On a flash/beep clip whose flashes last 100–133 ms, mhires at 20 fps with DAC audio showed some flashes for a single 17 ms frame and missed one or two in 23 when sliced, against a 33 ms minimum and none missed unsliced: the slower link leaves frames queued, and a short-lived one is skipped. And on a music video the audio sounded better unsliced to a listener, whatever the FM-wobble figure says. So `dma_slicing` defaults to `off`, and `auto`/`on` stay for a user who wants the steadier NMI rate.

Slicing is not free: each command costs ~0.4 ms of extra round trips plus a gap per slice, so bulk throughput falls ~2.4× (264 vs 634 KiB/s for 4 KiB, `scripts/diags/tr_spans_cost.py`), and a muted mhires frame push went from 16 to 43 ms when every write was sliced. Hence the gate: a write is sliced only while `note_nmi_consumer(True)` is in force, and only when it is longer than one slice — a segment of a sliced write is held to the same cutoff, so a short tail goes on WriteC64Mem too, and at `dma_slice_bytes = 0` the cutoff is a whole 1 KiB segment, which is to say WriteC64Mem in 1 KiB halts. The `AudioStreamer` sends that note once `NmiTimer.start` has armed the timer (verified, or unverifiable on a link that cannot read) and clears it in `stop()`; a muted scene, a setup upload, the ring prebuffer or a register write therefore stays on WriteC64Mem at full speed. It used to go out when the NMI vector was pointed at the player, before the prebuffer, so the whole prebuffer went out in slices for a consumer that was not running yet. The one-slice cutoff is measured, not assumed: a 32-byte write loses ~0.1 ticks either way, and from 64 bytes up slicing cuts the loss about 3×. Cart IO (`$DE00-$DFFF`), which the firmware refuses as a span target, also stays on WriteC64Mem.

Sliced commands carry at most `SPANS_SEGMENT_BYTES` (1 KiB). A 4 KiB sliced command holds the link ~15 ms, and the audio worker's ring writes queue behind it: a fifth of ring slots landed late on bitmap video, against none at 1 KiB. A command refused at its token because the bus is held (`TRSpansRefused`: REU emulation running, or the C64 paused) has written nothing, so `_emit` carries that segment and the rest of the write with WriteC64Mem instead of counting a failure; asking again per segment would pay the refusal's text drain (≥150 ms) for each one while the bus stays held.

**`dac_bitmap_tempo` follows the write path.** Sliced writes cost the NMI player fewer ticks, so a bitmap + DAC video drains nearer real time, and the U64-measured `tempo_scale` fractions would over-compensate it into playing ~9% fast. A TR+ writing sliced reports 0.97, measured on the reference music video at 0.972 MultiHires / 0.974 Hires (`mhires_tempo_clock_ab.py --tr-slicing auto`'s clock/wall); writing unsliced, the TR landed within 1% of the U64's 0.88 / 0.89 and keeps them. See [the tempo section in video-color.md](video-color.md#videopy--webcamsource-shared-broker--avfilesource-pyav).

**`read_memory` returns `None`, never raises.** The keyboard and menu pollers call it every ~100 ms and rely on `None` meaning "couldn't tell"; a raise would turn every transient link blip into a dead playlist. This mirrors the Ultimate's REST read contract.

**Kicks are `$0314` vector swaps, not LaunchFile.** LaunchFile resets the C64, and its async boot + fast-LOAD raced the scope bring-up and the keyboard poll; a launch-based SID start would have needed a pile of boot-race workarounds (boot settle, a bus-silent launch lock, a trampoline + pre-uploaded SYS stub, a verify-during-boot read). Instead, with the IRQ-enabled clear-loop chaining through `$0314`, both the SID player start and the char-ROM dump DMA their payload and swap the vector so the next kernal IRQ runs the stub once — no reset, no boot, and the display the caller painted survives, which is what lets `defer_audio` put the oscilloscope on screen before the first note. Both kicks refuse via `_require_irq_idle` on old firmware: the spin stub masks IRQs, the swap would never fire, and without the gate the failure mode is a silent hang or silent playback rather than an error. The orchestration above the kick is shared with the Ultimate — see [backend-agnostic orchestration in sid.md](sid.md#backend-agnostic-orchestration) and [char_rom.py](#char_rompy--reading-the-character-rom-off-the-machine). The post-swap `$0314` read-back (`_verify_player_irq`) is best-effort — a mismatch logs "audio may be dead" rather than raising.

**Bring-up retries; uploads replace.** After ResetC64Token the TR reboots its menu and re-inits SD, and PostFile is refused (FailToken) until the menu handler is ready — so bring-up retries up to 6 × 1.0 s instead of trusting any fixed post-reset delay. `_upload` deletes before posting because PostFile refuses to overwrite (`"File already exists."`); helper PRGs live under a dedicated `c64cast/` folder on the TR's SD/USB so retries and re-runs never touch the user's own file roots. Bring-up is best-effort (failures log), but `launch_program` re-raises — its caller (LauncherScene) has to know the launch never happened.

**`_settle_after_launch` goes through the lock, not the raw transport.** LaunchFile's ack is followed by asynchronous console text (see the [launcher-upload race](#known-issue-the-launcher-upload-race) below), and `_settle_after_launch` drains it — but it runs *after* `launch_file()` has already released `TRClient._lock`, at exactly the moment the keyboard/menu poller's own `read_memory` calls (which take that same lock) can be running concurrently. Reading `self.tr.transport` directly here would reopen the race this drain exists to close; it goes through `TRClient.drain_after_command` instead, which re-takes the lock for the duration of the drain. `_upload` also now logs a debug breadcrumb ("keyboard poller may be active during upload... corruption race possible") whenever it runs on read-capable firmware, so a field report's cryptic on-screen `?SYNTAX ERROR` can be correlated back to this known cause instead of investigated from scratch.

**No host-side readback between PostFile and LaunchFile — and no way to add one.** `post_file()`'s checksum is computed from the host's own copy of the data and verified device-side against what the TR actually received; that catches transfer corruption on the *PostFile command itself*, but not the launcher-upload race's actual mechanism (a stray poller read consuming bytes meant for a different reply). Closing that gap would need the host to read the uploaded file back off SD/USB and compare, but the wire protocol has no ReadFile-from-storage token — `ReadC64Mem` reads C64 memory, not TR storage — so there is nothing for `launch_program` or `_upload_and_launch_retry` to read back even if they wanted to. This is a real, open limitation of the current firmware protocol, not an oversight in this client.

## `teensyrom_dma.py` — TeensyROM link errors + the launcher upload race

### Errors carry the firmware's reason

`_expect_ack` captures the trailing text the TR emits after a NAK and puts it in the raised error, instead of surfacing a bare `FailToken (0x9B7F)`:

* A `"Busy!"` reply — program running, or menu handler inactive — raises `TRBusyError`, a subclass of `TRError`, so callers can distinguish it.
* Any other reply has its literal text appended (`"Not enough room"`, `"File already exists."`, …).

That reply text — plus the `Ping`/`Reset` status lines — is device-supplied free text with no framing of its own, so both transports' `drain_text` filter it to printable characters (`_sanitize_device_text`) before it can reach a log record or an exception message. `delete_file`/`post_file`/`launch_file` frame their path argument through `_encode_path`, which raises `TRError` (not a bare `UnicodeEncodeError`) for a non-ASCII path and rejects an embedded NUL outright — an unrejected NUL would truncate the device's own path parse early and leave the rest of the encoded path as extra bytes desyncing whatever command follows.

### Deadlines: per-command lock, not per-connection

`TRClient`'s docstring is deliberately scoped to *per command*: the lock serializes one command's own send+ack, so two threads' commands can't interleave on the wire, but it says nothing about chatter the TR streams asynchronously after a command's ack is already read and the lock released — that's exactly the [launcher upload race](#known-issue-the-launcher-upload-race) below. Code that needs to drain such chatter goes through `TRClient.drain_after_command`, which re-takes the lock, rather than touching `self.transport` directly.

Within a single command, both transports' `recv_exact` track a cumulative deadline (`time.monotonic() + io_timeout`) checked on every loop iteration, not only when a read returns nothing — a link that trickles in at least one byte per call (never a fully empty read) would otherwise never trip a per-chunk timeout and could hold `TRClient._lock` indefinitely, which was `TcpTransport`'s state entirely and `SerialTransport`'s partially (its deadline existed but was only consulted in the empty-read branch). `SerialTransport.drain_text` additionally overrides the underlying `pyserial` object's `.timeout` to `quiet_s` for the duration of the read loop (restored after) — without it, `read()` blocks up to the fixed `io_timeout` (2 s) waiting for any bytes, so the common "nothing to drain" case paid a multi-second stall instead of returning after its own much shorter `quiet_s`. Both `drain_text` implementations also cap total wall-clock time and total bytes (`_DRAIN_MAX_S` / `_DRAIN_MAX_BYTES`), independent of the quiet-window reset that both do on every byte received — a misbehaving or hostile device that never quite goes idle would otherwise keep the drain, and the lock every write/read command needs, open indefinitely.

### WriteC64Spans is sent in stages, so a failure leaves the firmware mid-command

WriteC64Mem's frame goes out whole and is acked once. `write_spans` sends a token, then a header and span list, then the payload, and waits for an ack after each: firmware without the command answers the token with text, and a header sent blind would be parsed as commands of its own. The cost is that a stage whose reply never comes leaves the firmware part way through — it may still act on the token (an ack lost to reboot chatter after a reset) and take the next command's bytes as its header. `_recover_spans` closes that window: if the header has not gone out it sends four zero bytes, which the firmware refuses as a zero-span header with nothing owed (and older firmware reads as two unknown `0x0000` tokens), then it waits out `_SPANS_RECOVER_QUIET_S`. That quiet covers the firmware's 500 ms per-byte wait for a silent sender plus the one second it then discards input. `probe_spans` always sends the same four zero bytes for the same reason, and counts as support an ack or a FailToken (the command exists but the bus is held), or, when chatter hid the reply, the refusal's own text.

### Known issue: the launcher upload race

Under investigation, **not yet fixed.** The TR launcher (`launch_program` = PostFile + LaunchFile) can produce an intermittently-corrupt upload.

The mechanism: the keyboard poller's `ReadC64Mem` — and likely the launcher's own input poll — shares the TR link with the launcher's reset+PostFile. A poll read landing in the post-reset chatter desyncs the stream, so the next PostFile drops a byte. The `.prg` then loads one byte short and BASIC reports `?SYNTAX ERROR`.

It is a race, so it reproduces intermittently; single-threaded runs and the Ultimate backend are both reliable. Three candidate fixes are open — a desync-safe `read_segment`, suspending the poller across reset+upload, or draining before upload — and all need a soak harness to verify. See [caveats.md](../caveats.md).

## `vic_stream.py` — the machine's own VIC output

Every other path in c64cast is open-loop. The render pipeline computes a screen, DMAs it, and never looks; `readmem` can confirm the *bytes* landed but not that the VIC drew what those bytes mean, so a character ROM that isn't the one assumed, an MCM bit-3 surprise or a mode switch caught mid-frame are all invisible from the write side. That is why `scripts/diags/` points a capture card at the HDMI output.

The machine can simply tell us. The Ultimate 64's FPGA taps the VIC's own pixel stream and pushes it out of the Ethernet MAC as UDP, with **no C64 involvement at all** — no cycles stolen, no bus contention, nothing a running show can disturb and nothing the stream can disturb in return. Socket DMA `0xFF20` starts it and names a destination; `0xFF30` stops it. Because the picture comes from the VIC rather than from the pipeline, it is also right for what c64cast did not draw: a SID scene's own display, the launcher's game, a machine somebody is typing on.

**Ultimate 64 only**, and the flag is not guessed from the family. The firmware compiles both commands under `#ifdef U64`; an Ultimate II+ is a cartridge in someone else's C64 with no VIC of its own, and a TeensyROM+ has neither the FPGA nor the MAC. `supports_video_stream` is optimistic on the Ultimate profile like `supports_sid_config`, and `refine_capabilities` revokes it from the same category that decides `supports_system_mode` — that category is the same `#ifdef` seen from the config API, and reading the answer twice would only create a way for the two to disagree.

**The wire format**, 12 bytes of header then packed pixels: `seq`, `frame`, `line`, `pixels-per-line` as four little-endian `uint16`s, four more documented bytes, then 4 bits per pixel two to a byte, **low nibble first**. Bit 15 of `line` marks a frame's last packet. Two things are read rather than assumed, because they are the two that vary: width comes from the header, and height is *counted* from how much of a frame arrived — ~272 on PAL and ~240 on NTSC, and not worth a table when the stream says so fifty times a second. The last four header bytes are ignored, as the firmware's own reference client ignores them: nothing needed is in them, and reading a field that turns out to mean something else is worse than not reading it.

**What it costs is the design constraint.** A PAL frame is 384×272 at half a byte a pixel — ~52 KB — and the machine sends every one, so the stream is ~2.6 MB/s for as long as it is on, whether or not anyone is listening. Hence two rules. It runs only while somebody is watching, which `control/screen.py` enforces by ref-counting. And it is started with the firmware's **own** auto-stop timer armed (`bufferSize` on the ON command, counted in FreeRTOS ticks at that firmware's `configTICK_RATE_HZ = 200`, so 5 ms each), re-armed while the receiver is still listening. A `finally` covers the ordinary exits; nothing in this process covers `SIGKILL`, and the failure that leaves behind — a machine firing megabytes a second at a closed port — is exactly what a watchdog counted down *by the machine* is for.

**The first ON after a cold ARP table does nothing**, and the retry is the fix. Before the firmware can stream to a unicast address it resolves the destination's MAC by sending up to ten two-byte UDP probes and watching its own ARP table; if the entry doesn't appear in time it gives up and never enables the stream. Those probes are what *populate* the table, so the attempt that failed leaves the next one ready — observed on hardware as "nothing at all, then instant on the retry". `PRIME_AFTER_S` makes the receiver re-issue the ON 1.5 s after starting, which turns a dead panel into a short delay; the periodic watchdog renewal takes over from there. (Those two-byte probes also arrive on our socket, which is the other reason the receiver ignores anything at or under the header size.)

Two smaller decisions. **Loss is not repaired**: a frame missing a packet is dropped whole rather than shown with a band of the previous frame in it, because this exists to answer "what is on the screen" and a stale band is a wrong answer — the next frame is 20 ms away. And the **destination is resolved by asking the routing table**: connecting a UDP socket to the machine sends nothing but makes the kernel pick the source address for that destination, which is the actual question, and unlike `gethostname` it gives the same answer on a laptop with a VPN, a container bridge and Wi-Fi all up.

**The wire protocol has no authentication**, so the receiver checks every datagram's source address against the machine it asked to stream (resolved once, at `start()`, the same way the destination is) before accepting it — otherwise anyone on the segment who guesses the bound port could inject fake frames. The partial-frame buffer also has its own byte cap (`_MAX_PARTIAL_BYTES`, well above one real ~52 KB frame), independent of `_expire_partial`'s silence-based timeout: a flood of packets that never sets the last-packet bit would otherwise grow that buffer without limit while waiting for the machine to fall quiet.

## Startup: BASIC clear-and-loop program

After `api.reset()`, `api.run_basic_clear_loop()` POSTs a 25-byte tokenized BASIC PRG (`10 PRINT CHR$(147) : 20 GOTO 20`) to `/v1/runners:run_prg`. `PRINT CHR$(147)` wipes the BASIC READY banner and homes the cursor; the infinite `GOTO 20` keeps BASIC out of the editor's direct-input mode so the kernal cursor-blink IRQ stays naturally suppressed. Audio bring-up still just uploads the NMI routine and starts the CIA #2 timer; the NMI fires regardless of what the BASIC loop is doing.

### The loop is the *only* way to stop the cursor blinking

Nothing c64cast writes touches BLNSW (`$00CC`), and nothing should. The obvious move — DMA `$80` there to tell the kernal editor's blink code to skip its toggle — was tried repeatedly and does not work: the editor's input-wait loop copies NDX (`$00C6`) into BLNSW on every pass, so with BASIC at READY the byte is gone microseconds after the DMA lands. Measured on hardware, a write to `$00CC` never reads back while every other zero-page address holds fine. Nothing the host can write holds that address down.

There was a `suppress_cursor_blink()` helper that made that write anyway, on the theory that it was still worth doing for the moments BASIC is parked elsewhere (after a SID player's `JMP *` spin survives teardown). It was removed: it is a no-op wherever the blink is actually visible, and its presence invited exactly the "just poke `$CC` harder" reflex that never works. Getting BASIC into the `GOTO 20` loop is the whole mechanism — there is no second one to fall back on.

### TeensyROM: LaunchFile leaves the loop un-run

The TR has no `run_prg`; `_bring_up_irq_clear_loop` PostFiles the same PRG and LaunchFiles it. Measured on hardware, the body lands at `$0801` but the first line's link pointer reads `00 00` and VARTAB sits at `$0803` — the signature of a BASIC cold-start init arriving *after* the copy. BASIC therefore sees an empty program, RUN drops straight back to READY, and the machine spends the whole session in the editor's input-wait loop. That is where the TR's blinking cursor came from, and why no amount of writing `$CC` could stop it. It also let the editor eat the keystrokes the keyboard poller reads out of KEYD.

`_ensure_clear_loop_running` repairs it with DMA only: re-write the program body to `$0801`, fix VARTAB to just past it (or RUN's `CLR` puts variables on top of the program), then type `RUN` + RETURN into the kernal keyboard buffer — which works *because* BASIC is stuck at READY, since that wait loop is exactly what consumes KEYD.

`_basic_is_at_ready` gates that repair, and is a **read**: CURLIN's high byte (`$003A`) is `$FF` in direct mode and the executing line number otherwise. The gate matters because typing into a running loop would leave keystrokes in KEYD for the poller to read as menu input (RETURN is a nav code). It used to infer the same state from the `$CC` write above — write `$80`, read it back, conclude from whether the editor had clobbered it — reading the state only as a side effect of a write that shouldn't have been happening at all.

### The probe has to wait for the loader to stop talking

LaunchFile acks and *then* streams its own console text back over the same link — `Remote Launch:` / `P:` / `F:` / `Loading IO handler` / `Resetting C64`, a C64 reset and BASIC cold start included. A fixed `time.sleep` after the launch guessed at how long that takes, and guessed short: measured on hardware, the first post-launch command's reply misaligned with the text and came back as the ASCII of `…mote Launch:`. The probe then failed, `_basic_is_at_ready` returned `None`, `_ensure_clear_loop_running` took its can't-read-the-state early return, and the repair was **silently skipped** — leaving BASIC in the editor with the blinking cursor the repair exists to prevent.

This is not a property of writes. A read collides identically; the earlier `$CC` write was simply the command that happened to be first in line. `_settle_after_launch` replaces the sleep with `drain_text`, which re-arms its deadline on every chunk and so waits for the stream to actually go quiet, consuming the text instead of leaving it to desync the next command.

## `char_rom.py` — reading the character ROM off the machine

Every C64-native glyph c64cast draws comes from the character ROM: the bitmap-mode text overlays (`scrolling_text` → `TextSurface` → `bitmap_text.load_glyphs`), `big_text`'s 8×-scaled scroller, the on-C64 menu, the oscilloscope's text rows, and the preview/recording renderers. With no ROM installed, `framebuffer._builtin_charset()` synthesizes an ASCII font with `cv2.putText` — legible, but not the C64 font, and PETSCII graphics codes come out blank. A user reported "the scrolling text looks bad"; that was the whole explanation, and it was a first-run defect rather than a rendering bug.

[char_rom.py](../../c64cast/hw/char_rom.py) is the single resolver every glyph consumer goes through — an explicitly configured path, else `paths.roms_dir()/chargen.bin`, else the legacy cwd-relative `assets/roms/characters.901225-01.bin` (so an existing checkout keeps working), else the cv2 fallback. Only the automatic answer is cached process-wide; an explicit path is read fresh, because the cache is deliberately not keyed by path and would otherwise hand every caller whichever file was asked for first.

The load path runs the same `verify()` the install path does, rather than only checking length — a resolved-but-garbage file (stale, wrong format, a typo'd `charset_path` that happens to name a real file) falls back to the cv2 font with a logged warning instead of rendering garbage glyphs silently. `ensure_installed` shares that check for its own gate: a resolved file that doesn't verify counts as "nothing installed" rather than as a reason to skip the auto-dump, so a bad file at a resolved path can't suppress it forever. A configured `charset_path` that doesn't exist at all also warns, naming what it fell back to — `resolve()` itself still falls through silently (a missing charset degrades, it never raises), but the substitution used to be invisible to the operator.

**Why it takes a 6502 stub.** The ROM is not RAM. A host `read_memory($D000)` returns the I/O page — VIC/SID/CIA registers — because what `$01` maps is decided *on the C64*, at read time. The only way to see the charset is to run code on the machine: clear CHAREN (`$01 = $33`, i.e. `$37` with bit 2 cleared), copy `$D000-$DFFF` down into plain RAM, restore the bank, and let the host read the copy back. `api.build_char_rom_dump_stub` is that code, in the hand-assembled-with-a-listing style of the SID player MC.

**Placement — both addresses are load-bearing:**

* The landing zone must be RAM readable **under default banking**, since `read_memory` sees whatever `$01` is at read time. That rules out the `$A000`/`$D000` underlay RAM. `$C000-$CFFF` is the proven-safe high RAM the SID player already lives in, and it survives `run_prg`'s soft reset (RAMTAS's memory-size scan restores every byte it probes).
* The stub cannot share those 4 KB — the copy would overwrite it mid-flight — and cannot live at `$0200-$03FF`, because RAMTAS zeroes the cassette buffer on every reset and the Ultimate kick *is* a reset. `$8100` is BASIC program RAM: far above the one-line `SYS` program `run_prg` loads at `$0801` (which creates no variables, so BASIC never grows into it), and clear of the `$8004` cartridge-signature window the KERNAL checks at reset.

**The two kicks**, split exactly like `_launch_sid_player` — the same shape of shared orchestration (here on `_StubRunnerBackend`, which owns the dump; the SID player's equivalent lives in `_SidPlayerMixin`), one per-backend hook (`_kick_char_rom_dump`):

* **Ultimate** — POST `10 SYS 33024` to `run_prg`. The stub gets the `CLI`/`RTS` tail (it was called from BASIC). Because the kick soft-resets, `Ultimate64API.dump_char_rom` re-establishes the BASIC clear loop in a `finally`, so the caller gets the machine back in the idle state it handed over.
* **TeensyROM** — swap `$0314/$0315` to the stub so the next kernal IRQ runs it once, the same primitive the SID player start uses: no reset, no boot, no fast-LOAD window. The stub gets the IRQ tail — restore the vector, `JMP $EA31` — and no `CLI`, because `RTI` restores the I flag from the stacked status. Gated on `supports_read`: the pre-cycle-clean spin-stub idle masks IRQs forever, so the swap would never fire.

**The completion flag** is what makes the read deterministic. The last byte of the blob is uploaded as `$00` and set to `$FF` by the stub as its final act; the host polls that one byte before reading the landing zone. Without it the read races the ~45 ms on-C64 copy, and there is no other signal — the Ultimate's `run_prg` POST returns once BASIC has *started* the program, not once `SYS` has returned.

**Verification is structural, not an equality test** against a known image, because a Swedish machine's charset (or a JiffyDOS font, or a replacement) is exactly the charset that user wants. `char_rom.verify` proves we got a charset and not I/O registers or blank RAM: at least one full 2 KB set; within each set, screen codes `$80-$FF` complement `$00-$7F` (the check that catches a botched `$01` bank — I/O and RAM cannot satisfy it, and an all-zero or all-`$FF` buffer already fails it outright); screen code `$20` blank and `$01` not (which is what rules out a buffer whose halves complement *by construction*, e.g. half zeros and half `$FF` — the complement check above cannot see anything wrong with that one). The complement check carries a small tolerance: the stock 901225-01 is *almost* exact but not quite — the reversed `@` at screen code `$80`, row 5, reads `$99` where the complement would be `$9D`. A verifier demanding exactness would reject the very ROM it exists to accept. The SHA-256 comparison against the stock digests is reported as a note and never affects the verdict.

A failed verification is a hard failure of `--dump-char-rom` and a logged warning of the auto path — an unverified file is never written, because a bad one is worse than none (the cv2 fallback at least renders legibly) and it would suppress the auto-dump forever.

**When it runs.** `char_rom.ensure_installed` is called from `session.build_stack` right after the reset + BASIC clear loop, where the machine is idle and nothing has painted. It fires only when nothing resolves already, the backend has both `supports_read` and `supports_run_prg`, and `[hardware].dump_char_rom` is on. It costs one `run_prg` round trip on the very first run against a given machine, invisible behind the existing startup, and never again. It is best-effort and never fatal; on success it calls `invalidate_cache()` so the run that triggered the dump already benefits.

No ROM bytes enter the repo, the sdist, the wheel, or a release asset. The bytes move from the user's hardware to the user's disk and stop.

## `c64.py` — the hardware constant register

Naming an address or register value in [c64.py](../../c64cast/hw/c64.py) is what keeps the code greppable (`VIC.D018_MEMORY` rather than a bare `"d018"`) and porting to another Commodore variant tractable. Most of it is a plain name table; the groups below carry *policy*, which is what earns the module a section:

* **`CIA2.PORT_A_BANK_*` are whole-byte values, not bit masks.** The upper bits of `$DD00` drive the serial bus / RS-232 outputs; c64cast writes the whole byte and deliberately clobbers them, with the `0x97` base keeping the serial lines idle-high to match the kernal's post-init state. Which VIC bank a scene may use is encoded here too: banks 0 and 2 are the only ones with kernal char-ROM mapped at their `$1000` offset, so the char-mode double-buffer swaps between those; bank 1 is normally off-limits because the audio ring lives at `$4000-$5FFF`. The waveform scene is the one exception — bitmap-only (no char-ROM dependency) and it stops the ring at setup (the SID plays on the real chip), so it can claim bank 1 for tunes whose payload occupies banks 0 and 2.

* **The derived-timing helpers (`cpu_clock`, `frame_rate`, `kernal_cia1_latch`) reject anything but "NTSC"/"PAL"**, case-insensitive and whitespace-tolerant (nothing at config load enforces `config.SYSTEM_CHOICES`' canonical spelling, so a lowercase or padded value legitimately reaches here). They used to fall through to PAL for *any* other string — including the unresolved `"auto"` config default, which `config.SYSTEM_CHOICES` explicitly allows, and any typo — silently giving every clock-derived constant (CIA latch, NMI budget, SID PLAY rate) the wrong standard's numbers with no diagnostic. A caller holding "auto" must resolve it first: `hw_provision.resolve_system` does this against live hardware before scenes are built, and the two offline-only validators that run *before* hardware opens (`scene_factory.validate_nmi_sample_rate`, `doctor._validate_audio_nmi_rate`) assume NTSC, matching `Ultimate64Cfg.system`'s own documented fallback.

* **The NMI budget constants are hardware measurements, not estimates.** `NMI_HANDLER_WORST_CYCLES = 68` supersedes an earlier 81-cycle *estimate* — a ring-prefill tone sweep on real hardware found the overrun onset, and `NMI_SAFE_MIN_PERIOD_CYCLES = 75` keeps margin for PAL and unit variation. `halt_quantum_bytes` sizes host writes from the measured ~1 cycle/byte DMA halt (1.02 µs/byte U64, 0.97 TR). The measurements and their consequences are told in [audio.md](audio.md#sample-rate-and-the-overrun-ceiling) (and [the ring-write split](audio.md#the-ring-write-is-split-and-spread)); the constants live *here* so `nmi_rate_safety` stays pure and is the single source of truth that config validation, `--doctor`, and the tests all import.

* **`RegionID` is a collision registry.** The write path's delta cache keys by region ID, not address — that is what gives a mode switch that reuses `$0400` a clean diff baseline after `invalidate_cache()`. IDs are claimed centrally, with reserved strides (per-voice `+0..9`, menu rows `+0..24`, and separate bank-2 IDs so the host-DMA double-buffer diffs each bank against its *own* prior content, not the other bank's), precisely so a collision is visible at definition time instead of surfacing as silent cache corruption mid-run.

* **`U64_API` is also a list of refusals.** `/v1/machine:writemem` is deliberately absent — writes go over socket DMA, not REST ([caveats.md](../caveats.md) has the transport measurements). `/v1/runners:sidplay` is deliberately absent because the firmware UI it draws hides VIC output (see `api.run_sid_player`).

* **`KEYBUF` names decoded PETSCII as it lands in KEYD** (`$0277`) — what the U64's keyboard-inject opcode writes and what the on-C64 menu poller drains — distinct from the raw matrix scan codes at `$00CB`. The kernal folds SHIFT into the cursor codes (SHIFT+CRSR-down decodes to CRSR-up, `$91`), which is why the menu reads direction straight off the code with no separate modifier read.

## `hw_provision.py` — live REU + sampler auto-provisioning

[hw_provision.py](../../c64cast/hw/hw_provision.py) enables the U64 REU and the Ultimate Audio sampler over the REST config API when the run needs them, and restores the originals at teardown. It lived in doctor.py until the name stopped fitting — every call from the normal run path went through a `from . import doctor as _doctor` alias, which was the code saying the name is wrong: diagnostics *observe*, this module *mutates* the machine.

The load-bearing property is **live + volatile**: a single-item `PUT /v1/configs/<cat>/<item>` applies through the firmware's `effectuate` and is never saved to flash (verified in the firmware source — `route_configs.cc` + `config.h` `at_close_config` call effectuate only). So even a missed restore reverts on the next power-cycle, which is what makes best-effort acceptable everywhere in the module: a failed restore just logs, and `provision_*` returns whatever it changed *so far* even when a later PUT fails, so teardown still restores partial changes.

`wants_reu` / `wants_sampler` are the single statement of which config shapes need each feature. Doctor's REU/sampler probes import them, so the `--doctor` report and the provisioner can never disagree about what a run requires; both return the *reasons* (which flags flipped the want) so log lines and diagnostics can point at the exact setting. One subtlety is deliberate: `use_reu_staged` defaults to the *string* `"auto"`, which is truthy — `wants_reu` tests `is True` so that only an explicit `true` is a hard requirement. Auto self-heals to the host-DMA double-buffer (also tear-free), so it must never be grounds for mutating the user's machine config. The provisioner is gated entirely inside itself (`auto_reu`, `profile.supports_*`, not `--skip-probe` — config is never written that couldn't first be read back — and the hard want), so `session.build_stack` calls it unconditionally. The full run-lifecycle narrative (call ordering around the availability resolvers, teardown, doctor severity) is [audio.md's auto_reu section](audio.md#ultimate64auto_reu--automatic-reu-provisioning).

REU sizing is always 16 MB: c64cast's highest REU offset is the video staging region near 14 MB (`modes_irq.REU_VIDEO_BITMAP_COLOR_BASE = $E13000`), so a smaller REU would silently wrap, and 16 MB is FPGA-backed — the maximum costs nothing.

`fetch_config_section` is the firmware response-shape normalizer — firmware 3.x nests the section under the category name; older/variant firmware returns the dict directly or as a single-item list, recognized via `field_hint`. It is single-sourced here because it previously lived, identically, in two doctor probes; a firmware shape change is a one-place fix. A category the device does not register comes back as `({}, None, None)` — an empty section with no error, distinct from a failed read's `({}, None, exc)` — because the transport underneath is `api.read_config_category_body`, the one place the two firmware answers for "no such category" (200 with only the errors array before 3.15; 404 with a JSON error naming the category from 3.15, GideonZ/1541ultimate#805) become one `None`. `Ultimate64API.get_config_category` sits on the same helper and returns `{}`, so the SID mixer, volume, panning and calibration readers see the same contract. A 404 without that JSON error is the route itself missing and stays an error.

The sampler half mirrors the REU half, with four quirks of its own: the sampler's *presence* is detected by whether the firmware exposes its config keys at all (there is no feature-flag endpoint); the mixer's audible volume label is `" 0 dB"` **with a leading space**, verbatim from the firmware's `volumes[]` table — the GET returns it and the PUT expects it; the restore dict spans two config categories (I/O map vs. mixer), hence the composite `"category\x1ffield"` keys; and the mixer category itself is **searched, not fixed** — the U64 carries `Vol Sampler L/R` in `Audio Mixer`, the Ultimate II+ (firmware 3.x) in `Audio Output Settings`, and a category the device doesn't have reads as empty rather than as an error (200-empty before firmware 3.15, 404 with a JSON error from 3.15; `fetch_config_section` returns both as an empty section with no error), so a hard-coded name read as "sampler absent" on the U2+ and silently downgraded its video audio to the 4-bit DAC even with the sampler mapped and audible. `read_sampler_config` probes the candidates in order, reports the first that actually carries the fields (`SamplerConfig.mixer_category`), and every mixer PUT and restore key targets the resolved category. Its "can't tell" contract is deliberately conservative: fields found ⇒ present, no fields with every candidate readable ⇒ absent, but no fields with *any* candidate unreadable ⇒ `None`, because "absent" can't be distinguished from "unreadable" there — and provisioning never writes config it couldn't first read back. `wants_sampler` names the scene shapes that route audio through the sampler (video scenes, and generative scenes with `audio_source = "file"`, whose 4-bit DAC rendering is staticky) — missing a sampler-routed shape there doesn't error, it leaves the sampler silently un-provisioned, which is why the predicate is single-sourced with the doctor probe. `sampler_is_available` runs *after* `provision_sampler` so a box this run just enabled reads as available.

`provision_master_volume` handles firmware 3.15's `Vol Master`, which the firmware multiplies into every mixer source, so at `OFF` the run is silent whatever the per-source levels say. It is its own provisioner rather than a step of `provision_sampler` because the 4-bit DAC and every SID scene go through the same mixer: gated on `supports_config`, not `--skip-probe`, and `wants_audio` (`[audio].enabled`, or a waveform/midi/asid/launcher scene or a SID generative scene, which sound with audio disabled; doctor's SID and master-volume probes use the same predicate). It searches the same candidate categories as the sampler mixer, raises the master only from `OFF` to `" 0 dB"` — a trimmed master is a deliberate level, and the per-source levels c64cast sets are relative to it — and restores through the same composite keys (`SystemStack.master_volume_restore`). The item is probed by presence, never by firmware version: 3.14e and C64 Ultimate 1.1.0 do not carry it, which reads as unity and writes nothing; an unreadable category logs a warning and writes nothing.

## `uci.py` — the Ultimate Command Interface at `$DF1C-$DF1F`

[uci.py](../../c64cast/hw/uci.py) speaks the four-register protocol a C64 program uses to ask an Ultimate for things: `$DF1C` control, `$DF1D` a write-only command FIFO, `$DF1E` result, `$DF1F` status. Wait for control to read idle, push the target and command bytes, raise `PUSH_CMD`, wait for BUSY to clear, drain `$DF1E` while control reports data and `$DF1F` while it reports status, then release. It drives the same registers and control bits as the firmware's own 6502 clients (`software/6502/unsorted/uci_wedge.s` in GideonZ/1541ultimate), which sequence them differently: they never wait for idle before a push, and they pace their reads off the state bits rather than off bits 7/6.

**No 6502 code is uploaded to reach it.** The Ultimate decodes a DMA read and a DMA write on the cartridge bus through whichever bank configuration is in force, so `$DF1C-$DF1F` answer the same `read_memory`/`write_memory` path everything else in c64cast already uses — which is why this module needs only a `MemoryBus` protocol and not a backend. The alternative designs were an uploaded stub polling the registers and a C64-side palette window; the first costs a PRG upload and a `SYS` per query, and the second does not exist in the FPGA sources.

`$DF1D` is a FIFO, so every byte is its own single-byte write: a two-byte block write lands the second byte on `$DF1E`.

**The control register is not just a state field.** Reading `$DF1C` returns `slot_status` from `command_protocol.vhd`: bit 7 response_valid, bit 6 status_valid, bits 5-4 state, bit 3 error_busy, bits 2-0 handshake_in (push / ack / abort). Bits 7 and 6 are `state(1) and not handshake_in(2)` on top of the buffer still having a byte to hand over, so neither port answers until the command reaches a data state — a drain that starts while it is still BUSY comes back empty rather than early. A handshake bit stays set after the write that raised it until the Ultimate has processed it, so **the state bits alone do not mean the interface is free**. The abort bit is the one that outlives the state it was written in: `command_protocol.vhd` leaves the state where it was, and the firmware answers the bit with `HANDSHAKE_RESET`, which rewinds the command pointer as well as clearing the bit — so a command pushed in that window is read back as a zero-length one and answered with an empty reply (`command_intf.cc`'s "Null command."). Checking only bits 5-4 made the first read of a run work and every one after it fail; `_is_settled` requires idle state *and* a clear handshake. `error_busy` is raised when a push arrives at a non-idle interface and is never cleared by the firmware, so it outlives whatever set it and is cleared on the way in.

**Handing the interface back is two different writes**, and picking the wrong one is a silent no-op. `command_protocol.vhd` gates the `NEXT_DATA` bit on `state(1) = '1'` — set only in the data states — so a command abandoned while it is still BUSY ignores the ack entirely and stays wedged, blocking every later command including the firmware's own clients. `ABORT` is gated on nothing — the same process sets the abort flag on any write with bit 2 set, and `command_intf.cc` answers that flag with `HANDSHAKE_RESET`, which forces the state back to `00` from wherever it was. `_transact` therefore acks only when it drained the whole reply and aborts otherwise, in a `finally` that covers everything after the command is pushed — and then confirms the register actually settled, escalating to an abort if it did not. That confirmation is not belt-and-braces: a palette read spends ~110 REST reads between the push and the release, the U64's DMA socket is closed under it during that window (firmware 3.15's one-second idle close). The write client used to learn of that only from a failed *send*, so the ack went into the closed socket and was lost; it now sees the close before the command and redials, so the ack lands. The confirmation stays, because a reset or an unanswered idle IDENTIFY can still lose the ack (and the next `flush` then raises). If the ack is lost, without the check the interface is left in a data state — wedged for every later command and for the firmware's own clients, which is how a working first read and a dead second one were traced. (`uci_wedge.s`'s `uci_abort` is not the model for that split: it aborts only from a data state and gets out of the others by pushing an empty command and acking that.)

**The confirmation is skipped when nothing took the command.** `command_protocol.vhd` moves the state to BUSY on the clock edge of the `PUSH_CMD` write, so a control register still reading idle on the next bus cycle is not the interface — with I/O banked out these are RAM cells that read back the byte just written to them, release write included, and a register that never clears the handshake bit looks exactly like one that is wedged. Insisting there spends both idle timeouts and ~290 single-byte reads and warns that a machine which was never asked anything may need a reset, on the path the fallback is documented to take quietly. `_took_command` is that one read; the release is still written either way, because "not the interface" is read off one register and a real wedge is the expensive way to be wrong.

**The status string is checked, not just the reply length.** The control target answers `NN,TEXT` — `00,OK` on success, `21,UNKNOWN COMMAND` for a command it does not have (other targets use other shapes; the software-IEC one answers a single binary byte) — and a length check alone accepts anything: a bus reading back a constant `$80` satisfies DATA_AVAILABLE forever and yields 48 identical bytes, which is a full-length, entirely fictional palette. The check includes the comma, because these four addresses are only the interface while I/O is banked in — with it switched out a DMA read answers from RAM, which is four steady but *unrelated* bytes, so a control cell claiming idle-with-data can sit beside a status cell that spells ASCII `0` as many times as it is asked. No repeated byte spells `00,`. Checking the code first also means the debug log says the machine did not know the command, rather than that the reply was empty.

Every failure — firmware without the command, a timeout, a short reply, a bad status, registers that are not the interface, a backend that cannot read memory at all — is a debug log and a `None`; the caller picks the fallback. Verified against a U64-II on 3.15a: an unimplemented command answers `21,UNKNOWN COMMAND` with a zero-length reply, the status check rejects it, the interface is left idle, and the next real command works — which is the path a machine without runtime palette control takes. `read_palette_rgb` catches `Exception` around the whole transaction, so that contract does not depend on which backend it was handed.

Two commands are wired up, both on target `4`: `read_palette_rgb` (`CTRL_CMD_GET_PALETTE`, `0x51`) and `set_palette_rgb` (`CTRL_CMD_SET_PALETTE`, `0x52`). Ultimate 64 firmware 3.15a added runtime palette control to the Command Interface (4d4f6a72, between the 3.15 and 3.15a tags, under the firmware's `#ifdef U64`); older firmware answers `21,UNKNOWN COMMAND`, which both paths handle quietly. What the read is for, and why it is named the way it is, is [palette resolution](video-color.md#palettepy--which-16-colors-the-machine-emits-hardwarehost_palette); what the write is for is [`[color].hardware_palette`](video-color.md#hardware_palettepy--pushing-a-scenes-own-16-colors-colorhardware_palette).

**A command with a payload** pushes it through the same `$DF1D` FIFO, one single-byte write per byte after the target and command bytes. The firmware checks the length exactly (50 bytes in all for `SET_PALETTE`) and answers anything else with `81,INVALID PARAMS`. `SET_PALETTE` has no data reply, so the transaction acks once the status has drained. A push is about 50 DMA writes plus the REST reads of the drain: 0.45–0.75 s measured on a U64-II.

## `menu_screen.py` — the Ultimate menu's own screen

Firmware 3.15 added `GET /v1/machine:menu_screen`, which returns what the Ultimate menu is drawing, and only while it is open: closed, it answers a 404 carrying `{"errors": ["Menu screen unavailable."]}`. That is why the [route probe](#apipy--ultimate64api--socket_dmapy--socketdmaclient) counts a 404 with a JSON error as *present* — on 3.15 the probe usually sees exactly that, and on firmware without the route (3.14, C64 Ultimate 1.1.0) it sees a 404 with an empty body and `supports_menu_screen` stays `False`.

The payload is 2000 bytes: 1000 character bytes for a 40×25 screen in reading order, then 1000 color bytes, `fg | (bg << 4)`. The characters are **not C64 screen codes**: the menu draws in its own font, the firmware stores the menu's byte with bit 7 set for reverse video (`Screen_MemMappedCharMatrix::output_raw`), and the printable range is ASCII. Codes below `0x20` are the font's line-drawing glyphs, named in the firmware's `screen.h`; the decoder maps them to box-drawing characters and anything else to `?`. A capture from a U64-II on 3.15a is the test fixture, checked against the HDMI frame taken at the same moment. A UI of any other size, such as the 60-column Telnet screen, is not served by the route at all; every HDMI overlay layout 3.15a configures (`u64_config.cc`) is 40×25, so an overlay menu is served.

What c64cast uses it for is the one bit "the menu is open", because that is a silent way for a run to show nothing. It depends on **User Interface Settings → Interface Type**, measured on the U64-II:

| Interface Type | The C64 | The picture | A REST reset |
|---|---|---|---|
| Freeze (the default) | stops — the jiffy clock does not advance | the menu replaces it | closes the menu |
| Overlay on HDMI | keeps running; DMA writes show | the menu covers the right-hand part | leaves the menu open |

Either way the menu takes the keyboard, and since 3.15 REST memory access no longer closes it. `--doctor` warns when it finds the menu open and logs the decoded screen at DEBUG for a bug report; it never presses the menu button, because doctor does not change machine state. A run checks once, after the bring-up reset and clear loop, so only a menu that survived the reset (an overlay) is reported. The check is one `GET`, gated on the probe, and absent from older firmware with the probe's INFO line saying so.

## `machine_input.py` — keyboard and joystick injection

Firmware 3.15 added `POST /v1/machine:input` on the Ultimate 64: up to 64 events per request, each `keyboard`, `joystick` (port 1 or 2) or `release_all`, with a `transition` of `press`, `release` or `tap` and the keys or directions in an `inputs` list — at most 8 keys or the 7 joystick inputs `up down left right fire fire2 fire3`. The body must be `application/json` and under 4096 bytes, and the firmware validates the whole batch before applying any of it. Key names are matrix positions, not characters (`"` is `left_shift` plus `2`), and `restore` is the NMI line, so the firmware accepts it only in a `tap`. [machine_input.py](../../c64cast/hw/machine_input.py) holds that vocabulary and those limits, and `encode_batches` validates every event and packs them into bodies the firmware accepts, so a bad event is a `ValueError` naming it rather than a 400 that drops the batch, and a long sequence goes out as several requests. `text_to_events` types text in the power-on uppercase mode, one tap per character; the firmware paces taps itself (a 60 ms hold and a 40 ms gap), so a whole line goes in one request.

`Ultimate64API.send_input` posts those bodies and returns the state the machine reports. A refusal or a transport failure returns `None` with a throttled WARNING, and never raises into a scene; a 200 whose body is not a JSON object returns `{}`, because the input was applied and only the state is unreadable; a 404 or 501 also revokes `supports_rest_input` for the connection. Each body is all-or-nothing, but a later body failing leaves the earlier ones applied. The capability comes from the [route probe](#apipy--ultimate64api--socket_dmapy--socketdmaclient) on `GET /v1/machine:input`: 200 on an Ultimate 64 on 3.15, 501 on an Ultimate II+ (the firmware registers the route to say it cannot), and a 404 with an empty body on 3.14 and C64 Ultimate 1.1.0.

`GET` (`input_state`) reports what the API and the Ultimate menu are holding, **not** the physical keyboard or joysticks, so it cannot replace the `$028D` and CIA polls in `control/keyboard.py` or the launcher's idle detection; it confirms only what c64cast injected. A machine reset releases everything the API holds. `SocketDMAClient.keyb()` — a DMA write into the KERNAL keyboard buffer — has no caller and is not a fallback: it can neither hold a key nor reach a joystick, so on firmware without the route the feature is simply not offered.

The consumer is `LauncherScene.inject_joystick`, which the `[midi_control]` `joystick` action calls on a note or pad press and release. It only queues the event; the scene's own sender thread posts it, so the MIDI reader never waits on REST. A request changes each input at most once: the firmware applies a body's events back to back, so a press and its release in one body would cancel before any CIA read, and a tap shorter than a round trip would vanish. The event that would repeat an input waits for the next request. A release is also held back until its press has been down for 60 ms from the reply (about three frames, and the firmware's keyboard tap hold; its own joystick tap is one 20 ms tick), because the next request follows one round trip later, which on a LAN can be shorter than a frame, and a program that reads the port once a frame would miss the tap. That hold caps one input at about fifteen taps a second, so an event that has waited 0.25 s for the sender — a jittering cc knob or a note-repeat pad outrunning it — makes the sender take everything queued and keep at most three events per input, in the order they were queued: its first release when it was held, then its latest press, and the release after it when it ends released. A tap in the backlog therefore still reaches the port, with the minimum hold, and only the changes in between are dropped — any other choice would stretch an input across the ones pressed while it was up, so tapping fire, then up, then fire would hold fire and up together; otherwise the queue would grow for the rest of the scene and every other input would wait behind it. The sender keeps its own view of what its posts left held; when a post fails on a machine that still has the API, the next one is `release_all` plus a press of everything held, so a dropped release cannot leave a direction stuck (retried every 0.25 s while that fails too). Once a 404 or 501 revokes `supports_rest_input`, the sender stops and further injections are dropped with the no-API warning. An injection counts as player input for the idle timeout, and teardown sends `release_all` before the reset. Teardown first waits up to 4.5 s for a post already in flight: one request can spend 2 s connecting and 2 s reading, and if teardown stopped waiting sooner, a slow press could reach the machine after the release and the reset and stay held into the next scene. For the same reason, the sender does not post a batch it dequeued after it was told to stop. A sender still posting when that wait runs out is waited for again at the start of the next pass, before setup forgets the queue and the sender's view of the machine: otherwise its late writes would land after that reset, and the new sender could not start while it lived, so the whole pass would drop its input. Measured on a U64-II on 3.15a with `scripts/diags/rest_input_probe.py`: typed `PRINT "HELLO"` ran at the READY prompt (HDMI capture and screen RAM agree), and holding fire on port 2 read `$DC00 = $6F`, back to `$7F` on release.
