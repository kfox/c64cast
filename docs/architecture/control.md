## `keyboard.py` — Commodore-key pause/resume, CTRL-key skip, SHIFT-key style cycle

`CommodoreKeyPoller` runs a background thread that polls `$028D` (the kernal's keyboard-modifier scratch byte) at 10 Hz via `api.read_memory`. Bit 0 = SHIFT, bit 1 = Commodore key, bit 2 = CTRL.

* **C= edge while running:** sets `Playlist.pause_event`. The run loop tears down the current scene + overlays, calls `api.pause_idle()`, then waits. `pause_idle()` leaves the machine in a paused state whose **kernal keyboard scan stays alive** so `$028D` keeps updating for the resume-hold detection. Backend-specific: the Ultimate's default is a plain `reset()` — no BASIC clear-loop, so the user sees the default C64 boot screen (BASIC banner + blinking READY cursor) as the paused indicator, and the editor's IRQ keeps `$028D` live. The **TeensyROM overrides** it to **clear the screen but keep the display ON (NOT reset, NOT blank)**: (1) a bare TR reset lands at the TeensyROM menu, whose own input handling doesn't run the kernal keyboard scan, so `$028D` would freeze and resume would strand; (2) turning the VIC display OFF (DEN=0) removes badlines, and the TR's cycle-clean DMA gates its `/DMA` assert on a safe VIC cycle (a badline) — no badlines means every read/write hangs, stranding resume *and* wedging the TR until a power-cycle (both HW-confirmed). Neither a reset nor a blank is needed: the IRQ-enabled clear-loop set up at bring-up is still running underneath every scene (that's what keeps `$028D` live so the keys work *during* a scene; the DMA only overwrites screen/VIC RAM, never the BASIC program), so clearing screen RAM to spaces with DEN left on gives a clean paused screen while badlines keep the resume-hold reads working — the closest possible idle to the working live-scene state. (`Playlist._handle_pause` clears `resume_event` *before* calling `pause_idle()`, not after, so a resume detected mid-call isn't wiped.)
* **C= held continuously for 3 s while paused:** sets `Playlist.resume_event`. The run loop calls `api.reset()` + `run_basic_clear_loop()` to clear the boot screen, then `_advance()` re-sets-up the same scene (we don't bump `self.index`). The "same scene" includes the same overlays — they each get a fresh `setup()` so audio + poll threads come back online cleanly.
* **CTRL edge while running:** sets `Playlist.skip_event`. The run loop forces `current.is_done = True` after the current frame, so the scene tears down cleanly and the playlist advances to the next interstitial. CTRL while paused is a no-op.
* **SHIFT edge while running:** sets `Playlist.cycle_event`. See "SHIFT style cycling" below.
* **SPACE while running (only when `[menu].enabled` + a read-capable backend):** opens/closes the on-C64 menu. SPACE isn't a `$028D` modifier, so the poller instead reads the kernal keyboard buffer — NDX `$00C6` + KEYD `$0277`, the same buffer the U64's CMD_KEYB opcode injects into — and toggles `Playlist.menu_event` (debounced by `_SPACE_COOLDOWN_S` so a held/repeating SPACE is one toggle). While `menu_active` is set the entire pause/skip/cycle branch is suppressed and the decoded cursor + RETURN codes drive menu navigation instead. `menu_eligible` gates the extra buffer read so it only happens when the menu is open or the current scene can host it. The menu driver is [`playlist_support.PlaylistMenu`](config.md#playlist_supportpy--playlist-collaborators) (its `service()` injects/removes the `MenuOverlay` from `scenes/overlays/menu.py`).
* **Chord rules:** C= + CTRL same tick → pause wins, skip suppressed. SHIFT held with C= or CTRL → SHIFT dropped (a thumb resting on shift while reaching for pause/skip shouldn't phantom-cycle the style).

The poller distinguishes "definitely not pressed" from "couldn't tell" — a failed HTTP read returns `None` and is ignored rather than phantom-resetting the held-time counter. The kernal IRQ must be intact for $028D to stay current.

### SHIFT style cycling

On a `cycle_event` the run loop calls three things:

1. `scene.cycle_style(api)` on the current scene — for scenes without a display_mode that still want SHIFT behavior, e.g. `WaveformScene` cycling to the next SID subtune.
2. `display_mode.cycle_style(api)` on the display mode.
3. `overlay.cycle_style(api, scene)` on every attached overlay.

Each surface rotates through its own list of named styles, invalidates whatever caches it owns so the next push fully repaints, and returns a label. The labels are combined into one log line: `cycle: <scene> → scene=<s>, display=<x>, <overlay>=<y>`.

**Opt-in by design.** `Scene` does not define `cycle_style` at all — the playlist checks via `getattr` plus `callable` — and the default `DisplayMode.cycle_style()` / `Overlay.cycle_style()` return None. Only surfaces that opt in actually rotate. `BigTextOverlay` opts in, rotating the message FG color through `(config, rainbow, *spectrum)`.

**`WaveformScene.cycle_style()`** advances `self.song` modulo `header.num_songs`, returning None for single-song SIDs. It tears down and re-runs `api.run_sid_player(...)` on the new song, rebuilds `SidHostEmu` so the visualizer tracks the right subtune, and resets `start_time` so the new song gets its full `duration_s` — re-resolved from the SongLengths DB when present, with an explicit user `duration_s` winning.

*Short-subtune skipping.* When the DB is loaded, candidates whose looked-up length is below `WaveformScene.MIN_CYCLE_SUBTUNE_S` (5 s) are skipped: most game SIDs put 1-3 s SFX in their tail subtunes, and the scope view of those is flat for most of the displayed time. The skip is bounded at `n-1` attempts, so an all-SFX SID still advances by one slot.

Startup is exempt — a user-configured `song`, or the PSID `start_song`, plays no matter how short. Pinning an SFX as the start song is itself a strong "play this" signal, the same reasoning behind an explicit `duration_s` also disabling skip.

**Scope and persistence.** Cycling is suppressed during interstitial transitions. Cycled style lives on the display_mode, overlay, and scene instance, so it persists across single-scene loop iterations and across pause/resume — but resets on a real scene boundary, since a multi-scene transition constructs fresh instances from config.

## `camera.py` — camera enumeration + name/VID:PID device selection (optional `camera` extra)

Lets `[video].device` (and `-d/--device`) be a **string** matched to a camera by name substring or USB `VID:PID`, not just a fragile cv2 index — the video-input analog of the TeensyROM+ serial USB VID/PID auto-detect (`teensyrom_dma.autodetect_serial_port`), and it deliberately mirrors that module's shape: a lazy import behind a best-effort enumerator, a pure duck-typed matcher (VID/PID primary, name substring fallback), a resolver that **warns** rather than silently guessing on ambiguity.

- `enumerate_cameras()` lazy-imports the optional `cv2-enumerate-cameras` package (the `camera` extra) and wraps its results into `CameraInfo` (`index`, `name`, `vid`, `pid`, `backend`), reading fields via `getattr` so tests can inject fakes without the extra. Returns `[]` (never raises) when the extra is absent or enumeration fails — same contract as `teensyrom_dma._list_comports`. Enumerates against the platform's native backend (`_platform_api_preference`: AVFoundation on macOS, Media Foundation on Windows, `CAP_ANY` on Linux).
- `parse_camera_device(value, *, field_name)` is the **offline** syntax validator (models `config.parse_wled_endpoint`): an int, an int-in-a-string, a name substring, and a valid `VID:PID` all pass; a spaceless colon-bearing token that *isn't* two hex halves (`0fzz:0066`) raises `ConfigError` with `field_name` threaded in. Called from `config._validate_video_device` in the load/`--doctor` validate pass — it never touches hardware, so `--doctor --skip-probe` stays offline. (The one config↔camera import edge is broken by importing `ConfigError` lazily inside the function.)
- `resolve_camera_index(device) -> (cv2_index, backend_or_None)` is the **runtime** resolver called from `WebcamSource.__init__`. An int (incl. `-1`→0) returns `(index, None)` = the unchanged `CAP_ANY` open. A string enumerates, matches VID:PID then name substring, and returns the matched camera's index **plus the backend it was enumerated with** (the caller must open with it). Missing extra or no match raises `RuntimeError` with an actionable message (extra-install hint / the enumerated candidate list); multiple matches warn and take the first.

`--list-devices` (`cli.list_devices`) prefers `enumerate_cameras()` for the video listing (name + VID:PID + correct index, cross-platform, merged with a best-effort resolution probe), and falls back to a cv2 open-probe + macOS `system_profiler` dump when the extra is absent.

## `vision.py` — webcam gesture control (optional, camera-as-input)

`VisionController` is a **second control surface** alongside the keyboard poller: a background thread reads frames from the shared `WebcamSource` broker, runs MediaPipe HandLandmarker, and sets the *same* `pause`/`resume`/`skip`/`cycle` events. The Playlist starts/stops it interchangeably with the key poller (`for controller in (key_poller, vision_controller)`), so the run loop can't tell which surface a press came from — exactly like the control plane. Reading the camera (not C64 memory) means it works on **any** backend — including a TeensyROM running firmware too old for the `$028D` keyboard poller (a cycle-clean TR+, fw v0.7.2.5+, reads memory via ReadC64Mem and gets the physical keyboard too, so vision is not the *only* TR control surface). Enabled by `[vision].enabled`; needs the `vision` extra (`mediapipe`) + a downloaded HandLandmarker `.task` model (`assets/models/README.md`). A missing dep/model logs "vision control disabled" and the stream runs without gesture control — it never crashes the playlist.

Gesture → control mapping mirrors the keyboard semantics: **running** → PINCH=pause, fast horizontal SWIPE=skip, OPEN_HAND=cycle; **paused** → PINCH held `hold_threshold_s`=resume, others no-op (same "pause means only the resume gesture matters" UI contract). Priority pinch > swipe > open-hand (the chord-rule analog), at most one event per tick, with a `gesture_cooldown_s` debounce on top of edge detection since gestures are noisier than key bits. A no-hand/failed frame returns `None` and skips the tick (no phantom state change), the visual analog of `keyboard.py`'s `None`-on-read-failure.

The hand tracker is pluggable behind the `GestureRecognizer` protocol; `MediaPipeHandRecognizer` lazy-imports mediapipe (like `video.py`'s `ensure_pyav`) so the rest of the app and the whole test suite run without the extra. The **static** pose classifiers (`is_pinch`, `count_extended_fingers`, `classify_static`) are pure functions on a `(21,3)` landmark array — directly unit-tested on synthetic fixtures, no camera/mediapipe. SWIPE is temporal (wrist x-velocity), handled in the controller. `latest_hands()` exposes the raw landmark snapshot as continuous state for future consumers (fingerpainting, pose/face scenes). The example config `c64cast/examples/vision-gesture.toml` runs the controller over a blank scene to show gestures work over any scene, not just webcam ones.

**Performance mode (Live DJ/VJ Phase 6).** With `[vision].performance = true`, `session.build_stack` calls `vision_controller.bind_performance(playlist)` after the playlist exists, and the **running-state** gestures are remapped to the clip-launch grid — a hands-free performance surface: SWIPE → `pl.performance.advance_clip()` (launch the next `[[performance.clips]]` slot, cycling in declaration order), PINCH-hold → `pl.toggle_effect_layer(0)`, OPEN_HAND-hold → `pl.toggle_effect_layer(1)`. Both bottom out in the **same thread-safe hand-offs** the MIDI/web surfaces use — an enqueued `ClipEvent` (drained on the playlist thread) and a GIL-atomic `enabled` flip — so nothing mutates a scene on the poll thread. The controller snapshots `self._perf` once per tick (bind is live-settable) and, when unbound, falls back to the transport events; the **paused**-state pinch-hold-to-resume gesture is unchanged in both modes. `advance_clip` lives in `PerformanceSession` (reads `active_slot`/`armed_slot`, enqueues the next slot) so the "which clip is next" logic stays with the grid, not the vision thread.

## `control_plane.py` — HTTP control plane (optional)

When `[control] enabled = true` and the `control` extra is installed (`uv tool install 'c64cast[control]'`), a FastAPI app runs on `127.0.0.1:8765` exposing:

* `POST /pause` → `playlist.pause_event.set()`
* `POST /resume` → `playlist.resume_event.set()`
* `POST /skip` → `playlist.skip_event.set()` (same path as a CTRL press)
* `POST /reload` → re-reads the config from disk and rebuilds the scene list at the next interstitial boundary

The same three events are fed by the keyboard poller, so HTTP and the C64 keyboard are equivalent control surfaces.

**The app is built over a registry, not a fixed map.** `build_app_for_registry(playlists, config_loaders, interstitial_factories)` takes three *providers* — zero-arg callables — and consults them inside each request; `build_app(...)` is the same thing with the three maps closed over as constants, and is what the one-shot CLI uses (it keeps its construction-time `ValueError` on an empty map, because a CLI run with no playlists is a bug, not a state). The indirection exists for the web console's long-lived host, where sessions start and stop under a server that keeps listening: rebuilding the app per session would drop the socket, every connected console and the `/perf` WebSocket on every show change. An empty registry means no session is running and every data/action route answers **`503 no session running`** — the one status a client can tell apart from "the server is gone".

`_resolve` takes **one snapshot of the registry per request** and hands it back alongside the resolved names, so a handler can't pause one generation's playlists and report another's — the maps are swapped wholesale by the session lifecycle while requests are in flight.

## `auth.py` — shared-token gate (optional)

`[control] token` (or `$C64CAST_CONTROL_TOKEN`, which wins) turns the whole control plane — routes, `/perf` console, WebSocket — into a token-gated surface. Empty is the default and leaves it open. That is allowed on loopback, where the port's audience is whoever already has a shell on the machine, and refused off it: `scene_factory.validate_control_cfg` rejects a non-loopback `host` with no token as a config error, so it surfaces from `--doctor` and from `session.validate_configs` before any hardware is opened rather than from a warning line during a running show. `[control].allow_unauthenticated` is the opt-out for a trusted show network — an opt-out rather than a removal of the open mode, which is a real deployment. The warning in `start_control_server` stays for a caller reaching that entry point directly, past the config gate. `viewer_token` adds a second credential that may only issue `GET`/`HEAD`/`OPTIONS`.

**One pure-ASGI middleware, not a per-route dependency**, for two reasons that are not stylistic:

* `BaseHTTPMiddleware` and every `Depends`-based scheme are invisible to `websocket` scopes, and `BaseHTTPMiddleware` buffers response bodies — which would ruin the binary preview stream the web console adds later.
* A WebSocket rejected from inside its handler can only close **after** `accept()`, which a browser reports as an ordinary disconnect. Closing before accept makes uvicorn answer the handshake with an HTTP `403`, the one outcome a client can tell apart from a server restart.

`install_auth` is called from `build_app_for_registry` rather than by its callers, so an app built somewhere new can't ship open by omission, and `tests/test_control_auth.py` walks `app.routes` asserting every path outside `PUBLIC_PATHS` refuses an unauthenticated caller.

**Token sources, in order:** `Authorization: Bearer` → `X-C64Cast-Token` → `?token=` → the `c64cast_token` cookie. The last two exist because a browser can set no headers on a plain navigation or a WebSocket handshake. `GET /api/login?token=…&next=/perf` — the only public path — trades the token for an `HttpOnly; SameSite=Strict` cookie and redirects, after which the console page and its socket authenticate themselves; `POST /api/login` does the same from a JSON body, for a login form that shouldn't put the credential in a URL. `next` is constrained to a single-leading-slash path, since `//host` and `https://host` are both offsite to a browser. No `Secure` flag: the control plane speaks plain HTTP on a LAN, and a Secure cookie would simply never come back.

**The read-only token is minted when somebody asks to share, not at startup.** `viewer_token` had existed since the gate did, and the console had no way to hand one out — so sharing it meant sharing the credential that can stop the show. `ViewerCredential` is the fix, and it is an object rather than a string for one reason: the app is built **once**, around a listening socket and every connected console, so a token settled at construction could only be changed by a restart — which is exactly the moment the feature is wanted. The gate and the login routes both read `.token` per request, and `POST /api/viewer-link` (`web_api.py`) issues it. Not generated alongside the full one at startup: a credential nobody asked for is one more thing that can leak. Once issued it is persisted to `paths.web_viewer_token_path()` at `0600`, for the reason the full one is — a link given to a guest should still open after the next restart.

Two details that are load-bearing rather than incidental. The issue route is a **`POST`** even though it reads like a read, because the gate lets a viewer through every `GET` and a read-only guest must not be able to fetch the link that made them one. And the link it hands out is the **`GET /api/login?token=…`** redirect form, not the `POST` one — a viewer token presented to `POST /api/login` is a write to the gate and answers `403`, however valid the token is. The route returns an origin-relative *path* and the browser prefixes `location.origin`: a host bound to `0.0.0.0` has no idea which of its addresses the phone in your hand reached it on, and the browser asking has exactly that.

**The one hole the middleware cannot plug** is `/perf/ws`. A socket is a single `GET` handshake, so method-based role enforcement can't see the command frames that arrive afterwards — `perf_ws` reads `scope["c64cast_role"]` itself and drops inbound frames from a viewer. The state payload carries `role` for the same reason: the page greys nothing out, but shows a `read-only` chip instead of letting every pad tap fail silently against a 403.

## `setup_gate.py` + `setup_api.py` — the appliance first-run setup window

`[web].setup_wizard` exists for one caller: a pre-provisioned OS image, booted with no connection target and a token nobody has seen. [SECURITY.md](../../SECURITY.md) documents the web console as the one surface with no unauthenticated mode — "it has no 'off'" — and this is the deliberate, narrow exception, off by default and meant only for that appliance image, never for a console someone configures themselves.

**A middleware *outside* the token gate, not a hole punched in it.** `auth.install_auth` already wraps the app by the time `serve.build_daemon_app` regains control. `Starlette.add_middleware` inserts at index 0 of `user_middleware`, and the stack wraps the router in *reverse* of that list — so the most recently added middleware is the **outermost**, and installing `SetupGateMiddleware` afterward puts it in front of the token check rather than trying to carve an exemption out of `TokenAuthMiddleware`'s own exact-match `public_paths`.

**No hardcoded route list.** `install_setup_gate` is called last — after `mount_web_app`, so `web_static.owned_segments` already knows every top-level path segment the app answers. The gate blocks any *reserved* segment except `assets` (the shell needs its own bundle to load) and the one exact carve-out, `SETUP_PATH` (`/api/setup`); an unclaimed path falls through to the shell's own catch-all, same as it always would. A route added anywhere else in the app is covered without this module changing.

**The setup surface still needs a second exemption**, because `SetupGateMiddleware` forwards an allowed request *into* the app it wraps — which includes `TokenAuthMiddleware`, one layer in. `auth.install_auth` gained a `public_paths` parameter for exactly this (it always existed on `TokenAuthMiddleware` itself; nothing threaded it through before this), and `control_plane.build_app_for_registry` takes the same parameter and unions it with `auth.PUBLIC_PATHS`. `serve.build_daemon_app` passes it `SETUP_PATH`, `SETUP_PAGE_PATH` and `web_static.shell_paths()` only while pending, so the exemption disappears the moment the app is rebuilt without it. `shell_paths()` is read off the same catalog `mount_web_app` serves from rather than written out here — a hand-kept list of the bundle's file names goes stale silently, and the symptom is a form that loads with no stylesheet.

**The form is a screen of the ordinary console bundle** (`web/src/lib/screens/Setup.svelte`), not a page the server renders. That is what the `assets` carve-out in the gate is *for*: the shell and its two files load, `web/src/main.ts` asks `GET /api/setup` once before it mounts anything, and it mounts the form instead of the console when the host answers "pending" — putting `SETUP_PAGE_PATH` in the address bar so a reload comes back to it. The alternative, an inline HTML page in the style of `auth.py`'s `_LOGIN_PAGE`, was rejected for one reason: the login page has to work when the bundle is *behind* the gate it is guarding, and this one does not — the gate lets the shell through on purpose.

**No credential crosses the wire until setup completes.** `GET /api/setup` answers `{"pending": true, "token_settable": …}` and never the token itself, because anyone on the LAN can call it while the window is open; the form shows a disabled, bulleted field when `token_settable` is false. The real token rides back exactly once, in the `login_url` of a successful `POST`, which the page navigates to after polling the port until the rebuilt app answers — by then the caller is the one who configured the box, and it is also the only way an appliance admin with no terminal on it can ever learn the token.

**`token_settable` is the fix for a lockout, not a nicety.** `_write_token` writes `paths.web_token_path()`, which `resolve_tokens` consults *last* — after `$C64CAST_WEB_TOKEN`, `[web].token` and `[web].token_file`. A host whose token is named by any of those would answer "ok" to a replacement and then come back on the old one, locking out the admin holding the new one, so `run_daemon` computes whether the token was generated and `setup_api` refuses a replacement outright when it was not.

**Nothing here supports a mid-run toggle.** `setup_api.register_setup_routes` and `setup_gate.install_setup_gate` are each called once, at app-build time, and are simply omitted from the rebuild once `paths.setup_state_path()` exists — see `run_daemon`'s restart loop, below — rather than switching off in place. That is also the reason a token *chosen* during setup needs a restart at all: `TokenAuthMiddleware` takes a plain string, not a live credential like `ViewerCredential`, so there is no cheaper way for a new one to reach it.

`setup_api.register_setup_routes` asks for exactly two things — a connection target and a token choice — and reuses existing machinery for both rather than growing a second config editor or a second serializer: `connect.parse_connection_uri` (the same parser `-u`, `--save-settings` and quickcast use) and the same machine-settings write shape `cli_commands.run_save_settings` uses (seed from `apply_machine_settings`, overlay, `config_serialize.dumps` with no `baseline` — the machine layer *is* the baseline). The completion marker (`paths.setup_state_path()`, a sibling of `run_marker_path()`) is written **last**, after the connection and any chosen token are already on disk, so a failure partway through leaves setup pending rather than half-configured.

Reset is deliberately CLI-only: `c64cast --reset-setup` removes the marker. There is no HTTP route for it — an admin who can run that command already has shell access to the box, and an HTTP route doing the same thing would reopen the unauthenticated window to anyone who could reach the port, undoing the containment `install_setup_gate` exists to provide.

## `console_mdns.py` — mDNS advertisement of the web console

Mirrors [`wled_device.py`'s `_register_mdns`/`_local_ip`](wled.md#wled_devicepy--virtual-wled-device--control-surface-wled-bridge-mode-1) shape rather than importing it: lazy `zeroconf` import, the same UDP-connect trick for the LAN-facing IP, and a `try`/`except` around registration that logs and gives up instead of raising — a discovery failure must never take an already-serving console down with it. The two modules don't share the helper because they answer different questions under different feature areas; a third independent copy of the same `_local_ip` trick already exists in `scenes/overlays/network.py`, which is the established shape for this one small helper in this codebase rather than a gap to centralize.

`ConsoleMdnsAdvertiser` registers one `_c64cast._tcp.local.` `ServiceInfo` per `run_daemon` loop iteration — a fresh instance, not a mutated one, so a setup completion that flips `pending` re-advertises with a TXT record (`md`, `ver`, `setup`) a discovery client can read as "configured" rather than the middleware having to reach back into an already-registered service. `serve.run_daemon` starts and stops it in the same places it starts and stops `ControlServer`.

**The advertised names are built from the *short* hostname, and a clash is zeroconf's to settle.** `socket.gethostname()` answers with an FQDN on plenty of machines (`c64cast.local` on macOS, `box.lan` under some DHCP servers), and reusing one whole would advertise `box.lan.local.` as the server name — a name nothing on the LAN resolves — so `_short_hostname()` keeps only the first label. Registration passes `allow_name_change=True` because the appliance case *is* the clash: two boxes flashed from one image share a hostname, and without it the second one's `register_service` raises `NonUniqueNameException` and it advertises nothing at all — in exactly the multiple-box situation this module exists for. Zeroconf renames it (`c64cast-2`) instead, and the log line reports the name that actually went out.

**A failed registration closes the `Zeroconf` instance it opened.** The `except` here can't just drop the reference the way the WLED sibling's can: there, `self._zc` is assigned inside the method the `try` wraps, so `stop()` can still reach a half-registered instance; here the assignment happens only on success, so anything not closed on the way out keeps its multicast socket and engine threads for the life of the process — once per `run_daemon` restart, at that. `stop()` closes on the same terms: a goodbye packet that fails is logged and stepped over rather than costing the close.

**Advertised only when `[web].host` is not one of `config.LOOPBACK_HOSTS`, and only when there is a LAN address to name.** `_local_ip()` reports the real LAN-facing address regardless of what the server actually bound to — right for the appliance's `0.0.0.0`, but a console left at `WebCfg`'s own default (`127.0.0.1`) would otherwise advertise a port nothing off the machine can reach, which reads as *worse* than not being discoverable: a LAN peer that finds the entry gets a connection refused, not a console. This is why an ordinary `--serve` on a laptop needs no separate opt-out to stay exactly as quiet on the network as it always was — the existing `host` default already decides it. `_local_ip()`'s own loopback fallback is the second way to reach that same unreachable A record — a box whose network isn't up yet — and is refused on the same grounds, before any `Zeroconf` instance is opened.

**`_advertised_ip` is the one helper here with no sibling in `wled_device.py`**, because a WLED device is always bound wide and `[web].host` need not be. `_local_ip()` is a *guess* — the interface the OS would route LAN traffic over — which is the right answer for `0.0.0.0` (listening on every interface anyway) and the wrong one for a host that names a single interface: on a multi-homed box the default route need not be the one the console bound, so the guess can advertise an address nothing is listening on. A concrete IPv4 `host` is therefore advertised as itself, and the guess is kept for the binds it cannot be wrong about (`0.0.0.0`) and the ones it cannot improve on (a hostname, or an IPv6 literal this A record can't carry anyway).

The appliance image's fixed hostname (`c64cast.local`, set by the OS image's Armbian + Avahi config, not by this module) answers "where is *the* appliance"; this module answers "what is serving here, and has it been set up" — the piece still needed once there is more than one box on the LAN, or none of them has a hostname a human chose.

## `app/serve.py` — the session supervisor

The web console's first non-HTTP piece, and the one the rest of it is built on. `SessionManager` owns at most one [`Session`](config.md#sessionpy--the-session-lifecycle) at a time and serializes every transition behind one lock: `idle → starting → running → stopping → idle`, with `error` as where a failed build parks its diagnostic. `error` is deliberately not sticky — `start()` from it is legal, because a machine that was unreachable a minute ago usually isn't now.

**Everything slow runs off the caller's thread.** `build_session` blocks for many seconds (open the backend, reset, settle, install the char ROM, probe the REU and the sampler) and teardown is not much cheaper, so `start()` and `stop()` return as soon as the transition is claimed and the caller watches the state feed. What deliberately does *not* run off-thread is validation: `validate_configs` is pure and hardware-free, so a bad config is refused synchronously — which is the whole reason that split exists.

**`start()` never implicitly stops.** Replacing a running show is `switch()`, so the one path that has to get stop → settle → start right is the one path that does it; `start()` while running raises `SupervisorBusy` (an HTTP `409`). `wait_for(state, generation=…)` takes a generation because "wait until running" is ambiguous across a switch — the show being replaced is running too.

**The build seam is a `publish` callback, not just a return value.** A build that fails *after* the stacks are up has already taken the hardware; handing the session over the moment it exists keeps "no hardware is left held" on the single path out of a generation, rather than splitting it between the supervisor and every build function. That is why a failed build routes through `stopping` on its way to `error` instead of jumping there.

| Mechanism | Exists because |
|---|---|
| `hardware_free_at` cooldown | The U64's DMA service refuses new connections for a few seconds after one closes ([caveats](../caveats.md)), and AVFoundation refuses to reopen a camera straight after `WebcamSource.release()`. Two facts, one timer, checked on the way *in* to a build so the UI can say "waiting for hardware" — and re-armed after a marker recovery, which opens and closes a backend of its own. |
| The `session-reap` poller | A non-looping show ends by itself. The CLI notices because it is parked in a join; a daemon has nothing watching, so a poller drives `running → stopping`. An *empty* thread list is not "finished" — it is a session whose playlists never started. |
| The run marker (`<data root>/run.json`) | A segfault in OpenCV or PyAV kills the process with the machine mid-show — the same exposure the one-shot CLI has. A marker found at the next start means the last run died, so `default_safe_state` opens a bare backend, resets, and closes before anything else touches the hardware. Deliberately *not* `_open_backend`: its probe, char-ROM install and provisioning could each fail and abandon the reset, which is the one thing that has to happen. |
| `SessionLogBuffer` | A hardware failure's diagnostic goes to the log and nowhere else. In the CLI that is fine — the user is looking at the terminal. A daemon's user is looking at a browser, so records are kept in a bounded deque tagged by generation, or the only answer the UI can give is "it didn't start". |

Supervisor threads are `daemon=False`, unlike every other background thread in the project, for the same reason the playlist threads are: these are the threads that tear the hardware *down*, and a daemon thread is killed at interpreter exit — mid-teardown, with the machine still held. The reap poller is a plain `PollThread` (it only observes). `_Workers.join` shares `session.join_bounded` with `join_playlists` (see [`session.py`'s `daemon=False` note](config.md#sessionpy--the-session-lifecycle)) rather than a single uninterruptible `t.join(timeout)` — `join_bounded` itself now logs a straggler by name on timeout, so neither caller has to.

Two things a supervised session must never inherit from the CLI: signal handlers, since `signal.signal` raises off the main thread, and `Session.interactive`, which stays False so the live-tune `input()` prompt can't hang the stop path forever.

**With `[web].setup_wizard` on, `run_daemon` is a `while True` around one build-and-pump cycle, not a single pass.** `pump_forever` takes an optional second event, `restart`, and returns when either it or `shutdown` fires; `run_daemon` tells the two apart on the way out — `shutdown` returns from the function, `restart` (set by `setup_api`'s completion handler, once every write has landed) loops back around, re-resolves the token, and rebuilds the app without the setup gate. `manager`, `store`, `media` and the signal handlers are all built once, outside the loop — only the app and its `ControlServer` are per-iteration, since nothing else needs to change across a restart the setup form triggers.

**`run_daemon` installs its own signal handlers — the daemon's `--serve` process is a foreground process too.** `_on_stop_signal` is `session.make_stop_signal_handler(shutdown.set, verb="shutting down the host")` — the same three-strike factory `cli._run_session` calls (see [`cli.py`'s SIGINT/SIGTERM note](config.md#clipy)): the first SIGINT/SIGTERM sets `shutdown` so `pump_forever` exits and `manager.close()` runs; the second restores `signal.SIG_DFL` for whichever signal just arrived, so a repeated SIGTERM from a service manager doesn't stay caught forever; the third then actually kills. `manager.close()` can spend up to 30s in `wait_for` and 30s more in `_workers.join` — a real teardown (final reset, DMA drain) is allowed to take that long — so `close()` logs how long it's waiting on, rather than leaving an operator watching a Ctrl+C with nothing printed. None of this makes the process itself unkillable: that guarantee is `cli.ensure_exit`, the force-exit backstop both `run_daemon` and `_run_session` return through (documented at [`cli.py`](config.md#clipy)).

## `web_api.py` — the web console's API + the host (`--serve`)

`--serve` (or `[web] enabled = true`, the same switch) replaces the process model rather than adding a surface to it: instead of running one config and exiting, c64cast becomes a server that owns the hardware and starts and stops shows on request. `serve.run_daemon` is that process — resolve the credentials, build one app, start uvicorn, and park the main thread in `pump_forever` — and `web_api.register_web_routes` is what the browser talks to.

**One app, built once.** The control-plane routes and the `/api/*` routes ride the same FastAPI app on the same port, because a host console with two addresses isn't one console. The app is built before any session exists and never rebuilt: [`build_app_for_registry`](#control_planepy--http-control-plane-optional)'s providers resolve `manager.session` per request, so a show change doesn't drop the listening socket and every connected browser with it.

The status code is the design:

| Route | Answers | Why |
|---|---|---|
| `POST /api/session/{start,switch}` | `202` | Building blocks for many seconds on hardware; the supervisor claims the transition and returns, and the caller watches `/api/ws`. A route that waited would hold a request open across a machine reset. |
| …the same, while busy | `409` | Mapped from `SupervisorBusy`, never from a state check in the route: reading the state and *then* acting on it races the reap poller, and the supervisor's own lock is the only place that decision can be made. |
| …with a config that won't run | `422` | The payoff for `validate_configs` being pure: the start that would have failed twenty seconds into a build fails immediately, with the supervisor still idle. `switch` gets this too, so a typo can't take down a running show. The detail is `SessionConfigError.detail` — the same diagnostic `validate_configs` already logged — so the browser names the actual scene or setting rather than an exit code; the old "see the log" text is only what's left when `detail` is empty (a `ConfigError` from the loader itself, which carries its own message). |
| `POST /api/session/stop` | `202`, always | A console that stops twice, or stops a show that just ended by itself, has got what it asked for. |
| `POST /api/session/live-tune` | `200` / `409` / `422` | Keeps (or drops) the knob changes made since the show started. Synchronous because it is a *config write*, not a transition — see ["Save-back under `--serve`"](#save-back-under---serve): `409` when nothing running or nothing a config field carries, `422` (with the store's report) when the result wouldn't load, file untouched and the changes still held. |

`GET /api/introspect` serves `introspect.as_dict()` — the same model behind `--describe`, the JSON Schema and `--init`, as JSON. The console reads *this* rather than the committed schema file because the schema deliberately drops `apply` ("does this take effect live?") and `applies_to` ("is this field meaningful for this scene type?"), which are exactly what a form needs to render. It is built once per process: it describes the code, not the run.

`WS /api/ws` is the `/perf` payload with a `session` key added, so a console that already renders the performance surface gains the supervisor for free. Log lines ride along **by sequence number** rather than as a re-sent tail — at ~3 pushes/sec, re-sending 500 lines each time would dwarf everything else on the socket. Inbound frames carrying `{"session": …}` drive the supervisor and everything else falls through to the performance engine, so a console needs one connection rather than two; like `perf_ws`, this route drops inbound frames from a `viewer` itself, which is the one hole the auth middleware cannot plug.

**The console is never unauthenticated.** `[control]` may run open because that is what it has always done and breaking those runs isn't a trade a security feature gets to make for the user; this surface has no history to preserve and it starts hardware, so `resolve_tokens` falls back to minting one (`secrets.token_urlsafe(32)`, persisted `0600` beside the DAC calibrations) and prints a ready-to-open login URL rather than binding open. Precedence is `$C64CAST_WEB_TOKEN` → `[web].token` → `token_file` → generated.

**The main thread is the preview thread.** HighGUI may only create and service a window there, and under `--serve` it is parked in `pump_forever` rather than in a join, so windows are opened when a generation appears and closed when it goes. Repeatedly opening and closing them across sessions in one process is the least-exercised corner of this design, which is why every call into a window is contained: `[preview]` under a host is "works from a terminal", not a supported deployment. The browser preview ([`u64_stream.py`](hardware-io.md), still to come) is the daemon's real answer.

Shutdown order is load-bearing: the session comes down *before* the server, so a console watching the state feed sees the machine stop rather than the socket vanish mid-teardown.

## `config_store.py` — the config browser and its root jail

`GET /api/configs`, `GET`/`PUT`/`PATCH /api/configs/{ref}` and `POST /api/configs/{ref}/validate` are what let a show be authored and then started without a shell. This is the first thing in c64cast that hands part of the host's filesystem to the network, so the boundary is a module of its own rather than a few checks inside a route: the jail is testable without HTTP, and a second caller can't reach the filesystem by a different path than the first. `web_api.py` maps its refusals onto status codes (`403` outside a root, `404` missing, `413` oversized, `422` won't validate) and does not re-implement any of them.

**Refs, not paths.** A file is addressed as `<root-label>/<relative>`, where the label is the root directory's own basename (`shows`, `shows-2` if two roots collide). Bare relative paths were the obvious alternative and were rejected: with more than one root they are ambiguous, and "first root that has it" is exactly the rule that quietly resolves to a different file than the operator meant. The same ref is what `POST /api/session/start` takes as its optional `{"config": …}` — one crossing between what a browser names and what the loader opens, and the store is what makes it safe.

**The check that holds is `resolve()` + `is_relative_to`.** Roots are resolved once at construction, so a symlink *inside* a root pointing out of it fails like any other escape; rejecting `..` up front only buys a better error message. Listing walks `followlinks=False`, which drops symlinked directories and the loop protection comes free. Note that an HTTP client collapses a literal `..` in a URL before it is ever sent, so the traversal case that actually reaches the route is the percent-encoded one — which is what the test uses.

**A write validates first**, through `config.load_master` + `validate_configs` on a scratch file **in the target's own directory** — an ensemble master resolves its per-system paths relative to itself, so validating one anywhere else reports missing files that are not missing. Refusing to save a config that cannot run is the point of having the editor talk to the loader at all; `POST …/validate` is what lets a UI see the error first. `validate_configs` writes its diagnostic to the log and raises an exit code, so the store collects what it logged rather than restructuring eight validators to return messages.

**`POST …/validate` with no `text` key checks the file as it stands on disk**, rather than silently validating the empty string — the bug it used to be. `validate_ref(ref)` is `validate_text` on that file plus one thing `validate_text` alone can't give a caller: `doctor.validate_load_result(loaded, probe_u64=False)` (the same collect-all pass `--doctor --skip-probe` runs, never reachable over HTTP before this) as a `diagnostics` list. The distinction is fail-fast versus collect-all: `validate_configs` (and so `validate_text`) stops at the first bad scene and names only that one; the doctor's per-scene loop catches each scene's failure independently, so a config with two bad scenes gets two diagnostics back even though the report's own `error` still names only the first. Diagnostics run whenever the file *loads* — including when `validate_text` itself refuses it — and stay empty only when it doesn't even parse, since there's nothing loaded for the doctor to look at. This is the console's pre-flight before a start or switch: `actions.launch` calls it ahead of `POST /api/session/{start,switch}` and refuses locally (`PreflightRefused`) rather than letting the supervisor find out from the 422.

**A refusal has to say which file it is about**, and that is not always the one on screen. Validation runs the *whole layered load*, so one stray value in `~/.config/c64cast/settings.toml` refuses **every** config on the host — with an error naming a section, and nothing anywhere saying the value is not in the file being edited. (Found by hitting it: `[color] color_match = "lab"` in the machine settings made every save 422 with a message about `[color]`, and the reflex is to hunt for a key in a file that does not contain it.) `_machine_layer_notes` is the attribution, and it is structural rather than a second load: a key is blamed only when the machine layer supplies it, the submitted text is silent about it, **and** the failure mentions it by name. All three, because a wrong pointer sends the reader further away than no pointer — a machine setting the file overrides is the file's problem, and one the failure never mentioned is nobody's. The notes ride on the report as `layers[]`, so the 422 a refused save answers with carries them too, and both editors render the same block. A settings file that will not *parse* is reported outright, since nothing on the host will load until it is fixed.

**`PATCH` is the form's save, and it round-trips through the dataclasses**: load the file, set the named fields, re-serialize, then hand the result to the same `write` a raw save goes through. Splicing values into the TOML text was the alternative and is worse in every direction — it needs a writer that knows where a key lives and where to put one that isn't there yet, and it can produce a file whose text no longer means what the form showed. Through the loader, a form save is exactly a load-modify-dump, and `load(dumps(cfg)) == cfg` is already property-tested. An edit names a `section` (or a `scene` index) and a `field`, plus a `value` or `reset: true` — reset puts the field back to the baseline, which under `minimal=True` is what *removes* the key, and is the inverse of the `is_default` flag the form renders. The editable field lists come from `introspect`, so an edit can reach exactly what the form drew and no more: not another scene type's fields, and not a section that doesn't exist.

**Three things are structural, not editable.** Adding or removing scenes, editing an overlay, and a scene's `type`. The first two were always the text editor's; `type` joined them after the form let one through: `describe` and the serializer both filter a scene's fields by `applies_to`, so re-typing a `blank` scene as `video` doesn't reinterpret `duration_s`, it *drops* it — the save succeeds and the scene quietly loses what it said. `_editable_scene_fields` subtracts `type` and `_apply_edit` names it in the refusal, because "this field has no editable field `type`" would read as a bug in the form rather than as the answer.

**One of those three came back with a route of its own.** "Add another clip to this show" is the most common structural change there is, and leaving it to the text editor meant the form's whole promise — author a show without a shell — stopped one step short of the thing people do most. `POST /api/configs/{ref}/scenes` and `DELETE …/scenes/{index}` are `add_scene` and `remove_scene`: a blank scene of a named `type`, or a **copy** of an existing one (`copy`, optionally `after`), which is the ask that actually recurs — re-typing a dozen fields to get a second clip like the first is what sent people back to the source. They are not a kind of `PATCH` body, because a `PATCH` names a field and these change which scenes exist. A copy is taken verbatim, name included: inventing `"opener (copy)"` would be guessing at what the show should call it, and the duplicate is visible in the list it was reached from. Removal refuses the last scene by name, so the answer is "a show needs a scene to play" rather than a loader error about an empty playlist. Editing an overlay and re-typing a scene stay where they were.

**Reordering got the same treatment, and reused `_rewrite` rather than inventing a fourth shape.** `PATCH /api/configs/{ref}/scenes/{index}` (body `{"to": n}`) is `move_scene`: `cfg.scenes.insert(to, cfg.scenes.pop(index))`, both indices bounds-checked before either happens, and a no-op move (`index == to`) is accepted rather than refused — it changes nothing, and the button either side of the list should not have to know it is at an edge. It is registered **before** the bare `PATCH /api/configs/{ref}` (same reason `/validate` and `/scenes` are: `{ref:path}` is greedy and would otherwise read "…/scenes/3" as a request to patch a file by that name), and it inherits `_rewrite`'s whole contract — validate-then-write, the `.bak` sibling, the ensemble and secret refusals, `partial=True` — for free, the same way `add_scene`/`remove_scene` do.

All write paths share `_rewrite`, which is the load → refuse-an-ensemble → refuse-a-secret → mutate → re-serialize → `write` spine. `patch` passes a mutation that applies edits; the scene routes pass one that inserts, pops, or pops-and-reinserts. Splitting them would have been repeated copies of the ensemble and secret refusals, which are the two a structural change must not skip.

**A structural change and a staged edit cannot be in flight together**, and the form refuses rather than reconciling: every staged edit is keyed by scene index, and adding, removing, or reordering a scene renumbers the ones after it (a move renumbers everything between the two indices, not just what follows the one that moved). Renumbering the staged edits to match would silently move an unsaved change onto a different scene, which is worse than being told to save or discard first — so the rule is shared rather than one route getting a pass the others don't.

**A config that loads is not a config that will run**, and the gap is media. `resolve_file_spec` lets a literal path through unchecked on purpose — a file can appear between load and playback, and a spec may legitimately name media on another machine in an ensemble — so a `video` scene pointing at nothing passed both **Check** and **Save** and failed seconds into the run, with the link open and the C64 already reset. `scene_factory.missing_media` reports those entries and `validate_text` puts them on the report as `warnings[]`, alongside `messages` and `layers`. A **warning**, not a refusal, because refusing would break the two cases the pass-through exists for; and carried through `write` as well as `validate`, because a save is the moment somebody stops looking at the check. URLs are skipped as not local, and globs are skipped because a glob with zero hits is already a loud error — warning about it as well would be a second voice saying the same thing.

**A show being built is not a show, and the pre-flight had to be told the difference.** A scene arrives from `add_scene` with a `type` and nothing else — which for `video`, `slideshow`, `waveform` and `launcher` means no `file =` yet, and on a host whose default media directory is empty that is a *fatal* resolve error at start-up. `write` runs the full start-up pre-flight, so the first step of building a show refused itself: the console said *add a scene* and the machine answered `assets/videos` is missing. The cut is one exception type. `scene_factory.MediaNotChosen` is raised only by the branch that means **not yet** — no spec at all, falling back to a default directory with nothing in it — and never by anything the user typed, so a bad glob or a path with a typo stays a plain `ValueError` and stays fatal. `_rewrite` writes `partial=True`, which excuses that one type and nothing else, and what would have been the refusal comes back as a `warnings[]` entry instead. A bad *value* the form itself produced still refuses and still changes nothing on disk: it is wrong now and wrong later, and the save is the last chance to say so. The raw text editor is unchanged — a hand-written save is a finished statement about the show, and the pre-flight is all that stands between it and a failure seconds into a run. The question is asked of `SessionConfigError.__cause__` rather than of the message, because the message is user-facing prose and moves.

CI is what found this, not the machine it was written on: the project's own `assets/videos/` is populated in a developer's checkout and holds one `README.md` in a fresh clone, so every test of the feature passed locally and all twelve jobs failed. The scene-structure tests now `chdir` to a directory with no `assets/` in it for that reason.

Two costs, both deliberate. **The file's prose does not survive** a re-serialize — comments and hand-authored layout are gone, which is why `annotate=False` is passed (a terse file close to what the author wrote, rather than the wizard's fully-commented style burying their file in generated help on the first save) and why the file's own `#:schema` directive is carried across rather than regenerated. **A config carrying a secret is refused outright**: the serializer never emits `SECRET_FIELDS`, so a round-trip would silently drop a DMA password the operator put there, and refusing the whole file is the only answer that neither loses it nor writes it back out.

**What gets written is the config the loader *resolved*, so every "is this set here?" question is asked against the machine layer** — `config.machine_baseline()`, not a blank `Config()`. `describe` reports `is_default` against it, `reset` puts a field back to it, `dumps` measures against it, and the secret check compares against it. Getting this wrong is not cosmetic: `minimal` used to measure against the dataclass defaults, so saving a show config on the machine with the capture card wrote that machine's `[video] device` into it, and the file then overrode the *next* machine's own setting. The same was true of the wizard and the on-C64 live-tune save-back, and the fix is one `baseline=` argument in [`config_serialize`](config.md#config_serializepy--the-writing-surface) that all of them now pass. `describe` also sends each field's baseline value, because the form has to be able to say what `Clear` will leave behind and the introspection document's `default` is the dataclass one — a different number on a machine with settings.

The replaced text goes to a dotfile sibling (`.gig.toml.bak`, invisible to the listing) because a remote overwrite of a show config otherwise has no undo at all. Ensemble masters read fine but come back with `kind: "ensemble"` and no form data — `config_serialize` refuses them by design, so the raw text editor is the whole story for one. The DMA password is withheld from the form via `config_serialize.SECRET_FIELDS`, the same list that keeps it out of a serialized config; the raw `text` is still the file, because this is an editor, not a redactor.

**What a ref bounds is which files are edited, not what a config can reach.** A saved TOML names media paths and URLs a session will open and `yt-dlp` will fetch, so remote config write access is equivalent to local shell-ish reach. That is why the full token gates it, why a `viewer` cannot write, and why `config_roots` defaults to the one directory the host was launched from rather than to anything broader.

**The packaged examples are a trailing read-only root** (`_append_examples_root`), so `--config example:NAME`'s catalog is browsable and copyable without being mistaken for somewhere a show can be saved — `_require_writable` refuses it, and `create` with `copy_of` is how one becomes an editable file. When a checkout is the working directory that root sits *inside* the cwd root too, so `_walk` prunes `paths.examples_dir()` from every non-read-only root: without it the walk lists each packaged config a second time as a writable file the console's `readonly`-keyed "Examples" toggle can't hide. The prune is skipped when `include_examples=False` (a test fixture) leaves nothing else to list them.

## `console_library.py` — favorites + recently-launched configs

`GET /api/library` and `POST /api/library/favorites` back the Session tab's two panels: **Favorites** and **Recently launched**, in place of the raw, unfiltered configuration list the console used to open on. Persisted to `<data root>/console.json` rather than the browser's own storage, because the point is that a phone and a laptop pointed at the same host see the same stars and the same recent list — a favorite starred from the console at the front of house should still be there from the console backstage.

**Same contract as `transport.JsonSlotStore`, not a subclass of it.** Tolerant load (a missing, corrupt, or wrong-shaped file reads as an empty library, and only well-formed entries survive), atomic write via `atomic_write_text`. Not a subclass because that class's contract is a *numbered-slot* map (`transport.py`'s WLED presets, Looks, loop presets), and this file's shape is two lists — a fourth reimplementation of the slot machinery for a shape that isn't slots would be the wrong reuse.

**Refs, not paths.** A favorite or a recent is stored as the same `<root-label>/<relative>` identifier `config_store.ConfigStore` already hands the browser, so it can be handed straight back to `store.resolve` with no translation and no second notion of "which file". A ref that no longer resolves — the file was moved or deleted since it was starred — is left in the list rather than pruned here: this module has no way to ask whether a ref is still good, and the client asking to render one is the one place that already finds out.

**Recents are recorded from every surface that starts a show**, not only the browser: `web_api.py`'s `POST /api/session/start`/`switch` call `record_recent` on success, and the WebSocket's `session: "start"/"switch"` command does the same — a launch from a MIDI controller or a script counts. A falsy ref (the host's own default config) records nothing, because a *config* library has nothing to say about "whatever this host was launched with".

## `media_store.py` — the media picker, its root jail, and its one write surface

`GET /api/media?kind=&q=` is what lets the Editor's `file =` fields offer what is actually on disk, instead of a bare text box the operator has to fill from memory; `PUT /api/media/{name}` is how a file gets there in the first place. It is `config_store.py`'s sibling and shares its jail discipline (`resolve()` + `is_relative_to`, the depth-capped, skip-dirs-pruned walk) through `fs_walk.walk_dirs` — a second copy of that check would be a second thing to get wrong.

**Two lists, not one.** `[web].media_read_write` is a *kind → directory* table (`video` → `assets/videos`, and so on), both browsable and uploadable; `[web].media_read_only` is a plain list, browsable only. This replaced a single flat `media_roots` list before that field ever shipped (it lived only under `## [Unreleased]`), because uploading needed an answer to "which directory does a kind land in" that a flat list can't give: a directory named `clips/` says nothing about what it holds, and a brand-new empty one has no contents to guess from either — so the mapping is stated, not inferred. An empty `media_read_write` table means the four directories the loader itself already defaults to (`scene_factory.DEFAULT_VIDEO_DIR` and its siblings); naming any kind there only ever changes that one kind (including turning it off with `""`), because a config author has no way in TOML to say "leave the rest exactly where they were" other than not mentioning them — see `_resolve_write_table`. `audio` has no default of its own (`generative`'s `audio_source = "file"` is the one media-bearing scene type that requires an explicit `file =`), so naming a directory for it is what turns audio uploads on at all.

**The kind comes off the extension, not a parameter.** The five kinds' extension tuples never overlap (`MEDIA_EXTS` inverts `_KIND_EXTS` on that assumption), so extension → kind is a function. This is also what settles what a two-kind `generative` scene (`sid` and `audio`) uploads without a client ever having to choose, and it means the upload route needs no `kind=` query parameter at all — `destination(name)` is the whole policy: structural checks (bare filename, no `..`, no leading dot, not empty, not absurdly long), then the kind off the extension, then whether that kind has anywhere configured to write to.

**Never an overwrite.** A name already taken in its destination directory is renamed `clip-2.mp4`, `clip-3.mp4`, … (`_unique_name`) — the same numbering `config_store._label_for` already uses to disambiguate a duplicate root label, so there is one way in this repository to say "that name was taken." The final name is chosen at *commit* time, right before the `os.replace` that lands the file, narrowing the TOCTOU window to as little as it can be made; `os.replace`'s atomicity means the loser of a genuine race replaces rather than corrupts, the same trade `ConfigStore.create` already accepts.

**Streamed, not buffered.** `receive(name)` hands back a context manager whose `write` takes one chunk at a time (`request.stream()` on the route side), because the body can be a multi-hundred-megabyte video arriving while this same host is simultaneously encoding video for a running show — buffering it whole in memory first is not acceptable. It can't reuse `transport.atomic_write_bytes` for that reason (that one takes its payload as a single `bytes`), so it reuses its *shape* instead: a temp file in the destination directory (`.part` suffix, invisible to `index` since no kind's extensions end in it), `flush` + `fsync`, then `os.replace` onto the final name. Any exception unlinks the `.part` and leaves nothing behind.

**Specs, not refs.** `ConfigStore` addresses a file as `<root-label>/<relative>` because it *writes* to a named file and ambiguity there would pick the wrong one. A media entry instead has to be a string `scene_factory.resolve_file_spec` will actually resolve — the value that goes straight into a scene's `file =` — so a listed (or uploaded) entry is built from the root's *configured spelling*, not a synthetic label. A root written `~/Movies` lists `~/Movies/clip.mp4` (the `~` stays a `~`, same as a hand-typed spec, and `paths.expand_user` handles it at resolve time on whichever machine opens the config); a root written `assets/videos` lists `assets/videos/clip.mp4`. The jail check itself still runs against the *resolved* path.

**Directories are entries.** `resolve_file_spec` treats a directory as a randomizer — one file picked at each scene `setup()` — which is exactly what an unset `file =` already does against the default asset dir, so a picker offering only files would hide the feature people want most for a slideshow or an HVSC tree. A directory is listed once per kind, exactly when it directly holds a file of that kind; nothing is inferred about a directory the walk cannot see into, matching `ConfigStore._walk`'s own choice not to follow a symlinked directory.

`q` is a case-insensitive substring match on the built spec, applied *during* the walk rather than after the `MAX_FILES` cap — so a search reaches media a plain listing would have already truncated away.

**This side existed a full release before the console asked it anything.** `api.media(kind, q)` took `q` from the start; nothing called it with one until `introspect.searchMedia` did, because `mediaOfKind` fetches once per kind and caches it for the page's lifetime — the right shape for the datalist everyone reads on mount, and the wrong one for a query, which wants freshness over reuse. Debounced (`debounce.ts`, `SEARCH_DEBOUNCE_MS = 250` in `ConfigForm.svelte`) at the field, not the request: `FieldInput`'s `onsearch` fires on the same keystroke that already drives `type()`, one call per kind a scene type browses so a two-kind `generative` field's search reaches both. A result **overlays** the unfiltered listing rather than merging into it — `mediaOptions` prefers `searchResults[kind]` outright when a query is live for that kind — because what the host just answered about a query is a more truthful list than the first 500 entries a plain walk happened to reach. An empty query clears the overlay immediately, bypassing the debounce, so backspacing to nothing snaps straight back rather than waiting out a request that would just re-fetch what was already there.

## `web_static.py` — the console's built UI, committed and served

The browser UI lives in `web/` at the repo root as Svelte 5 + Vite + TypeScript + Tailwind sources, and Vite compiles it into `c64cast/web/dist/`, which is **committed and shipped as package data**. That is the load-bearing decision: a `uv sync` install has no Node, no npm and frequently no route to a registry, so a build step at install time would mean the console simply does not exist for most users. Node is required to *change* the UI, never to run it. `make web` rebuilds the bundle, CI rebuilds it and fails on a diff, and `web/README.md` says so where somebody editing the sources will read it.

Committing build output has two consequences, and both are configured rather than left at the tool's defaults. **Asset names are fixed** (`assets/app.js`, `assets/app.css`) instead of content-hashed: a hash adds a new file to git on every rebuild and leaves the old one behind, which makes the artifact unreviewable. **The server therefore sends `Cache-Control: no-cache`** on everything, because a browser holding a cached `app.js` across an upgrade would run yesterday's console against today's API — the cache-busting the hashes would have bought is paid for a round trip at a time instead, which on a LAN is the cheaper half of the trade.

`mount_web_app` registers three routes and must be registered **last**, after every API route, because the third is a catch-all: `/` serves the shell, `/assets/{name}` serves one file out of a catalog built at mount time, and `/{path:path}` serves the shell again so the client can grow routes without a server change. Cataloging rather than resolving is deliberate — a request *names a key*, so nothing a client sends ever becomes a path component and there is no traversal to normalize, no containment check to get subtly wrong, and no static analyzer to persuade that the check was right. The price is that a rebuild under a running host needs a restart, which is what the Vite dev server is for. What that catch-all refuses is read off `app.routes` at mount time rather than listed in the module — a mistyped `/api/sessions` answering `200 text/html` is worse than a `404` because `fetch` parses it as success, and a hand-written list of paths to protect is a second copy of the route table. A missing bundle is not an error: `--serve` from a checkout that never ran `make web` comes up with the API and the zero-dependency `/perf` page, which is the reason that page was kept.

Nothing here does its own auth. The console is mounted onto an app the token middleware already wraps, so the shell is gated exactly like the API it talks to — which is also why an unauthenticated *navigation* gets an HTML form from `auth.login_page` rather than a line of plain text: the daemon prints a URL with the token in it at startup, and a phone whose cookie has gone otherwise has nowhere to put it back. A `fetch` keeps the plain-text 401, and a `viewer` refused a write keeps its `403` — re-entering a token that is working changes nothing.

### The screens

`App.svelte` owns one `Console` (the `/api/ws` feed as a reactive object) and one `Router`, and hands both down. The router is forty lines over `pushState`/`popstate` rather than a tab variable, because the server's catch-all already answers any unclaimed path with the shell: that makes `/config/shows/gig.toml` a link somebody can send and a reload that comes back where it was, and it makes the back button the browser's own rather than something reimplemented. An unauthenticated navigation to one of those paths still gets the login form, because the gate is upstream of the route.

**Session** drives `SessionManager` and is described by the state feed. **Config** is the editor, and its shape follows one decision: **the form names fields, the server writes text.** A form that saved TOML would have to emit it in TypeScript — a second serializer competing with `config_serialize`, which is the tested one — so it doesn't: `PATCH /api/configs/{ref}` takes named field edits and `ConfigStore.patch` composes the file through the dataclasses. That is what makes the *Settings* view writable without a line of TOML in the browser, and it is why the two views are not two editors of the same thing: *Source* replaces the file, *Settings* names what changed in it.

The form is also the *explained* view, which is the half the raw text cannot give you: `describe()` sends the value the loader actually **resolved** (machine settings and layered defaults show through, which reading the file will not tell you), what it falls back to, and whether the two agree; `/api/introspect` supplies the help, the choices and the `apply` flag. `FieldInput` turns a declared type into a control — switch, picker, number, JSON box — via the same classification the `--init` wizard prompts from, so the browser and the terminal offer the same shape for the same field.

**A union type gets both its halves.** `field_kind` classifies a declared type *as a whole*, which is all a one-question prompt can act on, and the form inherited that: `border` and `background` are `int | str` and got a number box, directly under help text saying you may write `"light blue"`; `force_palette_colors` is `int | list[…]` and got a JSON textarea, so setting it to `8` meant typing `8` into a control labeled as a table. `wizard.field_kinds` splits the declaration at its **top level** — `union_members` tracks bracket depth, so `int | list[int | str]` is two members and not three — and returns every kind, in declaration order. `field_kind` is untouched and still the wizard's: it must keep saying `complex` for a union containing a list, because that walk *skips* complex fields. The form renders a small kind selector above the control and opens on whichever member the stored value already is; switching shows an **empty** control rather than the stored value, because the stored value is the other type and rendering `"light blue"` in a number box is the bug being fixed. Nothing is staged until something is entered, so switching back is free.

**And a color field becomes the sixteen colors**, which is what the value means anyway. Type alone cannot say that — `[video].device` is `int | str` too, and its strings are camera names — and `choices` cannot say it either, because these fields accept an index as well and a picker built from `choices` would refuse one. So `FieldDoc.vocabulary` does: `"c64color"` on `border`, `background` and `force_palette_colors`, internal to the introspection document the way `apply` is. The swatches themselves are **served**, not copied — `introspect.palette_swatches()` reads the *live* `C64_PALETTE_BGR`, so a host that has matched the machine's own emitted palette offers the colors that machine really shows, and there is no second palette in the browser to drift from the first. The picker writes the **name**, which is the half of the union the form could not reach before and the half that still reads as a color a year later; a spelling it cannot place (the loader's fuzzy `"lgrn"`, `"blk"`) is reported as unrecognized and left alone rather than quietly re-selected, because a value edited by being looked at is worse than one the picker cannot draw.

Five consequences worth knowing.

The introspection document is ~150 KB and describes the *code*, so it cannot change while the process is up: `introspect.ts` memoises the in-flight promise, and a failed fetch clears it so a retry is possible.

`is_default` is what powers "only what this file changes" — on by default, because a config has 167 settable fields and a show file names a dozen of them, and the dozen is the question being asked. That filter is also what a *writable* form trips over: the field you want to add is, by definition, one the file doesn't change yet. Hence the finder beside it, which overrides the filter while a query is in it — and a row with an unsaved edit is never hidden by either, because losing sight of a staged change is how it gets saved by accident.

Unsaved edits are kept per ref rather than defended with a "you have unsaved changes" dialog: clicking another file to compare against is the common move, and losing an edit to it is the failure worth designing out. They live in `drafts.svelte.ts`, a module-level store rather than screen state, for two reasons that both bite: the Config screen is **unmounted** the moment somebody looks at Live, so an edit typed and then checked against the running show used to be gone on the way back; and the tab bar has to be able to mark that something is unsaved *somewhere*, which it cannot ask a screen that no longer exists. Both editors share it (`text` for the raw draft, `fields` for the form's staged edits) and it is in memory only — a draft that outlived the page would be a second copy of the config with nowhere to see it. A load that lands after a newer one has started is dropped by sequence number, so a fast click through a long list settles on the file that was clicked rather than the one the network answered last.

**A half-typed value is not an edit and not an error.** `FieldInput` parses on every keystroke and reports either a value or a reason; the reason lands on the row and disables the save, and the text stays where it was typed. It also holds the raw text only while the field has the caret — the value round-trips through the parent and comes back formatted, so binding straight to it rewrites `1.50` as `1.5` under the cursor and makes the decimal unreachable. That is the same rule the performance sliders follow while a finger is on them, arrived at independently and for the same reason.

**Scenes can be added, removed and reordered from the form.** *Add scene* with a type picker under the list, and **↑**/**↓**, *Duplicate* and *Remove* on each block — the routes described under `config_store.py`. Reordering deliberately isn't a drag: the scene card's `ondrop` already belongs to a media upload or a dropped URL, and a nested drag source would fight it. All four write immediately, like every other save, so the screen re-reads the file afterwards; and all four are disabled while an edit is staged, saying why, because adding, removing or moving a scene renumbers the ones a staged edit is keyed to.

**A green "Saved" cannot stand alone over a show that will not run.** `MediaWarnings` renders `warnings[]` inside both the check panel and the saved panel — *"scene 2 (video) names `/clips/opener.mp4`, which is not on this host"* — in the same block the loader's own diagnostics use.

**An upload shows a real bar, and can be canceled.** `api.uploadMedia` is the console's only `XMLHttpRequest` — `fetch` cannot report request-body progress, and XHR is the only browser API that can. `settle()` in `api.ts` is the shared tail (parse the body, throw `ApiError` for anything not 2xx) both that and `request()`'s `fetch` path funnel through, so the two transports produce the same error shape. `<progress>` (the console's first) goes indeterminate — no `value`/`max` — the moment `lengthComputable` is false, which happens when something between the browser and the host strips `Content-Length` from the streamed body; `uploadTotal` starts at the file's own `size` so the bar has a real number before the first `progress` event lands rather than sitting at 0 for however long the first chunk takes. Canceling aborts the `XMLHttpRequest` via an `AbortController`, needing nothing from the server: the aborted read is exactly what already drives `MediaStore.receive`'s `except BaseException` branch, which unlinks the `.part` file regardless of why the stream ended.

**Sharing the console meant sharing the token that can stop the show.** The Session screen's *Share* block asks the host for a read-only link and shows it selectable, with a Copy button that reports its own failure rather than silently doing nothing (`navigator.clipboard` is unavailable over plain HTTP outside localhost, which is exactly how this host is usually reached). The link is fetched on a tap and not on mount, because asking is what mints the token.

**Saved and in effect are two different things**, and the screen says which: a file that is the running config gets a *Reload scenes* next to it. Without that, a save is a change you cannot see, and the reflex — restart the show — costs a machine reset.

**Every launch pre-flights before it ever claims a start or switch.** `actions.launch` — the one function every launch surface goes through — calls `api.checkConfig(ref)` first and throws `PreflightRefused` (carrying the whole report) rather than calling `start`/`switch` on a config the check already knows will not run; a `null` ref (Live's *Start the host default*) has nothing on disk to pre-flight and falls through to the improved `422` instead. `errorsLogic.describeError` is the one status→sentence mapping every screen's `problem` line uses — Session and Config each grew their own copy before, and Config's silently had no `422` case, the one that matters when a start or a save is refused. The tab-bar Start button in `App.svelte`, reachable from every tab, has nowhere permanent of its own to show a refusal; it stashes one on `Console.launchProblem` (browser-local, same as `expectingStart`) and routes to Session, which claims it once and clears it. `Diagnostics.svelte` renders a pre-flight's `diagnostics[]`, grouped by category and dropping `level: "ok"` — it sits beside `MediaWarnings` wherever a `ValidationReport` is already rendered (`TomlEditor`, `ConfigForm`, Session).

**And a reload is not always enough**, which is the harder half. `session.reload_all` re-reads the file and hands the playlist fresh scenes; `[audio]`, `[video]` and `[ultimate64]` were read once when the session started and their threads are already running. So the save message splits its own count — *"Saved 3 changes. `[audio]` needs the session restarted; the rest apply on a reload."* — and when a save held something back, the running-config banner stops offering a reload as if it covered everything and offers a **Restart on this config** (`api.switch`) beside it. Which sections are which is `config.RELOADABLE_SECTIONS`, surfaced as `SectionDoc.reload` on the introspection document: the browser reads the host's answer rather than keeping a list that would drift the first time `reload_all` learned a new section. The staged-edit bar says it *before* the save too, because "will this show up" is a question worth answering while the change is still cheap to reconsider.

**The log follows you.** It is a collapsed bar fixed to the bottom of every screen showing the latest line, expanding to the same `LogPane` the Session screen used to own alone — because a save refused or a scene that failed mid-show is the host's own account of what happened, and the reader is on Configs or Live when it lands. The collapsed bar counts `ERROR`/`CRITICAL` lines arrived since it was last opened, so it can say there is a reason to open it without shouting about a log that is merely long.

**Every panel is a `min-w-0` grid item.** A grid item is min-content-sized by default, so a single unbroken string inside one — a log line, an absolute path — makes the *page* wider than the phone it is being read on, and every screen then scrolls sideways including the ones without the long string in them. The Session screen was doing exactly that: 1195 CSS px of scroll width in a 430 px viewport, with the log pane's own `overflow-x-auto` unable to help because the item around it had already grown to fit. `min-w-0` is what lets a panel be narrower than its contents so the scrolling happens inside it, which is where it was designed to happen. Worth knowing for anyone measuring this: a headless `--screenshot` at `--window-size=430` will *not* show the difference, because the OS clamps the window to a minimum width and the image is then clipped rather than re-laid-out — the honest measurement is `Emulation.setDeviceMetricsOverride` and `document.documentElement.scrollWidth`.

**Live** is the performance surface, and it renders `PerfBridge.state()` — the same payload `/perf` has always drawn, arriving on the same socket as everything else, so the screen costs no second connection. Commands go back up that socket as `{action: …}` frames, which `web_api._apply_command` passes straight to `bridge.apply` when they carry no `session` key: a browser launch and a pad launch are the same `ClipEvent` on the same queue. An idle host sends an empty `systems` list rather than an error, which is what lets the screen say "nothing is running" instead of failing; an ensemble puts each system on `/live/<name>`, and a name that no longer matches falls back to the first rather than blanking. That idle state also carries a **Start** of its own: "nothing is running" and "start something" are one gesture apart in intent, and used to be two screens apart in fact.

Five panels, and the split between them is about *addressing*, not about layout. **Clips** and **Looks** are the performance engine. **Effects** is the chain, addressed per layer, where bypass lives. **Tune** is `live[]` — the color pipeline, the generator, the scope: the knobs a MIDI controller and the on-C64 menu have always reached and the browser could not, grouped exactly as `introspect.live_targets()` groups them so a phone and a controller name the same knob the same way. Scalars reuse the effect rack's slider (one control, because both are a named number with a declared range and a normalized position — `Knob` in `types.ts`); choices get a picker, because a choice list has no position to drag. **Scenes** is `scenes[]` with a jump, next to the transport in the tempo bar: pause, resume and skip had been HTTP routes with no UI since before the console existed, so skipping a scene running long meant a keyboard at the machine or a `curl`. Under the Tune knobs sits the record of turning them: what a one-shot run offers back at exit, on a terminal a daemon does not have. It lists every change with where it started, tags a per-scene knob with the block it belongs to (`scene 3`, counted over the config's own `[[scenes]]` blocks — which the tooltip says, because that is not always the running order), marks the ones no config field can hold (`runtime only`), and offers one tap to keep the rest in the file the show is running from — or, for a run with no config file, the same pasteable block the CLI prints.

Two behaviors are carried over from `_PERF_HTML` deliberately, because both were found the hard way. **The beat pulse is extrapolated locally** from `bpm` and the sampled `beat_phase`: the feed pushes about three times a second and a beat at 128 bpm is shorter than that, so a pulse driven by arriving frames would visibly skip. The anchor it extrapolates from is a plain object rather than `$state` — the animation loop reads it every frame, and a reactive read there would re-arm the effect that owns the loop on every push. **A slider under the finger ignores the echo**: the host reports the value back at the push cadence, and letting that drive the input mid-gesture drags the handle backwards, so while the control has focus it shows what the performer set. The old console got this by refusing to rebuild the DOM around `document.activeElement`; the same rule here is a per-slider hold, released on blur or at the end of a gesture that never took focus (iOS Safari does not focus a range input on touch).

**Live is driven from the keyboard too — the app's first `<svelte:window>`.** `liveKeysLogic.ts` is the whole feature as pure functions: `isTypingTarget` bails on INPUT/TEXTAREA/SELECT/**BUTTON**/contenteditable, `commandForKey`/`commandForKeyUp` map a key to the same `{action: …}` frames the panels above already build, and `Live.svelte` is just the DOM plumbing — `event.repeat` (auto-repeat would spam a one-shot verb many times a second), the target check, and the `send()` loop over whatever the mapper returned. `BUTTON` is in the bail list for the same reason `ClipGrid`/`TransportBar` detect a keyboard-synthesized click via `event.detail === 0`: a global handler that also acted on the focused button's own key (Space, above all) would either double-fire the action or, had it called `preventDefault()`, silently break launching a clip with the keyboard. `hasModifier` covers Ctrl/Alt/Meta only, deliberately not Shift — a plain `?` is `Shift+/` on a US layout, and Caps Lock reports the same uppercase letters Shift would with neither meaning "this is a browser shortcut". `?` toggles the on-screen key list and is the one key `commandForKey` refuses to turn into a command — it is local UI state, not something to send. Held keys (`[`/`]`, rewind/fast-forward) send their press on keydown and their release on keyup; every other key is complete in one call, and a digit's launch sends a press *and* a release together, the same tap `ClipGrid` already sends for a keyboard-focused pad. A shortcut never reaches past the read-only gate: `commandForKey` takes the same `frozen` (`host.readOnly || !host.connected`) every panel is already disabled by, and returns nothing while it's set.

**The editor's check is as strong as `validate_configs`,** which is why that function validates every scene through `scene_factory.validate_scene_cfg` rather than only the eight section-level checks. It used to stop short of the scenes, and an unknown scene `type` or a `generative` `source` that does not exist passed both **Check** and **Save** — then failed a few seconds into the next start, as a `StackBuildError`, after the machine had been opened and reset. Follower-only scenes are validated with the rest: they are built lazily at broadcast time, so a bad one would otherwise surface mid-show.

## `screen.py` — the C64's screen in the browser

Everything else the console does is open-loop. It can author a show, start it, tune it and save it without ever showing what any of that did — verification meant looking at the television the Commodore is plugged into, which for a console meant to be held in one hand at a gig was the largest remaining source of friction and made every other improvement worth less than it should be.

The picture is the machine's, not c64cast's: [`hw/vic_stream.py`](hardware-io.md#vic_streampy--the-machines-own-vic-output) receives the Ultimate 64's own VIC-out UDP stream, so the browser shows what the VIC actually painted rather than what the render pipeline believes it wrote. That is the difference between a monitor and a second opinion from the same source, and it is why the panel is right for scenes c64cast does not draw at all.

**Ref-counted, because the stream is not free.** ~2.6 MB/s while it is on, so it is on only while somebody is watching: `ScreenFeed` counts watchers per system, starts the receiver on the first and stops it a few seconds after the last. The acquire/release pair is a **context manager** rather than two methods, because the two getting out of step is how a machine ends up streaming at nobody — and an HTTP client vanishing mid-response is the normal case here, not the exceptional one. The linger covers a page reload, which would otherwise pay the firmware's destination resolution and a second of black to end up exactly where it started. The receiver is opened *outside* the feed's lock: opening it talks to the machine, and holding a process-wide lock across a network round trip is how one slow device stalls every other request. A second request that wins the race meanwhile is detected and its extra receiver stopped.

**`multipart/x-mixed-replace` is the whole client.** One `<img>`: no script, no socket, no decoder in the page, and it works with JavaScript off — which is what makes it sayable on `/perf` as well as in the Svelte console. Binary frames on the existing WebSocket into a canvas was the alternative and buys control this does not need.

**PNG, not JPEG**, which inverts the usual advice for video and is right here: this is flat sixteen-color art with hard edges, the best case for PNG's filters and the worst for a DCT. A C64 screen is 5-15 KB as PNG — *smaller* than the JPEG that would put ringing around every character cell. Compression level 1 rather than 9, because on art this flat the difference in size is slight and the difference in time is not.

**Only new frames are encoded.** The receiver keeps the latest and nothing else, so an unchanged frame number means the machine has not painted since the last part and re-sending it would be bytes for no picture — a still screen therefore costs nearly nothing, which is the common case for a console left open beside a running show. The rate cap (`[web].screen_fps`, 0 to turn the screen off) governs encoding, not the machine: it is already sending every frame, and the ones not encoded are the ones no longer in `latest()`.

**Three GETs, deliberately.** `/api/screen` (what can show a picture), `/api/screen.png` (a still), `/api/screen/stream`. GET so the read-only role can watch — a viewer who cannot see the show has been handed a link to nothing. What a GET here does have is a side effect on the machine, and that is the accepted trade: it changes nothing about what the C64 is *doing*, and every alternative means a viewer cannot see the screen.

**The frame generator is blocking and the route is async**, so `_until_gone` bridges them: it pulls each part in a worker thread (the generator sleeps and encodes; running that on the loop would stall every other request) and checks `request.is_disconnected()` between parts, which a plain generator cannot await.

**The watch belongs to the *response*, not to the generator**, and that correction cost an afternoon. The obvious design holds `watching()` inside the frame generator and releases in its `finally`. It does not survive a real disconnect: the generator runs on a worker thread, the disconnect cancels the async task *while that thread is inside `next()`*, and closing a running generator raises `ValueError: generator already executing` — so the `finally` never completes, the watcher count never drops, and the machine goes on sending 2.6 MB/s. The route therefore `acquire`s before building the response and hands `release` to Starlette as a `BackgroundTask`, which runs when the body is done however it ended; `_until_gone` closes nothing, and an abandoned generator is suspended at a yield holding nothing.

**The sweeper is a thread of its own**, for the same class of reason. The first version drove `sweep()` from the state feed's push loop, on the argument that a timer whose only job is to notice nothing is happening is a thread paid for at idle. But `/perf` and a bare `<img>` open no WebSocket, so on those clients nothing ticked and nothing swept. Costing nothing at idle is preserved by *lifetime* instead: `ScreenFeed` starts the sweeper with its first receiver and the sweeper ends itself when the last one goes. Both of these were found by watching a real machine keep streaming after the tab closed, which is exactly the failure no local test notices and every network does.

## `midi_control.py` — process-wide MIDI control surface (optional, live performance)

When `[midi_control] enabled = true` and the `midi` extra is installed, `MidiControlListener` opens **its own** `mido.open_input()` and runs a 1ms-poll reader thread for the whole process — a *service*, not a Scene, unlike `midi_scene.py`'s `MidiScene` (only live while that scene is on screen). Mido ports are exclusive opens, so this is always a second port: it never shares a running `MidiScene`'s port even on the same physical controller (route the controller to two virtual ports, or OS-level MIDI Thru, to feed both from one device).

**Why no coalescing, unlike MidiScene.** `MidiScene._reader` coalesces continuous CCs to `_CONTROL_FLUSH_INTERVAL_S = 1/60` because it writes SID registers over the DMA socket and bursting it is unsafe. `midi_control.py` never touches the DMA socket from its reader thread — every action it takes is either a `threading.Event.set()` on a `Playlist` or a plain in-process `setattr()` — so there is nothing to throttle: every message dispatches the instant it arrives. This is the deliberate, load-bearing difference between the two modules; don't "fix" it by adding a flush interval.

**Two dispatch paths, chosen for latency:**

* **Discrete actions** (`pause`/`resume`/`toggle_pause`/`skip`/`cycle_style`/`jump`) reuse the existing `Playlist` Event-flag pattern — the same mechanism `control_plane.py` and `keyboard.py` use — picked up at the next clean frame boundary (one frame period, worst case; the run loop's pacing wait isn't interrupted early by these Events, same floor the keyboard/control-plane already accept).
* **`jump`** is `Playlist.request_jump(index, skip_interstitial=...)` — a primitive generalizing `skip_event`'s "force `is_done=True` at the next boundary" pattern to an arbitrary target index instead of always `index+1`. `_advance()`'s end-of-scene branch consumes a locked `_jump_target` (last-write-wins: a burst of pad hits collapses to the final target) in place of the usual `index+1` computation. `jump_transition = "cut"` (the default, and what a live-hit control should always want) skips `_enter_interstitial()` entirely and goes straight to `safe_setup` via the same `EnsembleCoordinator.wait_for_audio_claim` gate single-scene looping uses — a jump into an ensemble audio-gated scene **blocks on the real gate**, it does not silently retarget elsewhere (an explicit jump must not be second-guessed). `jump_transition = "interstitial"` routes through the normal "UP NEXT" card instead, for non-performance callers.
* **`param`** (continuous CC → an effect/generator knob) skips the Event/frame-boundary machinery entirely: `setattr(holder, name, scaled_value)` directly on `scene.effect`/`scene.source`, an unlocked cross-thread write already-safe by the same precedent `MidiScene.adsr`/`.pulse_width` etc. use (GIL-atomic single-attribute writes, read by the render loop's normal next pass). This is the cheapest path in the system — no Event, no `_advance()` indirection, picked up on literally the next frame render.

#### `transport.*` actions — a third dispatch path

Phase 2, extended in Phase 3.

**The vocabulary.** `_ACTIONS` gains `transport.play_pause`/`stop`/`loop_toggle`/`rw`/`ff`/`jog`/`record`, plus a plain `loop_slot` with no `transport.` prefix (mirroring `jump`/`param`). `_CC_TYPES` gains `"mmc"`.

**Why this path defers.** Unlike the two paths above, these do **not** mutate `Playlist` or scene state directly on the MIDI reader thread. `_apply`'s `transport.` branch — plus a sibling `loop_slot` branch, since it has no prefix to match `startswith("transport.")` — builds a `transport.TransportEvent` and calls `pl.transport.enqueue(event)`. Actual dispatch happens in `TransportSession.tick()` on the playlist thread; see the [`transport.py`](#transportpy--live-tune-tracker--save-back-phase-1--dj-transport-engine-phase-2--record-workflow--loop-presets-phase-3--controller-profiles-phase-5) notes below.

`loop_slot`'s event carries `slot` from `_CCMapping.slot`, validated `>= 1` in both `_parse_cc_map` and `config.validate_midi_control_cfg`.

**Two `_dispatch` wrinkles:**

* A `msg.type == "sysex"` branch parses an **MMC** (MIDI Machine Control) transport SysEx, `F0 7F <dev> 06 <cmd> F7`. mido strips the F0/F7 framing, so `msg.data == (0x7F, dev, 0x06, cmd)`. `_parse_mmc_sysex` wildcards the device byte and recognizes only `_MMC_COMMANDS = {0x01 stop, 0x02 play, 0x04 FF, 0x05 RW, 0x06 record, 0x09 pause}`, looked up as `("mmc", cmd)`.
* Note-release routing (`note_off`, or `note_on` with velocity 0) reaches `_dispatch` rather than being discarded at the door, but is dropped there unless the mapped action is in `_RELEASE_AWARE_ACTIONS` — `("transport.rw", "transport.ff", "transport.record", "transport.stop")` and `clip_launch`. Those are the actions whose pad chords need a real release to key off; everything else would only see spurious repeats.

> **MMC has no release concept at all.** A SysEx frame always dispatches `pressed=True, value=127`, since `_dispatch`'s sysex branch has no note-off equivalent. So an MMC-mapped Record or Stop still fires its one-shot action correctly, but cannot reliably drive the pad chords — those need a `note` mapping. `TransportSession`'s `_CHORD_HOLD_WINDOW_S` auto-expiry keeps this from wedging future presses; it just can't make MMC-sourced holds meaningful.

**Duplicated vocabulary, pinned by a test.** `config.py` keeps its own copy — `_MIDI_ACTION_CHOICES` / `_MIDI_CC_TYPE_CHOICES` / `_MIDI_MMC_COMMAND_CHOICES`, validated in `validate_midi_control_cfg`. The duplication is deliberate, on the same "config stays import-light" rationale as the existing `_parse_cc_map` split, and `tests/test_midi_control.py::MidiActionChoicesDriftTest` pins the two copies together.

**Side effect.** Mapping any `transport.*` action in `[midi_control].cc_map` forces `[audio].use_reu_pump` off process-wide via `cli._coerce_reu_for_transport` — see the [`scenes.py` transport note](scenes.md#videoscenes-transport-surface-midi-live-tune-phase-2) for why.

**No new defaults.** Neither `transport.record` nor `loop_slot` ships a MIDI default; both are fully opt-in via an explicit `cc_map`. `_DEFAULT_MIDI_CC_MAP` likewise carries zero MMC entries: a default that fires Record or Stop on an unmapped controller is a worse failure than one that does nothing.

#### The `LIVE_PARAMS` registry
`FrameEffect`/`GenerativeSource` each carry a class-level `LIVE_PARAMS: dict[str, tuple[float, float]]` (name → (min, max)), empty by default. A CC's 0-127 value is linearly scaled into the declared range and written with a plain `setattr` — no per-class wiring beyond the one-line class attribute. Only declare **independent single-numeric fields** here: a `setattr` is GIL-atomic for one attribute, not for two that must change together. Currently declared: `TrailsEffect.decay`, `PlasmaSource.{speed,scale}`, `TunnelSource.{speed,scale}`, `FireSource.{scroll_speed,intensity}`, and `PulseEffect.intensity` / `RgbShiftEffect.intensity`. The two reactive effects have no baseline output without a `MusicModulation`, so their `intensity` (a reaction-depth multiplier, `1.0` = full reaction depth, `0.0` = identity) is a **visible no-op on a non-reactive scene** — inherent, since there's nothing to scale. `VoiceScopeRenderer` (the scope-scene mixin — WaveformScene/MidiScene/AsidScene) also declares `LIVE_PARAMS = {"gain": (0.25, 3.0)}`, applied in `_compute_ys` as a trace-amplitude multiplier (the existing `np.clip` keeps an overdriven trace inside the strip); because a scope scene *is* the renderer (no source/effect holder), it's reached via a **`scene.` target prefix** — one case in `live_tune.resolve_holder`, which every surface goes through (see the `live_tune.py` notes below; the special-case used to be copied into `midi_control` and `wled_device` and kept in step by hand). To add a new live-tunable param to an effect/generator/scope, add one entry to its `LIVE_PARAMS` dict; nothing else needs to change.

**Ensemble targeting is by MIDI channel**, not a config-time system list: channel *N* (1-based) addresses the Nth system in ensemble order (the same order `playlists.keys()` / `stacks` iterate in), and a reserved `broadcast_channel` (default 16) addresses every system at once. A performer retargets by switching their controller's transmit channel — zero app-side round trip, unlike a menu or HTTP call. Single-system mode ignores channel entirely. Mirrors `control_plane.py`'s "one service for the whole ensemble" shape (`build_midi_control_listener(playlists: Mapping[str, Playlist], cfg)`), not a per-system controller.

**Config** (`[midi_control]`, `MidiControlCfg`) is process-wide like `[control]`: not in `_CASCADE_SECTIONS`, tracked via `LoadResult.master_midi_control` (parsed from the master TOML in ensemble mode, or the single config in single-system mode) rather than per-system `cfg.midi_control`. `cc_map` is a free-form `list[dict[str, Any]]`, following the `[[scenes.overlays]]` convention — validated by the consuming code (`config.validate_midi_control_cfg` / `midi_control._parse_cc_map`, deliberately duplicated so `midi_control.py` stays testable without importing `config.ConfigError`) rather than encoded rigidly in the dataclass. Ships a default map out of the box (notes 36-39 transport, notes 40-55 + Program Change 0-15 as a 16-scene jump bank, CC13-16 as an example knob bank) so the feature works with no config edits — see `--describe section:midi_control` for the exact table.

**Explicitly out of scope:** anything that would need a scene rebuild — display-mode switches, scene-type changes — is not exposed. Those cost real network/DMA setup time (`_build_display_mode`, teardown+setup) and are categorically wrong for a live-hit control; this mirrors the existing "live" vs "rebuild" axis in `config._APPLY_CHOICES` for the on-C64 menu. Only Playlist-level Events and `LIVE_PARAMS`-declared single-numeric-attribute writes are ever touched.

#### The `mode.<name>` holder and `LIVE_CHOICES` (Phase 1)
Beyond `effect.`/`source.`/`scene.`, a `param` target may address `mode.<name>` — the running scene's `DisplayMode`. `live_tune.resolve_holder` resolves `mode` → `pl.current.display_mode` and `live_tune.apply` then dispatches by kind: a name in the mode's `LIVE_PARAMS` (a **scalar** — `dither_strength`, `motion_smoothing`, `auto_fit_strength`) is a `setattr` on a property exactly like the effect/source path; a name in the mode's `LIVE_CHOICES: dict[str, tuple[str, ...]]` (a **discrete choice** — `dither_method`, `cell_strategy`, `color_match`, `palette_mode`) is applied through `mode.set_live_choice(api, name, value)`, where a CC **bucket-selects** across the tuple and a note/pad **cycles** from the current value (`mode.get_live_choice(name)`) — the one thing that stays MIDI's own, because it is a fact about the message kind rather than the target. `palette_mode` is special-cased inside `set_live_choice` because its setter needs the backend handle. The choice tuples equal `[color]`'s `metadata["choices"]` (minus the resolve-time `"auto"`) and a drift test pins them, so the live surface can't diverge from the config surface. `set_color_match`/the `motion_smoothing` setter re-derive the d²-space penalty scale + percell hysteresis (+ `_pal_pairwise`) so a live metric/smoothing change stays self-consistent. An applied param posts a brief OSD message (`Playlist.post_osd` → the current scene's `OsdState`) unless the surface asked it not to, and records the change into `Playlist.live_tracker` (mode targets only — the ones that map to config; see `transport.py` below). The WLED bridge and the web console reach all of this through the same `live_tune.apply`, which is what that module exists for.

**Controller profiles + `classify_message` + `osd.position` (Phase 5).** Three additions let a learned controller profile drop mappings in with zero cc_map edits (see `midi_setup.py` below for the wizard that writes them):

* **`classify_message(msg)`** — the msg → `(kind, number, value, pressed)` normalizer, **factored out of `_dispatch`** (which now just calls it) so the `--midi-setup` learn loop reads a controller *identically* to how the listener will later dispatch it — a learned mapping can't disagree with runtime interpretation. It's the SysEx-MMC / note-on / note-off-or-vel-0 / CC / PC branching, callable standalone.
* **Profile merge** — `resolve_effective_cc_map(base_cc_map, cc_map_is_default, controller_profile, opened_port_name, *, profiles_dir=None)` layers a controller profile onto the config's cc_map and returns a concatenated list fed to the existing later-`(kind,number)`-wins `_parse_cc_map` (so concatenation order **is** precedence). Precedence is **shipped-defaults < profile < explicit cc_map**: when `cc_map_is_default` (the user authored no cc_map — `config.MidiControlCfg.cc_map_is_default`, set False whenever any TOML layer specifies `cc_map`), the order is `defaults + profile` so a profile can **reclaim** the default note/CC numbers; when a cc_map *is* authored, it's `profile + user_list` so the user's entries win and the defaults aren't re-injected (`cc_map = []` still disables everything the profile doesn't map). `_load_profile_mappings` resolves `controller_profile`: `"off"` → none, `"auto"` → `_find_profile_for_port` (scan `paths.controllers_dir()` for the profile whose learned port name case-insensitively substring-matches the opened port, most-specific wins), `"<name>"` → the `<name>.json` profile. **Resolution happens in `MidiControlListener.start()` after `_open_port`** (not in `__init__`), because the `"auto"` match needs the resolved port name — `__init__` stashes the raw base cc_map + `cc_map_is_default` + `controller_profile`, parses the base as a usable fallback, and `start()` re-parses the effective list once the port is known; a malformed profile is caught and the base mapping kept (a bad profile file can never take down the listener). `build_midi_control_listener` threads `cfg.cc_map_is_default`/`cfg.controller_profile` through.
* **`osd.position` action** — a press-only cc_map action (added to `_ACTIONS` here + `_MIDI_ACTION_CHOICES` in config, drift-pinned): a tap flips the OSD corner, a double-tap within `_OSD_DOUBLE_TAP_S` (0.4 s, tracked per-playlist in `_osd_last_tap` on the listener) hides it, a tap while hidden re-enables it. It's dispatched directly on the reader thread (OsdState attrs are thread-safe simple writes) through `Playlist.cycle_osd(double_tap=...)`, which mutates `pl.current.osd`.

**`clip_launch` action (Live DJ/VJ Phase 2).** A note/PC/pad → clip `slot` action (in `_ACTIONS` + `_MIDI_ACTION_CHOICES`, drift-pinned) that — like `transport.*`/`loop_slot` — mutates nothing on the reader thread: `_apply` builds a `performance.ClipEvent(slot, pressed)` and calls `pl.performance.enqueue(...)`, drained on the playlist thread. It's **release-aware** (`_RELEASE_AWARE_ACTIONS`) so a gate note-off reaches the engine. `slot` is validated `>= 1` in `_parse_cc_map` alongside `loop_slot`. `start()` also calls `_add_clip_pad_mappings()` to fold each clip's own `pad`/`pad_type` (from `pl.performance.clip_pad_mappings()`) into the effective mapping as `clip_launch` entries, so a clip fires from its declared note/PC with no separate cc_map line (an explicit entry on the same `(kind, number)` wins). See [`performance.py`](#performancepy--clip-launch-grid-live-djvj-phase-2).

#### `fx_toggle` + the `fx<N>` target grammar (Live DJ/VJ Phase 3)

Two additions let a controller drive the **per-scene effect chain** (`scene.effects`, see [`effects.py`](scenes.md#effectspy--the-frameeffect-registry)) live — bypass a layer, and sweep a specific layer's params — without a scene rebuild:

* **`fx_toggle` action** (in `_ACTIONS` + `_MIDI_ACTION_CHOICES`, drift-pinned). `slot = N` (0-based effect-layer index, validated `>= 0` in `_parse_cc_map` + `validate_midi_control_cfg`). `_apply` → `_toggle_effect_layer(pl, N)` flips `scene.effects[N].enabled` — a plain GIL-atomic bool write, so it runs **directly on the reader thread** with no transport queue (like `osd.position`/`tempo_tap`; no scene mutation, no DMA). It's a **latched toggle** (each press flips; press-only, *not* in `_RELEASE_AWARE_ACTIONS`). An out-of-range slot or a scene with no chain is a silent no-op; it posts the same brief OSD (`fx0 bypass`) the param path posts.
* **Layer-addressed `param` targets.** A `param` target's holder segment may be `fx<N>` or `effect[<N>]` (0-based) in addition to the fixed `effect`/`source`/`scene`/`mode`. `live_tune.resolve_holder` parses it (`_FX_LAYER_HOLDER_RE`) and returns `scene.effects[N]` (or None out of range); the plain `effect` holder still falls through to `getattr(scene, "effect")`, i.e. the back-compat property → `effects[0]`. So `effect.decay` addresses the first layer (unchanged), `fx2.duty` addresses the third. `config._is_valid_param_holder` validates the same grammar at load time (kept mirrored, config stays import-light). This is also how the web console's effect rack addresses a layer: `PerfBridge.fx_param` composes `fx<N>.<param>` and hands it to the same resolver rather than walking `scene.effects` itself. `MirrorEffect` is the first effect to declare `LIVE_CHOICES` (`axis`), reusing the choice branch (a note cycles, a CC buckets) with no new dispatch code.

**`mod_source` (audio-vs-clock tempo lock).** Not a MIDI action — a per-scene config field (`[[scenes]].mod_source`, applied to every layer in `build_scene`) selecting which `MusicModulation` feeder a reactive layer reads: `"audio"` (the scene's own feature stream — the SID host-emulator, or the [live-input analyzer](audio.md#audio_featurespy--audio-input-music-features-reactive-visuals-from-live-input) on a `mic` source), `"clock"` (the Phase-1 `TempoClock`, via `Playlist.safe_setup` stamping `scene.clock_modulation = ClockModulationSource(pl.tempo)`), or `"off"`. Resolved per-layer in `scenes._apply_effect_chain` → `_effect_modulation`. This is what makes a `strobe` (or any reactive effect) lock to MIDI/tap tempo on a non-SID scene — the "synced to audio OR quantized via MIDI" requirement — with no new effect code. See the [effect-chain note in `scenes.md`](scenes.md#the-layerable-chain-live-djvj-phase-3).

#### Grid-controller LED feedback (Live DJ/VJ Phase 4)

The no-OSD constraint (the C64 output is audience-facing) leaves the performer with no on-screen readout of clip/effect state. Phase 4 fills that gap with **controller LEDs**: `midi_control`, otherwise an input-only surface, opens a **MIDI OUTPUT** port and lights the grid's pads.

**How a pad is lit.** A grid controller colors a pad by receiving a `note_on` at the pad's own note number, with the **velocity** selecting the color. That velocity→color convention is a property of the *controller*, not the show, so it lives in the learned controller profile's optional `feedback` block (written by `--midi-setup`), read back by `FeedbackMap.from_dict` and falling back to shipped Launchpad-X programmer-mode palette defaults (off / dim-gray / yellow / green / blue). `FeedbackMap` also carries the 0-based `channel` LED note-ons go out on.

> **Controller compatibility.** The note-on-velocity color convention is what **Novation Launchpad, Akai APC / MPC, and Ableton Push** use — those are the supported grids. It is **not** universal: **Arturia** controllers (BeatStep / BeatStep Pro, KeyLab) drive their pad LEDs over proprietary SysEx, not note-on velocity, and some (KeyLab mkII in user mode) accept no external LED control at all — so Phase 4 lights nothing on them (confirmed on a BeatStep Pro: the pads ignore the note-ons, and their color SysEx is undocumented). For a controller without note-on LEDs, the Phase-5 web/phone console is the intended off-screen feedback surface. A SysEx feedback backend could be added later behind a `feedback_protocol` selector if a specific controller warrants it.

**The states** (`compute_pad_leds`, a pure `state → {note: velocity}` function, unit-tested with no mido/threads): a clip pad is `active` (bright) when its slot is the live clip, `armed` (blinked) while arming, else `loaded` (dim); an fx-toggle pad is `fx_on` when its layer is enabled (not bypassed), else `off`. **Blink is host-side** — the feedback thread alternates the armed pad between the `armed` color and `off` on `_LED_BLINK_HALF_PERIOD_S`, so it needs no controller-specific pulse/flash channel and works on any grid.

**The loop.** `_setup_feedback` (called from `start()` after the mapping + clip-pad folds are final) resolves the profile `FeedbackMap`, builds the managed-pad lists (`_build_led_pad_lists`: each clip's **note** `pad` — first-wins by note, PC/CC/MMC pads can't be lit — plus every `fx_toggle` note mapping), and opens the output (`_open_output_port`: `feedback_port` → the profile's own `port` → the input device's name → first output; a missing/unopenable output disables feedback, warned not fatal). A daemon `_feedback_reader` thread then polls at `_LED_POLL_INTERVAL_S` (20 Hz): `_compute_led_map` snapshots every playlist's `active_slot`/`armed_slot` + current scene's enabled effect layers (GIL-atomic reads, the same never-lock/never-DMA rule the rest of the module follows), and `_emit_led_diff` sends `note_on` **only for pads whose velocity changed** (a static state is silent after the first paint; the armed blink is ~2 msgs/pad/sec). `_extinguish_all` (the reader thread's `finally`, which runs before `stop()` closes the port — `stop()` sets the stop flag, joins the thread, *then* closes) turns every managed pad off so the controller doesn't strand lit pads after shutdown.

**Config + wiring.** `[performance].midi_feedback` (bool) enables it and `[performance].feedback_port` picks the output device (both validated in `_validate_performance`, cascaded like `clock_port`); `build_midi_control_listener` threads `cfgs[0].performance.{midi_feedback,feedback_port}` through (identical across systems in ensemble mode — the LED-out port is process-wide, like the clock). `ControllerProfileStore` gains `.feedback()` (tolerant read of the `feedback` block) and `save(..., feedback=...)`; the `--midi-setup` wizard's grid/LED pass (`_learn_feedback` + the pure `build_feedback_block` helper) records the OUT port + optional per-state velocity overrides into it, preserving any existing block on skip. **Ensemble note:** clip/fx pads carry no channel (a pad maps once, first-system-wins), and enabled-layer state is unioned across playlists — exact for the common single-system performance, and a documented merge otherwise.

**Clock fast path + `tempo_tap` (Live DJ/VJ Phase 1).** MIDI real-time bytes — `clock` (`0xF8`), `start`/`continue`/`stop`, and `songpos` (`0xF2`) — are handled by `_feed_tempo(msg)`, called at the very top of `_dispatch` *before* `classify_message`. `classify_message` returns `None` for all of these (they're not mappable actions), so `_feed_tempo` short-circuits: it forwards the message to **every** playlist's `pl.tempo.feed_message()` (real-time bytes carry no channel, so an ensemble stays phase-locked to one DAW) and returns True to skip the mapping lookup. These are in-memory GIL-cheap writes on the reader thread — the same never-touch-DMA rule the rest of the module follows; 24 PPQN @ 200 BPM is only ~80 msg/s. A new **`tempo_tap`** press-only action (in `_ACTIONS` + `_MIDI_ACTION_CHOICES`, drift-pinned) calls `pl.tempo.tap()` for internal tap-tempo. When the external clock arrives on a *different* port than the control surface, `[performance].clock_port` opens a **second** input with its own `_clock_reader` thread that only calls `_feed_tempo` (mido opens are exclusive, so a clock_port that resolves to the already-open control port is a logged no-op — clock rides the control port anyway). `build_midi_control_listener` threads `clock_port` through from `cfgs[0].performance.clock_port`.

## `live_tune.py` — the one live-tune seam (Live DJ/VJ Phase 7)

Four control surfaces turn the same knobs, and until this module they resolved them three different ways: `midi_control._apply_param` scaled a 0..127 CC, `wled_device._set_live_param` scaled a 0..255 slider, and `perf_console.fx_param` walked `scene.effects` itself for the browser's rack. Two of the three carried a comment saying they were kept mirrored **by hand**. Adding the web console's tune panel would have made a fourth copy, and the browser is the caller most likely to grow new target kinds — so the copy was deleted before it was made.

**What the module owns** is everything a target string means: `resolve_holder` (the `scene` / `mode` / `fx<N>` / `effect[<N>]` / plain-attribute grammar, mirrored at load time by `config._is_valid_param_holder` so `config` stays import-light), `resolve` / `resolve_first` (does this holder's *class* declare that name in `LIVE_PARAMS` or `LIVE_CHOICES`), the range mapping, and the two behaviors that ride along.

**What the callers keep** is only what a value *means* to them, carried in a `Move`: a `position` out of a `full_scale` (127 for a CC, 255 for a WLED slider, 1.0 for an already-normalized web slider), a real `value` (a number, or a choice by name — what a browser sends), or `cycle` for a momentary trigger that has no position at all. That last one is why the MIDI surface still has a line of its own: a CC is a *position* and so buckets across a choice list, while a note or program change is a *press* and so steps to the next choice. Everything else about a MIDI knob turn is now the same code as a WLED slider drag.

Two behaviors belong here rather than in any caller, and having them in one place is most of the point:

* **The OSD line is the surface's decision, not the target's** (`Move.osd`). A controller wants the C64 to confirm what it just changed; the web console must not, because that surface exists precisely so a performer has a readout the audience does not see. Splitting it per-surface is what let `perf_console` stop being a separate write path.
* **The tracker entry is free.** `mode.<name>` targets are the live face of config fields — `[color]` for the ones a whole show shares, a scene's own `[[scenes]]` block for `palette_mode` — so a change to one records into `pl.live_tracker` (along with the current scene's `cfg_index`, since not every home is global), which a CLI run's exit offers to write back (see `transport.py`). Every surface that reaches a `mode.` target through this module gets that by construction rather than by remembering to call it, which is the concrete payoff for routing the browser here instead of giving it its own lookup. `serve.py` still tears sessions down with `save_live_tune=False` — a daemon has no terminal to prompt on and must not rewrite show files on every stop — so the CLI's exit flow never runs there; what acts on the entry under `--serve` is the console's own save-back ([above](#save-back-under---serve)), which was a one-place change precisely because every surface already came through here.

Effect / source / scene params are deliberately **not** tracked: they are transient runtime state, and recording them would write knob positions into a show file.

Everything is a plain attribute write on an object the render loop reads next frame — GIL-atomic, no DMA, no lock — so it is safe from a MIDI reader thread, an HTTP worker or the WLED listener alike. A target that does not resolve (no scene, no such holder, nothing declared) is a **silent no-op returning False**, because every caller is a control surface where the alternative is an exception on a thread nobody is watching, and because a scene can change between the frame that offered a control and the tap on it.

**Verify.** `tests/test_live_tune.py` covers the module directly — every holder prefix, scalar-by-position and scalar-by-value, choice by name / by position / by cycle, the OSD split, and the rule that only `mode.` reaches the tracker — against a fake exposing exactly the three things the module touches (`current`, `post_osd`, `live_tracker`), which is itself a measure of how small the seam is. The three callers keep their own tests (`test_live_tune.py`'s MIDI holder cases, `test_wled_device.py`, `test_perf_console.py`), so the extraction is pinned from both ends.

## `tempo.py` — process-wide musical beat grid (Live DJ/VJ Phase 1)

The tempo foundation the whole Live DJ/VJ arc consumes: **one beat grid, many consumers** (launch quantization, effect tempo-lock, WLED — all later phases). `Playlist` constructs one `TempoClock` per system as `pl.tempo` (mirrors `pl.transport` / `pl.live_tracker`; always present so consumers read it unguarded), built from `[performance]` via `build_tempo_clock()`. Kept **stdlib-only** (plus the leaf `modulation.py`), so it imports nowhere near mido or the render deps and a generator can read a `MusicModulation` from it without pulling them in.

**`TempoClock`.** Three drive modes behind one phase model:

* **External MIDI clock** (`tempo_source = "midi"`): the `midi_control` reader feeds `clock_pulse` / `start` / `continue_` / `stop` / `song_position`. `beat_phase` (accumulated quarter notes) advances **exactly `1/PPQN` per `0xF8` pulse** (`PPQN = 24`), so it tracks the DAW precisely and a jittery inter-pulse interval never causes a phase discontinuity (the jitter-immunity rationale of `MusicModulation.beat_phase`). `bpm` is an EMA of `60/(PPQN·dt)` per pulse. `song_position` decodes SPP's sixteenth-note unit to quarters (`spp/4`, so SPP 16 == one bar of 4/4). The grid starts on the first pulse even with no preceding Start (free-running clock sources).
* **Internal / tap** (`tempo_source = "internal"`, the default): free-runs at the static `[performance].bpm` from construction; a `tempo_tap` pad feeds `tap()`, which averages the recent inter-tap intervals into a live BPM and re-anchors the downbeat to the tapped instant.
* **Live audio** (`tempo_source = "audio"`): the beat the **live-input analyzer** already detects drives the grid. The audio-input analyzer ([`audio_features.py`](audio.md#audio_featurespy--audio-input-music-features-reactive-visuals-from-live-input)) runs a full `modulation.TempoEstimator` over spectral-flux onsets on an `audio_source = "mic"`/`"listen"` scene; `Playlist.run_one_frame` reads that scene's `features().bpm` each frame and forwards it into `pl.tempo.audio_drive(bpm, now)` (`_drive_tempo_from_audio`, gated by the `_tempo_audio_drive` flag). `audio_drive` takes **only the BPM** and integrates the grid's own phase from it — re-anchoring `_base_time` each call so the phase stays continuous across a tempo change, exactly like internal-mode advance — so `beat_phase` is monotonic and jitter-immune regardless of scene changes, and matches the MIDI/internal grid's contract (rate-locked, free phase; not phase-aligned to individual onsets, which `TempoEstimator` never was). `bpm <= 0` (analyzer unlocked, or the input went silent) freezes the phase and holds the grid stopped, so a scene with no feature stream never grows a phantom tempo. This is what lets a detected acoustic/line beat drive launch quantization, `mod_source = "clock"` effects, and WLED tempo with no MIDI clock or tap.

Phase is `phase(now) = _phase_base + (now − _base_time)·bpm/60` while running. Each external pulse snaps `_phase_base` forward exactly and re-anchors `_base_time`; between pulses the extrapolation is **capped at one pulse's worth** (`1/PPQN`) so the phase can't run ahead of a late clock byte and then jerk backward when it lands. Internal/tap/audio mode has no pulses, so the extrapolation *is* the advance, uncapped. `bar_phase` is `beat_phase / beats_per_bar` (accumulated bars — a launch quantizer watches `floor(bar_phase)` tick). All state lives behind a small `Lock` (the reads extrapolate several fields together); every method is cheap memory work, never DMA. `feed_message(msg)` is the mido bridge — duck-typed on `msg.type`/`msg.pos`, returns whether it consumed a clock message. The MIDI/internal drive modes start running immediately (internal) or on the first pulse (midi); audio mode waits for the first `audio_drive` with `bpm > 0`.

**`ClockModulationSource`** wraps a `TempoClock` as a `MusicModulation` feeder (the `mod_source = "clock"` selector of Phases 3/6 — no new effect wiring): `beat_phase`/`bpm` pass through, and `level`/`onset` are a pure function of the beat phase (an onset envelope that peaks on each beat and decays over `_ONSET_WINDOW_BEATS`), so a byte-stable render stays deterministic. Voices report silent. Phase 1 builds and unit-tests it but wires no visible consumer yet.

**Config** (`[performance]`, `PerformanceCfg`: `tempo_source` / `bpm` / `beats_per_bar` / `clock_port`) is a per-system scalar section cascaded like `[color]`/`[menu]` (in `_CASCADE_SECTIONS` + `_TOML_SCALAR_SECTIONS` + `introspect._SECTIONS`), validated by `_validate_performance` at load time. It's cascaded rather than process-wide because each `Playlist` owns its clock; in an ensemble every clock is fed the same broadcast clock, so they stay in sync, and `cfgs[0].performance.clock_port` (identical across systems after the cascade) resolves the listener's clock port.

**Verify.** `scripts/diags/tempo_clock_drive.py` streams clock over a virtual `mido` output for a HW/integration check and self-verifies against a local `TempoClock` offline (`--verify`). The exact tap-tempo / SPP / pulse-phase math — and the audio-drive lock/continuity/freeze behavior — is pinned deterministically in `tests/test_tempo.py` (synthetic evenly-spaced timestamps, no mido); the playlist bridge (`_tempo_audio_drive` flag, `_drive_tempo_from_audio` forwarding a fake scene's BPM) in `tests/test_playlist.py`.

## `performance.py` — clip-launch grid (Live DJ/VJ Phase 2)

The "video sampler" core: fire scenes from pads, **quantized to `pl.tempo`**, across every scene type — the thing the plain `midi_control` surface deliberately excludes, because a scene-*type* change costs real network/DMA setup. `PerformanceSession` hides that cost behind the bar count-in. `Playlist` constructs one as `pl.performance` (mirrors `pl.transport`/`pl.tempo`; always present, so an empty grid is a cheap no-op), built from `[[performance.clips]]`. Kept **stdlib-only** (`Playlist`/`Scene` under `TYPE_CHECKING`; the scene builder is injected) so playlist.py imports it without a cycle — the transport.py rule.

**The single rule that shapes it:** the MIDI reader thread only ever `enqueue`s a `ClipEvent`; **all scene mutation runs on the playlist thread**. That thread drains the queue in `service(pl)`, called at the **top of `Playlist._advance`** once per frame — `service` returns True when performance owns `pl.current` (an active clip), and `_advance` then suspends the normal playlist walk for that frame. The swap is done here (in `_advance`, before `run_one_frame` re-reads `pl.current`) and **never** inside `run_one_frame`/a tick — doing it there would render the just-torn-down scene held in that frame's local.

**Lifecycle.**

* **Arm** — a pad press arms the slot and spawns a **background build thread** (`pl.build_performance_scene(clip)` → `config.build_scene`), so decoder/URL-resolve cost overlaps the count-in. A `threading.Event` (`built`) hands the constructed scene back to the playlist thread. A second press supersedes a pending arm (`_cancel_arm` best-effort tears down a built-but-never-activated scene — it was constructed, never `setup`).
* **Quantized swap** — once built *and* the `quantize` boundary arrives (`_boundary_reached`: `off` = at once, `beat`/`bar` = when `floor(beat_phase|bar_phase)` crosses past the arm anchor; a **stopped clock also fires at once** so a pad always works), `_activate` calls `Playlist.perf_swap_scene` — the single-scene hot-swap generalized from `_apply_reload` (`safe_teardown` current + `safe_setup` armed, honoring the ensemble audio claim, all on the playlist thread).
* **Launch semantics** — `trigger` plays through / loops; `gate` (momentary — the note-release the `_RELEASE_AWARE_ACTIONS` path delivers) plays while held and restores the interrupted program on release; `toggle` latches on/off. `_progress_active` re-swaps the **same** Scene instance to loop (works for every type — video re-opens, waveform restarts the SID), or `_end_active` restores.
* **Return target** — a one-level `_Return`: a launch remembers whether it interrupted a **playlist scene** (by index — its Scene object is reused, so restoring is a cheap re-setup, not a rebuild) or a **prior clip** (by dict — rebuilt via the factory, a brief gap; a restored clip's own return collapses to the playlist base, bounding the chain). This is what makes "gate a stab over a running loop → release → back to the loop" work. The deferred **pre-warmed A/B decks** enhancement is what would remove the rebuild gap.

**No on-screen feedback** (the C64 output is audience-facing): armed/active/count-in state is exposed via `active_slot`/`armed_slot`/`clip_pad_mappings` for controller LEDs (Phase 4) and the web console (Phase 5), never `post_osd` to the screen.

**Looks — snapshot / recall (Live DJ/VJ Phase 6).** A *look* is the current **active clip + the on-screen scene's effect-chain state** (per-layer `enabled` bypass, `mod_source`, `LIVE_PARAMS` values, and any `LIVE_CHOICES` selection). `_snapshot_effects`/`_apply_effects_state` are pure module helpers over `scene.effects`; `LookStore` persists a `{"clip": <slot|null>, "effects": [...]}` map to `paths.presets_dir()/looks-<slug>.json` — a `transport.JsonSlotStore` subclass (see the transport notes below), so the tolerant-load / atomic-write contract (id 0 never stored, corrupt file → empty) is shared with `wled_device.PresetStore` rather than cloned from it. `default_look_store(name)` wires one per system into `PerformanceSession`; the `look_save`/`look_recall` MIDI actions (and the web console's `look` command) `enqueue_look(slot, save=...)` onto a **second SimpleQueue**, drained on the playlist thread in `service` — so the store read/write and the scene reads/writes all happen there, never on a control thread. A **recall that captured a clip** re-arms it and stashes `_pending_look_effects`, which `_activate` applies once the swap lands (matching by layer index, so a look recalled onto a differently-built chain skips what it lacks); a look with no clip applies its effect state to `pl.current` straight away. `_pending_look_effects` is cleared in `_arm`/`_cancel_arm`/`_reconcile`/the build-error path so a stale look can never bleed onto an unrelated later launch. `saved_look_slots()` surfaces the populated slots for LED/web feedback.

**Config + dispatch.** `[[performance.clips]]` is a `PerformanceCfg.clips` list-of-plain-dicts (the `[[color.hue_corrections]]`/`[[scenes.overlays]]` pattern — round-trips through `config_serialize` and the schema stays a loose array), validated by `config._validate_clips` (unique `slot`, choice-checked `launch`/`quantize`/`pad_type`, in-range `pad`, real scene `type`, unknown-key difflib). `config.clip_scene_cfg(clip)` strips the launch/pad keys and builds a `SceneCfg` from the rest via `_apply_section` — so a clip inherits every `[[scenes]]` knob for free (a looping continuous-frame clip is pinned to `duration_s = 0` / run-forever; video/audio clips re-setup on end instead). The `clip_launch` action (`midi_control._ACTIONS` + `config._MIDI_ACTION_CHOICES`, drift-pinned) carries a `slot` like `loop_slot`; the listener also **auto-folds** each clip's own `pad`/`pad_type` into the effective cc_map (`_add_clip_pad_mappings`, explicit entries win) so a clip fires from its declared note/PC with no separate mapping line. The build factory is injected in `session.build_stack`, closing over the stack's api/audio/source/cfg (mirrors the ensemble `build_follower_scene` wiring).

**Verify.** The launch state machine (quantize boundaries, gate/toggle/trigger, loop, prior-clip return) is pinned in `tests/test_performance.py` against a fake playlist with a hand-controlled beat grid; the `clip_launch` dispatch + pad auto-mapping through the real-`mido` listener path. `c64cast/examples/performance-clips.toml` is an asset-free (generative/blank) HW-runnable demo.

## `perf_console.py` — phone / web performance console (Live DJ/VJ Phase 5)

The other off-screen feedback surface the no-OSD constraint calls for (the C64 output is audience-facing): a phone-friendly touch page — clip grid, effect rack, tune panel, tempo readout + tap, transport, scene jump and looks — served by the **control plane** itself, not a separate server. `control_plane.build_app` always registers the Phase-5 routes at the end (`from .perf_console import PerfBridge, register_perf_routes`), so whenever `[control] enabled = true` the console is reachable at `GET /perf` on the same host:port as `/status`. It's the intended feedback surface for controllers that **can't** light their pads (Arturia / SysEx-only grids — the Phase-4 compatibility note), and it works from any phone browser with no app.

**Same engine as the MIDI surface — a web launch and a pad launch are indistinguishable downstream:**

* **Clip launch** → `PerfBridge.launch` enqueues a `performance.ClipEvent(slot, pressed)` onto `pl.performance` (drained on the playlist thread). The page sends `pressed=true` on `pointerdown` and `pressed=false` on `pointerup`/`pointercancel`, so **gate** (hold-to-play) and **toggle** work by touch and **trigger** simply ignores the release — no per-launch-type UI branching.
* **Tap tempo** → `pl.tempo.tap()`; **effect bypass** → a GIL-atomic `scene.effects[i].enabled` flip.
* **Live tune** → `PerfBridge.live(system, target, norm=…| value=…)` through `live_tune.apply`, the one seam the MIDI surface and the WLED bridge also come through. A slider sends `norm` (0..1), a picker sends `value` (a choice by name — a choice list has no meaningful position), and the key says which. A `mode.*` knob turned in a browser records into `pl.live_tracker` exactly as a MIDI knob's would, and the console's own save-back is what writes it (see ["Save-back under `--serve`"](#save-back-under---serve)). **No `post_osd`** anywhere on this surface — performance feedback stays off the audience screen — which `live_tune` carries as `Move.osd` rather than as a separate write path.
* **Transport + jump** → `PerfBridge.transport(system, "pause"|"resume"|"skip")` sets the playlist's own `pause_event`/`resume_event`/`skip_event`, the same events the C64's keys and a MIDI transport button set, so the run loop applies them at its next clean boundary; `PerfBridge.jump(system, index)` calls `request_jump(skip_interstitial=True)`. The jump is a **cut** on purpose: a console jump is a correction ("that one, not this one"), and the transition would put a title card in front of the thing being corrected to. `resume` on a show that is not paused is harmless (the event is simply never consumed), so unlike `/resume` there is no 409 here — the state feed carries `paused`, and the console renders one button that says what it will do.

**DJ transport (Phase 7): freeze-in-place, scrub, rw/ff, A/B loop.** The rest of `TRANSPORT_VERBS` (`freeze`/`unfreeze`/`rw`/`ff`/`seek`/`loop_toggle`/`loop_slot`) reaches a different engine than `pause`/`resume`/`skip` above: instead of the playlist's own events (a machine-level halt), each enqueues a `transport.TransportEvent` onto `pl.transport` — the same `TransportSession` queue the MIDI transport surface has driven since Phase 2, drained on the playlist thread once per frame via the current scene's duck-typed `transport_*` methods (`VideoScene`/`VideoTransportControls`). A web pause used to *stop the show*; freeze pauses the picture in place and mutes the audio, which is what a performer actually wants mid-set. `freeze`/`unfreeze` are guarded against the scene's own `transport_is_paused()` rather than sent as a bare toggle, so two open consoles (or a retried request) can't fight over which way a plain `play_pause` flips. `seek` carries an absolute `target` in content-seconds — a scrub bar's drag target — in a different domain from the MIDI `jog` action's 0..127 controller reading; `loop_slot` carries explicit `save`/`clear` booleans instead of relying on the MIDI surface's Stop/Record-held chord timing, since a touch console has no "hold Stop" gesture. `_transport_dict` (folded into `_system_state`'s `transport` key) is `None` for a scene that declares no transport surface (a generator, a picture, a scope) — the console renders no transport bar rather than one that writes nowhere.

**The live color/palette picker is `border`/`background` as ordinary `mode.*` live-tune targets.** `BlankDisplayMode.LIVE_CHOICES` declares them against the full sixteen-name palette (`palette.C64_COLORS`), so `introspect.live_targets()` — the same registry the Tune panel already renders from — picks them up with no new plumbing; the only registry-visible change is `LiveTargetDoc.vocabulary` (mirroring `FieldDoc.vocabulary`), set to `"c64color"` for exactly these two so a console renders swatches (`ColorSwatches.svelte`) instead of a `<select>`. Unlike every other choice, $D020/$D021 are VIC registers a mode only pokes once at `setup()` — `compose()`/`push()` re-derive color RAM every frame regardless, but the border and background registers do not — so `BlankDisplayMode.set_border`/`set_background` are two of the small set of choices in `_CHOICES_NEEDING_API` that get the backend handle to repaint live, alongside `palette_mode`. The config home is a `[[scenes]]` block, not `[color]` (a border is a per-scene kwarg like `palette_mode`, not a show-wide knob), so `transport._MODE_FIELD_TO_SCENE` carries both — the save-back writes the block of whichever scene was playing when the color was picked.

**Looks (Phase 6).** The console also drives the look snapshot/recall engine: `PerfBridge.look(system, slot, save)` enqueues a `performance.LookEvent` exactly as the `look_save`/`look_recall` MIDI actions do, `apply` dispatches an `{action: "look", slot, save}` command, and `_system_state` adds a `looks: [slot, …]` list of populated slots (from `PerformanceSession.saved_look_slots()`). The page renders a small Looks pad row — tap recalls, a **SAVE** toggle arms save-instead-of-recall — with saved slots lit. So a phone can capture and re-fire a full clip+effect "look" with no controller.

**State + transport.** `GET /perf/state` (and the `WS /perf/ws` push) return `{multi, systems:[{name, current_scene, scene_index, paused, scenes[], tempo, active_slot, armed, clips[], effects[], live[], tuned{}, looks[], transport}]}` — one entry per system (ensemble order; a single-system run is one entry, the page hides the system tabs). `armed` carries the count-in (`beats_remaining` to the quantize boundary, computed from `pl.performance.armed_detail` against `pl.tempo` in `_beats_remaining`). Commands go out as `POST /perf/command` (`{action: launch|tap|fx|live|transport|jump|look, …}`, dispatched by `PerfBridge.apply`); the WS is push-only from the server on a fixed `_PUSH_INTERVAL_S` (~0.35 s) cadence and the client **extrapolates the beat pulse locally** (bpm + last `beat_phase` + wall-clock elapsed) so the beat dots animate smoothly without a round-trip per beat. New read-only accessors on `PerformanceSession` (`clips_info()`, `armed_detail`) surface the grid + count-in without the console reaching into private state.

**Two generated control lists, and neither can drift.** The effect rack rows come from each **live layer's own class `LIVE_PARAMS`**. `live[]` comes from `introspect.live_targets()` — the same 29-target catalog the `--midi-setup` picker offers, cached at module level because it describes the registries rather than the run and building it pulls numpy/cv2 in through the mode and generator modules — **filtered to what the current scene actually resolves**. That filter is the design: a blank scene has no generator and a PETSCII scene has no dither, and a rendered control that writes nowhere is worse than an absent one. It also means the panel changes shape as the show advances, which is why the client keys rows by target and holds a slider's position under the finger. The per-layer effect knobs are *not* in `live[]` — those are addressed by layer (`fx2.amount`) and have the rack, where bypass lives too. `scenes[]` is `scene_rows(pl)`, shared with the control plane's `/scenes` so the two answers about what is playing cannot disagree. `tuned{}` is the other side of `live[]` — not what can be turned but what *has* been, from the playlist's live-tune tracker; see ["Save-back under `--serve`"](#save-back-under---serve) for why a browser is where that offer gets made.

**Idle behaves differently here than on the control-plane routes.** `PerfBridge` takes the same registry provider (`PerfBridge(lambda: list(playlists().items()))`) and re-reads it per call, but with nothing running it returns an empty `systems` list — a `200`, not the routes' `503` — and every write (`launch`/`tap`/`fx_*`/`live`/`transport`/`jump`/`look`) reports `False` rather than raising on an empty ensemble. Note the difference between *no system* and *no such target*: the first is False (nothing was addressed), the second is True and a no-op (the system was addressed and the scene simply moved on), because a console tap racing a scene change is normal and not an error. The page is the zero-dependency gig-day fallback: it has to stay loadable between shows, and it renders "No session running", clears the pads (a pad left on screen invites a tap that goes nowhere) and freezes the beat pulse instead of free-running a dead grid.

**A state frame that raises closes the socket rather than going quiet.** Both push loops (`perf_ws` and `api_ws`) build the frame inside their own `try`, separate from the socket's lifecycle handling below it. The difference matters because the two failures are not the same kind: a disconnect is normal and is swallowed, while a frame that raises is *our* bug — and swallowing that one leaves every connected console waiting forever for a push that is never coming, which reads exactly like a slow host. This is not hypothetical: growing the frame (`tuned`) past what an out-of-date test fake provided turned a would-be `AttributeError` into a suite that hung instead of failing. Now it logs and closes. Asserting it costs more than it is worth — the assertion needs the server to close an accepted socket, and `TestClient`'s websocket teardown blocks on exactly that — so `tests/test_perf_console.py` records it as checked by hand instead.

**The `_PERF_HTML` page reaches every action the bridge dispatches.** It drew clips, the rack, the tempo and the looks for three phases while `live`, `transport` and `jump` were reachable over `/perf/command` and had no control on the page at all — so the fallback could launch a clip but not skip a scene running long, and the one surface a performer has when the bundle was never built sent them to a keyboard at the machine. It now also draws **Tune** (`live[]`, grouped as `introspect` groups it, sliders for scalars and a picker for choices), **Tuned** (the tracker's record, with the same `scene N` and `runtime only` tags the Svelte console uses, and a Keep that posts to `/api/session/live-tune`), **Scenes** (a jump per scene, current one marked) and **pause/skip** in the tempo bar. That closes the gap rather than widening the page's remit: the Svelte console is still where a control surface *grows*, and this one exists to reach what already exists.

Two things follow from it being hand-written DOM in a Python string. Nothing type-checks the commands it builds, so `tests/test_perf_console.py` reads them back out of the page: the set of `action:` values it can send is compared against the ones `PerfBridge.apply`'s own source dispatches (a bridge action with no control is exactly the gap that was just closed, and a second hand-written list would hide the next one), and its transport verbs against `TRANSPORT_VERBS`. And nothing in CI renders it, so the panels were checked once by hand under jsdom against a canned state frame — every row drawn, every control's outgoing command inspected — which is a thing to redo, not to assume, when the page next grows.

**Save-back is the one control here that can 404, by design.** `/perf` is registered by the control plane, which a plain CLI run has too; the write route is registered by `--serve`. So the page always *lists* what has been tuned — a change about to be lost at the end of the show is what a performer most needs told — and a Keep tap on a one-shot run answers "this run saves at exit, not from here", which is true: that run has a terminal and asks there.

Like `wled_device.py`, this module deliberately **omits** `from __future__ import annotations`: the `WebSocket` route param is annotated with a name imported inside `register_perf_routes`, and stringized annotations would make FastAPI mis-read it as a query param and skip the WebSocket injection. (That's also why the routes live here and not inlined into `control_plane.py`, which *does* use the future import.)

**Verify.** `PerfBridge` state/launch/tap/fx/live/transport/jump + `_beats_remaining` are unit-tested against a fake playlist (`tests/test_perf_console.py`) — including that `live[]` lists exactly what the scene declares and nothing else, that a live write posts no OSD, that `_transport_dict` is `None` for a scene with no transport surface and mirrors one that has it, and that every Phase-7 verb (`freeze`/`unfreeze`'s current-state guard, `rw`/`ff`'s `pressed`, `seek`'s required `target`, `loop_toggle`, `loop_slot`'s explicit `save`/`clear`) enqueues the right `TransportEvent` rather than mutating the fake scene directly; the `/perf` page, `/perf/state`, `/perf/command`, and the `/perf/ws` push are driven end-to-end through the real control-plane app with `TestClient` (skipped when fastapi/httpx is absent, the control-plane test pattern), including the idle case over an empty registry (`PerfIdleTest`). `mode.border`/`mode.background` are exercised through the *real* `BlankDisplayMode` (not a fake mode) in `tests/test_live_tune.py` and `tests/test_blank_mode.py` — the picker's swatches have to land on the actual `$D020`/`$D021` write. HW: the console launches a clip + toggles an effect layer on the U64, matching a MIDI launch (shared engine); freeze/scrub/rw-ff/loop and the border/background picker are HW-checked per the plan's verification note (`hw-visual-verify`).

## `transport.py` — live-tune tracker + save-back (Phase 1) + DJ transport engine (Phase 2) + record workflow + loop presets (Phase 3) + controller profiles (Phase 5)

Phase 1 of the MIDI live-tune feature shipped the pieces that don't need a transport engine; Phase 2 added the transport session (seek / pause-in-place / A/B loop); Phase 3 added the record workflow + loop preset slots; Phase 4 added real audio resync across every splice (`[midi_control].loop_audio`, default `"on"` — see the `VideoScene` transport + `audio.py`/`sampler.py` `flush()` notes; the old mute-and-wall-clock behavior is now `loop_audio = "mute"`). Kept stdlib-only (`Config`/`Playlist` under `TYPE_CHECKING`, so it's cycle-free and importable from `playlist.py` and now `scenes.py`):

- **`atomic_write_text(path, text)`** — the crash-safe "temp file in the same dir, fsync, `os.replace`" write, factored out of `wled_device.PresetStore._write` so the config save-back and the loop-preset store share one implementation.
- **`JsonSlotStore`** — the shared base of the three numbered-slot JSON stores (`wled_device.PresetStore`, `performance.LookStore`, `LoopPresetStore`), extracted once their `load()` implementations had drifted into byte-identical copies. It owns the tolerant load (missing/corrupt/wrong-shaped file → empty map; only well-formed numeric-key → dict entries survive), the range-checked `save`/`delete`, and the atomic `_write` — which now also `mkdir(parents=True)`s the target's parent, a robustness fix that previously only `LookStore` had. Subclasses set `SLOT_MIN`/`SLOT_MAX` and override three hooks: `_unwrap` (where the slot map sits inside the loaded payload), `_envelope` (what wraps it on write), and `_coerce_entry` (per-entry validation/normalization). Only `LoopPresetStore` needs the hooks; the other two are the defaults.
- **`LiveTuneTracker`** — records each `mode.<name>` change as `target → (old, new)`, keeping the *original* `old` across re-tunes and dropping an entry that lands back where it started (so a knob swept back and forth nets to no change). `apply(cfg)` writes the tracked values into the config: `cfg.color` via `_MODE_FIELD_TO_COLOR` (`dither_method → [color].dither`, the rest same-named), or one `cfg.scenes[i]` via `_MODE_FIELD_TO_SCENE` for the knobs a scene owns rather than the show (`palette_mode`). `toml_snippet()` renders a pasteable `[color]` block for a quick-playback run with no file.
- **`TransportEvent` / `TransportSession` (Phase 2, extended Phase 3)** — the queue between the MIDI reader thread and the playlist thread for `transport.*` actions. It mirrors the existing rule that all scene- and DMA-adjacent mutation happens on the playlist thread only.

  `TransportEvent` carries:

  | Field | Meaning |
  | --- | --- |
  | action | Short name (`play_pause`/`stop`/`loop_toggle`/`rw`/`ff`/`jog`/`record`/`loop_slot`) — the cc_map action string with any `transport.` prefix stripped in `midi_control._apply`; plain `loop_slot` has no prefix to strip |
  | `pressed` | Note-on vs note-off; meaningful for the hold-aware `rw`/`ff`/`record`/`stop` |
  | `value` | Raw 0-127, used by `jog` |
  | `mode` | Jog's `abs` / `rel` |
  | `slot` | The pad number for `loop_slot` |

  `TransportSession.enqueue` runs on the MIDI thread and pushes onto a `queue.SimpleQueue`. `tick(pl, now)` runs on the playlist thread, called once per frame from `Playlist.run_one_frame` right after the fade-in step (`SceneFades.advance_fade_in`), drains the queue, and dispatches against `pl.current` via `getattr(..., None)`.

  That dispatch is **duck-typed**, so a scene without the `transport_*` surface is a silent no-op — the same shape as a `LIVE_PARAMS`/`LIVE_CHOICES` target that doesn't exist on the current holder.

  **Immediate actions.** `play_pause`, `loop_toggle`, and `record` dispatch immediately. `stop` does too, but its `bool` return decides whether `pl.stop_event.set()` fires (Phase 3).

  **The hold ramp.** `rw`/`ff` press and release update `_held: dict[str, float]`, mapping action → the wall-time the hold started. These are tracked **regardless of whether a scene is current**, so a hold starting before a scene becomes current still ramps once one does.

  Each `tick()` then applies:

  ```
  speed = min(30.0, 2 ** (elapsed / 0.75))
  ```

  in media-seconds per real second — doubling every 0.75 s of hold, capped at 30×. That times `dt` times ±1 is added to `scene.transport_position()` and passed to `scene.transport_seek()`.

  **Jog.** `"abs"` mode maps `value/127 * (duration or 0)` directly. `"rel"` mode decodes the CC byte as a two's-complement-style relative encoder in `_decode_relative_jog` — `1..63` → +N ticks, `65..127` → −(128−N) ticks, `0` and `64` → no motion, the common Launch Control / APC convention — and moves `ticks * _JOG_SECONDS_PER_TICK` (1.0 s/tick) from the current position.

  **OSD ownership.** OSD posts happen inside the scene's own `transport_*` methods via `pl.post_osd`, *not* inside `TransportSession`. That keeps OSD text ownership with the scene, consistent with Phase 1's `mode.*` pattern.
- **Record workflow + loop preset pads (Phase 3)** — `record` and `stop` are now also hold-tracked (`_record_held_since`/`_stop_held_since: float | None`, separate from the rw/ff ramp's `_held` dict so they aren't swept into the seek ramp) for the `loop_slot` pad chords: `_chord_active(held_since, now)` treats a hold as expired after `_CHORD_HOLD_WINDOW_S` (5.0 s) even with no release — necessary because an MMC-sourced SysEx frame (see `midi_control._dispatch`) always dispatches `pressed=True` with no release equivalent, so without the expiry a single MMC record press would wedge every later pad press as "clear" for the rest of the session. A `loop_slot` press resolves `clear = _chord_active(record_held)`, then (only if not clearing) `save = _chord_active(stop_held)` — Record wins if somehow both are held — and calls `scene.transport_loop_slot(slot, save=save, clear=clear)`. `record`/`stop`'s one-shot press action and their hold-bookkeeping both fire on every press (mirrors rw/ff's "bookkeeping survives no current scene" rule, but these ALSO drive an immediate scene action, so they fall through to the normal dispatch below instead of returning early). `record`/`stop`/`loop_toggle` all mutate the identical `VideoScene._loop_a`/`_loop_b`/`_loop_state` machine (see the `scenes.py` note above) — Record/Stop are just a second, richer entry point into it, not a parallel state, so the red-border feedback and pad-slot persistence apply uniformly regardless of which control armed/closed the loop.
- **`LoopPresetStore` (Phase 3)** — one JSON file per video under `paths.loop_presets_dir()` (the canonical `<data root>/presets/loops/`, `$C64CAST_DATA_DIR`-overridable, resolved at use time — see [`paths.py`](config.md#pathspy); machine-specific captured data, never committed), a `JsonSlotStore` subclass whose envelope hooks nest the slot map under `{"schema", "video", "size", "loops": {...}}` and whose `save(slot, a, b)` takes the loop points directly, skipping the base range check (loop slots are pad numbers with no fixed range; one file per video rather than one file per device holding many numbered presets). `loop_preset_key(filepath)` hashes `basename+":"+size` (`sha1(...)[:12]`) for a local file — path-move tolerant, not content-hash, the same tradeoff `PresetStore` already accepts — or the URL itself for a `"://"`-containing path; `_slugify` + `loop_preset_path` combine that key with a human-readable slug into `<data root>/presets/loops/<slug>.<hash12>.json`; `make_loop_preset_store(filepath)` wires both into a `LoopPresetStore(path, video_ref=..., size=...)`. The stored payload is `{"schema": 1, "video": ..., "size": ..., "loops": {"<slot>": {"a": <float>, "b": <float|null>}}}` — `b: null` means "loop to end of file". `VideoScene.setup()` rebuilds `self._loop_store` on every call (not just `__init__`) since a directory/glob-backed scene picks a different file each loop iteration.
- **`ControllerProfileStore` (Phase 5)** — the `--midi-setup` wizard's output: one JSON file per controller under `paths.controllers_dir()` (the canonical `<data root>/controllers/`, `$C64CAST_DATA_DIR`-overridable, resolved at use time), cloned from `PresetStore`'s tolerant-load / `atomic_write_text` shape but deliberately **not** a `JsonSlotStore` — its payload is a single `{"schema", "port", "mappings": [...]}` document, not numbered slots. `slugify_port(port_name)` makes the filesystem-safe `<port-slug>.json` stem (lower-cased alnum-run collapse — distinct from `_slugify`, which is video-path/URL-oriented); `controller_profile_path` + `make_controller_profile_store` wire it up. The payload is `{"schema": 1, "port": "<full mido port name>", "mappings": [<cc_map dict>, ...]}`; `.port()` / `.mappings()` load tolerantly (missing/corrupt file, or a malformed `mappings` list, → empty — a bad profile contributes nothing rather than crashing a run; each surviving entry is still shape-validated downstream by `_parse_cc_map`/`validate_midi_control_cfg`). The profile-merge resolver (`midi_control.resolve_effective_cc_map`, above) consumes these. **Phase 4** adds an optional `"feedback"` block (the grid-controller LED velocity→color convention + an output `port`) — `save(..., feedback=...)` writes it, `.feedback()` reads it tolerantly (→ `{}`), and `midi_control.FeedbackMap.from_dict` turns it into the runtime velocity map (see the [LED feedback note](#grid-controller-led-feedback-live-djvj-phase-4)).

#### Save-back on exit

`session._maybe_save_live_tune(stacks, overwrite)` runs after `teardown_stack`, so the terminal is free, and sits in `main`'s `finally` so it fires on a normal exit **and** on Ctrl+C:

| Context | Behavior |
| --- | --- |
| `--overwrite` | Silently `apply`s and `Playlist._save_config`s, keeping a `.bak` |
| Interactive terminal | Prints the changes and prompts — a plain `input()`, no wizard extra |
| Headless / non-tty | Prints the changes without saving |
| Quick playback (no config file) | Prints a pasteable TOML snippet |

`pending()` is the same record in structured form — one row per change with `old`, `new`, the config field a save-back would write it to, and the `scene` index saying which part of the file carries that field (`None` for `[color]`). `field` is `None` when nothing carries the change at all: effect and generator knobs are runtime state and never reach the tracker, and a per-scene knob turned on a scene the config never named has no block to be written into (see "Per-scene knobs" below). `describe()` is what a terminal prints; `pending()` is what a browser renders, and `_persistable()`/`apply()`/`toml_snippet()` are all derived from it so the two answers cannot drift.

`_MODE_FIELD_TO_COLOR` and `_MODE_FIELD_TO_SCENE` are the maps behind that `field`, and the first had a hole: `mode.cell_pick` is the live face of `[color] hires_cell_pick`, was offered by every surface, and was missing from the map — so turning it recorded a change every save-back then silently skipped. `MODE_FIELDS_WITH_NO_CONFIG_HOME` is the escape hatch for a target that legitimately has no config field anywhere (empty today — `palette_mode` was its only member until it grew the per-scene home), and a drift test in `tests/test_live_tune.py` walks `introspect.live_targets()` and requires every `mode.*` to be in exactly one map, to map to a field that still exists on the dataclass that map points at, and — for a choice — to offer only values that field accepts. A live knob that can't be saved is a test failure rather than a discovery.

`forget(keys)` is the other half: a surface that has *written* the changes somewhere drops exactly those, which is how the console's save-back withdraws its own offer without discarding a change no config field could hold. A `key` is the target for a global and `target@<scene>` for a per-scene one, which is also what keeps the same knob on two scenes discardable independently.

#### Per-scene knobs

`palette_mode` is the live face of `[[scenes]].palette_mode`, not of anything in `[color]` — so a save-back has to name a block, and the only moment the right block is knowable is the move itself. `scene_factory.scenes_from_config` stamps `Scene.cfg_index` with each scene's position in `cfg.scenes` (counted over the whole list, so an earlier `follower_only` scene — in the file, out of the rotation — doesn't shift the ones after it), `live_tune._record` passes whatever the current scene carries, and `record()` folds it into the key for the per-scene targets only. Three consequences worth stating:

- A `[color]` knob swept across a scene change stays **one** entry. The scene rides in on every record; only a per-scene target may key on it.
- The same per-scene knob turned during two scenes is **two** entries, because it is two settings. Collapsing them would write one scene's palette into both.
- A scene the config never named — a launched clip, an auto-inserted video, the no-scenes fallback — carries `cfg_index = None`, so its palette change is listed as unsavable rather than written into whichever block happens to sit at index 0.

The index is an address into the *file*, which is what both writers re-read before writing: `ConfigStore.patch` loads from disk, and it refuses an index the file has no block for (a 400 that leaves the record intact) rather than clamping it. `apply(cfg)` skips such an index for the same reason — a config reloaded shorter since the knob moved would otherwise get the value written into whichever scene inherited the number.

The store's own guard lands here too, and correctly: `_editable_scene_fields` only allows what the scene's *type* declares, and `palette_mode` is declared by the types that can have an mcm/mhires display mode — which is exactly the set of scenes on which the knob is tunable in the first place.

#### Save-back under `--serve`

There is no exit to prompt at. `serve.teardown` passes `save_live_tune=False` and must — a host that rewrote every show file it stopped would be unusable — so under the daemon the tracker records and the CLI flow above never runs. The browser is where the offer is made instead, on a tap rather than at a shutdown:

- `perf_console._tuned_dict` puts the record on the state feed beside the knobs (`live` is what can be turned; `tuned` is what *has* been), with the count a Save button acts on, the config path there is to write to, and — for a run with no config file — the same pasteable `[color]` block the CLI prints.
- `web_api`'s `POST /api/session/live-tune` (`action: "save" | "discard"`) is the write. It is an HTTP route rather than a performance-socket command because it *writes a config file*: it takes the store's refusals, its 422 report and its backup sibling, and a socket frame has nowhere to put a status code.

**The write goes through `ConfigStore.patch`, not the menu's whole-config dump**, for the same reason the console's form save does: the file is re-read from disk first, so a field edited in the config editor since the show started is still there afterwards, and a patch that would stop the config loading is refused with the file untouched. Every savable row goes into **one** patch — `_live_tune_edit` turns each into a `{"section": "color", …}` or a `{"scene": <i>, …}` edit from the row's own `scene` — so a mixed save is one write, one backup and one refusal rather than two of each. A refused save leaves the tracker intact (the Save button still means what it said) and only a successful one calls `forget`. A successful one also writes the saved fields back onto the run's own `Config` (`_restamp`): the C64 menu's save-back dumps *that* object wholesale, so leaving it stale would let somebody at the machine revert what was just saved from the browser without meaning to. Changes no config field carries are reported back as `kept_out` and left in the record rather than silently dropped, because a change that will be lost when the show ends is exactly the one worth telling a performer about.

#### The OSD

`scenes.OsdState` provides thread-safe `post`/`current`, plus `position` and `enabled`; `_annotate_osd` draws pre-quantization, like `_annotate_frame_number`.

Every frame-bearing scene draws it via `Scene._apply_osd`. `VideoScene` handles it inline so it can bust its identity-skip for one render on an OSD change: a steady frame with a changed OSD triggers one re-quantize, while a steady OSD keeps the skip — preserving the DMA-load rationale.

`[midi_control].osd = bottom|top|off` is stamped onto each scene's `OsdState` in `config.build_scene`.

**Text rendering.** Both `_annotate_osd` and `_annotate_frame_number` render through the shared `_blit_c64_text` compositor, which paints from the real C64 character ROM — `bitmap_text.glyphs_to_mask` over `load_glyphs()`, i.e. the uppercase charset [`char_rom.py`](hardware-io.md#char_rompy--reading-the-character-rom-off-the-machine) resolves (with its builtin-charset fallback) — instead of a Hershey vector font.

The 8×8 glyph cells are integer nearest-neighbor upscaled so the block spans a fixed fraction of frame width (0.55 for frame numbers, 0.85 for OSD), which keeps the authentic blocky pixel edges through the downscale to C64 output. White glyphs over a `cv2.dilate` black halo read on any background.

`bitmap_text.ascii_to_screen_code` special-cases `_` to screen code `0x6F`, the low horizontal-line graphics glyph, instead of the raw-mapping `0x1F` (← arrow). The C64 charset has no true ASCII underscore and `0x6F` is the closest visual match, so identifier text like `auto_fit_strength` reads correctly. This benefits every `ascii_to_screen_code` consumer, not just these overlays.

#### `auto_fit_strength` moved mode-side

To make it a live knob. The scenes install a full-strength `ColorFit` (accumulator `strength=1.0`), and `DisplayMode._fit_for_apply()` lerps it by `_auto_fit_strength` via `ColorFit.lerped` at `apply_color_fit` time.

Lerping at apply time is mathematically equivalent to baking the strength into the accumulator, at every strength — pinned in `test_live_tune.py` — so the move costs no fidelity.

## `midi_setup.py` — the `--midi-setup` MIDI-learn wizard (Phase 5)

`c64cast --midi-setup` (needs the `midi` + `wizard` extras) watches a controller and writes a reusable `transport.ControllerProfileStore` profile, so live control needs no hand-authored cc_map TOML. Mirrors `wizard.py`'s split — **pure helpers** (unit-tested with scripted fake-mido messages) plus a **thin questionary shell** (`run_setup() -> int`, 0 saved / 2 canceled-or-extra-missing) — and, like `--init`, runs *instead of* playback (dispatched config-free from `cli.run_introspection`, guarded on both extras with actionable install hints). The learn loop reads a controller through `midi_control.classify_message`, so a learned mapping matches how the listener will later dispatch it.

#### Pure helpers
`detect_encoder(values)` — relative-encoder detection: a value stream clustering near 0 (1,2,3 = CW) and near 127 (127,126,125 = CCW) with **nothing in the mid-range** is an endless encoder (proposed as a `transport.jog mode="rel"` binding); a swept absolute knob passes through the middle. `dominant_control(events)` picks the `(kind, number)` a learn burst intended (most frequent *pressed* event — a knob emits many CCs, a pad a note-on+off). `values_for` extracts one control's value stream (for encoder detection). `build_transport_entry`/`build_param_entry`/`build_jog_entry`/`build_jump_entry` assemble cc_map dicts (an MMC button classifies as `("mmc", cmd)` → a `type: "mmc"` entry, auto-recognized — no separate step). `dedupe_mappings` is a last-wins dedupe by `(type, number)` mirroring `_parse_cc_map`'s layering, so the review preview matches what the listener resolves. Everything the wizard can build is asserted to pass `validate_midi_control_cfg` + `_parse_cc_map` in the tests.

**Flow** (each step skippable): port pick → transport/OSD-button learn (press-prompted over `_TRANSPORT_BUTTONS`) → knob auto-scan (`_read_burst` collects a settle-windowed burst per knob, deduped by CC, encoder-flagged) → **target picker** driven by `introspect.live_targets()` (the single-source-of-truth grouping of every `LIVE_PARAMS`/`LIVE_CHOICES` across the effect/generator/mode/scope registries — an encoder additionally offers the jog target) → optional scene-jump pads → review table (remove/discard) → **grid/LED-feedback pass** (Phase 4: `_learn_feedback` picks the MIDI-OUT port and, optionally, per-state pad velocities via the pure `build_feedback_block` helper; skipping preserves any existing block on a re-run) → save via `make_controller_profile_store(port_name)` (`store.save(port, mappings, feedback=...)`). `introspect.live_targets()` is drift-tested against those class attrs (same spirit as the `LIVE_CHOICES` ↔ `[color]` metadata pin).
