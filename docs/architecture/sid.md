## `voice_scope.py` — shared 3-voice oscilloscope renderer

`VoiceScopeRenderer` is the SID-source-agnostic hires oscilloscope renderer, factored out of `WaveformScene` so `MidiScene` can reuse it. It's a **mixin** (both `WaveformScene` and `MidiScene` are `class X(VoiceScopeRenderer, Scene)`), so the renderer reaches its host's state as `self._<attr>` and `WaveformScene`'s byte output is the mixin's byte output — its test suite is the regression guard for both scenes. It owns the layout constants (`BITMAP_STRIPS`, `TITLE_ROW`/`META_ROW`, the `D011`/`D016`/`D018` poke values), the VIC hires bring-up (`_apply_vic_hires_bank`, which calls the shared `modes.engage_bitmap_mode` primitive — the SAME clear-then-flip path the Hires/MultiHires display modes use, see the modes/ "Bitmap engage clean-field" note; the scope passes its relocated bank + `write_region` clear IDs as arguments), the glyph + text-row rasterizer (`_paint_text_row`, `_load_glyphs`, `_ascii_to_screen_code`, `_layout_lr`/`_layout_lcr`), the per-voice color helpers, the three render paths (`_render_voice_fast`/`_scroll`/`_echo` → `_render_hires`), and the knob parsing + buffer allocation (`_init_scope_knobs` / `_alloc_scope_buffers`). A host scene satisfies a documented attribute contract (`api`, `emulator`, `_reg_lock`, `_screen_base`/`_bitmap_base`/`_dd00`/`_d018`, …) and supplies its own text-row CONTENT — for MidiScene/AsidScene that means just the two line builders (`_build_title_line`/`_build_meta_line`); the shared `_paint_info_rows` paints both rows in the standard colors/regions (WaveformScene keeps its own two-step painters because its metadata row needs a glyph override). `waveform.py` re-exports the consts that live here, so `from .waveform import …` (config, tests) resolves them too.

## SID player PRG — 6502 player, relocation, and per-call banking

SID playback uses a hand-encoded 6502 player (73 bytes) plus a SHIFT-driven re-INIT stub (35 bytes), both relocated per tune by `_choose_player_layout` in [api.py](../../c64cast/hw/api.py).

### Layout and relocation

Default layout is the player at `$C300` and the stub at `$C400`, used whenever there is no conflict. A SID whose payload would overlap gets a contiguous bundle (`player_base + 80 = stub_base`) placed in the largest footprint-clean RAM hole, falling back to just past or just below the payload.

`_build_basic_sys_stub` builds the BASIC SYS stub's decimal argument dynamically to match the chosen `player_base`.

`$C300` was chosen because [audio_handlers.py](../../c64cast/audio/audio_handlers.py) owns `$C000-$C2FF` for the NMI DAC and REU pump. The relocation picker refuses any layout that would overlap that region.

### Per-call `$01` banking

The player banks `$01` **per call**. `_init_bank_for` / `_play_bank_for` patch the value to `$36` — BASIC ROM banked out, KERNAL and I/O kept — around a `JSR init` or `JSR play` whose entry lives under BASIC ROM (`$A000-$BFFF`, e.g. Hyperion 2 at `$AE2A`). Without that, the call executes ROM instead of the tune's RAM, landing on the ROM SYNTAX-error stub and printing `?SYNTAX ERROR IN 10`.

It then restores `$37`, the resting default. Tunes like Comic Bakery that read BASIC ROM *as data* need it mapped between calls.

Restoring per call, rather than setting `$36` once and leaving it, is what keeps tunes like Election alive: they assume the `$37` resting environment between PLAY calls and crash without it.

### Runtime behavior

The real 6510 calls INIT once, and PLAY at IRQ time. The IRQ handler chains to kernal `$EA31`, so keyboard scan (`$028D`) and cursor-blink suppression both survive.

After installing the IRQ vector the player **spins forever** (`JMP *`) rather than RTSing back to BASIC. INIT routinely clobbers BASIC zero-page state, so a return would print a syntax error on the next interpreter step.

### What is refused

PSID only. Rejected: RSIDs, SIDs whose `load_addr` < `$0820`, SIDs whose `play_addr` is zero, and SIDs under KERNAL ROM (`$E000-$FFFF`).

The PAL/NTSC speed flag is **read**, per subtune, and drives the CIA #1 Timer A retune — see [System timing — PAL/NTSC, PLAY rate, and the Ultimate's System Mode](#system-timing--palntsc-play-rate-and-the-ultimates-system-mode) below and `[ultimate64].sid_play_rate`. Leaving the kernal-default rate in place is what made a PAL vsync tune play 19.7% fast, and that has not been the default since the tempo fix shipped.

### Backend-agnostic orchestration

Parse, layout, build, divider-tune, and subtune-reinit all live in `_SidPlayerMixin` — a SID-only tenant each concrete backend mixes in alongside `_StubRunnerBackend` (which carries the character-ROM dump), so the two features share the shape of the split and none of the state. Only the *kick* differs, via the abstract `_launch_sid_player`.

**Ultimate** — POSTs the `SYS` stub to `run_prg`.

**TeensyROM** — uses a pure-DMA `$0314` **vector swap** instead, the same primitive as `cue_song_reinit`. Over the running IRQ-enabled clear-loop it DMAs the blobs, then swaps `$0314` to the re-INIT stub, which the next kernal IRQ runs to `JSR init` and install the PLAY handler. No LaunchFile, reset, or boot — therefore no async-boot race.

`run_sid_player(defer_audio=True)` plus `begin_sid_audio()` split load from start. That lets WaveformScene paint the scope **before** the first note on TR, or assert the bitmap after the player as before on U64, where `run_prg` resets the VIC. The scene anchors its host-emu clock to `sid_audio_start_time()`.

The TR path is gated on `supports_read`, meaning cycle-clean firmware v0.7.2.5+; the spin-stub idle on older firmware masks IRQs so the swap cannot fire, and older firmware raises `BackendCapabilityError`.

The TR also has no REUWRITE, so `cli._coerce_reu_for_backend` forces `use_reu_pump` and any explicit `use_reu_staged=true` off on a no-REU backend, leaving host-DMA NMI DAC audio and host-DMA video. `--doctor` reports this.

See [caveats.md](../caveats.md) → "SID playback uses a C64-side player PRG", including the TeensyROM vector-swap subsection, for the full rationale.

## System timing — PAL/NTSC, PLAY rate, and the Ultimate's System Mode

Two independent errors used to ride on a SID played through this path, with two
independent levers. Keeping them apart is the whole point of this section.

### What the Ultimate's "System Mode" labels actually select

From the firmware's timing table (`software/u64/color_timings.cc`),
cross-checked by measuring φ2 and the VIC raster line count on a real unit:

| System Mode | cycles/line | φ2 | lines | HDMI out |
|---|---|---|---|---|
| `PAL` | 63 | 985 248 | 312 | 720×576 @ 50.12 |
| `NTSC` | 65 | 1 022 727 | 263 | 640×480 @ 59.83 |
| `PAL-60` | 65 | 1 022 727 | 263 | 640×480 @ 59.83 |
| `NTSC-50` | 63 | 985 248 | 312 | 720×576 @ 50.16 |

The **suffix selects the machine timing**; the **prefix selects only the analog
chroma encoding** (`VIDEO_FMT_NTSC_ENCODING`). So `NTSC-50` is a PAL-timed
machine emitting NTSC color, and `PAL-60` is an NTSC-timed machine emitting PAL
color — over HDMI the pairs are the same picture.

### What retiming does to the composite output

Over HDMI the prefix is invisible: the upscaler emits RGB either way, and the
only thing a capture device notices is 576p50 vs 480p60. On composite/S-Video
the prefix is the whole color signal, so the hybrids are the classic
non-standard combinations:

| Mode | chroma | field rate | subcarrier |
|---|---|---|---|
| `PAL` | PAL | 50 Hz | standard (`c_pal_50_283_5`) |
| `NTSC` | NTSC | 60 Hz | standard (`c_ntsc_60_227_5`) |
| `PAL-60` | PAL | 60 Hz | free-running (`c_pal_60_free`) |
| `NTSC-50` | NTSC | 50 Hz | free-running (`c_ntsc_50_free`) |
| `PAL-60/L` | PAL | 60 Hz | locked, 281.5 (`c_pal_60_281_5`) |
| `NTSC-50/L` | NTSC | 50 Hz | locked, 228.5 (`c_ntsc_50_228_5`) |

`_switch_system_mode` preserves the chroma prefix deliberately, so a set that
could decode color before still can. But **the field rate changes underneath
it**, and that is what a single-standard analog display may refuse to lock. In
practice `PAL-60` (what a PAL machine becomes when retimed to NTSC) is widely
tolerated by multi-standard sets and capture hardware; `NTSC-50` is rarer and
more likely to come out monochrome or unstable. A pure NTSC set fed `PAL-60`
usually locks sync and loses color.

Audio is unaffected as a signal path — the SID's output leaves by the same AV
connector regardless of video mode. What does change is *pitch*, because φ2
changed, and that is the entire point of the switch. It is identical on HDMI
and composite.

The `/L` variants lock the color subcarrier to an exact line ratio rather than
free-running it, and the firmware's own comment calls them the "best timing
match to original C64". Their periods are slightly *longer* (84422 / 81385 vs
84372 / 81300), so it is the plain hybrids that run ~0.1% fast. c64cast makes no
attempt to carry a `/L` choice across a retime: every `/L` mode is a hybrid, and
retiming a hybrid always lands on the other standard's plain mode, which has no
locked form. A composite user who chose `/L` loses it for the run and gets it
back at teardown — one more reason `sid_video_mode` is opt-in.

`hw_provision.SYSTEM_MODE_TIMING` encodes exactly this, which is why that table
looks backwards. It is not.

The switch applies live over REST with no Ultimate reboot — the firmware's
effectuate path only re-runs the PLL. c64cast still resets the *C64* afterwards
so the KERNAL re-runs its PAL/NTSC autodetect against the new timing.

### The defect: PLAY does not run once per frame

The C64-side player chains PLAY onto the **kernal's CIA #1 Timer A jiffy IRQ**.
That IRQ is a *wall-clock service* — TI$, SCNKEY, cursor blink — not a frame
interrupt, so the KERNAL programs it to ≈60 Hz on **both** standards (`$4025`
PAL, `$4295` NTSC; `c64.kernal_cia1_latch`).

A PAL vsync tune therefore played at 60.0 Hz instead of 50.12 — **+19.7%
tempo** — on a PAL machine as well as an NTSC one. Switching System Mode does
not touch this; it only changes φ2, i.e. **pitch**.

Over the 61 245 tunes in a full HVSC, ~80% are PAL + vsync, the population
taking the full error. PAL CIA-timed tunes (~10%) self-time from their own INIT
and drift only by the 3.8% clock ratio.

| lever | fixes | costs |
|---|---|---|
| CIA #1 Timer A latch (`[ultimate64].sid_play_rate`) | tempo (+19.7%) | nothing — software only, no video change |
| System Mode (`[ultimate64].sid_video_mode`) | pitch (+3.8%) | an HDMI mode switch + capture re-lock |

Hence the defaults: the tempo fix is on, the pitch fix is opt-in.

### Why the latch is written *after* INIT

On the Ultimate the player is kicked via `run_prg`, which soft-resets the C64 —
and the KERNAL's reset path reloads Timer A. A latch written before the kick is
gone before the first PLAY. So `_apply_play_rate` runs from
`_tune_play_divider`, ~200 ms in, reusing the latch sample that function already
takes.

Writing after INIT means a multispeed tune's own latch is already in place, so
two gates decide whether to overwrite it:

1. **The PSID speed bit for this subtune must say vsync.** The word at `$12` is
   one bit per subtune (0 = vsync, 1 = CIA-timed), which is why
   `cue_song_reinit` re-decides per subtune rather than inheriting the start
   song's answer.
2. **The sampled post-INIT latch must not already be far below the kernal
   default.** A 2×/3×/4× multispeed sits at 1/2, 1/3, 1/4 of it — well clear of
   the noise in an 8-sample max of a free-running down-counter. This catches
   tunes whose speed bit lies.

The latch is computed from the **machine's** clock for the **tune's** rate
(`cia1_latch_for_rate(frame_rate(tune_clock), machine_system)`), so tempo comes
out right on either machine; only pitch stays standard-dependent.

`WaveformScene._video_hz` reads `api.sid_vsync_play_rate_hz()` rather than
assuming 50/60 from the configured system — the scope's host emulator has to
advance the song at whatever PLAY is really being called at. It is re-read after
`run_sid_player` and after each subtune cue.

The REU audio pump reprograms the same timer, so `scene_factory` drops the
tempo correction (with a log) when `[audio].use_reu_pump` is on rather than
letting the two overwrite each other.

### `[ultimate64].system = "auto"`

This one field sets the CPU clock, the frame rate, the DAC NMI latches and the
scope rate at once, and a wrong value is silent. `hw_provision.resolve_system`
reads it off the machine's live System Mode after the backend opens — it cannot
happen in `make_backend`, which bakes `default_fps` and `host_sid_model` from it
before any API exists, so those profile fields are re-folded once the answer is
known. An explicit value still wins (it is how you describe a TeensyROM-driven
C64), but disagreeing with the machine logs a warning and is a `--doctor` error.

### Capture devices and 576p50

PAL timing at the Ultimate's SD scan resolution puts 576p50 on the wire, and
capture devices disagree about it: one tested device produced a torn/rolling
picture, another locked cleanly. Raising **HDMI Scan Resolution** to HD (720p)
made the first device lock — the upscaler's output is what the capture card
sees. `[ultimate64].hdmi_scan_resolution = "auto"` (the default) therefore
raises SD to HD *only when c64cast itself retimed the machine*: clean up after
our own change, leave a machine we did not touch alone.

Recovery, worth knowing before changing video modes: holding **C= and P** (PAL)
or **C= and N** (NTSC) at Ultimate boot forces System Mode back. Every write
c64cast makes here is live + volatile, so a power-cycle clears it regardless.

## `waveform.py` + `sidemu.py` + `sid_host_emu.py` — SID oscilloscope scene

`WaveformScene` (inherits `VoiceScopeRenderer`) plays a SID file on the U64 via `api.run_sid_player(...)` (DMA SID payload + 73-byte 6502 player relocated per-tune by `_choose_player_layout` — default $C300, bumped past the SID payload on overlap — then POST a matching `10 SYS <player_base>` BASIC stub via `runners:run_prg`) and visualizes the three SID voices' waveforms across the full screen. Display is bitmap-only (320×200 hires). Voices stack vertically — voice 1 top, voice 3 bottom.

The bottom two text rows carry the tune metadata: the **title row** (`_build_title_line`) is the song title left-justified + composer right-justified, fixed across subtunes; the **metadata row** (`_build_metadata_line`) is `SONG xx/yy` (zero-padded to `num_songs`' width) + copyright left-justified, and the SID's composed-for clock + chip right-justified (e.g. `PAL 8580`). When the SID targets one definite standard that differs from the current playback system (`[ultimate64].system`), the clock reads `native→system` (e.g. `PAL→NTSC 8580`) so the mismatch is visible; the `→` is a right-arrow synthesized by horizontally mirroring the ROM left-arrow glyph (`voice_scope._mirror_glyph_h`, blitted via `_paint_text_row`'s `glyph_overrides` — the C64 charset has no native `→` cell). Ambiguous (`PAL+NTSC`), unknown, or matching standards show the native value alone. Only the metadata row's song number changes on a SHIFT subtune switch, so `cycle_style` repaints just that row (the title row is untouched).

The firmware's `runners:sidplay` endpoint is deliberately avoided: on firmware 3.14d it draws its own "ULTIMATE C-64 SID PLAYER" UI on the HDMI scaler that covers everything we paint into VIC RAM. PSID-only — RSIDs (which install their own raster IRQ in INIT), tunes whose `load_addr` is below `$0820` (would collide with the BASIC SYS stub), tunes whose `play_addr` is zero (INIT installs own IRQ), and tunes with code/data under KERNAL ROM (`$E000-$FFFF`, where the player can't bank KERNAL out without losing its `$EA31` IRQ chain) are refused at scene setup with a clear error. Tunes under **BASIC** ROM (`$A000-$BFFF`) are supported — the player banks BASIC out per-call around the affected `JSR init`/`JSR play` (`$01 = $36`; see below). The PAL/NTSC speed flag is read per subtune and retunes CIA #1 Timer A when it says vsync (`[ultimate64].sid_play_rate`, default `auto`; `teardown` calls `api.restore_kernal_play_rate()` to undo it) — see [System timing — PAL/NTSC, PLAY rate, and the Ultimate's System Mode](#system-timing--palntsc-play-rate-and-the-ultimates-system-mode). See [docs/caveats.md](../caveats.md) for the full design discussion.

The visualization is driven by a hybrid setup:

* **Audio** comes from the U64's native SID chip (the audience hears the real hardware).
* **Per-voice waveforms** come from a Python-side `SIDEmulator` in `sidemu.py`. The U64's FPGA SID is faithful to real hardware — `$D400-$D418` is write-only and reads return open-bus zeros, so we can't ask the U64 what the SID is doing. Instead, `SidHostEmu` in `sid_host_emu.py` runs the same SID file in parallel on a host-side [py65](https://github.com/mnaberez/py65) pure-Python 6502. A `TrappedRam` wrapper around the emulator's 64 KB array intercepts writes to `$D400-$D418` into a 25-byte shadow. The background poll thread ticks the host emulator at the tune's **effective PLAY rate**, not at the video frame rate: `WaveformScene._video_hz` reads `api.sid_vsync_play_rate_hz()` (the kernal jiffy IRQ the C64-side player chains onto — ~60 Hz on *both* standards, never 50; see ["The defect: PLAY does not run once per frame"](#the-defect-play-does-not-run-once-per-frame)), and `_resolve_poll_rate` / `_detect_play_rate_hz` probe the tune's own CIA latch so a multispeed tune is ticked at its real multiple of that. `_poll_regs` then catches the emulator up to wall-clock each wakeup rather than assuming one tick per frame — assuming a nominal rate is what left the scope drifting progressively behind the audio, most visible as a voice's trace staying flat for a beat. The shadow snapshot feeds `SIDEmulator`, which mirrors per-voice waveform-select / pulse-width / ADSR state and synthesizes samples on demand. Phase is owned by Python (not synced to the real chip), so what you see is a faithful per-voice oscilloscope trace at the right frequency and envelope — not a phase-accurate scope of the audio output. PSID validation is shared with `api.run_sid_player` via `parse_psid_for_player`, so a tune the U64 side refuses is also refused at host-emulator construction with the same error.
* **Multi-SID tunes (2SID/3SID)** are auto-detected and shown as a **split scope** — one side-by-side window per SID chip in each voice row (chip 0 left … chip N right), the same layout `AsidScene` uses. Detection is `sid_host_emu.detect_sid_addresses`: the PSID v3/v4 header's second/third-SID address bytes (`$7A`/`$7B`, each encoding a `$Dxx0` base as `$D000 | byte<<4`), raised by an HVSC-style `_<N>SID.sid` filename hint when the header understates the count (the hint appends canonical stride-`$20` bases since it carries no addresses). One `SidHostEmu` runs the tune; its `TrappedRam` shadows **all** the chips' register banks (one 25-byte shadow per base — the single 6502 already writes every chip), and `WaveformScene` feeds each bank into its own `SIDEmulator`/scope window (`regs(bank)` / `retriggers(bank)`). For **audio** on the U64, `_apply_sid_hw_config` maps the U64's extra SID cores to the tune's own addresses (via `asid_sidmap.plan_sid_map_for_addresses`, which realizes the file's fixed `$Dxxx` bases on ≤2 sockets + 2 UltiSID cores, falling back to the canonical `plan_sid_map` layout when the exact set isn't hardware-realizable) — snapshotted before, restored on teardown by the shared `sid_hw_config` helpers. Single-SID output is byte-identical to the pre-multi-SID renderer (one window). Backends without a SID config API (TeensyROM) still show every chip's scope; only `$D400` is audible there.
* **SID Player Autoconfig** — see the dedicated subsection below.
* **Combined waveforms** (multiple waveform-select bits set) are rendered by `sidemu.voice_samples` as a **12-bit bitwise-AND** of the selected waveforms' unsigned oscillator outputs — the SID wires those outputs onto a shared bus, so the AND approximates the real chip's sparse "metallic" combined shape (faithful in character, not chip-exact — an accurate model needs reSID-style per-chip sampled tables, a noted future refinement). Single-waveform output is byte-identical to the pre-combined code (only 2+-bit voices change). `primary_waveform` (priority noise > pulse > sawtooth > triangle) is still used for the `per_waveform` color pick, not the trace shape. **Whether a voice is silent has one owner**, `sidemu.Voice.is_silent()` — no waveform selected, a zero frequency, or a dead envelope. The rule had been rewritten in every consumer and the copies disagreed: `voice_samples` omitted the frequency test, so a rest written as freq 0 with the waveform bits still set froze the phase accumulator and drew a DC-offset flat line pinned near the top of the strip, while the scope's own time-base picker already counted that case as silent. **Caveat (HW-confirmed):** the AND model *over*-represents sawtooth combos — on a real 6581 anything containing sawtooth ANDs down to near-silence (`pulse+triangle` is the one combination that reliably sounds), so MidiScene keeps saw/noise combos out of its interactive SHIFT/PC rotation (see `_WAVEFORM_CYCLE` in [c64cast/sid/midi_scene.py](../../c64cast/sid/midi_scene.py)); they're still settable via config. Closing that visual-vs-audio gap fully is what the chip-accurate tables would buy.
* **No filter, no master volume**: irrelevant to the per-voice oscilloscope view.

Coloring modes:

* `per_voice` — each voice gets a fixed C64 color from `voice_colors`.
* `per_waveform` — color reflects the currently-selected wave type (e.g. cyan for pulse, light red for sawtooth). Color RAM is rewritten only on transitions, not every frame.

Teardown order matters: `api.restore_kernal_irq_vector()` puts `$0314` back to `$EA31` first (so our IRQ handler is unhooked and PLAY stops being called), then `api.flush()`, then `api.silence_sid()` writes 0 to `$D418` and clears each voice's gate. If silence ran first, the IRQ could fire between the volume-clear and the gate-clears and PLAY would rewrite both. No reset, so the next scene paints over the waveform without the BASIC banner flashing.

The scene runs for `duration_s` — `runners:run_prg` doesn't surface a "finished" signal for the BASIC GOTO loop. Use SongLengths data via `[playlist].songlengths_file` if you have it; otherwise pick a duration that matches the tune, or accept `WaveformScene.FALLBACK_DURATION_S` (180 s), which is what `_resolve_duration_for_current_sid` returns with no explicit `duration_s` and no DB hit.

**It can also end early.** `_check_end_of_tune` ends the scene once every voice has been silent (below `ENV_SILENCE_EPS`) for `END_SILENCE_S` = 6 s *after* the tune has sounded at least once. That only ever shortens playback, and it is why a short subtune under a generous `duration_s` advances the playlist sooner than the number suggests. The window is deliberately generous so a musical rest doesn't trip it.

Visualization knobs (all compose; defaults preserve the redraw-from-scratch, wallclock-locked behavior so existing configs render identically):

* `time_base = "wallclock" | "auto"` — `auto` derives the per-voice time window from `v.freq` so `auto_cycles` complete cycles always fit, regardless of pitch. Silent voices (freq=0, wave=off, or envelope=0) fall back to wallclock per-voice so the trace doesn't collapse to a flat line on a divide-by-zero.
* `persistence = "off" | "short" | "medium" | "long" | "random"` — keeps a per-voice ring of the last N frames' **bool** trace masks (`_echo_history`, depth = the preset's color count). Each frame ORs the ring into the bitmap and colors each cell newest-first from `PERSISTENCE_ECHOES`, a fixed gray ramp — there is **no** per-frame decay and no intensity strip: a 1bpp bitmap cannot fade a pixel, so an echo is a hard render at a dimmer gray instead. `random` resolves to one of the named presets at scene setup (same sentinel pattern as `petscii_styles`); the resolved name is logged on the scene's startup line.
* `scroll_columns = 0 | N | [N1, N2, N3]` — per-voice FIFO: shift the voice's persistent bool strip left by N columns and draw only the new N columns on the right edge. Scalar broadcasts to all three voices; list assigns per voice (so one strip can scroll fast, one slow, one stay redraw-style). Scroll mode rewrites the whole strip per frame and busts the dirty cache on purpose; cost is bounded (≈700 KB/s of DMA at 60 fps, well under the ceiling). SHIFT-cycle zeroes the strip buffers so a `persistence = "long"` trail from the prior subtune doesn't ghost-merge into the new one.
* **Both are single-window only.** `_set_window_count` derives the per-voice render modes from these two knobs (`_resolve_render_modes`, the one derivation both construction and a live reflow share) and then forces all three voices to the fast path whenever the split scope has more than one window, warning when it has to discard a configured mode — per-window scroll/echo would need every persistence buffer re-keyed to (voice, chip) at per-window widths, which v1 does not do. Because the derivation is re-run rather than clobbered, a shrink back to one window (a `WaveformScene` moving from a 2SID tune to a 1SID one) gets the configured mode back.

### Host-emulation budgets, and what a tune is allowed to declare

The host emulator runs an untrusted file — SID files are downloads, and a pool spec auto-picks them — on the render thread, so two classes of hostile input are bounded at the source.

**Every INIT/PLAY call is bounded by steps and wall clock, not only by emulated cycles.** py65 binds all 105 undocumented opcodes to `inst_not_implemented` with a `cycletime` of 0, so a routine built out of them advances `processorCycles` not at all and a cycle cap alone cannot terminate it — a crafted PLAY measured 7-21 s per `tick_play()` against a cap the comments budget at ~4 ms. `_run_routine` therefore also counts interpreter steps (a step budget equal to the cycle cap can never bind on a routine the cycle cap would have caught first, since every implemented opcode costs at least 2 cycles), and it consults a wall-clock `deadline` every `_WALL_CLOCK_CHECK_STEPS`. That last one exists for INIT: its cap is 2 M *cycles*, which is not a duration, and every `SidHostEmu` runs INIT in its constructor. `cap` is an explicit argument per caller rather than inferred from the log tag, and every budget test is re-guarded by the sentinel so a routine that completes on the very step that crosses a budget is not reported as capped.

**`TrappedRam` wraps the address bus, and anything py65 raises is a capped pass.** `MPU.WordAt(addr)` reads `addr+1` without masking, so a 3-byte absolute-addressing opcode executed at `$FFFE` asks a 64 KB `bytearray` for index `$10000`. `IndexError` is not `ValueError`, so it escaped `_pick_and_load_sid`'s "log it and try the next candidate" handler and `Playlist.run` ended the show — six bytes of 6502 in a 133-byte file. Masking in the trap is also the more faithful emulation. The `step()` call is wrapped as well, on the principle that py65 is not written against hostile input: whatever else it raises comes back as `last_routine_capped`, so the tune is refused by the pre-flight rather than unwinding into the scene.

**An undocumented opcode ends the pass but does not condemn the tune.** `_run_routine` stops at one rather than executing it — py65 advances the PC by 2 regardless of the real instruction's length, which derails the instruction stream — but it sets `saw_undecodable_opcode`, *not* `last_routine_capped`. The two must stay separate. `play_preflight_failure` reads only `last_routine_capped`, which means "the pass just run does not terminate"; feeding it the opcode verdict as well refused every tune whose PLAY contains a LAX/SAX/SLO, which is a normal hand-rolled-player idiom that the U64's real 6510 executes, with an error message blaming a raster spin that was not happening. What the flag does mean is that every pass stopped at the same instruction, so the RAM footprint sampled from that emulator is a *prefix* of the tune's behavior — which is what `FootprintSample.complete` reports.

**Every deadline this emulator compares is read on the clock that produced it.** `HostEmuBudget.deadline_for` returns an instant on the budget's own (injectable) clock, and `SidHostEmu` stores that clock as `self._now` for `_run_routine` to compare against. Reading `time.monotonic()` there instead coincided with the truth for every shipped run — the default clock *is* `time.monotonic` — and was meaningless for every injected one, so a test that combined an injected clock with a routine long enough to reach a wall-clock check would have proved nothing while passing.

**"Capped" answers two different questions and needs two flags.** `last_routine_capped` is per-pass and is the pre-flight's question: did the pass just run terminate. `any_routine_capped` is sticky and is `FootprintSample.complete`'s: is anything sampled from this emulator a prefix. Computing the second from the first meant the constructor's INIT — which runs once, before the caller holds the object, and whose cap is measured in millions of cycles — reported a full footprint made of the bytes it had written before the cap. A fat decompressor truncated at `_INIT_CYCLE_CAP` (or at the shared budget) therefore handed `api._find_free_layout` a hole the rest of INIT was about to fill.

**One budget covers a whole tune's analysis, and a truncated sample says so.** Per-call soundness leaves the call *count* open, and the file sets the count: `WaveformScene.setup` pays two footprint runs plus one per subtune (up to `_UNIFIED_LAYOUT_MAX_SONGS`), a SHIFT press pays one per candidate (up to `_MAX_CYCLE_CANDIDATES`), and `num_songs` is a raw 16-bit header field nothing else bounds. Each run drawing its own `FOOTPRINT_DEADLINE_S` (2 s) meant a 306-byte PSID declaring 16 subtunes measured 43 s of blocked main thread, and one SHIFT press re-spent it with the audio already silenced. So `setup`, `cycle_style` and the PLAY-rate probe each open one `HostEmuBudget` (`ANALYSIS_BUDGET_S`, 6 s) and thread it through every `SidHostEmu` construction and every footprint run: a run gets `min(FOOTPRINT_DEADLINE_S, what's left)`, an INIT gets `min(_INIT_DEADLINE_S, what's left)`, and the scan loops stop when it is gone. 6 s leaves an ordinary 16-subtune tune and Galway's Times of Lore (11 subtunes) finishing comfortably; what a slower tune gives up is the optional work — the unified bank pin, the later SHIFT candidates — not the show.

The pre-flight and the pool walk are inside the budget too. `play_preflight_failure` takes one and checks it between passes, because 50 PLAY passes plus an INIT measured ~1.1 s for a crafted tune and `_MAX_PICK_ATTEMPTS` of those blocked the constructing thread for ~8.8 s. `WaveformScene._pick_and_load_sid` and `SidFileAudioSource._pick_and_load` therefore open ONE budget for the whole walk rather than one per candidate — a per-candidate bound bounds no walk. A candidate refused because the budget ran out says exactly that; refusing it as a raster spin is the message this gate has already been wrong about once, which is why the pre-flight returns a reason string rather than a bare bool.

`ram_write_footprint` / `ram_play_access_footprint` return a `FootprintSample(ram, complete)` rather than a bare bitmap, because consumers place hardware on the result: `api._find_free_layout` puts the relocated player MC in the largest hole the bitmap leaves, and `_choose_display_layout` picks the VIC bank from it. A run cut short — by the clock, by a capped routine, or by an undocumented opcode — returns a prefix, and a late write the dropped tail would have marked reads as free RAM: the player goes there, PLAY overwrites it, and the tune is silent with a crash to BASIC, which is the regression the footprint was added to prevent.

**A prefix makes a placement more conservative, never less — and no call site gets to forget that.** The flag rode back on two `FootprintSample` values that three call sites each had to consult, and two of them logged the warning and then handed the prefix to `_find_free_layout` and `_choose_display_layout` anyway. So the two whole-tune consumers — `WaveformScene.setup` and `SidFileAudioSource.setup` — no longer see a `FootprintSample` at all: they call `analyze_placement`, which runs both footprints and returns `PlacementFootprints(avoid, display, play_bank, trusted)` with the decision already applied. On an untrusted sample both views widen to the union of everything the tune was observed to touch (INIT writes included — the display view gives up its "INIT-only scratch is paintable" concession, which is the cheapest real narrowing available and uses observed data rather than guesswork), and `play_bank` drops to `None` so `run_sid_player`'s address heuristic decides instead of an intersection the missing tail could have created or destroyed. If the widened bitmaps leave nothing free, the callers' existing `ValueError` paths abort the scene and the playlist advances — the same code that already handles "no free VIC bank", not a second refusal written beside it. Refusing every untrusted tune outright was the alternative and is wrong: one undocumented opcode anywhere in PLAY makes a sample a prefix.

The per-subtune scans keep their own answer, because theirs is cheaper than widening. `_choose_unified_display_layout` refuses to pin a bank at all on an incomplete sample, since the pin *suppresses* `_cycle_pick_candidate`'s per-subtune re-check and its fallback costs only a possible bank move on a SHIFT. `_cycle_pick_candidate` skips such a candidate exactly the way it skips an unrenderable one — and unlike `setup`'s one-off choice, this one is made while the audience is watching — and `cycle_style` keeps the default `$01` bank when the chosen subtune's write footprint is a prefix.

**The poll thread's catch-up is bounded by time, not only by tick count.** `_MAX_CATCHUP_TICKS` (120) assumed ~0.2 ms a tick; a PLAY that stays legally inside `_PLAY_CYCLE_CAP` measured 15.8 ms, making the batch 1.9 s on a thread whose period is 1/60 s. The tune also sets the rate the batch is sized against — `play_rate_hz` honors a CIA #1 Timer A latch up to 8× the video rate and PLAY writes that latch itself — so the target could advance faster than the thread could ever tick, for the scene's whole duration. Both catch-up threads — `_poll_regs` and `music_features.SidFeatureStream._poll_loop`, which was a verbatim copy of the same bound — therefore go through one `sid_host_emu.run_catchup_passes`, which stops after `_MAX_CATCHUP_PERIOD_FRACTION` of one poll period. The `_reg_lock` is still taken per tick rather than once around the batch: the render thread wants the same lock, and holding it across a burst would starve exactly the thread the bound protects.

**A time bound smaller than one indivisible pass is not a bound.** `run_catchup_passes` runs a PLAY pass before it consults the clock, and it has to: a PLAY given a deadline of its own stops mid-frame, leaving the `$D4xx` shadow holding half the writes and the scope showing that — which is why `_PLAY_DEADLINE_S` applies on the analysis paths (footprint runs and the pre-flight, where a truncated pass is a sample already distrusted) and not on the render path. So the tune could set both sides of the comparison: a CIA #1 Timer A latch for 400 Hz gives a 2.5 ms poll period and a 1.25 ms catch-up allowance, against a legal PLAY measured at 10 ms — a 401% duty cycle, back-to-back for the scene's whole duration, taking the render thread's time with it under the GIL.

Two changes make the bound bind. The poll period is now separate from the per-tick song `dt`: `_poll_dt` stays `1/rate` (the ADSR envelopes must advance at the song's pace, not the thread's), while `_poll_period` — what `PollThread` sleeps and what the catch-up allowance is a fraction of — is floored by `sustainable_poll_period_s` so one *measured* PLAY pass fits inside `_MAX_CATCHUP_PERIOD_FRACTION` of it. The measurement comes from the PLAY-rate probe, which already runs up to `RATE_PROBE_TICKS` passes and times them — but it did not come free, and the shape of that mistake is worth keeping. The probe's loop consulted the rate at the *top* of each iteration, so a tune that programs CIA #1 Timer A from INIT — where the rate is settled the moment INIT returns — broke out having timed nothing and reported a pass cost of `0.0`. The floor was therefore skipped on exactly the tunes it was written for: a 399.3 Hz CIA-timed tune measured here kept its 2.50 ms poll period against a pass it had never priced. The probe now times a pass *before* it reads the rate, the same order and for the same reason as `run_catchup_passes`, and it lives in `sid_host_emu.detect_play_rate_hz`, which `WaveformScene` and `SidFeatureStream` now share instead of each carrying a line-for-line copy of the loop — the copies are how the rate-before-cost order came to be wrong in two places at once. The probe pass deliberately gets **no** `_PLAY_DEADLINE_S`, unlike every other analysis path. A deadlined pass is a censored measurement: truncated at 50 ms it prices a pass that will really spend 120 ms on the render path (which passes no deadline of its own), the floor is then sized at less than one pass, and the catch-up thread runs back to back — the exact GIL starvation the floor was written to prevent, with the warning calling the truncation a measurement. What bounds one pass is the *step* cap in `_run_routine` and not the cycle cap: `_PLAY_CYCLE_CAP` counts emulated cycles, py65 charges 0 for the 105 undocumented opcodes, and the 50 k step limit is what actually binds — a PLAY that spins on a raster forever measures 7.1 ms undeadlined. What bounds the loop is the shared `HostEmuBudget`, checked before each pass, so an expensive pass ends the probe after it rather than being cut off inside it.

**"Not measured" and "measured as free" are different answers and now have different values.** `pass_cost_s` is `float | None`: `None` means no pass was timed at all, which with the default tick count only happens when the tune's analysis budget was already gone. `0.0` still means a pass ran and was quicker than the host clock could resolve, which genuinely needs no floor. One value carried both readings, and `sustainable_poll_period_s` took the cheap one, so the costliest input in the system was classified as the cheapest; an unmeasured pass is now charged `UNMEASURED_PASS_COST_S` (16 ms, the worst a legal pass can cost) and the warning says which of the two it is rather than reporting an assumption as a measurement. That charge is a fail-safe default and not an inference — a spent budget is drained by INITs and footprint runs as much as by PLAY, so it says the tune's *analysis* was expensive, which is only correlated with an expensive PLAY. What settles the direction is that the two errors are not symmetric: assuming free saturates a core silently, assuming expensive slows the wakeups visibly and logs why. A pinned `reg_poll_hz` — the scenes' constructor parameter, which nothing in the config surface currently reaches — no longer skips the probe either: it pins the rate, and what a PLAY pass costs is a property of the tune and the host, not of who chose the tick rate. Stretching the wakeups makes the scope (or the reactive visuals) fall behind the audio, which is visible and logged; a saturated core is neither. And `run_catchup_passes` returns `CatchupResult(passes, overran)` rather than a bare count, because the case the count cannot express is exactly this one: one pass was due, it ran, and it outlasted the whole allowance on its own — a "complete" batch by pass count. Both callers warn once on `passes < requested` **or** `overran`.

**Extra-SID addresses are validated where they are decoded.** `_decode_extra_sid_addr` accepts only what the PSID spec permits: even bytes resolving into `$D420-$D7E0` or `$DE00-$DFE0`. Anything else — an odd byte, a byte below `$42`, a base equal to `$D400` — is refused and the tune degrades to single-SID, which is the fallback the code always claimed. It also refuses a base whose 25-byte window reaches hardware c64cast drives itself (`hw.c64.RESERVED_IO_WINDOWS`, shared with the multi-SID planner — see [Multi-SID on the U64](#multi-sid-on-the-u64-asid_sidmappy)): the spec's "cartridge I/O" window covers the whole `$DFxx` page, where c64cast runs both the REU's command registers (`$DF00-$DF0A`) and the Ultimate Audio FPGA sampler (`$DF20-$DFFF`, seven 32-byte channel files — the range the firmware's "Map Ultimate Audio $DF20-DFFF" switch is named after). `WaveformScene.teardown`'s 25-byte zero write at a declared base lands on `$DF02`/`$DF03` — the running C64 destination pointer the audio ring's NMI handler reads back mid-transfer — or walks a sampler channel's control/volume/start/length file while that channel is playing the session's video audio. So the surviving cartridge bases are `$DE00-$DEE0`. `detect_sid_addresses` additionally appends a base only when its 25-byte window touches none already accepted, because `TrappedRam._addr_map` is a dict comprehension over the bases and a later bank silently wins every colliding key: two chips at one address (reachable from the header, and from an HVSC `_NSID` filename over a header that already claims that slot) left the earlier chip's scope window flat for the whole tune while the audience heard it play.

**A failed pre-flight aborts the scene rather than cueing the subtune.** `_build_host_emu` is the single construction site for the parallel emulator — initial load, SHIFT cue, and `$37→$36` hard relaunch all go through it — and it runs `sid_host_emu.play_preflight_failure` on the emulator it is about to hand back, under the caller's analysis budget. INIT and PLAY are separate 6502 entry points per subtune, so song 1 passing the gate vouched for nothing about song 2, and the cue path used to re-INIT the real machine on an ungated subtune. When a SHIFT-cycled subtune fails, `cycle_style` logs at ERROR, sets `is_done`, and returns None — the playlist advances instead of the scene cueing a tune that would leave the C64 silent and unresponsive.

### SID Player Autoconfig

`sid_autoconfig.py`, config `[ultimate64].sid_model`.

Matches each chip's **model** (6581/8580) to what the tune's PSID header requests. This is orthogonal to the address routing above, which only ensures a chip is *audible* somewhere — not that it is the *right-sounding* chip.

**Decoding the header.** `sid_host_emu.parse_sid_header` decodes `SidHeader.sid_models` — one entry per chip present, parallel to `sid_addresses` — from the PSID v2+ flags word at header offset `$76-$77`:

| Field | Bits | Byte |
| --- | --- | --- |
| sidModel1 | 4-5 | low (`$77`) |
| sidModel2 | 6-7 | low (`$77`) |
| sidModel3 | 8-9 | high (`$76`, bits 0-1) |

Each entry is gated on the same version and address-byte conditions that make its chip's `sid_addresses` entry exist, mirroring the firmware's `ConfigSIDs`.

**The decision function.** `sid_autoconfig.plan_sid_model_config` is pure. For each chip with a definite model requirement — a `None`, `"?"`, or `"6581+8580"` header value is always a no-op — it checks whatever currently answers that chip's address via `sid_hw_config.detect_socket_models`, reading `"SID Detected Socket N"`, then:

1. Already matches → no-op.
2. The *other* physical socket reports the required model → remap that socket's address, using the same `SID Addressing` / `SID Sockets Configuration` PUTs that `asid_sidmap.plan_sid_map_for_addresses` uses.
3. Otherwise → fall back to a free UltiSID core, setting its `"UltiSID N Filter Curve"` item (category `"UltiSID Configuration"`, confirmed live via `GET /v1/configs`) to a fixed representative curve, `"6581"` or `"8580 Lo"`. The full enum also offers `"8580 Hi"`, `"6581 Alt"`, `"U2 Low"`, `"U2 Mid"`, and `"U2 High"`, none exposed as a config knob in this pass. The same step also sets `"Auto Address Mirroring"` to `Disabled` and disables whichever socket currently answers that address — see below.
4. Otherwise → warn and leave the chip unchanged.

**An UltiSID route that doesn't take the address away is inaudible by design.** Pointing a core at `$D400` does not make the core what a listener hears. `Auto Address Mirroring` lets a socket mirror the core's base, and a socket left `Enabled` there answers alongside it — and by the policy in `sid_hw_config.current_source_map` (a socket's real chip is what sounds; a core "at" the same address is just mirroring) the socket is what every downstream consumer then reports. So the mixer pass reads the *socket* as the source the tune plays on, unmutes it, and mutes the core that autoconfig just configured. The result is a log that says `chip at $D400 (8580) → ultisid1 (filter curve '8580 Lo')` while the 6581 in socket 1 is what actually plays — reproduced on hardware as thin, screeching 8580-tune-on-a-6581 playback with no error anywhere. Step 3 therefore disables both mirroring and the displaced socket, exactly as `asid_sidmap.plan_sid_map` already does for multi-SID routing. Both items are in `MANAGED_ADDRESSING_ITEMS` / `MANAGED_SOCKET_ITEMS`, so the snapshot puts the user's config back at teardown.

The socket-swap branch (step 2) deliberately leaves both knobs alone: a real chip answering its own address needs no help from either, and writing them would churn config the restore then has to undo.

**The setting.** `"auto"` (default) reads the header per chip. An explicit `"6581"`/`"8580"` forces that model for every chip, ignoring the header. `"off"` disables header inspection entirely. The same knob drives the Ultimate II+'s emulated stereo SIDs through a much shorter path — see [`emusid_mixer.py`](#emusid_mixerpy--u2-emulated-stereo-sid-snoop-routing--model-matching); everything below is the U64 surface.

**Multi-SID does not use this pass — it routes and matches in one.** `plan_sid_map_for_addresses` takes the header's `required_models` and the live `socket_models`, so a socket claims an address only when it carries the model that chip asked for; unclaimed sockets are disabled and each core's filter curve is set from the model its chips want. See [Multi-SID on the U64](#multi-sid-on-the-u64-asid_sidmappy).

**Why one pass, and not route-then-correct.** Splitting the work — route first, fix models after — cannot be made correct, because the two planners decide chip placement from different premises and the second silently invalidates the first. Reproduced on hardware with 6581s in both sockets, playing Jammer's *Light Years* (3 chips at `$D400/$D420/$D440`, all tagged 8580):

1. Routing is model-blind, so it seats chips 0-1 on the 6581 sockets and chip 2 on UltiSID 1 at `$D440`.
2. The model pass sees two 8580-wanting chips on 6581s, finds no matching socket, and moves them onto UltiSID 1 (`$D400`) and UltiSID 2 (`$D420`) — **taking the core chip 2 was given**. `$D440` is left addressed to nothing and chip 2 goes silent, while both sockets stay `Enabled` and answer `$D400`/`$D420` alongside the cores.
3. Panning then reads `SidMap.sources`, which describes the pre-correction placement, and pans sources the tune is no longer using.

**Where the pass still runs.** Single-SID tunes (nothing to route, but a tune requesting 8580 on a 6581-socketed `$D400` still needs remapping) and the canonical fallback layout `plan_sid_map`, which is chosen only when the tune's exact addresses aren't realizable and is model-blind. `WaveformScene._plan_multi_sid_map` reports which case applied; the fallback re-derives the model plan **after** applying the map, against the now-current addressing.

**The single-snapshot rule.** Address routing, model correction and the mixer changes all merge under **one** snapshot taken before any is applied. Two sequential `snapshot_sid_config` calls would capture the first change as if it were the original state, corrupting the teardown restore. `sid_hw_config.SidHwSession` enforces this mechanically: every consumer (WaveformScene, AsidScene, SidFileAudioSource, dac_calibration's per-socket loop) holds one session whose `snapshot()` is first-call-wins, `fold(originals)` merges the mixer/model values a change overwrote, and `restore()` puts the whole set back and resets the session — replacing the per-scene `_saved_config` dict + three identical `_fold_into_restore` copies it grew out of. It's also a context manager (restore on `with`-exit) for function-scoped uses.

**The other call site.** `SidFileAudioSource` — the `generative` + `audio_source = "sid"` path in `audio_source.py` — has no address-routing counterpart, so it calls the simpler `sid_autoconfig.apply_sid_autoconfig` wrapper directly, folding the returned originals into its own `SidHwSession`, restored in `teardown()`.

Both call sites are best-effort, and no-op on a backend without a SID config API (TeensyROM).

> A genuinely fixed physical 6581/8580 chip cannot be reconfigured to the other model. Autoconfig can only *route around* it, never transmute it — see [caveats.md](../caveats.md).

`tests/test_sid_autoconfig.py` carries the decision-matrix coverage.

### SID panning

`sid_panning.py`, config `[ultimate64].sid_panning`. U64, plus the Ultimate II+'s two emulated stereo SIDs via the same planners (`emusid1`/`emusid2` sources — see [`emusid_mixer.py`](#emusid_mixerpy--u2-emulated-stereo-sid-snoop-routing--model-matching)).

Spreads a tune's SID chips across the stereo field: a single SID centered, a multi-SID tune fanned out so each chip occupies its own place in the image. Applied live before playback, restored at teardown — the same best-effort snapshot/apply/restore contract as address routing and model autoconfig, and folded into the **same** saved-config dict so one restore puts everything back.

**Panning is per audio *source*, not per address.** The U64 mixes each source — physical SID socket 1/2, UltiSID core 1/2 — at its own pan, via the `Audio Mixer` category items `Pan Socket 1`/`Pan Socket 2`/`Pan UltiSID 1`/`Pan UltiSID 2` (enum `Left 5 … Left 1, Center, Right 1 … Right 5`, confirmed live against a U64). So a chip is panned wherever it was *routed*, which is why panning runs **last**, after any address remap has decided that placement.

Where the per-chip source comes from:

| Case | Source of truth |
| --- | --- |
| Remapped multi-SID (WaveformScene, AsidScene) | `SidMap.sources` — a tuple parallel to `SidMap.addresses`, populated by both planners in `asid_sidmap.py` |
| Single-SID / no remap (WaveformScene, `SidFileAudioSource`, AsidScene at setup) | `sources_for_addresses` → `sid_hw_config.current_source_map`, the live addressing read (shared with `sid_autoconfig`, which moved its `_current_addr_map` body there); on the U2+ surface, the emulated sides' snoop topology instead |

Panning runs **after** address routing for the same reason, and in `AsidScene._reconfigure_chips` it runs after `_set_window_count` (which resets the column order).

**The list is indexed by source, capped at 4.** There is exactly one pan control per source, so `sid_panning` entry *k* positions the *k*-th source the tune claims (`distinct_sources`, first-claim order) — **not** chip *k*. Through 4 chips the two coincide, since each chip lands on its own source. A list longer than `MAX_PANNED_SOURCES` (4) could never take effect and is rejected at config load.

**The achievable count is lower when the tune doesn't use both sockets.** The ceiling is 2 (UltiSID cores) + 1 per socket *playing a chip* — which is not the same as populated, since model-aware routing skips a socket whose chip is the wrong model for the tune. With **no socket in use there are only two distinct pan positions**, so a 3+ chip tune necessarily doubles chips onto a shared pan; `_warn_if_sources_limited` warns at apply time (and separately when the config carries more entries than the machine can use).

**Values and defaults.** An entry is an int `-5..5` (negative = left, `0` = center) or a label string; both normalize through `pan_to_label`. A configured list wins, truncated or center-extended to the source count; empty means `default_pan_spread`:

| Sources | Spread |
| --- | --- |
| 1 | `[0]` (Center) |
| 2 | `[-3, 3]` |
| 3 | `[0, -3, 3]` |
| 4 | `[-2, 2, -5, 5]` |

These are ordered by **musical importance**, not as a uniform fan: with an odd count the primary chip sits dead center and the rest flank it; with an even count the first two chips sit closest to center and later ones spread wider.

**A spread the hardware can't carry collapses to center.** When chips outnumber sources — a 3-SID tune on a machine with no socketed 8580, where all three land on the 2 UltiSID cores — the table's spread would throw two chips hard left against one hard right, which misrepresents the tune rather than opening it up. `default_pan_spread(n_sources, n_chips)` returns all-Center in that case. This is a *default*, not a cap: an explicit `sid_panning` still spreads doubled-up sources however the user asks.

**The scope's columns follow the pans.** Because the spreads are importance-ordered rather than monotonic, raw chip order would draw the 3-SID default as `Center | Left 3 | Right 3` while it *sounds* left-to-right as `Left 3 | Center | Right 3`. So `apply_panning` also returns a `window_order` (`window_order_for_pans`: chips sorted by pan, ties keeping chip order), which the scene hands to `VoiceScopeRenderer.set_window_chip_order`. Scope column *w* then shows `window_order[w]`, and `_scope_emulators()` — the single choke point every window-indexed render/color path goes through — serves the emulators in that order. The 3-SID default therefore puts the primary chip in the **middle** column; the 4-SID default puts chips 1-2 in the two middle columns. An all-equal or single-chip set yields the identity order, so those renders are unchanged, and `_set_window_count` resets to identity (the panning pass re-applies afterward).

**Only differences are written.** `apply_panning` reads the mixer once and PUTs only the sources whose pan actually changes, returning just those originals. A tune whose panning already matches (the common single-SID-on-a-centered-mixer case) writes nothing at setup and restores nothing at teardown.

Applies to the three tune-playing scenes: `WaveformScene`, `AsidScene` (at setup for the initial chip, and again on every `_reconfigure_chips` remap so the spread tracks the live chip count), and `SidFileAudioSource` (the `generative` + `audio_source = "sid"` path). **`MidiScene` is deliberately excluded** — it is a live instrument rather than a tune, always one voice-set at `$D400`, and carries no SID-hw snapshot/restore scaffold; pan it from the U64's own mixer if wanted.

`tests/test_sid_panning.py` covers the pure planner + the diff-only apply.

### SID volume

`sid_volume.py`, config `[ultimate64].sid_volume`. U64, plus the Ultimate II+'s two emulated stereo SIDs via the same policy (see [`emusid_mixer.py`](#emusid_mixerpy--u2-emulated-stereo-sid-snoop-routing--model-matching)).

The panning sibling, and the reason it exists: **the U64 mixes each source at an independent level, and the two UltiSID levels are commonly `OFF`.** Routing a chip onto an UltiSID core — which multi-SID routing and model autoconfig both do freely — then produces silence *with no error anywhere*: the chip is mapped, the player writes to it, and nothing comes out. Confirmed live on a stock machine (`Vol UltiSid 1`/`2` = `OFF`, `Vol Socket 1`/`2` = `" 0 dB"`), which silently drops the third chip of any 3-SID tune and every ASID chip past the second.

The mirror failure is just as real, and is why unused sources are muted rather than left alone: a tune that deliberately uses the socketed chips is doubled by an UltiSID core still mapped at the same address with its level up — including the LED mirrors this codebase now sets up deliberately.

**The policy**, one source at a time (`target_level`):

| Source | Level |
| --- | --- |
| In use, `sid_volume` entry set | that entry |
| In use, currently `OFF` | `" 0 dB"` |
| In use, at some other level | left alone — a rig trimmed to `-6 dB` is a deliberate choice |
| Not in use | `OFF` |
| Absent from the mixer read | left alone — writing it would make a change with no original to restore |

**Same shape as panning throughout.** A pure planner (`plan_sid_volume`, `resolve_volumes`, label/int conversion) plus one best-effort `apply_volume` that reads the mixer once, writes only what differs, and returns the originals for the caller's restore snapshot. Source derivation is shared, not duplicated — `sid_panning.distinct_sources` decides which sources a tune claims and in what order — so `sid_volume` is indexed by **source**, exactly like `sid_panning`: entry *k* is the *k*-th source claimed, capped at 4.

A configured list is truncated to the source count and padded with *auto*, not with a level: padding with a level would let a one-entry list silently dictate every other source.

**Values.** A dB int (`0`, `-6`, `3`), a label (`"0 dB"`, `"-6 dB"`, `"off"`), or a stringified int. Two firmware traps, both confirmed live via `GET /v1/configs/Audio%20Mixer`:

* the volume items spell it `Vol UltiSid 1`/`2` (lowercase `id`) while the pan items spell it `Pan UltiSID 1`/`2` (uppercase `SID`). The inconsistency is the firmware's.
* every non-negative level carries a **leading space** — `" 0 dB"`, not `"0 dB"`. An exact-match comparison against a stripped string never matches, so the mixer would be rewritten on every setup and the "no change ⇒ no writes" contract would be quietly lost.

The ladder is also **not** a uniform 1 dB fan — `OFF`, `-42`, `-36`, `-30`, `-27`, `-24`, then every dB from `-18` to `+6` — so an int with no representation (`-20`) is rejected at config load rather than snapped to a neighbor.

Applied at the same three call sites as panning, folding into the same restore snapshot: `WaveformScene._apply_sid_volume`, `AsidScene._apply_sid_mixer` (setup and every remap), and `SidFileAudioSource._apply_sid_mixer`.

`tests/test_sid_volume.py` covers the conversions, the policy, the pure planner and the diff-only apply.

### LED mirroring of socketed SIDs

The U64's built-in LED display is driven by **UltiSID core activity**, so a tune playing entirely on socketed chips lights nothing unless a core is also listening at those addresses. Both planners therefore point leftover cores at the socket-served addresses instead of unmapping them (`asid_sidmap.mirror_bases`) — which is how the firmware ships by default (`UltiSID 1 = $D400`, `UltiSID 2 = $D420`, both at `Vol OFF`).

The mirrors carry no chip of their own, so they never appear in `SidMap.sources`, which means `sid_volume` classifies them as not-in-use and mutes them. That is the whole safety story: LEDs from the core, audio from the real chip, and nothing doubled.

Mirroring is skipped unless the UltiSID split is off, since a split core answers a window of 2 or 4 addresses whose extra instances would collide with the real chips. That costs nothing in practice — a split is only ever chosen when both cores are already hosting real chips, leaving nothing spare to mirror with.

**Single-SID tunes are deliberately not mirrored.** They never reach a map planner (there is no address to route), so nothing touches the UltiSID addresses — and the firmware default already parks the cores at `$D400`/`$D420` with `Vol OFF`, so the LEDs light anyway. Adding a mirror there would mean the single-SID path starts writing addressing config it otherwise never touches, breaking the HW-verified rule that an already-matching single-SID tune produces **no REST traffic at all**. The cost is that a machine which has explicitly unmapped its cores gets no LEDs on single-SID tunes; set `UltiSID 1 Address` back to `$D400` on the U64 itself if that matters.

## `midi_scene.py` — MidiScene (live MIDI → SID + oscilloscope)

`MidiScene` (inherits `VoiceScopeRenderer`) turns the C64 into a 3-voice MIDI sound module and visualizes it with the **same** hires oscilloscope as `WaveformScene`. Note on/off → voice freq + gate; pitch-bend → ±2 semitones on gated voices. **Voice allocation** layers a mono melody over a polyphonic sustain pad: held notes keep their voice, and a new note over capacity steals the *most-recently-started* voice (`max` of `_VoiceState.seq`, a monotonic assignment counter — not a timestamp, because `max` breaks ties toward the lowest index and a clock coarse enough to give a chord's note-ons one shared value would therefore steal the pad instead of the newest voice) so the older/held notes form a stable pad while an overlapping line/arp cycles on the top voice; freeing a voice resurrects the most-recent still-held suspended note (LIFO). **Gate-edge hard restart:** the real SID re-attacks only on a gate 0→1 edge, so re-using an already-gated voice (re-press / steal / trill) writes a gate-off control byte *before* the new voice block — without it the chip changes pitch but never re-triggers (silent note while the host-emulator waveform, fed a `retrigger` flag, still moves). The MIDI reader thread coalesces continuous-controller floods (wheel sweeps) to ≤60 Hz so they can't burst the DMA socket; notes stay immediate.

**The reader's drain carries both `_midi.poll_pending` bounds, and the work bound is the scene's own number.** The count bound (`MAX_MSGS_PER_DRAIN` = 64) is shared with `AsidScene` and needs no adjusting. The *work* bound does, because the two readers' per-message cost differs by three orders of magnitude: `AsidScene._handle_sysex` decodes and pokes a shadow, while `MidiScene._handle_msg` reaches `_program_voice`, which blocks on the link **inside** the drain — up to two writes per note message (the gate-off byte that forces the envelope edge on a re-press, plus the seven-register voice block). `poll_pending`'s default `MAX_DRAIN_WORK_S` is 4.167 ms; one Ultimate write is a measured 5.222 ms (`HardwareProfile.write_cost_floor_s`, flat from 8 B to ~2.4 KB). So under the shared default an *ordinary* note pass here is already past its deadline after message one, and every note pays its own 1 ms poll sleep and its own coalescing flush — the opposite of what the budget was reasoning about. `_drain_budget_s(profile)` is what the reader passes instead: never tighter than the shared default (a TeensyROM write is 0.287 ms, so that link keeps the default's larger pass), widened only far enough that a full chord of worst-case notes — `SID.N_VOICES` messages × two writes — retires in one pass. That is ~31 ms on an Ultimate, so a note flood can leave the controller flush up to two periods late; the alternative was arpeggiating a chord across three passes 1 ms apart. The sizing lives on the caller because the caller is what knows its own cost — `_midi` reaching a `HardwareProfile` would invert the layering, and the other caller's number is different.

### Per-voice multi-waveform
Each voice has its own waveform: `self.voice_wave_bits[idx]` (authoritative, combos allowed) and `voice_wave_names[idx]`, built from `midi_voice_waveforms` — empty means all voices share `midi_waveform`. `_program_voice` ORs in `voice_wave_bits[voice_idx]` rather than one global.

`parse_waveform_spec("pulse+triangle")` returns the OR'd bits plus a canonical name; `_PC_WAVEFORMS` and `_WAVEFORM_CYCLE` entries are canonical. The host emulator renders combos faithfully via `sidemu.voice_samples`' 12-bit bitwise AND, so the scope matches the chip's combined wave.

**Three control surfaces**, all opt-in — the default is a shared single-channel pool:

1. **Static** — `midi_voice_waveforms`.
2. **SHIFT** (`cycle_style`) — advances *every* voice one step through `_WAVEFORM_CYCLE`: the four singles, then `pulse+triangle`. Per-voice offsets are kept, so a uniform single-bit set cycles in lockstep while a mixed set keeps its relative spread. `_set_voice_waveform` re-emits per voice, and off-cycle combos advance from their dominant single's slot.
3. **Program Change** (`_program_change`, gated by `midi_program_change`) → waveform. Shared mode sets all voices; multitimbral sets the message's channel.

> `pulse+triangle` is the only combined waveform that reliably sounds on a 6581 — sawtooth and noise combos AND down to near-silence on real hardware, so they stay out of the interactive rotation. `midi_voice_waveforms` can still set them explicitly.

**Multitimbral mode** (`midi_voice_mode = "multitimbral"`): `_handle_msg` routes by `msg.channel` through `_chan_to_voice`, built from `midi_voice_channels`, to `_note_on_mt`/`_note_off_mt`. Each voice is monophonic with its own held-note LIFO, and unmapped channels are ignored. Per-voice ADSR, PW, and filter stay global — deferred.

**Instrument controls.** Velocity maps to loudness: `_program_voice` writes velocity into that voice's **sustain** nibble as `velocity >> 3`.

The CC map:

| CC | Target |
| --- | --- |
| 1 | Pulse width, mapped to an audible `[128, 3968]` window so wheel-to-zero doesn't mute |
| 7 | Master volume |
| 74 | Filter cutoff |
| 71 | Resonance |
| 73 / 75 / 72 | Attack / decay / release |

The filter is audible because `_program_global_sid` routes all three voices through it via `$D417`'s low 3 bits — route none and CC74 sweeps a filter no voice passes through. Cutoff defaults open, so a lowpass patch is neutral until swept. `$D418` writes always carry the filter-mode nibble, so a CC7 volume change can't clobber it.

The key difference from `WaveformScene`: **no py65 host emulator.** MidiScene *is* the writer — it computes every SID byte it sends — so it keeps a 25-byte `$D400-$D418` register **shadow** (`_sid_shadow`, indexed by `addr - $D400`) updated alongside every SID write and feeds `SIDEmulator.update_registers(...)` directly under `_reg_lock`. A re-gate of an already-gated voice (re-trigger / voice steal) shows no off→on edge to `update_registers`, so `_program_voice` passes a per-voice `retrigger` mask to force a hard re-attack (else a plucked sustain=0 voice would flatline after one decay). A background `PollThread` (`midi-env`) advances the ADSR envelopes at the video rate (60/50 Hz) so attack/decay/release tails evolve on screen between MIDI events; render phase is owned by the emulator (advanced by `voice_samples` during render), same as WaveformScene.

Display is fixed bank-0 hires (no relocation — MidiScene uploads no SID payload and leaves the audio ring idle). Bitmap-only ⇒ `_validate_midi` reports a `hires` display so PETSCII overlays are rejected (same as waveform). **Voice strips show activity by color**: `process_frame` change-detects each voice's sounding state (gated or envelope > eps) and repaints its strip color — its configured/per-waveform color while sounding, **gray when idle** (a released voice's flat trace then reads as "off", which is why no per-voice note text is needed). The two bottom text rows are change-detected (repainted only on note/CC events): row 22 = per-voice waveform tags + `VOL nn` (`_build_title_line` via `_abbrev_waveform`: `1:PUL 2:SAW 3:NOI`, combos as `P+T`); row 23 = a live controller readout (`PW nn%  CUT … RES … A. D. R.`). `target_fps` defaults to half the video rate (30/25), like WaveformScene; the scope knobs (`color_mode`/`time_base`/`auto_cycles`/`persistence`/`scroll_columns`/`voice_colors`/`waveform_colors`) all apply.

## `asid.py` + `asid_scene.py` — AsidScene (ASID client → real SID + oscilloscope)

**Framing.** `AsidScene` makes c64cast an ASID **client**: any ASID *host* (DeepSID in a browser, SIDFactory II, Plogue chipsynth C64, Elektron ASID-XP) streams packed SID register writes over MIDI SysEx, and c64cast plays them on the **real SID chip** (U64/TeensyROM) with the shared 3-voice oscilloscope on HDMI. It is a **new input path, not an audio-fidelity change** — ASID carries only SID-synthesizable chip music (never arbitrary/PCM audio; the spec forbids digi and its ≈50-75 Hz frame rate can't reach the DAC's ≈13-14 kHz sample rate), so it does **not** replace the sampled DAC / FPGA-sampler path and is orthogonal to the bus-halt wobble (that wobble lives on the PCM ring path, already solved on the U64 by the off-bus sampler; SID tunes already have a wobble-free resident-player path). See the [ASID spec](https://github.com/thomasj/asid-protocol).

### `asid.py` — the pure decoder
 No mido, no hardware, so it's unit-tested by feeding byte sequences (`tests/test_asid.py`). `decode(data)` takes a SysEx payload (mido's `msg.data` = the bytes between `F0`/`F7`, starting with the `0x2D` manufacturer id), validates the id, dispatches on the command byte, and returns an `AsidUpdate` (or `None` for foreign SysEx). Honored: `0x4E` register data (the workhorse — SID chip 0), **the multi-SID streams `0x50-0x5F` (SID2..SID17 = chips 1..16, same packed format)**, `0x4C`/`0x4D` start/stop, `0x4F` character display, `0x31` speed (PAL/NTSC + multiplier + frame delta + a **buffering-requested** bit in `buffering_requested`), `0x32` SID type (6581/8580, per chip), and **the `0x30` timing recipe** — decoded into `timing_recipe`, an ordered `(asid_reg_id, wait_cycles)` list (`data0` bits 0-5 = register index in write order; `data0` bit 6 + `data1` bits 0-6 = the 0..255 cycle delay after that write). `0x60` OPL-FM **and any unrecognized command byte** come back `dropped=True` — the catch-all is the branch that matters for an untrusted-input decoder, and `tests/test_asid.py` feeds it one. The buffered ring player below honors the recipe, the coalesced path ignores it (a whole-image block write needs no per-register order).

**The wire bounds live here, at the decode boundary.** A `0x30` recipe is a SID *write order*, so it is capped at `MAX_TIMING_RECIPE_PAIRS` (28, the register-table length) and a register id repeated in the order keeps only its first position. Both bounds are load-bearing and neither substitutes for the other: SysEx has no length limit on a virtual/network MIDI port and the recipe persists until the next `0x30`, so an uncapped decode let a 400 KB message turn every subsequent four-register frame into 200,004 ops on the MIDI reader thread — while a fully spec-legal 28-pair recipe repeating one id still pushed a single chip past `asid_player.MAX_OPS_PER_CHIP`, which `pack_slot` then truncated, deleting the *later* chips' writes from the slot. `0x32`'s `chip_index` is likewise clamped to the range the multi-SID commands can produce, so no consumer is handed an index this decoder would never otherwise emit. Every register/type update carries a `chip_index` (0 for `0x4E`, `cmd - 0x50 + 1` for the multi-SID commands, `data0` for `0x32`) so the scene routes it to the matching SID address. The `0x4E` unpack reconstructs each present register's 8-bit value (7 low bits from `register_data`, 8th from the packed MSB bytes) and maps the ASID register ID → SID offset via `_ASID_REG_TO_OFFSET` (keyed by offset `addr - $D400`, so it doubles as a shadow index). **Double control write:** ASID orders the three voice control registers last (IDs 22-27) so a frame can carry a *second* write to each control reg — the gate-off→gate-on hard-restart trick. The decoder keeps the second (final) value in `regs` and surfaces the first in `control_first` for the scene's two-phase emit.

### `asid_scene.py` — the scene
 `AsidScene(VoiceScopeRenderer, Scene)`, `WANTS_AUDIO_LOCK = True`, is the sibling of `MidiScene` (see below): same VoiceScopeRenderer visualization, same MIDI-port plumbing, a 25-byte `$D400-$D418` shadow + `SIDEmulator` **per chip**. The difference is the input — MidiScene *synthesizes* SID writes from notes/CCs, AsidScene *relays* the finished register bytes — so all synth knobs (waveform/ADSR/filter/voice allocation) are gone; ASID carries that state. It has **two playback paths**, selected by `asid_buffered_player` (auto/on/off): the default *coalesced* path and the *buffered* ring player (next subsection). In the **coalesced** path the reader thread drains SysEx into the per-chip shadows and flushes a hardware block write at `_FLUSH_INTERVAL_S` (≤60 Hz) so a burst or high-multispeed tune can't outrun the ≈200 writes/s DMA ceiling (high multispeed is frame-decimated — this is the limitation the buffered path removes). Each flush is one `write_regs(<chip base>, *shadow)` block write **per dirty chip**; a within-frame hard restart first emits the `control_first` values as individual `write_memory` calls *before* that chip's block (so the gate-off pulse reaches the chip), passing a `retrigger` mask to `update_registers`. Bitmap-only ⇒ `_validate_asid` reports a `hires` display (PETSCII overlays rejected). Info rows: title = name + SID count + play state + SID type; meta = the host's `0x4F` "now playing" text if any, else a per-voice waveform + `VOL nn` summary of the primary chip. `0x31` PAL/NTSC switches every emulator clock live. Teardown stops the ring player first (if buffered), then silences every mapped SID, restores the SID-address config (below), and restores bank-0 + the **char-mode** `$D018` (`D018_CHAR_DEFAULT` = `$14`, matrix at bank+`$0400`, bitmap bit clear) — like MidiScene and WaveformScene, which write the same constant for the same reason. All three used to write `D018_HIRES_BITMAP` here while the comment claimed the char-mode default: the scope's own value, left pointing at the bitmap layout. Each scene's teardown test asserts the **literal** `"14"`, not the constant: comparing the byte teardown wrote against the constant it wrote it from compares the code to itself, and setting `D018_CHAR_DEFAULT = 0x18` left all three green. `tests/test_voice_scope.py` supplies the independent half by driving a real char-mode engage from another module and comparing the constant against what the VIC is actually left holding. The next scene's mode engage owns `$D011`; this write only puts the matrix pointer back where a char mode expects to find it, which is exactly what `hires.py`'s teardown does when its flicker handler may have moved it.

**The reader's drain is bounded, and the bound is load-bearing.** mido's `iter_pending()` yields until the port queue is momentarily empty and the rtmidi input queue has no size limit, so a backlog arriving faster than `_handle_sysex` retires it never returns — and the coalesced flush and the `stop` check both live *after* the drain. The consequences were a SID stuck sounding whatever was last flushed, and a reader still live past `teardown`'s bounded `PollThread` join (which `_pollthread` documents as deliberately abandoning the worker), free to land a block write after `silence_sid()`. The loop now drains through `_midi.poll_pending`, which hands out at most `MAX_MSGS_PER_DRAIN` = 64 messages per 1 ms pass and re-checks `stop` inside it; the busiest legitimate stream (16× multispeed, 8 chips) is ~9 messages per pass. `MidiScene`'s reader has the identical shape — an unbounded drain in front of a rate-bounded coalescing flush, with note handling doing DMA writes *inside* the drain — so it uses the same helper rather than a second corrected copy. (`midi_control.py`'s two readers still call `iter_pending()`; they have no post-drain flush to starve, so what remains there is only the teardown-join half — their per-message *logging* cost is bounded by [`_wire_log.py`](config.md#_wire_logpy--wire-triggered-logging-is-o1-per-stream) instead.) The pass carries a **work** bound as well as a count bound — `MAX_DRAIN_WORK_S`, a quarter of the flush period — because 64 messages is not 64 units of work: see [`_wire_log.py`](config.md#_wire_logpy--wire-triggered-logging-is-o1-per-stream) and [`_midi.py`](config.md#_midipy--the-guarded-mido-import) for the measurements. That default is sized for *this* reader's microsecond-per-message consumer and is explicitly not universal; `MidiScene` supplies its own, for the reason its section gives.

**`0x31` at the scene: derive, latch, retune on a window.** `_apply_speed` derives the rate (frame delta wins, else the multiplier against the video rate) and *latches* it; `_retune_if_due` is the half that reaches hardware, and it runs at most once per `_SPEED_RETUNE_INTERVAL_S` (250 ms). It does not re-implement the band — the clamp is `asid_player.clamp_frame_rate`, the constants and the warning text are single-sourced there, and `set_frame_rate` clamps again on the way in. The scene-side clamp exists so `_frame_rate_hz`, which the coalesced path and `setup`'s `start()` both read, agrees with the cadence the CIA was actually programmed for; it sits on the *apply* path so a flood of out-of-band requests cannot spend the log any faster than it can spend the link.

**The retune window is a defense, not a nicety.** Each retune is a blocking CIA-latch write plus a `flush()` round trip on the single-connection DMA socket the render path and `AudioStreamer` share — plus, pre-arm, a full handler re-upload — and `_handle_sysex` runs on the MIDI reader thread. Applying one per message therefore did two things at once: it spent the ~200/s link budget on CIA latches, and it backed rtmidi's unbounded input queue up *behind* the bounded drain, which is what starves the register flush and outlives teardown's join. (The drain's own 64-message bound is not the limiter here: `poll_pending` retires tens of thousands of messages a second when the handler is cheap — only a handler that blocks on DMA makes a backlog grow, so the fix belongs on the blocking path, not on the drain.) The previous throttle deduplicated the *argument* (`rate == _speed_request_hz`), which alternating any two rates defeated, and 999/1000 Hz are both in band, so not even a clamp warning fired. Requests inside the window are **coalesced, not dropped**: the newest is latched and applied when the window opens, and the reader loop calls `_retune_if_due` every pass so a host that changes speed once and then goes quiet still gets its change. Forwarding stays unconditional on arming (Symptom 2 above).

**Setup snapshots the SID-address baseline before anything folds into the session.** `SidHwSession.snapshot()` is first-call-wins by design (the single-snapshot rule), so a `fold()` from the mixer pass makes a *later* snapshot a silent no-op. `AsidScene.setup` used to run `_apply_sid_mixer()` first, which meant the snapshot inside `_reconfigure_chips` captured nothing and the six `MANAGED_ADDRESSING_ITEMS` a remap overwrites — `Auto Address Mirroring` among them — had no restore entry at teardown. A single remote `0x50`-`0x5F` frame was therefore enough to reconfigure the user's U64 SID addressing permanently. Setup now takes the baseline explicitly, before the mixer pass, whenever multi-SID is live.

**Re-activation re-derives the map, and forgets the previous stream.** Playlists reuse scene instances, so `setup` resets `_active_chips` / `_chip_addresses` / `_max_chip_seen` and the window count back to single-chip. Without that, lap 2 kept `_max_chip_seen` from lap 1, `process_frame`'s growth guard (`_max_chip_seen + 1 > _active_chips`) was false, `apply_sid_map` was never re-issued — and the scene went on writing chips 1..N to addresses the teardown restore had already un-mapped. The reset is at the top of `setup`, not in `teardown`, because teardown's silence loop still needs the mapped addresses. `_reset_stream_state` then clears everything else the *wire* owns, and the cadence fields are the ones that reach hardware: `setup` hands `_frame_rate_hz` straight to `AsidRingPlayer.start`, so lap 1's host picked lap 2's CIA rate before a single byte arrived. It also puts the player back to one chip (`reset`) — a stale count is what lets a later remap *shrink* the ring, since `reinit`'s guard only compares against the count the player already holds — and drops the previous tune's queued frames, which would otherwise have become the new stream's prebuffer. The per-chip register shadows go back to zero with them, because the *coalesced* path writes the whole 25-byte image on every flush: a lap-2 frame touching four registers would otherwise carry lap 1's ADSR, pulse widths and filter settings to the chip alongside them, and teardown has already silenced the SIDs, so zero is what the hardware actually holds. `self.system` is restored to `_machine_system` with the emulator clocks: a `0x31` retunes `self.system` to whatever standard the *tune* declares, and the kernal CIA latch a teardown writes back is PAL/NTSC-specific, so anything restoring a hardware default reads `_machine_system` (writing PAL's `$4025` on an NTSC machine leaves the jiffy clock ~3.8% fast).

**Teardown does not delegate C64 quiescence to the player.** After `_player.stop()` it calls `restore_kernal_irq` itself, unconditionally. The player's own restore is correct, but its writer thread can outlive its bounded join, and the scene — not the player's bookkeeping — is what owes the next scene a machine running the kernal IRQ at the kernal rate. Two idempotent DMA ops buy that outright.

### `asid_player.py` — buffered C64-side ring player

Gives cycle-accurate multispeed.

**The problem.** The coalesced path is host-driven, so multispeed tunes (`0x31` up to 16×) drop the intermediate frames between flushes — arps, vibrato, and hard restarts all mangled — and every flush jitters.

**The approach.** Move frame *consumption* onto the C64. U64 only, since it needs a bus-clean `reu_write`. `asid_buffered_player` `"auto"` engages it when `profile.supports_reu`; `"on"` forces it, warning and falling back without an REU; `"off"` always coalesces.

**Producer side (host).** The reader groups the stream by frame — every `0x50-0x5F` between two chip-0 `0x4E` messages, emitted on the next `0x4E`, start, or stop, costing one frame of latency. It serializes each active chip's *frame deltas* into a fixed-size **slot** (`serialize_frame` + `pack_slot`), with the absolute SID address baked in host-side from `_chip_addresses` so the 6502 stays chip-agnostic, then `push_frame`s it to `AsidRingPlayer`.

**A recipe orders registers against each other; it never orders the two writes within one.** `serialize_frame` positions by SID register *offset*, not by ASID register id. A voice's hard restart is two writes to a single control register under two ids — 22+v gate-off, then 25+v gate-on — so the pair goes out as a unit at the first recipe position naming either of them, in frame order, each write still taking the wait its own id was given (so a recipe naming both loses neither). Grouping by id instead meant a recipe that named 25+v but *not* 22+v emitted the gate-on value at the recipe position and the gate-off value afterwards, in the tail append that picks up whatever the recipe omitted: the voice ended the frame gated **off** where the tune had asked for a re-attack. Ids 25-27 are the ordinary control ids, so that was the default outcome for any stream using them, not an exotic one — and the recipe comes straight off the wire (`data0 & 0x3F`), so the correct order has to be a property of the serializer rather than of a well-formed input.

The player REUWRITEs slots into a ring in REU SDRAM at `RING_BASE = $300000`, clear of the mic, sampler, and video regions, ahead of a **computed read head**:

```
read_head = floor((monotonic − gate) · rate)
```

The C64 crystal is exact, so this is fully open-loop: no servo, and **no C64→host reads during playback**, which satisfies the "no rapid U64 reads during capture" rule.

**Consumer side (6502).** A handler at `$C000` — the whole page is free, since AsidScene runs no `$D418` DAC or NMI — is fired by **CIA #1 Timer A** at the ASID cadence and pops one slot per tick:

1. Pull the slot REU→landing-buffer (`$C400`) via a main-RAM src tracker at `$C800`, wrapping at ring end. As with the tracked audio pump, it never trusts the REU read-back.
2. Execute its ops — `[n_ops]`, then `[addr_lo][addr_hi][value][wait]` × n — self-modifying a `STA` target per op and busy-waiting `wait` units of ≈`DELAY_CYCLES_PER_UNIT` cycles each. That reproduces the `0x30` recipe's inter-write timing and hard-restart order.

`n_ops == 0` is a **hold** tick: the SID holds state, which is the graceful underrun pad, with no echo. A tick divider chains `$EA31` every Nth tick so SCNKEY and jiffy stay ≈60 Hz.

**Bring-up arms lazily** — this is hardware-driven, and both symptoms below were observed. `start` prefills holds, uploads the handler, seeds the tracker, programs the CIA #1 latch, and starts the writer thread. But it does **not** swap `$0314` or start the read-head clock until a real-frame prebuffer has accumulated (`_try_arm`).

That matters because the producer is real-time: an ASID host does not begin streaming the instant we install.

* **Symptom 1 — arming eagerly.** The computed read head runs away during the startup gap and lands real frames in already-consumed ring slots. Heard as unbroken holds. Arming when the prebuffer is full instead makes `gate_time` coincide with data flowing, so the write head stays a full `lead` ahead.
* **Symptom 2 — ignoring `0x31` before arming.** `0x31` retunes the CIA latch and re-anchors the cumulative read head, so absolute-slot alignment survives a rate change. It must apply **before arming too**, because a `0x31` almost always arrives at stream start, before the prebuffer fills. Dropping it arms at the wrong video-rate cadence and silently decimates the tune.

**The `0x31` rate is clamped before it reaches the CIA** (`clamp_frame_rate`, ~15-1000 Hz). The ceiling is the protocol's own: the speed multiplier is 4 bits against the video rate, so 16 × 60 Hz is the fastest cadence a host can legitimately ask for. The floor is the hardware's: CIA #1 Timer A is a 16-bit down-counter, so `cpu_clock / 65536` is the slowest it can realize. The clamp is not a nicety — `cia1_latch_for_rate` clamps the *latch*, not the rate, so an unclamped `frame_delta_us = 1` (a legal 8-byte SysEx message) became latch 1: a C64 IRQ every two cycles into a handler that needs hundreds, so the 6510 never leaves it, while the host's computed read head advanced ~511,000 slots/s and the writer chased it flat out over the shared DMA socket. A malformed rate clamps to the *floor*, not the ceiling — slow is the safe direction. **This is the boundary**: the scene's `0x31` handling should derive its rate and hand it here rather than clamping separately. `tick_divider_for_rate` carries its own 1..255 bound for the same reason, because the divider is emitted as an `LDA #N` immediate and `build_player` now refuses a value that immediate cannot hold.

**Arming is one contiguous write, and the pad has a floor.** `_try_arm` runs entirely under the lock `set_frame_rate` needs on the MIDI reader thread, and at a 16× multispeed the prebuffer pins at `RING_SLOTS // 2` = 256 slots — one DMA write per slot was ~1.3 s of held lock with the reader not draining `iter_pending()`. Those slots are contiguous and payload under a few KB is free on this link, so they go out as one transfer (capped at `_MAX_DMA_BURST_BYTES`, like the ring prefill). It also refuses to arm when the prebuffer it drained came up short — stale slots from a chip-count `reinit` satisfy the queue-depth check but not the ring. The writer's underrun pad is batched and paced the same way: it appends `lead_panic` holds in one write and sleeps the time they buy, because nothing else paces that branch and a spec-legal 16× stream that then goes quiet leaves the lead negative forever — unpaced, it padded at the link's maximum rate indefinitely (measured 705 `reu_write`/s against the ~200/s ceiling), taking the socket from the render path.

A chip-count change `reinit`s the player with a new slot size. **The writer `PollThread` is created once and restarted, never replaced**: its "already running" guard lives on the object (see `_pollthread`'s docstring), so discarding it on teardown let a writer still blocked in `reu_write` past the 1 s join be abandoned rather than waited for, and the restart then raced a second writer over one `_write_pos` and one ring — reachable from a single `0x5F` SysEx via `_reconfigure_chips`. The loop exits on its own stop event rather than a shared flag, so a later `start()` can never un-stop it.

**A live writer is a hard precondition, not a warning.** `start()` and `reinit()` both *refuse* when `is_running()` is still true after the stop, because a `PollThread.start()` that declines a duplicate never clears the stop event: the abandoned worker exits on its next check, nothing spawns a replacement, and the player would install, never arm, and stay silent for the whole run while the log claimed it was padding holds. Worse, that worker keeps REUWRITEing at the *old* slot size — and `reinit` assigns `slot_size` right after the stop, so the rest of a blocked burst went out at the new stride, landing 912-byte slots across a 240-byte ring. The 6502 then reads `n_ops` from a mid-op byte and decodes `[value][wait]` pairs as absolute addresses: `STA` anywhere in the C64's 64K, from attacker-supplied SID register values, including `$0314` and the handler itself. A flood of `0x31` blocks the shared DMA socket past the join, and one `0x5F` triggers the `reinit` — so the precondition is checked. Failing it leaves the player **down** (teardown has already handed the machine back to the kernal) rather than half-reconfigured; the next scene activation brings it up once the worker is gone. `_write_slots` also snapshots `slot_size` once per call, so a payload list and the stride it was built for cannot disagree half way through even if the precondition were ever bypassed.

**Teardown restores on "installed", not on "armed", and the arm is locked against it.** `start()` programs CIA #1 Timer A immediately but hooks `$0314` only once a real-frame prebuffer arrives — and the sender controls that absolutely (one `0x31`, no `0x4E` ever, which is exactly the "stream that never sends chip 0" case). Restoring only when `_armed` therefore left Timer A at the wire's rate for every scene that followed: at the 960 Hz band ceiling the machine burns a third of its cycles in `$EA31` with the jiffy clock 16× fast, until a power cycle. `restore_kernal_irq(api, system)` puts back both halves — vector then latch — and teardown calls it whenever `start()` ever touched the machine. The disarm claims that state under the same lock `_try_arm` holds across its whole arm sequence (bounded, so a wedged link can never hang a scene teardown — it warns and restores anyway), and `_try_arm` re-checks the writer's stop event immediately before the `$0314` write. Without both, a writer still inside the arm's blocking DMA when the join timed out finished afterwards and hooked `$0314` → `$C000` *after* teardown returned — with the SID already silenced and the next scene running, against a ring nobody feeds, at the ASID CIA cadence, and with an orphaned handler rewriting the whole REU control block (`$DF02`-`$DF08` + a `$91` fetch-exec) at up to 960 Hz, which the next scene's audio pump reads back as its live write head.

**One gate on the queue.** Every consumer takes slots through `_take_slot`, which drops anything not sized for the current layout. Two of the three call sites used to filter and the blocking `get` in the writer's underrun-pad branch did not — a guard whose failure mode is the arbitrary-`STA` decode above is not one to keep three copies of.

**The frame's cycle cost is bounded, not just its op count.** A `0x30` supplies a wait per write straight off the wire, and `MAX_OPS_PER_CHIP` bounds only the count: 28 ops each carrying the maximum 255-cycle wait cost 9324 C64 cycles for **one** chip — over half a 60 Hz NTSC frame — and two chips at plain 60 Hz already overrun the period. An overrunning frame does not queue politely: the CIA fires again before the handler returns, so the 6510 never leaves the ASID IRQ (jiffy clock and `SCNKEY` dead, the `$EA31` chain running at a fraction of the promised 60 Hz), and because the read head is open-loop by design the host goes on writing at the requested rate while the C64 consumes at whatever it manages, with no way to resynchronize. So `_emit_buffered_frame` prices each slot — `frame_cycle_cost`, which is `PER_OP_CYCLES` per op plus `WAITED_OP_EXTRA_CYCLES` per waited op plus `DELAY_CYCLES_PER_UNIT` per wait unit, all counted off `build_player`'s `oploop` — against `AsidRingPlayer.frame_cycle_budget()`, which is `FRAME_BUDGET_FRACTION` of one consume period at the *machine's* clock (a `0x31` retunes which standard the tune claims, never the crystal the CIA counts). `fit_frame_to_budget` then scales the waits down proportionally, to zero if that is what it takes, and the scene warns once per stream. The waits give because they are the wire-supplied half; every register write still goes out, since a frame whose ops alone outrun the period is the documented v1 frame-fit ceiling and deleting writes would mangle the tune worse than a slow kernal chain that teardown undoes anyway.

**Those three constants are re-derived from the assembly, because "counted off `oploop`" used to be a claim rather than a check.** They were hand-counted literals sitting beside a golden blob of the assembled player, with nothing relating the two: that detects a constant being *edited*, and not the assembly moving underneath it — the direction that produces the 6510 lockup this section is about. Demonstrated by mutation: inserting a `NOP` into `oploop`, regenerating the golden blob to match, and leaving `PER_OP_CYCLES = 65` alone left the whole ASID suite green while every op was under-charged by 2 cycles. `build_player_symbols` now returns the label addresses beside the blob, and `tests/test_asid_player.py` walks `oploop`..`tail` and `dloop` with a table of the 6502's own per-opcode cycle counts, taking each branch the ordinary path takes. An opcode the table does not carry is an error rather than a skip, so a new instruction in the player forces the table to grow. The same pass pinned the *direction* of the model's error: `PER_OP_CYCLES` is the best case (four `LDA ($FB),Y` cost one more each across a page boundary, and a wrapping slot pointer trades the taken `BCC` for an `INC $FC`), so a worst-case op runs ~12% dearer than charged — which is inside the headroom `FRAME_BUDGET_FRACTION` reserves, and is now asserted rather than left unsaid.

Because the producer feeds in real time at exactly the consume cadence, the ring's lead can never *grow* past the startup prebuffer — so the prebuffer is seeded to the full lead for maximum jitter cushion, and a genuine producer stall pads a hold (SID holds its last state — no echo). HW-verified on the U64-II: at a 2× multispeed the buffered player's audio modulates at exactly 2× the coalesced path's rate (measured by spectral flux), i.e. it plays every frame where the coalesced path decimates to ≈60 Hz. The pure builders (`serialize_frame`/`pack_slot`/`slot_size_for_chips`/`build_player` + the CIA-latch helpers) and the ring math are unit-tested in `tests/test_asid_player.py`. `build_player`'s output is pinned by a **golden blob**, and the memory map by literal addresses: every other assertion there is symbolic or structural, so flipping the op loop's `STA $0000` to `STX` — every SID write storing X instead of the value, total silence — or relocating `HANDLER_ADDR` onto the landing buffer the REU pull overwrites each tick both used to leave the whole suite green. Both documented bring-up symptoms above now have a test, and each was verified by re-introducing the failure and watching it go red. Regenerate the blob only for a deliberate handler change, and read the diff opcode by opcode. v1 limitations (documented in caveats): a frame-fit ceiling on the op cost itself, and coarse cycle delay.

### Multi-SID on the U64 (`asid_sidmap.py`)
 When the stream reveals a chip index > 0 and the backend exposes the multi-SID config surface (`profile.supports_sid_config` — U64 only), the scene honors real multi-SID. The **pure planner** `plan_sid_map(n_sids, socket1_present, socket2_present)` decides the U64 address map: it prefers **physical socket SIDs** (chips 0-1 → sockets at `$D400`/`$D420` when detected), then fills the tail from the two UltiSID FPGA cores using the minimal address-line split (`Off`/`1/2`/`1/4`, up to 8 total). The cores sit on the `$D400` page when no sockets are used (chip 0 stays at `$D400`) or the `$D5xx` page when sockets occupy `$D4xx` — the firmware force-aligns a split core's base (`1/2`→`$40`, `1/4`→`$80`), so the `$5xx` page keeps cores clear of the sockets at any split. `Auto Address Mirroring` is disabled so each base responds distinctly. The planner is unit-tested against a Python port of the firmware address math (`u64_offsets`/`split_bits`/`fix_splits`) that asserts the realized instances are distinct and cover the routed addresses (`tests/test_asid_sidmap.py`). Chip count is **detected dynamically**: the reader tracks the max chip index seen; `process_frame` (main thread, to keep display mutation off the reader) grows the map — snapshots the current SID-address config once (via `api.get_config_category`, restored on teardown), applies the new map live (`api.put_config_item`, no reboot / not flashed → reverts on power-cycle), updates routing, and reflows the split scope. The **scope subdivides each of the three voice rows horizontally**, one cell-aligned window per chip (`voice_scope._compute_window_slices`), a 1px gutter between chips; a single chip takes the full row, so waveform/midi render exactly as they do without the split. `asid_multi_sid` (default true) and `asid_max_sids` (1-8) gate/cap it; on TeensyROM or when disabled, extra chips downmix to the primary SID with a one-time warning. See docs/caveats.md.

**The growth request comes from the mapped slot, not the wire index.** `_chip_for` is the routing decision — an index at or past `asid_max_sids` downmixes to slot 0, which is what the shipped example promises ("surplus downmixes") — and the `_max_chip_seen` update reads the same answer. It used to read `min(chip_index, _max_sids - 1)` off the raw wire index instead, so the two disagreed: an ASID stream merely *touching* chip 10 (the protocol addresses up to chip 16) drove a maximal 8-SID remap with no data behind it — eight mapped addresses, eight scope windows of which seven could never be anything but blank, eight panned/volumed mixer sources and a ring-player re-init to the 912-byte slot, all from one 8-byte SysEx.

**The remap's hardware half is guarded and retried.** `apply_sid_map` + `AsidRingPlayer.reinit` run inside a try/except; a raise leaves `_active_chips` and the window count untouched, so the growth guard stays true and the next rendered frame retries (WARNING once, DEBUG while it keeps failing — the retry is per frame). Without that, a raise from `reinit` reached `Playlist._render_scene_frame`, which retires a crashing scene permanently, so a single transient link hiccup ended the ASID set. `_active_chips` is also published *after* `_set_window_count`, never before: the two must move together, because `process_frame` indexes `_scope_emulators()` (length `_n_windows`) up to `_active_chips`.

**A not-yet-mapped chip's frame is carried forward, not dropped.** A chip's first frame arrives on the reader thread before `process_frame` has run the remap, so it has no address yet. The coalesced `_flush_to_sid` leaves it in `_dirty_chips` and flushes the whole 25-byte shadow after the remap; the buffered `_emit_buffered_frame` serializes *deltas*, so clearing the accumulators unconditionally lost that chip's initial ADSR / pulse-width / control setup for good — the host never re-sends it, and the emulator mirror still showed a correctly-configured voice the hardware was not playing. It now clears only the chips it actually serialized (and mirrors only those into the emulators), so the deferred deltas accumulate and go out with the first post-remap frame.

**Two planners, one policy.** `plan_sid_map` above is the *canonical* layout — it chooses its own addresses and knows only which sockets are populated, which is all an ASID stream can tell it (no chip-model information rides the protocol). `plan_sid_map_for_addresses` realizes a `.sid` file's **own** fixed bases and additionally takes `required_models` + `socket_models`, so a socket claims a target only when it carries the model that chip asked for. That is what lets routing and model matching happen in one pass — see [SID Player Autoconfig](#sid-player-autoconfig) for why they cannot be split into two.

Both share the rest of the policy:

* **Unclaimed sockets are explicitly `Disabled`.** A socket left enabled at an address the plan just handed to an UltiSID core answers alongside it, and the tune plays on both chips at once. The disable is unconditional rather than gated on chip detection, because detection is exactly what can't be trusted when a stale config is the problem.
* **Spare cores mirror the socket addresses** rather than being unmapped, so the LED display still lights — see [LED mirroring of socketed SIDs](#led-mirroring-of-socketed-sids).
* **Cores beyond that are `Unmapped`**, so a stale mapping from a previous run can't answer an address this plan didn't intend.
* **A core window never covers an address an enabled socket already answers.** `plan_sid_map` gets this for free by moving cores to the `$D5xx` page; `plan_sid_map_for_addresses` has to enforce it, because it places cores at the file's own bases and the firmware aligns a split core's base *downward*. A four-chip tune whose first address matched the socketed chip's model used to enable SID Socket 1 at `$D400` and put a `1/2`-split core over `$D400` as well — the tune on the real chip and the core at once, the "detuned double" policy point 4 forbids. Core placement now rejects a split level whose window intersects a claimed socket, and if no level clears it the socket claim is dropped rather than the map: every chip audible on emulated cores beats falling back to a canonical layout that ignores the file's addresses.
* **A core base must be one the firmware can express.** `_ULTISID_BASE_WINDOWS` transcribes `u64_sid_base[]` (`$D400-$D7E0` and `$DE00-$DFE0`, `$20`-granular). Bounded only below, any `$20`-aligned address up to `$FFFF` looked realizable and would have been PUT verbatim.
* **A core window never covers I/O c64cast drives itself**, and the test runs on the base the planner *realizes* rather than the one a caller declared. `sid_host_emu._decode_extra_sid_addr` refuses a declared base overlapping `hw.c64.RESERVED_IO_WINDOWS` — but downward alignment moves the base *after* that test passes, so a PSID v4 header declaring `$DF20` and `$DF60` (second/third SID bytes `$F2`/`$F6`, two bytes of a downloaded `.sid`) was covered by one `1/4`-split core at `$DF00`: a live REST PUT putting a SID on the REU's status/command/address/length registers, which the DAC audio pump and the ASID ring player both drive and which the audio NMI handler reads `$DF03` back from mid-transfer. `_plan_ultisid_cores` now checks every `$20`-granular instance a split level realizes and falls through to the next level exactly as the socket check does; running out of levels returns `None`, which the caller turns into a warning plus the canonical-layout fallback. The windows are one tuple shared with the decoder — `$DF00-$DF0A` (REU) and `$DF20-$DFFF` (Ultimate Audio sampler) — because two copies is how they drift apart, and the two together leave `$DE00-$DEE0` as the usable cartridge bases.

The oracle in `tests/test_asid_sidmap.py` asserts each routed chip is realized *by the source the map says plays it*, and that the only address answered by two sources is a deliberate LED mirror. It runs over **both** planners — sweeping `plan_sid_map` across counts × socket combinations and `plan_sid_map_for_addresses` across target sets × socket models × model requirements. Aiming it at `plan_sid_map` alone is why the socket/core collision above shipped under a sentence claiming the oracle already ruled it out.

**Follow-ups (see auto-memory):** the reverse direction — c64cast as an ASID *host* emitting `0x4E` from the `sid_host_emu` register capture to drive external ASID synths; and per-chip color tint / labels on the split scope (v1 distinguishes chips by position + gutter only).

## `sid_hw_config.py` — shared SID hardware-config plumbing

The REST half of every U64 SID story above: snapshot the `SID Addressing` / `SID Sockets Configuration` / `UltiSID Configuration` categories, apply a plan, put the user's config back on teardown. It was extracted from `AsidScene` so `WaveformScene`'s multi-SID support could reuse it verbatim; today it also serves [autoconfig](#sid-player-autoconfig), [panning](#sid-panning), [volume](#sid-volume), `SidFileAudioSource`, `dac_calibration`'s per-socket isolation ([audio.md](audio.md#table-selection-auto-and-per-system-calibration)) and `--doctor`'s SID probes. Two contracts govern everything in it: every function is **best-effort** — a failed config read returns a benign empty default and a failed write logs, because a REST hiccup must never crash a scene — and every caller gates on `api.profile.supports_sid_config` (U64 only: TeensyROM has no config API, and the Ultimate II+ has a config API without any of these categories; the U2+ gets its own smaller surface via [`emusid_mixer.py`](#emusid_mixerpy--u2-emulated-stereo-sid-snoop-routing--model-matching) instead, and the scope draws every chip on any backend regardless).

The `MANAGED_*` item tuples are the module's real contract: the exact `(category, item)` set a snapshot/restore round-trips, which must match both the firmware's names (`u64_config.cc`) and the items the planners emit — a plan that PUTs an item the snapshot didn't record is a change the teardown can't undo. `MANAGED_MODEL_ITEMS` (the UltiSID filter curves) is deliberately a third sibling rather than folded into the addressing or socket tuples: distinct REST category, distinct concern — chip model, not address routing. `_put_all` splits its log level by direction: a *forward* apply that fails deserves a WARNING (the caller wanted that change to take), while a *teardown restore* that fails only leaves the U64 as the user last configured it — DEBUG.

`current_source_map` — which source answers each `$Dxxx` address right now — carries the module's two subtlest decisions. Physical sockets are folded into the map **last**, so they win an `Auto Address Mirroring` collision: when a populated socket and an UltiSID core both report the same address, the socket's real chip is what a listener hears and the core is merely mirroring. That exact collision masked which source was actually audible during the autoconfig hardware verification — one of the two bugs only real hardware surfaced. The v1 simplification: a split UltiSID core is tracked only at its configured base address, not the secondary instance a `1/2`/`1/4` split expands it across, so a chip at that secondary address gets a harmless re-route instead of recognition. `detect_socket_models` exists un-collapsed beside `detect_sockets` because its consumers treat the socket strings ("6581"/"8580") as chip *identity*, not mere presence — the calibration store keys on them.

`SidHwSession` — the one-snapshot restore tracker every consumer holds — is covered with the rule it enforces under [SID Player Autoconfig](#sid-player-autoconfig): `snapshot()` is first-call-wins, mechanically enforcing the single-snapshot rule the per-scene dicts used to uphold by call-site discipline alone.

## `emusid_mixer.py` — U2+ emulated stereo SID (snoop routing + model matching)

The Ultimate II+ has no SID sockets and no UltiSID cores — in a cartridge port, a tune plays on whatever chip the host C64 carries. Its audio jack is fed by two FPGA SID *emulations* instead: `SID Left`/`SID Right` in the firmware's `Audio Output Settings` category, mixed as `Vol/Pan EmuSid1/2`, each snooping bus writes at one configurable base address (`"Snoop $D400"`). Whether a chip is heard on that jack is therefore pure configuration, and the silent-failure modes mirror the ones [SID volume](#sid-volume) exists for — the stock right-side base is not `$D420`, so a 2SID tune ships half-silent with no error anywhere.

**The host C64's own output can't carry a multi-SID tune at all.** A real SID's partial address decode answers the entire `$D4xx-$D7xx` region, so on the machine's own audio out both chips' writes land on the one physical chip and render as mush. The snooped emulations are the only output where a multi-SID tune can sound as authored — which is what makes routing worth doing on this device.

**Routing retargets spare *enabled* sides.** `apply_emusid_routing(api, addresses)` runs before panning/volume at all three tune-playing call sites: a side already snooping a tune address keeps it; a spare side — snooping an address the tune doesn't play, parked in cartridge I/O (`"IO $DExx"`), or merely duplicating an address another side already covers — is retargeted to the first uncovered tune address, in chip order (an uncovered chip made audible beats a covered one doubled). A side the user *disabled* is never touched: enabling hardware they turned off is a bigger intervention than retargeting what they left on. The snoop-base enum covers only the twelve standard multi-SID addresses, so an inexpressible address (ASID's third chip at `$D440`) stays uncovered — warned, never snapped to a neighbor. Originals fold into the caller's `SidHwSession` restore set like every other mixer write.

**One category is the whole surface, and the capability is evidence-based.** `Audio Output Settings` is registered only by the U2/U2+/U2+L firmware (`audio_select.cc`; the U64's `u64_config.cc` registers `Audio Mixer` instead), so `Ultimate64API.refine_capabilities` grants `profile.supports_emusid_mixer` from the same `GET /v1/configs` it already makes to revoke `supports_sid_config` — zero extra round-trips, and the two flags are mutually exclusive in practice. Unlike the optimistic multi-SID claim, this flag stays conservative-False on an unprobed run (`--skip-probe`, probe failure), which keeps exactly the pre-flag behavior; and `read_emusid_category` additionally requires the enable fields to be present in the read-back, so a surface that can't be read is never written (the firmware answers a GET for a missing category with HTTP 200 and an empty body). Field names and both enum ladders were confirmed live and against the firmware source — they are byte-identical to the U64 mixer's, leading space in `" 0 dB"` included.

**Panning, volume, and the resolved verdict ride the shared machinery.** The two sides are ordinary mixer sources named `emusid1`/`emusid2` (after the `Vol/Pan EmuSid1/2` items — the firmware's Left/Right names are historical, each side has its own pan), merged into `sid_panning.PAN_ITEM`/`sid_volume.VOL_ITEM`; `mixer_category_for` resolves which category a backend's items live in, and `sources_for_addresses` derives each chip's source from the snoop topology instead of the U64 address map. One merged item map is safe because a backend only ever derives its own surface's sources, and a planner probing the other surface's item finds no current value and leaves it alone. The volume policy lands unchanged: each chip's primary side is made audible, every other side — including a redundant mirror of a covered address — is muted, and the user's doubling comes back at teardown. [`sid_resolved`](#sid_resolvedpy--the-resolved-audio-line) reads the same category back for its verdict.

**Teardown must silence every routed chip *before* the config restore.** The emulation's voice state survives a machine reset (HW-verified: a mid-note side kept droning through the app's exit reset *and* an explicit `machine:reset`, and only a bus write to its registers stopped it). So a teardown that restores the snoop bases first strands a still-ringing side at its home address, where no c64cast write will ever reach it again — the drone persists until someone writes that address by hand. `WaveformScene.teardown` and `SidFileAudioSource.teardown` therefore zero all 25 registers at every non-`$D400` tune address (the same idiom `AsidScene.teardown` already used) after the kernal vector restore and before `SidHwSession.restore()`. There is no allowlist at the teardown loop itself, and deliberately so: the guarantee that those addresses are SID addresses now lives at the source, in `_decode_extra_sid_addr`'s PSID-window validation and `detect_sid_addresses`' distinct-base rule (see ["Host-emulation budgets"](#host-emulation-budgets-and-what-a-tune-is-allowed-to-declare)). Validating once, where an untrusted header byte becomes an address, is what keeps every consumer of that tuple safe — the trap map and the hardware routing as well as this write. This ordering also closes a latent U64 gap: extra chips at `$D420`+ were never silenced at scene teardown at all (real chips self-heal at the app's exit reset, but between playlist scenes a gated-on voice could sustain into the next scene).

**Model matching is the short version of autoconfig.** `apply_emusid_model(api, addresses, required_models)` runs straight after routing at both `.sid`-playing call sites, under the same `[ultimate64].sid_model` knob as [SID Player Autoconfig](#sid-player-autoconfig): each side snooping a tune chip is set to the 6581 or 8580 that chip asked for. The U64 version needs a three-step ladder because matching there means *finding a different chip* — swap sockets, else fall back to an FPGA core, else give up. Here the side already is an emulation, so it is simply told which chip to be: a mismatch is always fixable in place, nothing is ever displaced, and there is no "no matching hardware" branch to warn about. `Filter Curve` and `Combined Waveforms` are separate config items but move together — a side on an 8580 curve with 6581 waveform combining emulates neither chip — and the firmware's `sidchip_sel` ladder for both is exactly `6581`/`8580`, with none of the UltiSID's `8580 Lo`/`8580 Hi`/`6581 Alt` variants to pick between. The pass re-reads the category rather than reusing routing's copy, so the models land on wherever each chip actually ended up; the U64 path re-derives after a map for the same reason. A requirement the ladder can't express is skipped rather than approximated, which covers the header's "unknown" and "6581+8580" without a separate check, and a chip no side snoops is left alone — routing has already warned that it is inaudible here.

**What model matching still can't reach: the host machine's own SID.** On a U2+ the tune also plays on whatever chip the host C64 carries, out the machine's own audio jack, and no amount of emulated-SID configuration changes that physical chip. So a tune asking for the other model gets a matched pair of emulations *and* an unmatched host chip — which is exactly why [`sid_resolved`](#sid_resolvedpy--the-resolved-audio-line) reports the two routes as separate clauses on one line, and keeps the WARNING when either disagrees with the tune.

Deliberately out of scope for now: enabling a disabled side, and multi-SID ASID streams on the U2+ (`AsidScene`'s `multi_sid` gate still requires the U64 surface; its routing call covers the single-chip case). `AsidScene` takes no model pass on either surface — an ASID stream carries no PSID header to match against. `tests/test_emusid_mixer.py` covers the label round-trip, the topology read, both planners, and the gated applies; the teardown ordering and the model round trip are pinned in `tests/test_waveform.py` and `tests/test_audio_source_sid.py`.

## `sid_resolved.py` — the resolved-audio line

One log line, emitted once per scene setup after routing, model matching, panning and volume have all settled, naming the chip a listener will actually hear:

```
sid hardware: $D400 → ultisid1 (8580 Lo) @ 0 dB Center
sid hardware: $D400 → socket1 (6581) @ 0 dB Center — tune wants 8580
sid hardware: $D400 → ultisid1 (8580 Lo) @ 0 dB Center; also audible: socket2 (6581) at $D420 @ -6 dB
```

**Why it exists.** Every planner above logs its *intent* and none logs the outcome, and they can disagree without producing an error anywhere — the config PUTs all succeed. A core can be configured and never reach the mixer; a socket can keep answering an address a core was just handed; a level the user trimmed to `OFF` can silence a perfectly routed chip. The only symptom is wrong-sounding or silent playback, and diagnosing it means reading four REST categories by hand — which is exactly how the mirroring bug under [SID Player Autoconfig](#sid-player-autoconfig) was found, after a hardware session spent proving that a log saying `→ ultisid1 (8580 Lo)` described a chip nobody could hear.

**It is a read-back, not a summary of the plans.** The planners are the thing it exists to catch, so it re-reads `SID Addressing`, `SID Sockets Configuration`, `UltiSID Configuration` and `Audio Mixer` and reports what they say. `SidHardwareState` holds that snapshot; `describe_resolved_audio` is a pure renderer over it, so the whole verdict matrix is unit-testable without hardware.

**The verdict drives the log level.** A chip that is unmapped, muted, or on a model the tune didn't ask for makes the line a WARNING; otherwise INFO. Model matching compares by prefix, so a core's `"8580 Lo"` satisfies a header asking for `"8580"`. Two deliberate non-verdicts: a level the mixer didn't report counts as *audible* (claiming silence we never measured sends someone hunting a mixer problem that isn't there), and an empty `required_models` — an ASID stream, which carries no PSID header — reports routing and audibility only.

**Bystanders** — sources the tune doesn't play on that are still audible — are drawn from the address map rather than the mixer, so a source that is merely unmuted but answers no address (a disabled socket the user never turned down) isn't reported as something they can hear.

Called from all three SID hardware paths: `WaveformScene._apply_sid_hw_config`, `SidFileAudioSource._apply_sid_mixer`, and `AsidScene._apply_sid_mixer` (which re-emits after every remap, since a stream growing past 2 chips spills onto cores). Best-effort, and silent on any read failure. `tests/test_sid_resolved.py` covers the renderer and the read-back.

**The emulated-stereo-SID read-back.** A backend without the multi-SID surface but with the U2+ surface renders from [`emusid_mixer`](#emusid_mixerpy--u2-emulated-stereo-sid-snoop-routing--model-matching)'s one category instead (`read_emusid_hardware_state`, same `SidHardwareState` shape): the side snooping each chip, its `Filter Curve` as the model, its `Vol/Pan EmuSid` items as level and pan — `$D400 → emusid1 (6581) @ 0 dB Left 3`. The declared host-SID verdict below is *appended* to that line rather than replaced by it, because on such a device the host machine's own SID plays the tune too, just on a different output; a mismatch on either route keeps the WARNING.

**The declared-host fallback (`[hardware].host_sid_model`).** A backend without the multi-SID config surface (TeensyROM has no config API; the Ultimate II+ has one without the SID categories) can't read any of this back, and originally the line was simply skipped there — which also skipped the single most audible verdict, the model match. Nothing on such a link can *ask* what chip the host C64 carries, but the user can declare it: `[hardware].host_sid_model` (`auto` | `6581` | `8580` | `unknown`) rides in on the backend profile (resolved by `make_backend`, next to the NTSC/PAL frame-rate resolution it already does), and `describe_declared_audio` renders the primary chip against it — `$D400 → host SID (6581 declared) — tune wants 8580` as a WARNING. `auto` applies the NTSC=6581 / PAL=8580 convention, which is weak enough that the line says `assumed` rather than `declared` and the convention itself is logged once per run, explicitly as an assumption; `unknown` opts out of the verdict entirely. The fallback fires only when the backend *can't* read (`profile.supports_sid_config` false), not when a capable backend's read fails transiently — on a U64, "host SID" would be a wrong claim about a machine with four possible sources.

**Per-chip declaration (`[hardware].host_sid_chips`).** The single-chip reading above held only as long as "can't route extra chips" implied "has only one chip". A C64 with an internal dual-SID mod (ARM2SID, SIDFX, DualSID) breaks that inference: it answers at a second address in its own hardware, so a multi-SID tune plays on both chips with no routing whatsoever — the mod has already done in silicon what `plan_sid_map_for_addresses` does in config. The old wording told such a user their second chip was inaudible while they were listening to it, which is the worst direction for this line to be wrong in, since its whole purpose is to be trusted over one's own ears.

So the declaration widened rather than the inference: `host_sid_chips` is a `{hex address: model}` table (validated at load — a typo would otherwise surface as a chip quietly missing from the verdict), resolved to sorted `((address, model), ...)` pairs on the profile by `resolve_host_sid_chips`, and `describe_declared_chips` gives each of the tune's chips its own verdict against whatever is declared at its address. It supersedes `host_sid_model` outright when present, and clears `host_sid_model_assumed` with it: a machine described chip by chip leaves the NTSC/PAL convention nothing to infer, so the once-per-run guess warning would be noise. A tune address with no declared chip renders as `no chip declared` and is *not* clean — on a partly-declared machine that is the honest statement, and dropping it would hide the chip most likely to be misplaced. Unlike `describe_resolved_audio` there is no bystander clause: a declared chip the tune doesn't drive receives no writes and makes no sound, and this line is about what a listener hears.

Nothing in the audio path changed for any of this. The player already `JSR`s the tune's own play routine, so `STA $D420` reaches the bus and whatever sits there answers; `_decode_extra_sid_addr` accepts every window the PSID spec permits — `$D420-$D7E0` and `$DE00-$DFE0`, even bytes only — minus the bases whose 25-byte register window reaches hardware c64cast drives itself, which today means the whole `$DFxx` page: the REU command registers at `$DF00-$DF0A` and the Ultimate Audio sampler at `$DF20-$DFFF` (`hw.c64.RESERVED_IO_WINDOWS`, and the paragraph on decode-time validation above). What remains of the cartridge-I/O window still collides with a TR+ or U2+ occupying the port — a hardware conflict, documented in caveats.md, not something code can resolve. It does *not* accept the whole `$D000-$DFF0` I/O page: that was never the spec, and a header byte naming a CIA or the VIC turned scene teardown into a 25-byte write over `$DC00`. The declaration affects what gets *said*, and — via `host_chip_fit` below — which tune a pool picks. It never changes a chip.

**Tune selection (`host_chip_fit` + `[hardware].host_sid_tune_match`).** The verdict tells a listener their tune doesn't suit the machine; on a link that can't re-place chips, that is all it can do, because the chip is what it is. The free variable is *which tune* — a `waveform` scene whose `file` spec resolves to a directory or glob picks one at random per `setup()`, and it can pick with the declarations in mind. `host_chip_fit` is that predicate, and it routes through `describe_declared_chips` / `describe_declared_audio` rather than re-deriving the match: a picker that disagreed with the line logged moments later would be worse than no picker at all. `WaveformScene._order_by_host_fit` partitions the *already-shuffled* pool (so the grouping is a bias on a random order, not a reordering that makes one tune the deterministic pick for a whole class of machines) and `prefer` keeps the misfits as a fallback tail while `require` drops them. Candidates are judged from `_HOST_FIT_HEADER_BYTES` of each file — the PSID header ends at `$7C` and the extra-SID address bytes are its last relevant fields — so an HVSC-sized directory costs short reads rather than a full load per tune.

**The undeclared machine (`_warn_unplaceable_chips`).** The per-chip verdict and the pool picker both need a declaration to say anything, and that leaves the largest population — machines that have declared nothing — with no statement about the case likeliest to be a mistake: a `_2SID.sid` picked out of a collection and played on a stock C64. The asymmetry was backwards. Someone who described their hardware carefully got `$D420 → no chip declared`; someone who described nothing got an INFO line at most, and on a U2+ nothing at all, while listening to six voices' worth of writes pile onto one three-voice chip.

So this warning depends on no declaration. It can, because the assumption runs the safe way: chip 0 is excluded outright (every C64 has a SID at `$D400`, declared or not, so including it would fire on ordinary single-SID tunes), and for the rest "this machine has one SID" is true unless someone deliberately installed a mod — the false-positive case is a user who can silence it permanently with `host_sid_chips`, which is the same nudge the declaration wants anyway. It lives beside `_warn_output_split` rather than inside `_declared_host_verdict` because that function returns `None` on an undeclared machine, which is exactly the case being closed; folding the check in there would also flip every 2SID tune's verdict line to WARNING on a U2+ where the emulated side is fine.

Two wording branches. The address split matters: a chip inside `$D400-$D7FF` collapses onto the primary (partial decode), while `$DE00`/`$DF00` is cartridge I/O and makes no sound at all, and calling the second one a collapse would be wrong. And on a U2+ the emulations *do* play the tune as authored, so the warning names the Ultimate's own jack — and suppresses `_warn_output_split` for that tune, since both end in "listen on the Ultimate's jack" but the split warning blames the chip *model*, which is the wrong diagnosis for a chip that isn't there. Suppression is per tune, not a global mute: `_output_split_logged` is only spent when that warning actually fires, so a later model-mismatched tune still gets it.

Three no-opinion cases return `None`, and the caller treats each as "don't filter". `supports_sid_config`: the U64 re-places chips per tune, so no tune is a poor fit. An *assumed* model: the NTSC/PAL convention is weak enough to warrant a warning but not weak-tolerant enough to justify dropping files out of someone's directory — the verdict may act on a guess, selection won't. And nothing declared at all. The asymmetry between the two declarations carries over from the verdict: `host_sid_chips` describes the whole machine so an undeclared tune address fails (this is what skips 2SID tunes on a single-SID machine), while `host_sid_model` judges the primary chip's model alone — it names a chip without claiming it is the only one, and inferring a chip *count* from it would reject working tunes on a machine whose second chip we were never told about. Default is `off`: a directory the user pointed at is a statement of what they want played. `require` falls back to the unfiltered pool with a WARNING when nothing fits, so a mis-declared machine surfaces as a log line rather than a scene that can never start.

## `songlengths.py` — HVSC SongLengths lookup

The High Voltage SID Collection ships `Songlengths.md5`, mapping each SID file's MD5 to per-subtune durations; a hit is what lets a waveform scene run exactly as long as the tune instead of a guessed `duration_s` (the precedence — explicit duration > DB > fallback — is [`WaveformScene`'s](#waveformpy--sidemupy--sid_host_emupy--sid-oscilloscope-scene)). Loading is `scene_factory._load_songlengths`' job ([config.md](config.md#scene_factorypy)): memoized per path, and when `[playlist].songlengths_file` is unset it auto-detects an unpacked HVSC under `assets/sids` — memoized including the not-found result, since an HVSC tree is tens of thousands of files; an explicit empty string opts out.

The one hard-won fact in the module is the key. The shipped database is keyed by a **plain MD5 of the entire raw file, header included** — not the field-selective fingerprint libsidplayfp's `SidTune::createMD5()` computes (which deliberately excludes the free-text name/author/released fields so re-tagged rips still match). The data-only digest looked right and failed silently: tunes present in the database reported "not found". `md5_of_sid`'s docstring carries the verification against shipped entries.

Parsing is tolerant by line — comments, malformed lines, and non-MD5 keys are skipped, never fatal — but *positional* within an entry: an unparseable duration is kept as a `None` slot so the 1-based subtune indexing (PSID convention) stays aligned for the durations that did parse. `LengthsDB` is the hold-it-open form; the `song_length` convenience re-reads the file on every call and says so — `scene_factory`'s memoized loader is the long-lived holder in practice.
