## `ensemble.py` — audio slot coordination

**Ensemble audio coordination.** In ensemble mode (`[ensemble]` in the master TOML) at most one system's playlist may hold the ensemble audio slot — tracked as `Ensemble.audio_holder` + `audio_lock` in [ensemble.py](../../c64cast/app/ensemble.py). Scenes whose class sets `WANTS_AUDIO_LOCK = True` (`VideoScene`, `WaveformScene`, `MidiScene`, `LauncherScene`) try to claim the slot in [`playlist_support.EnsembleCoordinator`](#playlist_supportpy--playlist-collaborators)`.resolve_next_index`; on contention they get **skipped** to the next non-gated scene in the playlist, with `Playlist.safe_teardown` releasing the slot when the holder's scene ends. (`LauncherScene` overrides `competes_for_audio_lock()` so `bypass_audio_lock = true` opts out — several systems can then run interactive launchers at once, each player hearing their own SID.) Live scenes (`WebcamScene`, `BlankScene`) are built with `audio = None` in ensemble mode regardless of TOML — they never compete for the SID. Single-system runs keep `ensemble = None` and bypass the gate entirely. An ensemble system whose playlist is entirely audio-bearing scenes will idle when the slot is held elsewhere; the loader emits a WARNING on this configuration.

## `orchestrator.py` + `orchestrators/` — cross-ensemble scene coordination

The framework for a scene that spans **all** systems in an ensemble instead of running on one. When a system's playlist enters a scene with `orchestrate = true` (`SceneCfg.orchestrate`; requires `name`, ignored single-system), that system becomes the **conductor**: `resolve_orchestrator(scene_cfg)` picks the `Orchestrator` subclass that `claims()` the scene's shape, and every *other* system is interrupted and runs a **follower scene** until the conductor releases it.

Two patterns share one interface. **Span** (shipped: `BigTextSpanOrchestrator`) — each follower renders a *slice* of the conductor's content, so N screens act as one 320·N-pixel canvas. **Mirror** (not yet implemented) — each follower renders the *same* content in lockstep (synchronized video / SID / a webcam only one system is wired to); same protocol, the snapshot just carries different state.

**Registry.** `@register_orchestrator` appends to a process-wide list at import time; subclasses live in `c64cast/app/orchestrators/` and only register if imported, so `c64cast.app.cli` imports the package at startup. `resolve_orchestrator` raises `OrchestratorError` when **zero or more than one** subclass claims a scene — both are configuration bugs, and the design deliberately surfaces them at load time rather than leaving them to be debugged from a broken broadcast.

**Event plumbing lives on `Ensemble`, not the orchestrator.** `ensemble.broadcast_interrupt` / `broadcast_resume` are per-system `threading.Event` dicts (`populate_broadcast_events`), and `ensemble.active_orchestrator` is a single-slot field. This split matters: each follower playlist holds a reference to *its own* ensemble event, so a wake-up is delivered regardless of which orchestrator instance owns the current broadcast. `begin(cfg)` returns `False` (rather than raising) if a broadcast is already running, so the conductor's playlist falls back to rendering locally instead of hanging; it **clears leftover resume events before setting the interrupts**, so the new cycle's `end()` is unambiguously the one that fires them. `end()` is idempotent.

**Follower side** is `playlist_support.EnsembleCoordinator.handle_broadcast_interrupt` (driven from the run loop when the playlist's `broadcast_interrupt` event — wired by `Playlist.bind_ensemble` — is set). It saves the current scene index, tears the current scene fully down (overlays hold threads/network state, so a half-teardown leaks), builds the follower scene via the injected `build_follower_scene` factory, stamps the role via `scene.bind_orchestrator(orch, conductor=False, index=…)`, spins `run_one_frame` until `broadcast_resume` fires or `stop_event` is set, then tears down and restores the saved index. Two guards worth knowing: a **stale** interrupt (orchestrator ended between `set` and the check) is ignored rather than fatal, and the conductor install **skips a scene that already has an orchestrator** — the follower's fallback cfg can *be* the conductor's `orchestrate = true` cfg, so without that check a follower would clobber its own role and become a second conductor. `EnsembleCoordinator.release_scene` clears both `ensemble.active_orchestrator` and the scene's stamp (`scene.clear_orchestrator()`), because a scene object is reused across loop iterations and a stale stamp would suppress the next setup.

**Follower cfg resolution.** `follower_scene_cfg_for(name)` prefers a scene in the follower's own per-system TOML with the same `name` **and `orchestrate = false`** (so per-system visual params take effect without minting a second conductor), else falls back to the conductor's cfg. `follower_only = true` marks a scene as available for this override but excluded from normal rotation.

**Subclass hooks** are non-abstract by design (`_on_begin` / `_on_end`) so a subclass opts in only when it has per-broadcast state. `_on_begin` may **raise `OrchestratorError` to refuse a broadcast**, and the exception propagates out through `begin()` so the conductor surfaces a clean error rather than starting a half-built broadcast. `snapshot()` is the one abstract state channel and is called from **follower render threads**, so it must be thread-safe.

**`orchestrators/big_text_span.py`** is the worked example. It `claims()` a `blank` or `mcm` scene carrying a `big_text` overlay, and refuses in `_on_begin` unless the conductor is the **rightmost** system — the message enters from the right edge of that screen, so any other conductor is geometrically wrong. It keeps its own `_state_lock` separate from the base's `_lock` so follower `snapshot()` reads don't contend with `begin`/`end`. One ordering subtlety drives two comments in the file: the conductor's overlay calls `publish_bits` **before** `begin()`, so followers see populated state the instant their interrupt fires — which is why `_on_begin` resets only `_abs_scroll_px` and leaves `_bits` alone, and why `_bits` is allocated in `__init__` rather than per-broadcast. `local_x_left_px(follower_index, abs_scroll_px)` is a pure function (unit-tested directly) mapping a system's left-to-right index to its window into the shared canvas; `end_threshold_px` tells the conductor when the message has cleared the leftmost screen.

## `paths.py`

The single source of truth for **where machine-local files live**, so the app works identically from a repo checkout or an installed wheel. Repo-anchoring a data path via `Path(__file__).resolve().parent.parent` is a latent bug for any non-editable install, which is why nothing in `dac_calibration_store`, `transport`, or `wled_device` resolves one itself.

**Two structural rules.**

* *Stdlib-only, and it deliberately imports nothing from the package.* That puts it at the bottom of the dependency graph, so config, transport, doctor, and cli can all import it without a cycle.
* *Everything is a function, never a module constant.* Env overrides are therefore read late, on each call, so a test can redirect them with a plain `mock.patch.dict(os.environ, ...)`. Every call site is a cold path anyway — config load, calibration save, preset-store construction.

**The resolvers.**

| Call | Resolves to |
| --- | --- |
| `settings_path()` | The machine-settings TOML: `$C64CAST_SETTINGS`, else `<config base>/c64cast/settings.toml` |
| `data_root()` | The persisted-data base: `$C64CAST_DATA_DIR`, else `<data base>/c64cast` |
| `calibration_dir()`, `presets_dir()`, `loop_presets_dir()` | Derived from `data_root()` |

Config base is `%APPDATA%` on Windows, else `$XDG_CONFIG_HOME`, else `~/.config`. Data base is `%LOCALAPPDATA%`, else `$XDG_DATA_HOME`, else `~/.local/share`.

**`legacy_data_root()`** returns the old repo anchor **only** when a `pyproject.toml` sits there — that is, a source checkout rather than an installed package. It is consumed solely by `legacy_presets_dir`, behind `transport.warn_if_legacy_presets_orphaned`'s one-time heads-up; [`doctor.py`](#doctorpy--config-and-environment-diagnostics)'s data-dir probe deliberately doesn't nudge — stale legacy files are surfaced at use time by the resolver that knows which store was actually looked for. There is no implicit migration.

### Packaged resources — `example:NAME`

The same module also answers "where do the files we *ship* live", for the two trees that had to move **under** the package so setuptools could put them in the wheel (`[tool.setuptools.package-data]`): `c64cast/examples/*.toml` (+ `examples/ensemble/`) and `c64cast/data/c64cast.schema.json`. Before that they sat at `config/examples/` and the repo root, i.e. nowhere an installed user could reach — which broke the entire documented onboarding path (`--config config/examples/hello.toml`) for anyone without a checkout.

| Call | Resolves to |
| --- | --- |
| `examples_dir()` | `<package>/examples` |
| `packaged_schema_path()` | `<package>/data/c64cast.schema.json` |
| `example_config_paths()` | Every packaged config: top-level demos sorted, then sub-directory ones (`ensemble/`) |
| `example_name(path)` | The `example:` name — path relative to `examples_dir()`, suffix dropped (`hello`, `ensemble/master`) |
| `resolve_example(name)` | That name back to a path; `ValueError` with `difflib` suggestions otherwise |
| `resolve_config_spec(spec)` | `example:NAME` → real path; anything else (incl. `None`) passes through |

**Why a real filesystem path, not a `Traversable`.** `_package_dir()` goes through `importlib.resources.files("c64cast")` so any loader answers, but then *insists* the result is a `pathlib.Path` and raises otherwise. Two reasons: a config is handed to `open()`, and an ensemble master resolves its per-system files relative to **its own directory**, which a read-only `Traversable` cannot express. Every install shape c64cast supports unpacks to real files; a zipimport does not, and the explicit error beats a later `TypeError` from `open()`.

**One hook.** `cli._resolve_configs` calls `resolve_config_spec(args.config)` on its first line, so the prefix is gone before anything reads the value. The loader, the ensemble per-system resolver, `--doctor`, the SIGHUP reload and the live-tune write-back therefore need no knowledge of it. A bad name is a *usage* error (exit 2 via `main`'s `ValueError` handler), not a `ConfigError` — nothing was wrong with a config, the name just didn't exist.

**The two discovery commands** live with the other config-free ones in `run_introspection`. `--list-examples` renders `introspect.render_list_examples()`, which *generates* the index by reading each file's own leading comment paragraph (first sentence, `Single-scene demo:` prefix and `(see <URL>)` citations stripped) — the hand-kept Markdown table it replaced had drifted about 15 files behind, and a generated one cannot. It tags demos whose **scene** `file` points at `assets/` as needing user media; an overlay's `file` (the `logo` one) is deliberately not counted, because that overlay draws a placeholder when the file is missing and the demo runs as shipped. `--print-example NAME` writes one to stdout, which is the supported way to get an editable copy — the packaged original lives inside the install and is not meant to be edited in place. That is also why `config_serialize.schema_directive_for` resolves against `packaged_schema_path()` (relative while the schema is near the output file, absolute for a user-level install) rather than hunting for a repo-root schema that no longer exists.

**The URL fallback is version-pinned.** When no local path works, `config_serialize.DEFAULT_SCHEMA_PATH` is the raw-GitHub URL built by `_published_schema_url(__version__)`, naming the release's own tag (`v0.1.0`) so an editor validates against the schema that version accepts. A checkout has no tag to name — `__version__` is the `"0+unknown"` fallback — and gets `main`.

**Which is also why it is the *fallback*.** A pin is the only directive form an upgrade leaves behind: it names a snapshot, and nothing reads the line at run time, so the file keeps loading while the editor quietly judges it by a release the user no longer has. The local path has the opposite property for free — an upgrade rewrites `<package>/data/c64cast.schema.json` in place, so a config pointing there tracks the running install release after release with nothing to maintain. That is the whole reason `--print-schema-path` exists as a command (`cli_commands.run_introspection`, honoring `--config` because the answer is relative from inside a checkout): the User's Guide used to print a pinned URL and tell the reader to substitute their version by hand, which is a maintenance task disguised as a one-time setup step — and the example it printed had itself been stale since 0.1.0. Moving *ahead* of the install is not the fix and no surface offers a `main`/`latest` address: a schema newer than the program stops flagging real mistakes and starts offering keys the loader will reject, which is strictly worse than lagging. `pinned_url_version` reads a pin back out (anchored, so a fork's URL isn't mistaken for one of ours) for the `--doctor` check below.

## `config.py`

Dataclasses for each section, `load()` parses TOML, `merge_cli()` overlays argparse values (only non-None ones — argparse defaults to None for every overridable option so the merge is unambiguous). Turning the validated config into live scenes is [`scene_factory.py`](#scene_factorypy)'s job.

**`scene_color(cfg, s)`** resolves a scene's effective `[color]`: the global section untouched when `s.color` (the `[scenes.color]` sub-table) is empty, otherwise a deep copy with the scene's authored keys applied over it. `s.color` is a raw `dict[str, Any]` — the TOML keys as written — rather than a nested `ColorCfg`, specifically so a scene can override a field back to its *dataclass default* even when the global section set it away from that default; a "differs from `ColorCfg()`" merge (the machine-settings cascade's idiom, below) would read such an override as unauthored and let the non-default global win. `load()` pops the `color` table out of a `[[scenes]]` entry before `_apply_section` (mirroring the `overlays` pop) and validates its keys against a throwaway `ColorCfg()` for the same unknown-key difflib hint a top-level `[color]` typo gets. `[scenes.color]` is per-scene-file syntax, not a cascade layer — it is resolved once, inside a single loaded `Config`, and never touches `_CASCADE_SECTIONS` or the master-defaults machinery below (`[[scenes]]` never cascades at all).

### Machine-settings layer

**The shared apply loop.** `_apply_toml_sections(cfg, data, *, source, unknown=None)` — the scalar sections, the `[color]`/`hue_corrections` special case, and the validator battery — was extracted from `load()` so the project file, the machine-settings file **and the ensemble master** go through identical code. Same unknown-key handling, same validations.

The master used to be the exception, with a hand-written tuple of `(section, dataclass)` pairs in `load_master` standing in for the loop, and the two had drifted: six sections a master file may legally carry (`[hardware]`, `[teensyrom]`, `[vision]`, `[dsp]`, `[audio_features]`, `[wled]`) never reached `_apply_section` at all, so they produced neither an applied value nor an `UnknownKey` — no warning, no doctor row. `[hardware]` and `[teensyrom]` are *listed in `_CASCADE_SECTIONS`*, so the cascade dutifully ran over a `defaults.hardware` nothing had populated and could only ever copy the machine layer: a master `[hardware] backend = "teensyrom"` read as nothing while every system quietly dialed the default Ultimate URL. The tuple also ran three of the ten validators, so a master `[ultimate64].sid_panning` was copied into every system without the check whose whole stated purpose is to fire before the mixer is configured. The fix is that the master has no apply path of its own — not a longer tuple.

**`validate_sections(cfg)`** is the battery, called from the apply loop *and* from `merge_cli`. Every validator used to fire only at parse time, one layer below the last one that writes: a CLI flag or an env var landed in an already-validated `Config`, so `--system nonsense` reached the run unchecked. `merge_cli` is the last word on everything except the connection target, which `cli._resolve_configs` applies afterward so one `-u` string can pick the backend and the endpoint together (`parse_connection_uri` validates it itself).

**`choices` is enforced generically** for the scalar sections (`_validate_choice_fields`), rather than by a hand-written validator per field. The fields nobody had written one for failed *open*, and `sid_video_mode` failed open into a machine retiming plus an HDMI output-mode switch, because `hw_provision` tests it as `!= "off"`. Two documented exemptions live next to the check: `ultimate64.sid_play_rate` (`"auto"`/`"off"` *plus* a rate in Hz) and `ultimate64.system` (matched case-insensitively, because `hw/backend.py` and `hw/hw_provision.py` both `.upper()` it and the lowercase spelling has always worked). `[color]` is out of scope on purpose — every choices field it has is already checked by a session/mode validator, and the console's layer-blame report is built on those refusals arriving from `validate_configs` with a loadable config in hand. `SceneCfg` is out of scope too: `scene_factory.validate_scene_cfg` checks scene fields per type, with messages that know which type is building.

**A `bool`-annotated field refuses a non-bool.** Every consumer of a bool field is a plain truthiness test, so a quoted TOML `allow_unauthenticated = "false"` stored the truthy string `"false"` and meant the opposite of what it read as — on two of the switches that decide network exposure. The tri-states (`bool | str`) are untouched: their annotation is not `bool`, and their own validators own the vocabulary.

**A field carrying `internal` metadata is not a config key.** `_apply_section`'s valid set skips it, so derived run state cannot be authored from a file: `cc_map_is_default` is set False only when a layer really wrote a `cc_map`, and setting the flag directly inverted `midi_control.resolve_effective_cc_map`'s precedence with no `cc_map` in sight. The `internal` metadata gates the four *rendering* surfaces; it did not gate the apply path.

**`hue_corrections` is replaced per layer, not appended to.** Appending made the layers concatenate — machine settings declaring band X plus a project TOML declaring band Y gave `[X, Y]`, with no way for the project file to override, reorder or remove X — against "every layer above the defaults overrides the ones below it", and against `scene_color`, which has always treated the same field as an all-or-nothing replace. It also broke the round trip: `config_serialize` writes a list-of-tables whole or not at all, so `[X] + [X, Y]` wrote `[X, Y]` and reloading appended onto the machine layer again to give `[X, X, Y]`. `hue_corrections_replace_defaults` keeps its own, separate meaning against the built-in purple rescue.

**Unknown keys are collected, not logged.** `_apply_section` drops a key no dataclass field accepts and records an `UnknownKey(section, key, source, hint)` into the caller's list; only when that list is `None` (bare `load()` — the SIGHUP reload and the interstitial factory) does it log on the spot. An `UnknownKey` with an empty `section` names an unrecognized *table* instead — the shape the per-section walk can never see, since a table the loader applies to nothing never reaches `_apply_section` at all, which is how a whole misspelled `[hardwear]` block used to vanish without a diagnostic. `machine_baseline(unknown=None)` takes a collector for the same reason: without one, a stray machine-settings key was logged out-of-band *and* collected by the sibling `apply_machine_settings` calls, so `--doctor` printed the very preamble warning this split exists to avoid, and `_dedupe_unknown` could not collapse it because the escaping record never entered the list. `load_master` threads one list through every layer and hands it to the caller on `LoadResult.unknown_keys`, so **the presentation is the caller's choice**: a normal run logs them (`cli._log_unknown_keys`), `--doctor` renders them as CONFIG rows. The split exists because a `log.warning` printed *above* the report is where a stray key hides — it reads as preamble next to the formatted `[WARN]` rows, misses the summary tally, and the run continues on defaults, so a config whose setting silently does nothing looks like a clean bill of health. Warn, not error: an ignored key still leaves a runnable config, and erroring would make a stale key from an older schema unbootable.

Machine settings are re-applied once per system in ensemble mode (plus for the master defaults and the cascade baseline), so `_dedupe_unknown` collapses identical `(source, section, key)` records — one stray key there is one problem, not N+2.

**The hint searches every section, not just this one.** `_known_key_index()` maps each valid key to the section(s) that accept it, built from the same dataclass `fields()` the apply path and the JSON schema read (so it can't drift from what a section takes). An exact match in *another* table wins over difflib, because that case — key spelled perfectly, wrong table — is the one plain within-section `get_close_matches` can never catch: `palette_mode` under `[color]` is a real key that belongs on `[[scenes]]`, and the old warning could only say "unknown", with no near-miss to offer. Order is: exact match elsewhere → near-miss here → near-miss anywhere.

**Loading and overlaying.** `load_machine_settings()` parses `paths.settings_path()`: a missing file yields `{}`, a parse error raises `ConfigError`, and `[[scenes]]`/`[ensemble]` are rejected with a warning and dropped — the file holds cross-run *defaults*, not playlists. `apply_machine_settings(cfg)` then overlays it onto a `cfg` in place, logging one INFO line naming the path, the tables it supplied and a rough field count when a file was loaded. It names the *tables* because `(4 fields)` cannot tell an operator that this is the layer which turned a network switch on — the residue of a reviewer's (rightly rebutted) claim that the layer is an escalation path: write access to `~/.config/c64cast/settings.toml` already owns the project TOML and the venv, so the exposure is not new, but the observability gap was real. Both that line and the banned-table warning are deduped on the file's `(path, mtime, size)`, because the layer is re-applied once per system in ensemble mode plus twice more (master defaults, cascade baseline) — one file is one problem, not N+2 lines of it, which is exactly what `_dedupe_unknown` already does for stray keys.

**A parse error does not echo a credential.** `_format_toml_error` re-reads the file to quote the offending source line (Python 3.11–3.13 don't expose `.doc` on `TOMLDecodeError`), and cli.py logs a `ConfigError` at error level with `--log-file` mirroring it to disk — so a syntax error on a `dma_password = "…"` or token line copied the secret there, and a TOML typo is precisely the error whose log gets pasted into an issue. The line goes through `_redact.redact_secrets` first; the caret is dropped when something was redacted, because the substitution moves the columns it would point at. The same class shows up on the connection target: `connect.redact_target` masks userinfo and secret-shaped query values, and `parse_connection_uri` switches to that spelling once, so every message below it is safe to log by construction — the `user:pass@` guard was otherwise writing the credential to the exact destinations it exists to protect.

**Where it applies.** It is the lowest layer above the dataclass defaults, applied **first** in three places:

1. `load()`, before the file's own sections.
2. The `load_master` ensemble branch — the master-defaults `Config()` gets the overlay first, so master TOML beats machine settings.
3. `quickcast.build_config`, so quick playback inherits it.

Full precedence: defaults → machine settings → project/per-system TOML → master cascade → CLI → env.

**The ensemble subtlety.** `apply_master_defaults(defaults, sys_cfg, baseline=...)` takes a **machine-overlaid** `baseline`, not a fresh blank `Config()`, as its "did this system set the field" reference. A value coming only from the machine layer therefore counts as unset, so the master TOML can still override it, while an explicit per-system value wins over both. That keeps machine < master < per-system exact. Cascaded values are `deepcopy`'d: a bare `setattr` handed every inheriting system the *same* list/dict object as the master and as each other (`color.hue_corrections`, `performance.clips`, `hardware.host_sid_chips`, `ultimate64.sid_panning`/`sid_volume` are all mutable), so one system mutating one in place would have mutated every system's, invisibly at the config layer.

**The classification is total.** `_CASCADE_SECTIONS` (cascading, with a per-section never-cascade field set) and `_NEVER_CASCADE_SECTIONS` (not cascading, each with its reason) together list every scalar section plus `[color]` exactly once, and a test in `tests/test_ensemble_config.py` asserts the partition and that every cascading section really does receive a master value. It used to be one list plus a don't-list inside a comment, with a third hand-written membership in `load_master` — three memberships, no rule, and no test, which is how the six-section drift above survived. `_MASTER_PROCESS_WIDE_SECTIONS` (`[control]`, `[web]`, `[midi_control]`) is the subset a master can still put to work because `LoadResult` hands them to the runtime directly; anything else in the never-cascade set reaches nothing from a master file, so `load_master` says so out loud. Today that is `[video]` alone. Whether it should instead cascade with `{"device"}` skipped — the idiom `ultimate64.url` and the TeensyROM device fields already use, which would make a master `[video].use_reu_staged` work — is a product decision, and `tests/test_ensemble_config.py::test_video_section_does_not_cascade` currently pins the section-level exclusion.

**The env layer reaches the process-wide sections.** `apply_env_credentials(cfg)` owns the credential env vars, and `load_master` calls it on the master defaults as well as `merge_cli` calling it per system. The ensemble's `[control]` is `LoadResult.master_control` — `defaults.control`, an object no `merge_cli` call ever touches — so `C64CAST_CONTROL_TOKEN` landed on N per-system Configs nothing reads while the plane came up on whatever the shared master TOML declared, the exact opposite of the field's own promise that env beats the file "so a config that lives in a shared repo doesn't have to carry the credential". (`[web]` behaved correctly only by accident: `serve.py` re-reads `C64CAST_WEB_TOKEN` at bind time.) An exported-but-*empty* variable now counts as unset rather than as "blank it": `VAR=$UNSET_OTHER` in a service unit is the classic way to produce one, and clearing a configured token there either refuses the run (a non-loopback bind) or comes up unauthenticated (loopback), neither of which is what the empty value was trying to say.

**`[recording].path` is in the never-cascade set**, alongside `ultimate64.url` and the TeensyROM device fields, for the same reason they are: it names something one system owns. A cascaded path would hand every system's `cv2.VideoWriter` the same file, and the writers don't detect the collision — the run finishes with one truncated stream and no error anywhere. `config.resolve_recording_path(recording, name, is_ensemble=..., baseline=None)` supplies the per-system name instead, folding the system into the stem (`recording.mp4` → `recording-left.mp4`) and passing an explicit path through untouched. "Explicit" is measured against the **machine-overlaid** baseline, the same reference the cascade uses — measuring against the dataclass default made a `settings.toml` `[recording].path` look explicit for *every* system, skip the stem, and point N writers at one file, through the one layer every other layering decision in the module treats as unset. `baseline` lets a caller that already has one pass it in; without it the settings file is read per call. `session.build_stack` calls it where it builds the `StreamRecorder`; `doctor._validate_ensemble_recording_paths` calls it too, to catch the case the derivation can't fix — two per-system TOMLs spelling out one path — which is an *error*, not a warning, because nothing downstream will complain.

**The audio-contention mirror.** `_scene_contends_for_audio` claims to mirror `Scene.competes_for_audio_lock()`, and `_warn_audio_only_ensemble` is its only caller. `generative` belongs in `_AUDIO_BEARING_SCENE_TYPES` for one arm: `scene_factory._build_generative` builds a `SidFileAudioSource` (`wants_audio_lock = True`) for `audio_source = "sid"`, so a playlist made entirely of generative+SID scenes really does contend for the slot and used to get no warning at all — the exact footgun that warning exists for. The mirror is pinned by a test now, because it had already drifted once.

Path resolution is [`paths.py`](#pathspy).

## The config-metadata surfaces — `introspect.py`, `schema.py`, `config_serialize.py`, `wizard.py`

One declarative model, four renderers. Every `config.py` dataclass field carries `metadata={"help", "choices", "applies_to"}`, overlays carry `HELP`/`PARAM_HELP` plus the restriction attributes, and these four modules are the *only* consumers: `introspect` reads the model for the terminal, `schema` for editors, `config_serialize` writes it back as TOML, `wizard` drives prompts from it. The invariant isn't aspiration — each surface is pinned: `tests/test_introspect.py` holds the choice tuples and static tables to the runtime registries, `tests/test_schema.py` fails CI when the committed schema drifts from a fresh build, `tests/test_config_serialize.py` enforces the round-trip contract, `tests/test_wizard.py` pins the wizard's gates to introspect's, and `tests/test_example_toml_drift.py` holds the annotated example TOML and the reference book to the same fields. So adding a config field is: fill in its metadata, run `make schema` — and a skipped step fails a test rather than shipping a stale surface. The design exists because the hand-kept alternative had already failed once: the examples README's Markdown index drifted ~15 files behind before it was replaced by generation (that story is under [`paths.py`](#packaged-resources--examplename)).

### `introspect.py` — the model and the terminal renderers

Builds the frozen doc dataclasses (`SectionDoc`/`FieldDoc`, `SceneTypeDoc`, `OverlayDoc`/`ParamDoc`, `ModeDoc`) and renders `--list-*`, `--describe`, and `--compat`. Overlay parameters need no separate declaration: `_overlay_params` reads each overlay's typed `__init__` signature via `inspect.signature` — the signature *is* the doc, with `PARAM_HELP` merged across the MRO (most-derived wins) so a subclass inherits shared param docs and declares only what it adds. Fields whose metadata says `internal` (run-state trackers like `cc_map_is_default`) are dropped before any surface sees them, and `FieldDoc.apply` ("live" vs "rebuild", the on-C64 menu's read-only gate) is likewise internal — never emitted to the schema, the serializer, or the example TOML.

`SectionDoc.reload` answers the neighboring question at a coarser grain: `FieldDoc.apply` is whether a *running scene* can take a change in place, `SectionDoc.reload` is whether a **reload** picks the section up at all. It reads `config.RELOADABLE_SECTIONS`, which is a claim about `session.reload_all` — that a reload re-reads the file and rebuilds the scenes, while `[audio]`, `[video]` and `[ultimate64]` were read once when the session started and their threads are already running. The constant lives in `config.py` rather than beside `reload_all` so that `introspect` (and through it the web console, which has to answer "will this show up?" at the moment somebody saves) can read it without importing the session machinery; a test pins the names to real sections and to `reload_all`'s own docstring.

The module is **deliberately import-light**: it imports `config` and the overlay registry but *not* `modes` (which pulls in cv2/numpy) — the six display modes live in a static `_MODES` table, sync-tested against the real mode classes, so `--describe` and the schema build never pay (or crash without) the heavy imports. `_SECTIONS` and `_SCENE_TYPES` are the same kind of mirror (`config.load` / `validate_scene_cfg` stay the authority; the tests hold the mirrors to them). The one exception proves the rule: `live_targets()` — the `LIVE_PARAMS`/`LIVE_CHOICES` roll-up behind the `--midi-setup` target picker ([control.md](control.md#midi_setuppy--the---midi-setup-midi-learn-wizard-phase-5)) — imports the effect/generator/mode/scope registries lazily inside `_iter_live_holders`, because only that picker needs them. `overlay_mode_ok` mirrors `overlays.validate_for_scene` against a `ModeDoc`, and `test_matrix_mirrors_validate_for_scene` pins the two, so the `--compat` matrix is the loader's truth, not a parallel opinion; the matrix's "audio overlays need `[audio].enabled`" footnote renders only when some overlay actually carries `REQUIRES_AUDIO`, because the spectrum overlays used to and no longer do — unconditional, the note "would otherwise be a lie by default".

### `schema.py` — the editor surface

Emits the JSON Schema (draft 2020-12) that a `#:schema` directive points TOML editors at (Taplo, VS Code's Even Better TOML) for key/enum completion, hover docs, and typo flagging. The committed copy at `c64cast/data/c64cast.schema.json` ships inside the wheel and is regenerated by `make schema`; `tests/test_schema.py` tests it *as a validator*, not just as a file — a fresh build must match the committed copy, every shipped example config must validate against it, and a deliberately typo'd key must be rejected. Structure choices worth knowing: an unrecognized type annotation maps to `{}` — unconstrained rather than wrong; `choices` on a `list[str]` field constrain the array's *items*, not the array value; `[[scenes.overlays]]` gets one `if`/`then` branch per overlay (each with `additionalProperties: false` and that overlay's required params) so editors offer exactly the right keys per `type`; per-scene-type branches narrow the `display` enum to what each type supports; and `[ensemble]` is deliberately permissive — master TOMLs shouldn't be flagged, and modeling the multi-system table's internals isn't worth the coupling.

### `config_serialize.py` — the writing surface

`dumps`/`dump` — the inverse of `config.load`, under the contract **`load(dumps(cfg)) == cfg`**, property-tested across every shipped example config. It is the foundation the write-back features stand on: the `--init` wizard, the on-C64 menu's save flow, and `--save-settings` all emit through it. The writer is hand-rolled, and the docstring names the rejected alternatives: `tomli-w` cannot represent comments (the annotated output *is* the point), and `tomlkit` would be a new runtime dependency for output the round-trip test already proves correct. Emission policy: `None` is never written (TOML can't represent it, and `None` always means "fall back to the dataclass default"); `minimal=True` omits fields equal to the **baseline** — the way a human writes a config — but a scene's `type` is always written even at its default, because the discriminator is what makes a block unambiguous and copy-pasteable.

**What `minimal` measures against is the caller's to say, and getting it wrong writes the machine into the show.** `baseline=None` means the dataclass defaults, which is right only for a Config built on nothing else — in practice just `--save-settings`, which *is* the machine layer and would write an empty file if it measured against itself. Every caller that serializes a Config the *loader* produced passes `config.machine_baseline()`: the web console's form save, the `--init` wizard, and the on-C64 menu's live-tune save-back. Without it, a machine setting that differs from a shipped default gets written into the file it was only ever layered under — save a show config on the machine with the capture card and the file grows that machine's `[video] device`, which then overrides the next machine's own. The rule is one line: **the baseline must be the Config the serialized one was built on top of**, which is why `wizard.build_config` grew a `base` parameter rather than only the dump growing a `baseline` — a blank Config dumped against a machine baseline is the same bug pointing the other way, writing out every dataclass default the machine layer disagrees with. `config.machine_baseline()` is the shared constructor, and it is also the ensemble cascade's "unset" reference (["The ensemble subtlety"](#machine-settings-layer)), which is the other place the same question is asked.

List-of-table fields (`hue_corrections`, `performance.clips`, `midi_control.cc_map`) are dropped when the baseline already carries them: a list is written whole or not at all — TOML has no way to say "these rows on top of those" — so the only honest minimal answer is to omit one this layer did not add to. Those three section-level fields, plus scene `overlays` and a scene's own `[scenes.color] hue_corrections` override, are routed out-of-band to `[[…]]` blocks *after* their section's scalar keys, because TOML forbids scalar keys once a sub-table header opens; the three section-level ones share one `_SECTION_TABLE_ARRAYS` lookup in `_emit_section` rather than a hardcoded branch per field, so a fifth one is a table entry, not a new `if`. Two hard refusals: non-finite floats, and ensemble *master* configs (scope v1 — masters are authored across multiple files and aren't what the wizard produces). `SECRET_FIELDS` suppresses the DMA password and the `[web]`/`[control]` tokens, which is what makes the serializer safe to point at a checked-in path; the version-pinned `#:schema` URL fallback is covered under [`paths.py`](#packaged-resources--examplename).

**`save_machine_settings` is the one exception to that suppression, and the only writer of `settings.toml`.** Both writers of that file — `--save-settings` and the appliance setup form — are *merge-and-rewrite* paths: seed a Config from `apply_machine_settings` (which reads the whole file, secrets included), overlay this invocation, write the file back. Suppressing secrets on that write means rewriting the file *without* what the seed just read out of it, and that is not a hypothetical: the setup form did exactly that, silently, on the first successful POST — costing an appliance the `dma_password` its own password-protected U64 needs, and erasing a `[web] token` pin that `token_settable` exists to protect, from an unauthenticated caller. `dumps` therefore takes an `include_secrets` flag with exactly one sanctioned caller, and that caller is a *function*, not a documented shape: `setup_api._write_connection`'s docstring used to assert it mirrored the CLI's save path "exactly" while missing the guard that path had, which is the weakest possible way to hold two write paths together. What each caller still owns is the seed and the overlay; from the serialize onward there is one implementation. It returns `(path, echo_text, kept)` where `echo_text` is the same content *without* the secrets, because `--save-settings` prints what it saved and a terminal is not where a credential belongs — the preserved keys are named, never quoted — and the file is restricted to `0600` when it carries one, the way every other secret this project persists is.

**Line 1 is this module's to work out**, which is why `schema_directive_for` (what belongs after `#:schema`, relative-vs-absolute) and `pinned_url_version` (reading one back) live here next to `DEFAULT_SCHEMA_PATH` rather than in `wizard.py`, where they started when `--init` was the only caller. There are three now — the wizard, `--print-schema-path`, and `doctor`'s staleness check — and the last one settles it: a diagnostic pass must not have to import the config *builder* (and its `wizard` extra) to judge a file it already loaded.

### `wizard.py` — the prompting surface

`--init` is the fourth surface: instead of rendering the model for reading, it *drives prompts* from it — scene types, per-type `display` enums, field defaults/choices, and overlay offers all come from `introspect`, and `compatible_overlays` runs the same `overlay_mode_ok` gate as the loader, so the wizard cannot offer an option the loader would reject (`test_filter_matches_introspect_gate` pins the equivalence). The result is validated with `scene_factory.validate_scene_cfg` — the loader's own check — but with a "write it anyway?" escape rather than a hard refusal: an imperfect file the user can hand-edit beats a discarded session. Output goes through `config_serialize.dumps`, annotated and `#:schema`-tagged (`config_serialize.schema_directive_for`'s relative-vs-absolute rule is under [`paths.py`](#packaged-resources--examplename)), and the wizard's configs round-trip through the serializer in tests.

The module splits into **pure helpers** (`make_scene`, `build_config`/`build_multi_config`, `compatible_overlays`, `scan_assets`, `validate_all`, …) and a **thin questionary shell**, so the buildable logic unit-tests without a terminal — the split `midi_setup.py` explicitly mirrors ([control.md](control.md#midi_setuppy--the---midi-setup-midi-learn-wizard-phase-5)). `questionary` imports lazily, so the dependency exists only for `--init` (missing → an install hint, not a crash). The guided flow handles `_CORE_SCENE_FIELDS` (type → file → display → name → audio → overlays) and the "advanced" walk generates prompts for every other field applicable to the chosen type, skipping list/dict fields as hand-edit territory; `_SELF_AUDIO_TYPES` (waveform/midi/asid/launcher) never get the "enable audio?" question, because their audio is scene-driven rather than streamer-driven; and `_ASSET_SPECS` mirrors the loader's default-directory/extension constants so the file picker suggests exactly what `build_scene` will search.

## `scene_factory.py`

`scenes_from_config()` is the factory that turns `[[scenes]]` entries into real Scene instances; it also handles video-interleaving from `[playlist].videos_dir`. `validate_scene_cfg` (fanning out to the per-type `_validate_*` helpers) checks every entry up front, and the `resolve_*` helpers coalesce the tri-state knobs (dither / color_match / cell_strategy / REU staging / double-buffer / audio backend) into concrete per-scene values — doctor mode calls the same functions, so a config is validated identically with and without hardware.

`build_scene` mirrors the validator's shape: the `_BUILDERS` table dispatches to per-type `_build_<type>` helpers, each taking a frozen `_SceneBuildContext` (the SceneCfg plus the run-wide context — api, streamer, probe verdicts), and a shared epilogue then applies what every scene gets: duration resolution, an explicit `target_fps`, the effect chain, overlays, and the debug/OSD/pre-emphasis stamps. Cross-type policies live in shared helpers rather than being pasted per branch — `_resolve_live_audio` (the ensemble live-scene audio suppression webcam/blank/generative-mic all share) and `_resolve_sampler_audio` (the DAC→Ultimate Audio sampler swap video and generative-file both make).

**Both dispatch tables are held to `config.SCENE_TYPES`.** `_VALIDATORS` is the mirror of `_BUILDERS` — every `_validate_<type>` has the one signature `(s: SceneCfg, cfg: Config) -> DisplayMode | None`, and `None` means "no display mode", which only launcher returns (it owns the VIC, so it carries neither a mode nor overlays and `validate_scene_cfg` returns right after it). The validator dispatch used to be an if/elif ladder whose `else` spelled all ten type names out by hand, so `SCENE_TYPES` had *four* copies with only two of them pinned: a type added to the model and the builder table passed the drift test, passed config load, and was then refused as "unknown scene type" from inside `build_scene` at run start. `tests/test_scene_factory_seams.py` now holds `_VALIDATORS == _BUILDERS == SCENE_TYPES`, and the refusal message is built from `SCENE_TYPES`. The blank/random refusal that three of those validators hand-wrote — with three wordings and three different mode lists — is `_reject_non_quantizing_display`, over the one `QUANTIZING_DISPLAYS` tuple that `display = "random"` also picks from; webcam had no validator at all, so it had no refusal, and `display = "blank"` on a webcam opened the camera and painted an empty screen with no error.

**Every scene reaches `build_scene`, including an auto-interleaved video.** `scenes_from_config` synthesizes a `SceneCfg(type="video", display="hires_edges")` per interleaved clip (`_interleaved_video_cfg`) rather than constructing `VideoScene` itself. It used to construct it directly and hand-copy one of the six things `_build_video` does — the frame-push cap. Everything else was silently absent, kept from crashing by the Scene defaults: no `tempo_scale` (so the documented bitmap+DAC tempo compensation was off for exactly the hires_edges-over-`$D418` case it exists to correct), no `_resolve_sampler_audio` (so a sampler-capable U64 played interleaved clips on the lo-fi DAC while every configured video scene got the off-bus sampler), and no `color`, `loop_audio`, effect chain, overlays or epilogue stamps.

**One display-mode wiring, in one place.** `DisplayWiring` is the frozen bundle of everything except the mode *name* that decides how a scene's `DisplayMode` is wired — the raw `[video]` tri-states (not resolved bools), the probe verdicts, the effective `[color]`, the scene type, and `force_host_dma`. `display_wiring_for_scene(s, cfg, …)` builds one from a (SceneCfg, Config) pair; `build_wired_display_mode(display, wiring)` is the single entry point that resolves REU staging, the host-DMA double-buffer, flicker blend, `dither_method` and `cell_strategy` against a concrete mode name. `_display_mode_for_scene` is now just `resolve_scene_display` plus those two.

That seam exists because the wiring had a second copy. `SlideshowScene._maybe_rebuild_display_mode` re-picks a concrete mode at every `setup()` when `display_spec == "random"`, and it used to import the five `resolve_*` helpers back out of this module and re-derive the whole cluster by hand — against a `_build_display_mode` with 13 defaulted parameters, so every omission was silent. It had already lost two: `dither_method` and `cell_strategy` were never passed, so a `display = "random"` slideshow took the `"none"`/`"frequency"` defaults from its very first slide and quietly dropped the documented static-scene resolution (`auto` → floyd-steinberg + error-min); and `has_buffer_overlays`/`audio_reu_pump_active` went to `resolve_flicker_tolerance` but not to `resolve_double_buffer` in the same function, so a slideshow running the REU mic pump could get the `$0314` raster IRQ the pump already owns. The scene now stashes the factory's own `DisplayWiring` and rebuilds through `build_wired_display_mode`, recomputing only `has_buffer_overlays` (overlays are attached after construction). Adding a field to the wiring reaches both callers by construction.

`resolve_scene_display` **delegates to `_resolve_slideshow_display`** for a slideshow whose `display` is anything but `"random"`, because it is doctor's per-scene reporting helper as well as the builders' and doctor branches on its answer: it skips the `color_match` report for `hires_edges` and the `cell_strategy`/`motion_smoothing` reports for anything that isn't `mhires`. Answering `hires_edges` for a default-display slideshow both named a mode the build never produces and dropped the one scene type whose `auto` resolutions actually differ from all three reports. `"random"` stays as authored — it has no single answer, and delegating would roll a die. For the same "one pick is not the answer" reason, `_overlay_check_modes` validates a `"random"` slideshow's overlays against *every* member of `QUANTIZING_DISPLAYS`: `mcm` is in the pool and rejects a buffer-painting text overlay, so checking the single pick the validator happened to roll made the same unchanged config load on about four runs in five, and `--doctor` return a different verdict per invocation.

**Per-scene color.** `_display_mode_for_scene` calls `config.scene_color(cfg, s)` itself (no signature change, so the positional test call in `tests/test_flicker_blend.py` keeps working) and threads the result everywhere it used to read `cfg.color` — `flicker_tolerance`, the `dither`/`cell_strategy` resolution, and the `color=` kwarg into `_build_display_mode`. `_SceneBuildContext.color` is the same resolution as a property, so every `_build_<type>` helper passes `ctx.color` where it used to pass `cfg.color`. `validate_dither_cfg`/`validate_color_match_cfg`/`validate_cell_strategy_cfg`/`validate_motion_smoothing_cfg`/`validate_flicker_cfg` keep their `(cfg: Config)` signature — unchanged for `session.py`/`doctor.py`'s existing call sites — but now loop `effective_colors(cfg)`, the global section plus one more effective `ColorCfg` per scene with an override, so a bad value inside a `[scenes.color]` block is caught the same way a bad `[color]` value is, naming the scene it came from. `validate_scene_cfg` rejects a non-empty `color` on a scene type that paints no frame, the same `_EFFECT_SCENE_TYPES` set `effect`/`effects` are scoped to. See [`video-color.md`](video-color.md#per-scene-color-override-scenescolor) for the resolution details and the scene-aware live-tune save-back this also touches. `flicker_tolerance` was the one `[color]` field outside that family and is in it now: a typo used to raise a plain `ValueError` out of `resolve_flicker_tolerance` deep inside the display build — a different exit code (3, not 5) for the same class of config typo, naming only `[color]` and never the scene the override came from — and that raise is only reachable from a frame-bearing scene, so a bad global value in a SID-only or blank-only playlist was never checked at all, `--doctor --skip-probe` included.

Split out of `config.py` (which it imports the declarative model from): config stays clear of the scene/display runtime, while this module imports it at module top — the ~30 imports config.py had to defer to function level (its docstring called the placement cycle-avoidance) live at the top here. The two `quickcast` imports are the deliberate exception: quickcast imports this module's `*_EXTS` constants at module top, so the reverse import stays deferred. The config-metadata single source of truth is untouched — introspect/schema/serializer/wizard read the dataclass metadata in `config.py`, and nothing in this module feeds that pipeline.

`_display_mode_for_scene` (shared by the webcam/video/slideshow/generative builders) is also where `[color].dither = "auto"` resolves to a concrete method per scene type via `resolve_dither_method` (static `slideshow` → `floyd-steinberg`; motion scenes → `blue_noise`) before threading `dither_method`/`dither_strength` into `_build_display_mode` → the mhires/mcm/hires constructors. See the `[color].dither` note under `modes/` for the mechanism.

### The `file =` grammar

`split_file_spec` is the one place a spec is cut into entries, and it is deliberately not `spec.split(",")`: a URL may legitimately carry a comma (the Akamai/Limelight HLS shape `.../clip_,500,800,.mp4.csmil/master.m3u8`, and yt-dlp's own resolved stream URLs, which this module writes *back* into a scene's file spec). So after a URL entry a comma only separates when the next fragment announces a new entry — it begins with whitespace, or is itself a URL. `http://h/a.mp4,b.mp4` is one URL; write `http://h/a.mp4, b.mp4` for two entries. `is_media_url` is the one URL predicate: the scheme test was written three times with two definitions, and `_is_single_url_spec`'s extra "no comma" clause was what made a comma-bearing direct URL *both* ineligible for yt-dlp resolution *and* fragmented into pieces reported as paths the user never typed.

Inside `resolve_file_spec`, `os.path.isdir` is tested **before** the glob branch, mirroring the `isfile` precedence that was already there: a real directory named `Clips [2024]` (yt-dlp's `%(title)s [%(id)s]` convention, which produces such directories for playlist downloads) was otherwise read as a character class that matched nothing and reported as "glob matched no files". The recursive walk of the default SID directory is the explicit `recurse_default_sid_dir` keyword rather than a sniff at `label` — `label` is message text, and keying behavior to it meant the `generative`/`audio_source = "sid"` arm, which shares that default directory, silently stayed shallow on every real HVSC layout (all of which have zero `.sid` files at the top level), while rewording an error message could switch HVSC discovery off.

`validate_scene_cfg` is reachable from the network (`config_store` → `session.validate_configs`), so the filesystem work it does is bounded where a config-named path could otherwise be turned into unbounded I/O: `_check_first_sid_clears_display` requires a regular file and caps its read at `MAX_SID_BYTES`, so a FIFO named `x.sid` can no longer block the request thread and a multi-gigabyte one can no longer exhaust memory; and a `**` glob whose first path segment is itself a pattern under `/` is refused outright, since walking every mounted volume is no media spec's intent. A general depth/time bound on glob expansion is still open — the ceiling trades against legitimately deep HVSC and media trees.

Every message that quotes a spec goes through `redact_media_spec`, which strips URL userinfo and hands the rest to `_redact.redact_secrets`. A private asset is legitimately reached with `file = "https://user:token@cdn.example/clip.mp4"`, and the spec is quoted into `--log-file`, the report `config_store._capture_errors` renders in a browser, and `recording_metadata`'s snapshot — which `scripts/scene_config_to_description.py` renders as `Source video: <url>` in a **published** video description. The repo already refuses a `user:pass@` netloc on the connection target for exactly this reason; a secret inside a scene `file` value was covered by none of that, because it sits in a value rather than in its own field.

A resolve failure's message does still distinguish *why* a spec did not resolve (wrong extension / empty directory / glob matched nothing / not on this host), and that reaches a console client verbatim — so a full-token console actor can probe path existence outside the roots `config_store` jails itself to. This is deliberate, not an oversight: `_resolve_file_spec_or_explain` exists to say *which* directory is empty and what to drop in it, `MediaNotChosen`'s docstring turns on the console being able to tell *not yet* from *wrong*, and `missing_media`'s pass-through exists so a spec may name a file on another machine in an ensemble. The credential required is already administrator-equivalent (`api_config_read` returns config text verbatim, `[web] token` included). Recorded here so the scope is a decision rather than an accident.

### URL video scenes

A video scene's `file` may be a single media **URL** (direct link or a yt-dlp-resolved YouTube/etc. page). `_build_video` resolves it via `quickcast.resolve_video_url` — the **one** resolution site, shared with quick playback — so configs and `c64cast MEDIA…` behave identically: the URL's `t=`/`start=`/`#t=` timestamp folds into `start_s` (an explicit `start_s` wins), the resolved title becomes the scene name, and audio-only URLs are rejected. Resolution is a network call at load/build time only — never in `validate_scene_cfg`, which stays offline. `validate_scene_cfg` (hence `--doctor`) instead does an **offline** check: a single non-direct URL (`_is_single_url_spec` + `quickcast.url_needs_ytdlp`) with the `yt` extra missing is rejected up front with an install hint, rather than failing at playback with ffmpeg's cryptic `Invalid data found` when PyAV tries to open the page as a media file. A page URL *mixed into* a multi-entry spec is refused there too: only a whole-spec URL is ever resolved, so such an entry stayed in the candidate pool as raw HTML for PyAV to choke on — the very failure the offline check exists to prevent, and it happened even with the `yt` extra installed.

Three things guard the resolution itself, because it is a network fetch made from inside `build_scene` — i.e. after `build_stack` has opened the link and reset the machine, with yt-dlp's own logger routed to `log.debug`. One `log.info` line names the URL before the call, so a slow extraction is not an unexplained hang. `quickcast.URL_RESOLVE_TIMEOUT_S` bounds it: with no `socket_timeout` (and nothing in the tree calling `socket.setdefaulttimeout`), a host that completed the handshake and then never answered held the C64 reset with the DMA socket open until the process was killed, and under `serve.py` the supervisor stayed `STARTING` so `POST /api/session/stop` could not end it either. And the resolved values are treated as untrusted: a `stream_url` whose scheme is not http/https is refused (for the generic extractor it comes from the fetched page's own markup, and `resolve_file_spec`'s literal-path branch gates on the suffix alone, so a `file://` or `udp://` value would reach ffmpeg, which honors both), while the title goes through `_clean_scene_name` — collapsed of control characters and length-capped, since it lands in `log.info` calls interpolated with no args, where an interior newline is enough to forge a second `--log-file` record.

The songlengths lookups (`_songlengths_cache`, `_songlengths_autodetected`) are process-global memos, which is right — an HVSC tree is tens of thousands of files, and the autodetect memo deliberately ignores its `root` argument (pinned by `tests/test_config.py::test_result_is_memoized`). What they lacked was an invalidation hook: `serve.py` starts and stops sessions over the life of one process, so unpacking HVSC or fixing `[playlist].songlengths_file` could not take effect without a restart once the first miss was cached as `None`. `reset_songlengths_cache()` clears both, and `session.reload_all` calls it.

## `cli.py`

**Three modules:** `cli.py` keeps arg parsing (`build_parser`), config resolution (`_resolve_configs`), and the process-level wiring only a foreground CLI can do — signal handlers, and the mapping from a failure back to an exit code. The single-shot terminal commands (`list_devices`, `run_introspection`/`run_suggest_palette`, `run_save_settings`, `run_install_char_rom`, `run_dump_char_rom`, `run_calibrate_dac`, `run_doctor`, plus `configure_logging`) live in `cli_commands.py`, which never imports `cli`. Stack construction and the session run live in [`session.py`](#sessionpy--the-session-lifecycle). All three log through the same `"c64cast"` logger, so output is unchanged — but a test patching a symbol a command resolves (e.g. `make_backend` under `--dump-char-rom`) must patch it on `c64cast.app.cli_commands` now.

`cli` re-exports every name it moved to `session.py` (`build_stack`, `teardown_stack`, `_pump_previews_until_done`, `StackBuildError`, the phase helpers…). Callers and diag scripts have always found them at `c64cast.app.cli`, and a module split is not a reason to break that.

**`main(argv)`'s shape:** `configure_logging` runs once, immediately after `parse_args` — every command below it logs (a wizard can run for minutes; `_resolve_configs` can warn about a stray TOML key before `load_master` even returns), so a handler has to exist from the first line, not just once a config happens to load. `--list-devices` and the introspection family (`run_introspection`) dispatch first, unconditionally, because they need neither a config nor hardware. Every other config-free, hardware-free command (`--save-settings`, `--install-char-rom`, `--check-for-updates`, `--upgrade`, `--motd-line`, `--reset-setup`) is one entry in `_TERMINAL_COMMANDS` — a `(predicate, run)` tuple per flag, looped rather than copy-pasted as a chain of `if args.x: return run_x(...)`, so a new command can't forget the loop's own `except (ValueError, RuntimeError)` → exit 2 mapping (this is what makes a bad `-u` target given to `--save-settings` land in the usual usage-error exit instead of escaping as a traceback — `run_save_settings` calls `connect.parse_connection_uri`, which can raise `ConnectionURIError`). `_resolve_configs` gets the same mapping, plus a `log.debug(..., exc_info=True)` right before its `log.error` so `-v` recovers a traceback for a genuine internal defect — the catch there stays broad (`ValueError`/`RuntimeError`, not narrowed to specific types) because plenty of *legitimate* config validation in `config.py` raises plain `ValueError` too, and narrowing it would misclassify those as unhandled.

`_resolve_configs(args)` picks the front door: positional `MEDIA` args route to `quickcast.build_config` (in-memory single-system Config; mutually exclusive with `--config`); otherwise `config.load_master` (+`merge_cli`) for the config-driven path. The scheme-aware `-u/--url` target (or `$C64CAST_URL`) is then applied via `connect.apply_to_config` onto the single system's connection fields — skipped in ensemble mode, where the per-system-flag guard rejects a CLI target so each system keeps its TOML identity. From there both paths share one run path: `scene_factory.scenes_from_config()` builds the playlist, and the Playlist gets an `interstitial_factory` built from the `[interstitial]` section and a `CommodoreKeyPoller` for pause/resume. `merge_cli` doesn't touch the connection fields — the URI owns them — so a SIGHUP/control-plane reload re-merges scenes without disturbing the already-built backend.

**SIGINT/SIGTERM must always end the process — a three-strike shape.** `session.make_stop_signal_handler(on_first_signal, verb=...)` builds the handler both foreground entry points install for both signals: the first sets a caller-supplied stop flag so an in-flight DMA finishes rather than being cut (killing mid-DMA is what wedges the hardware into needing a power cycle), the second restores `signal.SIG_DFL` for whichever signal just arrived — so a repeated SIGTERM from a service manager isn't caught forever either — and the third, now hitting the default disposition, actually kills. `_run_session` calls it with `sess.stop_event.set`; `serve.run_daemon` calls it with `shutdown.set` (its own use is documented in [`app/serve.py` — the session supervisor](control.md#appservepy--the-session-supervisor)). The factory only builds the closure — `signal.signal` still raises off the main thread, so each caller installs it itself.

Even that isn't sufficient by itself: a signal handler can only run once the main thread returns to the interpreter, and a hung non-daemon thread (see `join_bounded` above) means it never does. `main(argv)` is unchanged — every test module that imports it keeps calling a plain function that returns an exit code — but the installed console script is `run(argv) = ensure_exit(main(argv))`. `ensure_exit` polls `_lingering_threads()` (every non-daemon thread besides the main one) for up to `FORCE_EXIT_GRACE_S` (5s): if none survive, `main()`'s code is returned untouched; if one does, it's logged by name, stdout/stderr are flushed and `logging.shutdown()` runs (`os._exit` skips both, which would otherwise drop the last lines of `--log-file`), and then `hard_exit` — `os._exit` by default, injected so a test can assert the call instead of killing its own process — actually leaves. This is the one mechanism for both exit paths (`run_daemon` and `_run_session`), which is why it lives at the process boundary rather than being written twice.

`run_save_settings(args)` implements **`--save-settings`** — one of the terminal commands in `cli._TERMINAL_COMMANDS` (dispatched in `main()` right after `run_introspection`, before `_resolve_configs`, like `--init`, and wrapped in the same `ValueError`/`RuntimeError` → exit 2 mapping `_resolve_configs` gets, so a bad `-u` target here can't escape as a traceback): it starts from a machine-overlaid `Config()` (so a save *merges* with the existing file), applies this invocation's whitelisted flags (`-u/--url` decomposed via `connect.parse_connection_uri`, plus whatever `cli_commands.SAVABLE_SETTINGS_FIELDS` names — one `(args dest, section, field, flag name)` table drives the "nothing to save" error text, `--save-settings`'s own `--help` string in `cli.py`, and the apply loop, so the three can't drift out of sync the way three hand-copied lists once did), and writes the result sparsely (only non-default fields) and atomically through [`config_serialize.save_machine_settings`](#config_serializepy--the-writing-surface) — the one writer of that file, shared with the appliance setup form — printing the path + contents and exiting 0. Nothing savable provided → prints what's savable and exits 2. `$C64CAST_URL` never auto-saves (explicit flags only). A secret already in the file *survives* the merge, which is what that shared writer exists for; it used to be dropped, and the warning that landed here first was only ever a report of the loss. What is printed is the secret-free rendering of the same content, with the preserved keys named rather than quoted. `_connection_is_builtin_default(cfg)` gates the quick-playback "no connection target" warning so it fires only when neither a CLI target nor machine settings supplied a connection.

## `session.py` — the session lifecycle

Everything between "the configs are resolved" and "the hardware is back where we found it": `build_stack`/`teardown_stack` and their phase helpers (`_open_backend`, `_build_audio`, `_build_input_controls`, `_build_preview_and_recording`, `_resolve_reu_available`, `_resolve_sampler_available`, the two `_coerce_reu_*` guards), the playlist run (`start_playlists` → `pump_until_done` → `join_playlists`, composed by `run_foreground`), and the live-tune save-back.

The module exists because a session's lifecycle has to be callable independently of the one-shot CLI — a long-lived host has to be able to start, stop and restart one inside a single process. `_run_session` is now a composition of five steps, cut along seams that were already inside it:

| Step | Does |
|---|---|
| `validate_configs(loaded, cfgs)` | Every per-system check and every scene in it (`scene_factory.validate_scene_cfg`), plus the coercions a feature combination forces (`_coerce_reu_for_transport`). Raises `SessionConfigError(exit_code)`. |
| `build_session(args, loaded, cfgs)` | Profiler install, `Ensemble` allocation, the `build_stack` loop, ensemble binding. Returns a `Session`. |
| `start_services(sess)` | Control plane, MIDI listener, WLED device — each independently guarded. |
| `run_foreground(sess)` | Start the playlist threads and block until they finish. |
| `teardown_session(sess)` | MIDI → WLED → control → stacks reversed → live-tune save-back. |

**`validate_configs` is pure and hardware-free on purpose.** That is what lets a caller reject a bad config without disturbing a session that is already running — the alternative, accepting a start request and failing twenty seconds later inside `build_stack`, is a much worse answer to give a user. The scene checks are part of it for that reason: `validate_scene_cfg` is hardware-free too (`doctor` has always called it without an api, an audio streamer or a source), so running it here moves a bad scene ahead of the machine being opened and reset. A scene failure keeps exit code 3 — what `build_stack` already returned once `scenes_from_config` reached the same error — so the failure moved, it did not change identity.

**One validator list, not two.** `validate_configs` walks `scene_factory.PER_SYSTEM_VALIDATORS` rather than naming each `validate_*_cfg` by hand; the hand-written list had already fallen behind (`validate_wled_cfg` was reached only by `doctor.py`, so `--doctor` rejected a bad `[wled]` section and a real run did not), and a test holds the tuple to a partition of the module's `validate_*(cfg: Config)` callables. The two section-scoped validators (`validate_control_cfg`, `validate_midi_control_cfg`) stay out of it deliberately: `[control]` and `[midi_control]` are process-wide, so they are checked once against the master rather than once per system. `start_services` now parses `[wled].listen` *inside* its try and catches `ConfigError` there too, mirroring the MIDI block — outside it, a typo'd port took the whole session down with an unmapped traceback after every system's hardware was already open, which is the opposite of the per-surface guarantee that function's docstring makes.

**A failed build leaves no hardware held**, at both scales. `build_session` tears down the stacks that did come up, in reverse, before `StackBuildError` propagates — and *within* one stack, `build_stack` registers every resource on a `contextlib.ExitStack` as it acquires it (camera, backend, the three volatile hardware provisions, audio, vision controller, framebuffer/preview/recorder), so any failure from the camera open to the last constructor releases exactly what came up, in reverse of acquisition, one `_release_step`-guarded step each. On success the ladder is `pop_all()`d and the returned `SystemStack` owns those resources instead — the one place they are released is then `teardown_stack`. This replaced four hand-written partial unwinds (one full reverse ladder with no per-step guard, plus three that remembered only the camera), which is what left a raise inside `restore_sampler` stranding `api.close()` and the camera, and left everything between `provision_reu` and the `Playlist` constructor with no unwind at all.

`teardown_stack` also detaches the framebuffer's write listener, and `_build_preview_and_recording` detaches it again when neither consumer survives (preview off, `StreamRecorder` refusing a fourcc). Nothing in the tree reads `SystemStack.framebuffer`; without the detach, every DMA write for the rest of the run pays a shadow-memory update for a feature that is off.

**`build_stack` opens the camera for a `[[performance.clips]]` table too.** `type` defaults to `"webcam"` in a clip (`config._CLIP_DEFAULTS`), so a clip grid can hold webcam clips with no `webcam` `[[scenes]]` entry anywhere — and the clip build factory closes over `source`, so a `None` there means `scene_factory._build_webcam` raises at launch and `performance._arm`'s background build files it into `armed.error`, killing that pad silently for the whole show. `config.clip_scene_type` answers "what will this table build" without running `clip_scene_cfg`'s full `_apply_section` pass, which would raise on an unrelated bad key long before validation is due.

**Signals are deliberately absent here.** `signal.signal` raises `ValueError` off the main thread, so a session started from a worker must not inherit handler installation; `cli._run_session` installs its own and `session.reload_all(sess)` is what its SIGHUP handler calls.

`Session.interactive` (True for the CLI) marks a session that owns the terminal and the process. It gates the two things that assume both: the live-tune `input()` prompt, which would hang a daemon's stop path forever, and the in-session control plane, whose port a long-lived host would already be holding.

Playlist threads are `daemon=False` — a daemon thread is killed at interpreter exit, which can cut an in-flight DMA and wedge the machine into needing a power cycle. `join_playlists` would rather give each thread `_STOP_JOIN_S` (5s) and log a stuck one.

**`teardown_session` stops and drains the playlists itself**, before it touches a stack. That is what makes its "safe to call from a `finally:`" true rather than a precondition on the caller: the stacks are where `audio.close()`, the final reset and `api.close()` live, and running those underneath a worker still issuing DMA writes is the same mid-DMA cut. Both steps are no-ops on the ordinary path (`run_foreground` and `serve._run_stop` have already drained), so they cost nothing when the caller did it right and cover every escape where it could not — a raise out of `start_playlists`, or any non-`KeyboardInterrupt` escape from `pump_until_done`. `start_playlists` appends into the caller's own list (`sess.threads`) as each thread starts, for the same reason: if the k-th `start()` raises, the k-1 workers already running are still reachable, where a returned list would have been lost with the exception.

**`run_foreground`'s `except KeyboardInterrupt` is not the CLI's stop path.** `cli._run_session` installs `make_stop_signal_handler` on SIGINT and SIGTERM before calling it, so a signal *sets `stop_event`* and the playlists drain at their next frame boundary; the except is the fallback for a caller that installed no handler. Escalation in that handler is tracked per signum, as its docstring has always said — one shared flag meant the first SIGTERM after a SIGINT armed `SIG_DFL` a signal earlier than documented and dropped its own stop request.

**Abandoning a stuck `daemon=False` thread doesn't actually let the process leave.** `threading._shutdown()` joins the very same thread again on the way out of the interpreter — untimed, and with no signal delivery, because that join runs after `main()` has already returned its exit code. That is what turned a stuck playlist into a process that never exits, with no log line and nothing left to interrupt. `join_bounded(t, timeout, poll_s=_JOIN_POLL_S)` is the one polling join every non-daemon join site in the project shares (`pump_until_done`'s headless branch, `_pump_previews_until_done`'s fall-through, `join_playlists`, `teardown_session`'s drain, `serve._Workers.join`) — it exists so this measurement, and the "did not exit; abandoning" log on timeout, only has to be made once, with the timeout actually given to that thread rather than some caller-side total. What actually closes the gap is the force-exit backstop at the process boundary: see [`cli.ensure_exit`](#clipy).

**The preview fall-through is one of those sites, and was the last one missed.** When `_pump_previews_until_done` leaves its pump loop it joins the playlist threads itself, and three ordinary paths reach that join: the operator closes the window (closing a window is not a stop signal), a draw failure disables it, and — on the very first iteration — a headless opencv build, where `PreviewWindow.open()` logs "preview disabled" and never sets `is_open`. A bare `join()` there parked the main thread exactly where no handler runs, and since the CLI's SIGINT arrives as a handler rather than as `KeyboardInterrupt`, `[preview].enabled = true` over SSH was a run that neither SIGINT nor SIGTERM could stop and that never reached its final reset. It is `join_bounded(t, math.inf)` now, like the headless branch. The pump itself stays on the main thread — that part is a hard Cocoa requirement, not a choice ([`preview.py`'s note](video-color.md#framebufferpy--previewpy--the-software-mirror-behind-preview-and-recording)).

The caller that starts and stops sessions *over time* — rather than once, like the CLI — is [`serve.py`'s `SessionManager`](control.md#appservepy--the-session-supervisor).

## `connect.py` — scheme-aware connection targets

`parse_connection_uri` decomposes the one `-u/--url` target string (or `$C64CAST_URL`) into the existing config fields — `[hardware].backend` plus the `[ultimate64]`/`[teensyrom]` connection fields — which remain the canonical store a TOML sets directly; `hw.backend.make_backend` reads them unchanged, so this module is purely the CLI/env front end. The single string replaced five flags (`--backend`, `--tr-transport`, `--tr-serial-port`, `--tr-host`, `--dma-port`) in the same change that folded the standalone `cast` entry point into `c64cast`: one scheme-aware target points the CLI at any supported device, because the scheme selects the backend *and* its transport/endpoint together. Rare per-link knobs (`dma_port`, `tcp_port`, `baud`, `storage`) ride as `?query` params so they never become flags.

Every routing decision falls out of the URL *shape*. For `tr://`, an empty netloc is serial — no path → auto-detect, a `/dev/…` path → that device node — and a non-empty netloc is a TCP host, with one special case: a `COM\d+` netloc routes back to Windows serial (a COM port looks exactly like a host in a URL), taken from `parts.netloc` verbatim because `urlsplit.hostname` would lowercase it. `http(s)://` rebuilds the URL from its parts rather than passing `target` through — `?query` knobs are consumed into `ConnectionSpec` fields, and leaving them in the base URL too would land `?dma_port=64` inside the string `Ultimate64API` concatenates every REST path onto (the `u64://` branch never had this bug; it already rebuilds `f"http://{parts.netloc}"` from parts).

**A target must not carry a `user:pass@` netloc, on any scheme.** None of them has a use for one — the Ultimate's REST API has no HTTP auth, and `requests` would send it as a Basic-auth header on every call regardless — so `parse_connection_uri` refuses it outright rather than accepting it as a way to smuggle a secret past "the DMA password is env/config-only, never a CLI flag": a credential embedded in `-u`/`--url` would otherwise ride into `[ultimate64].url`, from which `--save-settings` both persists it to `settings.toml` and echoes it to stdout in plaintext. `?query` keys are checked too: a scheme's known set is enforced (an unrecognized key, or a recognized one with a blank value, raises rather than being silently parsed as absent) and a netloc port is validated the same way on every scheme (`_netloc_port`, shared by `u64://`, `http(s)://` and `tr://`'s TCP form) rather than only on `tr://`, where `urlsplit.port` used to raise unguarded elsewhere.

**The config field reads the same strings**, through this same parser. `config._normalize_ultimate_url` runs in `_apply_toml_sections` — so both the TOML layer and the machine-settings layer go through it — and rewrites `[ultimate64].url` to the base URL the REST client wants: `u64://HOST` → `http://HOST`, and a bare host → `http://` + it. Before that, a `u64://` written into a file went straight to `requests`, which has no adapter for the scheme, and the startup probe reported only "could not reach the hardware" with `No connection adapters were found` at debug level — an error that sends the reader to the cabling. The two surfaces still differ in one place, and correctly: `-u` must refuse a schemeless target because the scheme is how it picks a backend, while a value already inside `[ultimate64]` has nothing left to pick, which is why the bare host the shipped example has always promised is accepted here and nowhere else. Query params are refused rather than applied — in a file each of them is a field of its own, and two ways to set `dma_port` in one document is a precedence question nobody should have to answer — and so is a `tr://` target, which names a backend the section it sits in has already named differently.

`ConnectionSpec` is what keeps precedence honest: every field except `backend` defaults to None, and `apply_to_config` writes only the non-None ones — a bare `tr://` leaves `serial_port` at None for `make_backend`'s auto-detect, and any knob the URI didn't carry keeps its TOML/machine-settings value. The `cfg` parameter is duck-typed against a local `_Cfg` Protocol and the module still imports nothing from the package (no cycle for `cli`, `cli_commands`, or `quickcast`), but it is no longer `cfg: object` — `_Cfg` and its nested `_Hardware`/`_Ultimate64`/`_Teensyrom` Protocols declare exactly the fields this function writes, so a config-side rename now fails type-checking at this call site instead of succeeding as a silent `setattr` of a dead attribute. (The three sub-object members are declared `@property` rather than plain attributes — a plain Protocol attribute is invariant, which made mypy refuse the real `Config` here even though it structurally satisfies each nested Protocol; `apply_to_config` only ever mutates fields *of* `hardware`/`ultimate64`/`teensyrom`, never replaces the sub-object, so the covariant read-only form is all it needs.) `ConnectionURIError` subclasses `ValueError` so a bad target lands in the CLI's existing usage-error handling (exit 2) rather than needing a handler of its own. The three call sites — `_resolve_configs` (with its ensemble-mode rejection), `run_save_settings` (parse-and-decompose into machine settings), and `quickcast.build_config` — are covered under [`cli.py`](#clipy) and [`quickcast.py`](#quickcastpy--quick-playback).

## `quickcast.py` — quick playback

The library behind positional `MEDIA` arguments: `build_config` classifies each file/directory/glob/URL argument into one `SceneCfg` and returns an **in-memory-only** `Config` — no TOML on disk, scenes in argument order, no interleaving, no loop. It is deliberately a *classifier*, not a second player: the result runs through the same `build_stack` → `run_foreground` → `teardown_stack` path as a config file, and the module adds no playback machinery. (It began as a standalone `cast` entry point; folding it into `c64cast` — the same change that introduced [`connect.py`](#connectpy--scheme-aware-connection-targets) — reduced it to this library, with `cli._resolve_configs` picking the front door.)

Two integration rules keep the shortcut equivalent to a config-driven run, and both exist because their absence shipped. Ordering: `apply_machine_settings` first, then the quick-playback policy (`loop = false`, `interleave_videos = false`), then the shared `merge_cli`, then the `-u` target — so a saved connection target is inherited without a per-run `-u`, `--loop` still overrides the policy, and an explicit target wins over the saved one. And **every** flag goes through `config.merge_cli`: it used to hand-pick a subset, and twelve of the twenty-one `CLI_TO_CFG` flags — plus `C64CAST_DMA_PASSWORD`, which `merge_cli` is also where the env var folds in — were accepted and silently dropped, so quick playback couldn't reach a password-protected Ultimate at all (#223). The regression test asserts against `CLI_TO_CFG` itself rather than a list of flag names, so a newly mapped flag is covered the day it's added.

Classification is by extension group (the `*_EXTS` tuples re-exported by `scene_factory`; [scenes.md](scenes.md#scenespy--scene-state-machine) has why they're defined in `scenes.py`), one scene type per group; the `"audio"` sentinel builds a `generative` + `audio_source = "file"` scene — `_AUDIO_GENERATOR` plasma on an `_AUDIO_DISPLAY` mcm char display, a char mode so no bitmap DMA competes with the audio ring. A directory or glob becomes a scene whose `file` keeps the original spec, so the scene re-resolves and random-picks at every `setup()`; its type is the single type the contents imply, and mixed contents are rejected ("point cast at a directory/glob of a single kind"). Two orderings are deliberate: an existing file wins over glob interpretation, because YouTube-style `name [videoid].mp4` filenames carry glob metacharacters and would otherwise be mis-parsed as patterns (mirrors `resolve_file_spec`); and a non-existent literal path still classifies by extension, deferring to the scene's own `setup()` to report a clear "file not found" if it's still missing at play time.

Two override policies are narrower than they look. `_DEFAULT_VIDEO_DISPLAY = "mhires"` matches `SceneCfg`'s own unset-display resolution for video but stays an explicit constant because quickcast also applies it to slideshow, whose `SceneCfg` default differs. And `-t/--duration` applies only where it means "play this long" (`_DURATION_TYPES`: waveform, slideshow, and audio — where it caps the track's natural length); video rejects the override (video-driven), and a launcher would read it as an idle timeout — surprising for a playback shortcut.

A URL argument is stored on the `SceneCfg` **verbatim** and resolved later in `config.build_scene` — the one resolution site shared with config-driven runs ([`scene_factory.py`](#scene_factorypy) above) — while the `t=`/`start=`/`#t=` timestamp is parsed here, offline, into `start_s`. `resolve_media_url` passes direct media URLs through (PyAV opens http(s) itself) and hands everything else to a lazily-imported yt-dlp, preferring a single *progressive* stream because PyAV can't merge separate DASH streams without downloading — and 360/720p is ample for a 320×200 downscale. The failure modes are deliberately boring: missing yt-dlp is a `RuntimeError` naming the install command, and an extraction failure is a `ValueError` carrying yt-dlp's own reason — which takes real work, because `YoutubeDL.trouble()` writes error text straight to stderr regardless of `quiet` unless a `logger` is supplied (`_YtDlpLog` absorbs it at debug level), and the `DownloadError` message arrives `"ERROR: "`-prefixed and ANSI-colored whenever yt-dlp thinks stderr is a tty (`no_color`, plus a strip-and-`removeprefix` as belt and braces). `url_needs_ytdlp` is the offline mirror of the passthrough test, so config validation and `--doctor` can flag a yt-dlp-requiring URL with the `yt` extra missing before playback instead of at it.

## `doctor.py` — config and environment diagnostics

`--doctor` collects **every** failure into one grouped report instead of failing fast: per-scene validation runs inside try/except so one broken scene doesn't hide the rest, and each system's connectivity probe returns diagnostics rather than raising so one dead machine doesn't hide the others' reports. `cli_commands.run_doctor` merges the CLI flags into the configs before validating, so `--skip-probe` and `C64CAST_DMA_PASSWORD` behave exactly as on a real run; the exit code is 1 on any error-level diagnostic. `--skip-probe` makes the whole pass offline — the environment probes always run.

There is no parallel registry of checks: everything doctor validates is the run path's own predicate. Scene validation is `scene_factory.validate_scene_cfg` plus the same `resolve_*` helpers ([`scene_factory.py`](#scene_factorypy) above), the REU/sampler wants come from `hw_provision.wants_reu`/`wants_sampler` so the report and the provisioner can never disagree about what a run needs ([hardware-io.md](hardware-io.md#hw_provisionpy--live-reu--sampler-auto-provisioning)), and the NMI-rate ceiling is `c64.nmi_rate_safety` ([audio.md](audio.md#sample-rate-and-the-overrun-ceiling)). The module only *observes*: the live REU/sampler provisioning that used to sit alongside the probes moved out to `hw_provision` (#242) after every call from the normal run path had gone through a `from . import doctor as _doctor` alias — the code saying the name was wrong. Diagnostics observe; `hw_provision` mutates.

Each ENVIRONMENT probe exists because its failure cost a real debugging session (the probe docstrings carry the cases). The interpreter/hard-dep probes catch "the active python isn't the synced project env" — the root of the classic "No module named cv2" time-sink. The opencv probe reads `cv2.version`'s build stamp rather than distribution metadata, because every opencv wheel (plain, contrib, headless) unpacks into the same `site-packages/cv2/`, installers co-install them, and only the stamp says which one actually survived — `[vision]`'s mediapipe → opencv-contrib-python is exactly where it happens (#216); a headless build additionally warns that `[preview]` can't open a window. The dev-only probes (.venv match, `uv lock --check`) are gated on `_running_from_checkout()` because `uv lock --check` exits nonzero for "no project found" exactly as for real drift — an installed user used to be told their lockfile had drifted from a `pyproject.toml` they don't have. The extras hint for installed users is `[all]` rather than the one missing extra, because extras don't accumulate: installing `c64cast[midi]` over `[video]` trades one missing feature for another. The rest of the section is the one-stop "where everything lives" answer — machine-settings file and its recognized sections, data/controllers dirs, and the character ROM with its verify verdict (absence is a warning that names the symptom, "text renders in a built-in ASCII font", because nothing else ever says so out loud).

Severity tracks *consequence*, not category. A failed REST probe on an Ultimate is an **error** only when a scene actually starts via the REST runner (`_wants_rest_runner`: waveform, launcher, generative with `audio_source = "sid"`) and a warning otherwise — DMA-rendered scenes keep playing without REST. Both emulated SIDs disabled is a warning, not an error, because a physical SID chip can still sound. REU disabled is informational when `[ultimate64].auto_reu` will provision it live for the run, and an error only when the user opted out of auto-provisioning ([audio.md's auto_reu notes](audio.md#ultimate64auto_reu--automatic-reu-provisioning) own that lifecycle). The offline DAC-curve resolution *hedges* rather than asserts — offline it can only try the fallback identity key, so calibration files it can't match yield "cannot confirm", and any system that got a precise live answer from the connectivity probe has its offline line suppressed entirely; [audio.md's calibration-reporting note](audio.md#how---doctor-reports-calibration) tells that story, including why the suppression keeps the report self-consistent.

**The `#:schema` check reads the file, not the Config** (`_validate_schema_directive`, using `LoadResult.paths`) — the directive is a comment the loader never looks at, which is exactly why it needs a check: a stale one costs nothing at run time and shows up as an editor underlining a setting that works. Four judgments, and the shape of each is the point. A pin to another version is a warning with the replacement line in the hint (`pinned_url_version` above). A **path** is judged by *content*, not location — any copy byte-identical to `packaged_schema_path()` is doing its job wherever it sits, and a copy that differs describes a different c64cast whatever tree it lives in, which is the case a path comparison misses: a leftover venv from before a Python-version bump still answers the path. A path that doesn't resolve is a warning ("an install that moved"). Everything else is left alone deliberately — somebody else's URL carries no promise this could check, a differently-named file (`./house-style.schema.json`) is a hand-picked answer rather than a stale pointer at ours, and a config with **no** directive gets no row at all, because a report that names every file lacking an optional line is advertising rather than diagnosis.

It diagnoses and never rewrites, which is the same call `config_store` makes when it carries a file's own directive across a save instead of regenerating it ([control.md](control.md#config_storepy--the-config-browser-and-its-root-jail)): a team's shared schema and a deliberate pin to an older release are both legitimate, and neither is distinguishable from staleness by inspection. Same posture as `--version` printing its install directory (#301) — say what you see, print the line to paste, leave the file to its owner.

`print_report` orders categories by a known list but prints unknown categories after the known ones instead of dropping them — a check reporting under a new category must never look like a check that passed. That exact bug nearly ate the ensemble recording-collision error when it was added (#216), and `test_every_category_used_in_source_is_in_category_order` pins the list to the source since. The collision check itself (`_validate_ensemble_recording_paths`; the policy story is [the `[recording].path` note](#machine-settings-layer) above) normalizes paths the way the filesystem reads them — expanded, absolutized, `normcase`'d — because two spellings of one file must compare equal or the check misses exactly the case it exists for.

## `upgrade.py`

`--upgrade` and `--check-for-updates` exist because `--version` printing its install directory (#301) only ever answered the question for a human willing to recognize `uv/tools/` or `pipx/venvs/` in the path — it never made the machine act on it. This module is the first place anything in the package parses that shape: `detect_install()` reads the *path* the running code sits in (never a receipt file — `uv-receipt.toml`, `pipx_metadata.json`) and returns which of `uv-tool` / `pipx` / `pip` / `uvx` / `checkout` / `unknown` owns it, in that checked order (checkout first, because nothing below should ever override "this is c64cast's own source tree"; `archive-v0` next, because that's the one segment that only ever appears in an ephemeral `uvx`/`uv run --with` environment and never in a `uv tool install`). No parsing of installed extras happens anywhere in here, on purpose: `uv tool upgrade` and `pipx upgrade` both replay their own recorded install spec, so a narrow install (`c64cast[video,midi,web]`) keeps its extras across an upgrade without this module reading either receipt format.

`install_root()` (`Path(__file__).resolve().parents[2]`) is the single home for an expression `cli.py`'s `_version_text` and `doctor.py`'s `_REPO_ROOT` each used to compute independently before this module existed — any module living directly in `c64cast/app/` gets the same answer regardless of whose `__file__` supplies it, so `doctor._REPO_ROOT = install_root()` and `cli._version_text`'s `home = upgrade.install_root()` both just call it now rather than keeping a second copy in sync. `doctor.py`'s own `_running_from_checkout()` stays independent (it reads `doctor._REPO_ROOT`, not this module's function) precisely so a test can still `mock.patch.object(doctor, "_REPO_ROOT", ...)` and see it reflected — collapsing that predicate too would have broken every existing test that patches the doctor-side name.

The module is deliberately import-light at module scope: stdlib only, with `requests` imported lazily inside `latest_release()` — matching the lazy-import convention `cli_commands.py`'s introspection commands already use for anything not needed on every invocation. The point isn't cleanliness; it's that `--upgrade` has to keep working when a hard runtime dependency (cv2, numpy) is broken, since fixing exactly that is the reason someone would reach for it.

**The comparator has one deliberate special case.** `_release_tuple` reads only the leading digit run of each dot-separated component (`"0.4.0rc1"` → `(0, 4, 0)`, matching every suffix `scripts/bump_version.py`'s `VERSION_RE` allows) rather than depending on `packaging` for full PEP 440 ordering — it isn't a runtime dependency here, and release-number comparison alone is exact for every version this project publishes. But `c64cast.UNINSTALLED_VERSION` ("0+unknown") parses its leading "0" as a syntactically valid release too, which would make every published version look "newer" than "not installed" — true, but not the claim `--check-for-updates` is supposed to make. `is_newer` checks the sentinel by value before it ever reaches the generic parser, rather than trusting the parser to reject it (it doesn't, and a test pins the regression). On a tied release with a prerelease suffix on one side (`local = "0.4.0rc1"`, `remote = "0.4.0"`), the tie-break falls to a plain string comparison — PyPI's `info.version` never reports a prerelease, so a tie there means the stable release already supersedes whatever prerelease is running.

**`run_upgrade`'s checkout branch refuses on a dirty tree** (`_checkout_is_dirty`, `git status --porcelain`) rather than running `git pull` regardless — a deliberate deviation from "always run the two commands", made because a pull colliding with in-progress work is exactly the kind of surprise an upgrade command must not spring. A `None` from `_checkout_is_dirty` (git missing, or the check itself failing) is treated the same as "dirty": "can't verify" is not "clean". `_confirm` mirrors the live-tune save prompt in `session.py` — check `sys.stdin.isatty()` before reading, so a script or CI run without `--yes` fails fast with an actionable message instead of hanging on a read that will never come. `_run_command` runs with the console attached (not `capture_output`, unlike every probe in `doctor.py`) because the point is for the user to watch uv/pipx/pip/git's own progress, not to receive a captured summary.

**`_upgrade_checkout` refuses four ways before it moves any source**, and each refusal names the cause it actually found. A tree with **no `.git`** is an unpacked release archive, not a checkout — `pyproject.toml` ships inside the sdist, so the very user the module was written for (the one who unpacked an archive over their working directory) lands in the checkout branch with no repository at all; `git status` exits 128 there, which reads as `None` from `_checkout_is_dirty` and used to print "could not be checked (is git on PATH?)" plus "Commit or stash first", every word of it wrong for the actual cause. A **dirty tree** is the deliberate deviation from "always run the two commands", `None` ("can't verify") is refused the same way but in its own words rather than borrowing the dirty tree's advice, and a missing **`uv`** is pre-flighted here rather than discovered by `_run_command`'s per-command check *after* `git pull` has already moved the source — which left the tree on new code with the old dependency set, plausibly unimportable if the release moved an opencv/PyAV/numpy pin. Every branch of `run_upgrade` itself dispatches on `install.kind`: two kinds carry no command (`uvx`, `unknown`), so the older `install.command is None` test was correct only by branch order, and a sixth command-less kind (a distro package, a read-only appliance install) would have silently impersonated `unknown` instead of naming itself.

**The ceiling on an install command is an hour, not two minutes, and `$C64CAST_UPGRADE_TIMEOUT_S` lifts it** (`0` removes it). `subprocess.run(timeout=...)` SIGKILLs the child when it expires, and a `uv sync --all-extras` or `pip install --upgrade` resolving a moved opencv/PyAV/numpy pin downloads ~100 MB — or builds it from source on a Pi-class host with no matching wheel, which two minutes does not cover. Killing that partway through replacing site-packages is how the one command meant to *repair* an install produces a broken one, so the ceiling now sits where only a wedged process reaches it, `_interrupt` sends SIGINT (the signal uv/pip/pipx/git already unwind cleanly from; `terminate()` on Windows, which has no per-child equivalent) with `_INTERRUPT_GRACE_S` before SIGKILL is used at all, and the message says the upgrade may be only partly applied and names the env var. It is not removed outright because `--yes` makes unattended runs legitimate, and those have no user at the console to notice a hang. `_run_command` also *launches* the path `shutil.which` resolved instead of handing the unqualified name back to `exec`, which would re-resolve `PATH` — the binary that was verified is now provably the one that runs, which matters under the `sudo -E` an admin reaches for on a system install. The read-only `git status` probe keeps its own short `_PROBE_TIMEOUT_S`: it mutates nothing, so it is safe to kill.

**`latest_release` keeps "never raises" by catching broadly, not by enumerating types** — the enumeration was wrong twice. A body that decodes to a list, a string, a number, `null`, or `{"info": null}` raises `TypeError` from the subscript chain, and the lazy `import requests` sat *outside* the guard, so a half-installed `requests` (the state an upgrade exists to fix) raised `ImportError` through a function `doctor._probe_updates` relies on never failing. The caught exception is logged at debug, which is the only thing that distinguishes a DNS failure from a corporate proxy's 403 from a TLS trust error from a change in the shape of `info.version` — before it, all four were the same indistinguishable `None` and the only trace on an appliance was an `unanswered_since` timestamp. The version itself is checked by `looks_like_version` rather than `str()`-coerced: coercion turned a *well-shaped* body with a wrong field type into a fabricated answer nothing downstream could catch, `{"info": {"version": 5}}` reading as the release `"5"` — newer than everything this project has published. `detect_install` matches `uv/tools` and `pipx/venvs` as **adjacent** path components (`_has_adjacent`), which is what its docstring always said; unordered membership also matched a hand-made pip venv sitting under a directory called `tools` beside one called `uv`, and printed that user the wrong installer's command.

`doctor._probe_updates()` folds the same PyPI check into `--doctor`'s ENVIRONMENT section, beside the `c64cast version` line it answers — reusing that category rather than opening one of its own for a single row. It is gated by its own `probe_updates` keyword on `validate_load_result` (default `False`), separate from `probe_environment`: it is the one probe in that function that hits the network unconditionally, and a caller that wants the offline installation checks (`config_store.validate_ref`'s per-Start preflight, which explicitly asks for neither) must not also get a PyPI query it never asked for. `cli_commands.run_doctor` passes `probe_updates=not skip_probe`, so `--doctor --skip-probe` stays fully offline — the same flag that already gates the U64 reachability probe. The probe never reports `error`: a flaky network says nothing about whether the install itself is broken, so it can only `warn` (update available, with `hint="c64cast --upgrade"`) or `ok` (current, in a checkout, or unreachable).

## `update_state.py`

`upgrade.py` answers "is there a newer release" on demand, for a human at a terminal — nothing before this module persisted that answer anywhere else. Two readers need it without a terminal: the web console's `GET /api/update` (`control/web_api.py`) for its update banner, and, on the appliance image, an `/etc/update-motd.d/` script via `c64cast --motd-line` (`packaging/motd/`). `--check-for-updates --write-state` is the one writer — it calls `upgrade.latest_release()`/`upgrade.is_newer()` exactly once, the same call `--check-for-updates` already made to print its own answer, and hands the result to `write_update_state` rather than querying PyPI a second time for the file. The state lives at `paths.update_check_path()` (`<data root>/update_check.json`) as a single "last known answer" slot — not a log, because nothing here needs history, only "what is the latest release, and when did we last manage to ask".

`read_update_state` is tolerant the same way `JsonSlotStore` is (`control/transport.py`): a missing, corrupt, or wrong-shaped file reads as `None` rather than raising, because "no check has ever run yet" (a freshly imaged box, five minutes old) and "the file predates a field this version expects" are both routine, not failures worth surfacing. `motd_line()` centralizes the one piece of interpretation both readers would otherwise duplicate — "is this worth printing" — as a single function returning `""` for nothing to say (no check, an unreachable PyPI, or already current) and a one-line message naming both versions and the exact `c64cast --upgrade` command otherwise; `cli_commands.run_motd_line()` prints it or doesn't, and never touches the network itself, which is what makes it safe to run unconditionally from a login script.

`record_check()` is what a finished check calls, and it is not a plain overwrite. An attempt that couldn't reach PyPI learned nothing about which release is current, so it contributes only its `checked_at` and leaves the last real answer standing: writing its empty hands instead would retract a pending-upgrade notice over one lost DNS lookup, and leave it retracted until some later attempt succeeded — a day away on the appliance's timer, and possibly never on a machine that ran one manual `--write-state`. What the failed attempt does establish is `unanswered_since`, the date its silence began (kept from the previous record once set, cleared by any answer). That field, not `checked_at`, is what tells a reader how old the held answer is: an appliance offline for a year still bumps `checked_at` daily as its timer fails. It is absent from files written before it existed, so it reads as `None` rather than making an older file unreadable.

Both surfaces spend it on a second message. `is_stale()` treats `unanswered_since ?? checked_at` as "when this host last learned anything" — the fallback covers a laptop with no timer, whose last attempt answered and whose `checked_at` therefore *is* that moment — and `STALE_AFTER_DAYS` (30) is how long that may be before `motd_line()` says so at the login prompt instead of quoting an answer that old, and before the console draws its second banner. The threshold lives here and rides out on `GET /api/update` as `stale_after_days`: `updateBannerLogic.isStale()` reads the host's number rather than carrying a copy that could drift from it (a response that names no threshold is simply never called stale). The console's version is dismissible until the next upgrade — keyed on `running_version`, per browser — rather than for a fixed spell, because a box with no internet cannot make the reminder stop being true, and one that returns every month on a machine deliberately kept off the network is just noise; the MOTD, which is redrawn from scratch at every login and has nowhere to keep a dismissal, simply prints. In both, a pending upgrade outranks staleness: naming the release to move to already says everything "we haven't heard from PyPI" would, and acting on it settles both.

`read_update_state` is tolerant in the sense of *never raises and never guesses*, which is why every field is type-checked rather than coerced. `float()`, `bool()` and `str()` cannot fail, so a mistyped field became a confident wrong answer instead of the routine "nothing recorded yet": `bool("false")` is `True`, which spells a pending upgrade that does not exist, and `rechecked()` cannot correct it because a record whose `running_version` already matches is returned untouched — the login banner offering the release the box already runs. `_timestamp` additionally rejects a non-finite or non-positive date, because `json.loads` accepts the bare `NaN` and `Infinity` literals and *every* comparison in `is_stale` reads as "not stale" for either; `is_stale` treats a date more than `_FUTURE_TOLERANCE_S` ahead of `now` as stale rather than fresh for the same reason — "can't tell how old this is" is not "recent", the asymmetry `_checkout_is_dirty`'s `None` already gets. One poisoned timestamp otherwise disabled the module's only safeguard against quoting a dead answer, permanently and with no other symptom. And the guard is one broad `except` rather than a list of exception types: `Path.read_text(encoding="utf-8")` signals invalid bytes with `UnicodeDecodeError` (a `ValueError`), while the read was wrapped in `except OSError` alone, so one bad byte raised out of a "never raises" function into `GET /api/update` and into the login MOTD script — and since `record_check` reads before it writes, the run that would have replaced the bad file died first and the slot stayed broken until a human deleted it.

**`_version` is a privilege crossing, not a formatting nicety.** The unit writes this file as the unprivileged `c64cast` account while `packaging/motd/98-c64cast-update` renders `motd_line`'s text from `/etc/update-motd.d/`, which pam_motd runs **as root** at every login — and the unit's own comment requires both surfaces to resolve the same file, so the working configuration is exactly the one where a low-privilege account owns a file root reads. A bare `str()` let a newline in `latest_version` forge an additional, official-looking MOTD line ("SECURITY: apply the hotfix now: curl … | sudo sh") and let ESC/OSC payloads rewrite the banner around it. Both version fields now have to match `upgrade.looks_like_version` — the same gate `latest_release` uses, so a hostile mirror's payload is refused before it is ever written — and the terminal is the only sink that acts on control bytes (the console binds these values as Svelte text nodes).

`record_check` reports a write it cannot do and drops it rather than raising. `cli_commands.run_check_for_updates` records *before* it prints the answer it already holds, so a data root that is read-only, full, or holding a directory where the file belongs turned `--check-for-updates --write-state` into a traceback that also threw away the network answer the user asked for, and made `c64cast-update-check.service` fail with a stack trace despite the `SuccessExitStatus=0 4` it carefully enumerates. The read-modify-write is **single-writer by convention** and not locked: two concurrent runs (the daily timer overlapping a manual `--write-state`) both see the same previous slot and the loser's contribution is dropped — bounded, since the slot holds one last-known answer and the next successful check heals it, but a failed attempt that read before a successful one wrote will carry the older answer forward and re-date the silence from now. A second writer (a web-console "check now" button is the obvious one) is the change that would want an `O_EXCL` lockfile beside `update_check.json` around both steps.

Neither reader trusts the recorded verdict as written: both pass it through `rechecked()` first, which re-answers `newer` against the version running *now*. `newer` was true of whatever was running when the check ran, so an upgrade taken since then would leave the banner and the login line offering the very release the box already has — until some later check happened to overwrite the file, which on a machine that ran one manual `--write-state` and has no daily timer may be never. The re-answer is `upgrade.is_newer()`, a pure version comparison with no network in it, so it costs nothing to redo on every read; a check whose `running_version` already matches is returned untouched, sentinel versions and unparsable ones included.

## `playlist.py` — the run loop: scene walk, pacing, crash tolerance

`Playlist.run()` is the render loop, and it runs on a worker thread — the process's main thread stays parked in `session._pump_previews_until_done` because cv2's HighGUI may only be serviced from the main thread (the `[preview]` caveat). One loop iteration services, in order: a pause request (`_handle_pause` — the C=-key pause/resume story, including the clear-`resume_event`-before-`pause_idle` subtlety, is in [`keyboard.py`'s notes](control.md#keyboardpy--commodore-key-pauseresume-ctrl-key-skip-shift-key-style-cycle)), a queued SIGHUP reload (`request_reload` swaps the whole scene list at this boundary, tearing the current scene down so its overlays release threads and network state), a broadcast interrupt, then `_advance()`, the menu, and one rendered frame. Every control surface — the keyboard poller, vision gestures, MIDI, the web consoles, the HTTP control plane — talks to this loop through the same `threading.Event`s or a drained queue, honored at frame boundaries; the rule every module in [control.md](control.md) cites, that **all scene- and DMA-adjacent mutation happens on the playlist thread**, is enforced by this design rather than by locks. The logger is a per-instance child (`c64cast.app.playlist.<system>`) so ensemble runs attribute each line to a system while `assertLogs` on the parent logger still captures it.

**The scene walk.** `_advance()` is a three-state machine over `(current, transitioning, is_done)`: no current scene → resolve the next index (through the ensemble gate) and set up the interstitial; interstitial finished → swap in the real scene; scene finished → fade out, tear down, honor a pending jump ([`request_jump`, documented with the MIDI surface](control.md#midi_controlpy--process-wide-midi-control-surface-optional-live-performance)), and walk on — wrapping at end-of-list, or setting `stop_event` when `[playlist].loop = false`. The interstitial is an **injected factory** (`interstitial_factory(name) → Scene`) so tests stub it out and custom card designs can replace it. Before the card is built, `_safe_prepare_next` calls the upcoming scene's `prepare_next()` so a randomized scene picks its file *now* and the "UP NEXT" card names the real content rather than a directory spec; a failure there degrades to a stale name on the card — the scene's own `setup()` re-picks — instead of stranding the transition. A one-scene playlist auto-detects into **single-scene mode**: no interstitials, looping by teardown + re-setup of the same Scene object (which works for every type — a webcam re-reads its source, a video re-opens the file, a waveform restarts the SID), and skip events dropped because there is nowhere to skip to. The clip-launch engine gets first refusal at the top of `_advance` (`performance.service`); while a launched clip owns the program the normal walk is suspended — [`performance.py`'s notes](control.md#performancepy--clip-launch-grid-live-djvj-phase-2) own that story.

**Pacing** is deadline-based rather than sleep-per-frame: each frame advances a deadline by the scene's budget and sleeps only until it (via `stop_event.wait`, so shutdown shortcuts the nap). The budget comes from `frame_time_for` — `scene.target_fps`, else the display mode's `default_target_fps`, else the system default — and the *policy* for which scenes default below the system rate (DMA bus-halt ceilings) is the fps list under [scenes.md's fade-timeline note](scenes.md#scene-fade-timeline-playlist). When the loop falls more than two frames behind, `_advance_deadline` snaps the deadline forward — dropping the missed frames — instead of bursting writes to catch up, so animations stay tied to wall-clock time and the DMA link isn't slammed. A snap that drops at least `_AUDIO_DISTURBANCE_DROP_S` (0.5 s) of frames also calls `audio.note_playback_disturbance()`: a seek catch-up or stream rebuffer loads the bus abnormally, and without the signal the adaptive NMI-rate loop would chase the transient and glide the audio pitch — the warm-up-gate story in [audio.md](audio.md#audiopy--audiostreamer). Routine 1–3-frame drops stay below the threshold by design.

**Crash tolerance is tiered**, and the tiers are deliberate (all pinned in `tests/test_playlist.py`). A scene that raises in `process_frame` is logged and advanced past — torn down normally so the next scene starts. An overlay that raises in `setup` or `process_frame` is disabled individually (`ov.disabled`) and the scene continues without it. A teardown that raises is logged and the loop continues — and `EnsembleCoordinator.release_scene` runs *after* the guarded teardown precisely so a crashing scene cannot strand the ensemble audio slot or conductor role. `cycle_style`, `prepare_next`, and fade-push failures degrade in place (keep the current style / show a stale name / end the fade) — a broken extra is always better than killing the stream. The one deliberate hard stop: a scene whose `setup()` raises propagates out of `_advance` and aborts the run ("playlist advance failed; aborting") — there is no recovery from an unstartable scene that isn't a retry loop, so the run exits cleanly instead.

**`run_one_frame`** was extracted from the loop body so the broadcast-follower interlude ([the orchestrator notes above](#orchestratorpy--orchestrators--cross-ensemble-scene-coordination)) can drive a follower scene through the identical render + overlay + heartbeat + frame-drop machinery. Its internal order is load-bearing: the fade-in step and `transport.tick` run *before* the scene composes (so a seek issued this tick is visible in this frame); the render skips overlays that declare `PAINTS_INTO_BUFFERS`, which already composed into the scene's buffers during `process_frame` and would race the scene if run again; then `is_done` resolves — a busy overlay defers it (e.g. BigText finishing a scroll-off), but a CTRL skip overrides even that, applied *after* the `is_done` assignment so the two can't race. The heartbeat logs `api.stats` deltas as rates every `heartbeat_interval` (default 10 s; the first tick only establishes the baseline, so no zero-second window) and promotes itself to WARNING when errors exceed 1/s — otherwise a user running without `-v` would never see a failing link. On the profiler's cadence the loop also emits the backend's per-DMA-write latency line, which is what distinguishes "CPU render is slow" from "producer blocked on the network".

Several fields live on the Playlist because of its position, not its job. `transport`, `tempo`, `performance`, and `live_tracker` are **always constructed** — cheap when unconfigured — so control surfaces read `pl.tempo` etc. unguarded ([control.md](control.md) has each one's story). `user_dim` (the WLED `bri` dim) is owned here rather than on the display mode because mode instances are per-scene: `safe_setup` re-stamps it onto each fresh mode so a dim survives auto-advance ([the `user_dim` note](video-color.md#persistent-brightness-dim-user_dim)). The WLED audio-sync broadcaster is built, started, and stopped around the loop and polls `_active_features` from its own thread ([wled.md](wled.md#wled_syncpy--wled-audio-sync-broadcast-wled-bridge-mode-3)). And while the on-C64 menu is open and idle, the loop swaps `run_one_frame` for `_idle_pace` — pacing without rendering: single-buffer VIC RAM retains the last scene + panel, so *not* re-rendering is what keeps the menu panel rock-steady over a scene that repaints every tick; `menu.repaint` forces a one-shot re-render on open/nav/value-change so the live preview still updates.

## `playlist_support.py` — playlist collaborators

`SceneFades`, `PlaylistMenu`, and `EnsembleCoordinator` — split out of a 1,400-line `playlist.py` in 2026-08 (#247) with method bodies moved verbatim, so `playlist.py` keeps one job: the scene walk and the frame loop. Each class holds a back-reference to its Playlist; they are extensions of the state machine, not services behind an interface. The refactoring roadmap's companion idea, a `PlaylistControls` facade to give the five control surfaces a narrow contract, was evaluated in the same PR and deliberately **not** built: the surfaces touch only public members, and their union is ~20 attributes — the Playlist's whole silhouette — so a facade would have renamed the coupling, not narrowed it.

**`SceneFades`** owns the transition timeline; the scene-facing behavior — what fades when, and how a CTRL skip cancels — is [the fade-timeline note in scenes.md](scenes.md#scene-fade-timeline-playlist), and the palette-remap mechanism (the C64 has no global brightness register, so a "fade" is a nearest-darker-palette-index remap) is [video-color.md's fade note](video-color.md#scene-fade-dim-toward-black). What lives here is the machinery: fades are counted in *frames* at the scene's own budget (`fade_frames` = `round(duration_s / frame_time_for(scene))`), gate on `supports_compose` so non-compose scenes (waveform/MIDI scope, native launcher) are untouched, and the fade-out replays the mode's cached last buffers via `repush_faded` — freeze + dim, never a re-compose. `ended_via_skip` and the skip-during-fade-out branch both consume the skip event, so one CTRL press can't skip two scenes; a failed fade push ends the fade rather than delaying teardown.

**`PlaylistMenu`** drives the SPACE-key on-C64 menu. The Events (`menu_event` / `menu_active` / `menu_eligible` / `nav_queue`) stay on the Playlist — they are [the keyboard poller's contract](control.md#keyboardpy--commodore-key-pauseresume-ctrl-key-skip-shift-key-style-cycle) — while the overlay lifecycle and the save-back flow live here. `open()` injects a `MenuOverlay` (from `scenes/overlays/menu.py`) into the running scene's overlay list at runtime, and both `open()` and `close()` call `api.invalidate_cache()`: the delta cache doesn't know the panel overwrote screen cells, so without the flush the covered cells would cache as unchanged and never repaint. `menu_eligible` is re-published on every `service()` call because it gates the poller's kernal-keyboard-buffer drain — consuming keys (`$00C6 = 0`) must never happen on a launcher scene that watches the buffer itself. A scene swapped out from under an open menu (reload, broadcast) drops the menu state cleanly rather than forwarding nav keys to a dangling overlay. `can_save` requires both the in-memory Config and its source path (the serializer rejects an ensemble master), and `save_config` writes a `.bak` of the original before `config_serialize.dump` replaces it.

**`EnsembleCoordinator`** is everything multi-system; every method is a fast no-op or pass-through when `playlist.ensemble` is None, so the Playlist calls in unguarded rather than sprinkling `if ensemble` branches. Its two claim shapes are deliberately different: `resolve_next_index` (the multi-scene path) *skips forward* past audio-gated scenes to the next runnable one, blocking only when every scene is gated — a rotation should keep showing something; `wait_for_audio_claim` (single-scene loops, hard jumps, clip-launch swaps) *waits on the real gate*, because a single scene can't skip itself and an explicit jump must not be silently retargeted. Both stamp the claim onto the scene so the matching `release_scene` — which runs even when the scene's teardown raised — releases the slot and clears the per-scene conductor stamps; Scene objects are reused across loop iterations, and the stale-stamp failure modes (plus `handle_broadcast_interrupt`, the follower-side interlude) are detailed with [the orchestrator framework above](#orchestratorpy--orchestrators--cross-ensemble-scene-coordination).

## `profiler.py` — per-frame timing

`--profile` records each frame's wall-clock breakdown and emits a periodic per-scene summary into the normal log stream. Off by default, and "off" is genuinely free: `get_profiler()` returns a `NullProfiler` whose methods are no-op context managers with parameter names matching `FrameProfiler`'s (so keyword calls work against the union type), which is what lets every call site skip the `if profiler:` guard — the hot path pays one attribute lookup and a `with` statement (~0.5 µs).

Two collaborators feed it, split across a seam that motivates the process-global accessor. `Playlist.run` opens the `frame` context and the top-level `wait`/`cpu_render` stages and drains the `api.stats` write/byte deltas into `record_counts` at the frame boundary; `scenes._render_with_overlays` opens the `compose`/`overlay_compose`/`push` sub-stages — and reads `get_profiler()` rather than taking the profiler as an argument, keeping it off a render-path call signature. One Playlist + one API per process makes the singleton appropriate; `cli` installs it via `set_profiler` **before** constructing the Playlists so the accessor is right for the very first frame, and notes the flip side where it does: process-wide means per-scene timings mix across systems in ensemble mode (a per-system split is a possible future enhancement). `stage()` sums repeated entries within one frame (`overlay_compose` runs once per overlay) and records nothing when no frame is open, so profiler calls during setup can't pollute a scene's numbers. It is deliberately not thread-safe — everything that touches it runs on the playlist thread.

The stats window is sized to the cadence: a 64-sample ring is ~2 s at 30 fps, matched to the 10 s summary interval — long enough to smooth single-frame outliers, short enough that the numbers still track scene transitions. Summaries are nearest-rank percentiles over the sorted ring (avg/p50/p95/max): nearest rank is the `ceil(p * n)`-th smallest sample, so the 0-based index is `ceil(p * n) - 1` and `_nearest_rank` computes exactly that. Truncating (`int(p * n)`) lands one rank high whenever `p * n` is a whole number — at the steady-state n=64 it reported the 33rd smallest frame time as the median, and at n=2 it reported the maximum.

**`emit_if_due` prints only the scenes that are still rendering.** A scene's ring keeps its last 64 frames forever and `frame_total.count()` never returns to zero, so iterating the whole `_stats` dict re-printed every scene the process had ever rendered — one line per tick, forever, reporting minutes-old numbers under a fresh timestamp with nothing marking them dead, which is the opposite of what the 64-sample window is sized for. A per-scene frame counter is compared against its count at the last line; a scene with nothing new is skipped, and dropped once it has been idle for `_IDLE_TICKS_BEFORE_DROP` ticks. That bound also matters because the key space isn't small: `MediaFileMixin._pick_filepath` rewrites `self.name` on every pick and a video scene prefers the container's own `title` tag, so each distinct file mints a bucket.

That same provenance is why `_format_line` renders the scene name as `!r`, truncated to `_MAX_SCENE_NAME`: `video.probe_container_title` only `.strip()`s the tag, so an interior newline survives, and `emit_if_due` passes the finished line to `log.info` with no args — a hostile file's title tag would otherwise write a second, fully forged record into `--log-file` and anything reading it downstream. Stage columns are the six known names first (stable order) and then any other stage a caller opened, rather than a whitelist that silently drops what it doesn't recognize. A non-positive `[debug].profile_interval` still instruments every frame and prints nothing, which is indistinguishable from a broken profiler, so `FrameProfiler.__init__` says so once. `emit_if_due`'s first tick only establishes the baseline, and when the cadence fires it returns True so callers can chain extra same-cadence lines — which is exactly how the run loop appends the backend's per-DMA-write latency line, the number that distinguishes "CPU render is slow" from "producer blocked on the network" ([the `run_one_frame` note above](#playlistpy--the-run-loop-scene-walk-pacing-crash-tolerance)).

## `recording_metadata.py` — per-scene SCENE_CONFIG_JSON logging

`Playlist.safe_setup` calls `log_scene_recording_metadata` once per scene activation (loop re-entries and random-pool re-picks included, right after `scene.setup()` so `scene.filepath`/`scene.name` are already the picked values) to log one `SCENE_CONFIG_JSON`-tagged line: a snapshot of that scene's *coalesced* settings — `scene._cfg` (the `SceneCfg` already merged defaults→config→CLI by `config.merge_cli`, filtered per scene type via the same `applies_to`-metadata idiom as `introspect.scene_types`) plus the relevant slices of the global `Config` (`[color]` in full, a curated `[audio]` subset, and `hardware.backend`/`ultimate64.system`/`ultimate64.sid_model`). `build_scene_recording_metadata` does this from already-resolved in-memory state only — no live U64/TeensyROM reads, since a REST poll during an active recording risks contending with the DMA link (see the "no rapid U64 reads during capture" practice).

Two things are deliberately left out, because the payload is meant to be pasted straight into a public YouTube description: `[ultimate64].url`/`dma_password` and `[teensyrom].host`/`serial_port` never appear (only the backend kind + system + sid_model do), and nothing resolves further than the *configured* value — e.g. `[audio].dac_curve` is logged as configured (`"auto"`, `"mahoney_ultisid"`, …), not further resolved against live calibration-file/device-identity state.

The `source` block is scene-type-specific. For `video`, `config.build_scene` (see the note above) resolves a URL's `file` into a local `file_spec` var for the `VideoScene` constructor but never mutates `s.file` itself — so `scene._cfg.file` still holds the **original URL exactly as given** with no extra plumbing, while the actual (often ugly, CDN-signed) resolved stream URL never appears in the log. `quickcast.resolve_media_url`/`resolve_video_url` return a frozen `ResolvedMedia` (a small dataclass, not a tuple — the tuple this replaces had already been widened once, for `title`, and a second widening for `uploader`/`license`/`webpage_url` was the thing being avoided); `scene_factory._build_video` stashes the whole thing onto the `VideoScene` instance as `source_info` (`None` for a local file), and `_video_source` reads its `uploader`/`license`/`webpage_url` back — whichever fields yt-dlp itself left blank stay `None`. `copyright` for a URL is the yt-dlp `license` field verbatim when the site supplied one; failing that, an "uploaded by `uploader`" lead when yt-dlp at least named one; failing that, the same fixed **unknown** string as before. For a local file, `copyright` instead checks the already-open `AVFileSource.container.metadata` (PyAV, lowercased keys) for a `copyright`/`rights`/`license` tag — real on stock/licensed footage, absent on most casual clips. Wherever nothing is found it stays worded as an admission rather than a `TODO:`, because the blob exists to be pasted into a public description and a line nobody edited still gets published. `waveform` and `generative` (with `audio_source = "sid"`) scenes are different: the PSID header (`WaveformScene.header` / `SidFileAudioSource.header`, a `sid_host_emu.SidHeader`) routinely carries a real `name`/`author`/`released` (copyright year + composer), so those are used verbatim — no placeholder.

`extract_scene_configs(log_text)` pulls every `SCENE_CONFIG_JSON` payload back out of a `--log-file` run (formatter-agnostic — it searches for the marker substring, not a fixed line format), and `render_description(payload)` renders one entry as a human, paste-ready text block; both are pure functions so [scripts/scene_config_to_description.py](../../scripts/scene_config_to_description.py) is a thin argparse+file-I/O shell around them (default: render the last entry; `--all`/`--index N` for the rest).

## The package-root utilities — `_pollthread.py`, `_midi.py`, `_native_io.py`, `_redact.py`

The 2026-08 reorganization sorted every module into one of the eight topic subpackages except the entry point and these four: process-level plumbing with consumers across subpackage boundaries in every direction (`_pollthread` alone is imported from six of the eight areas), belonging to no topic. Their docstrings carry most of the design; the notes here add the tree-wide contract each one anchors, and where each came from.

### `_pollthread.py` — the background-loop idiom

Every background loop in the tree is a `PollThread` — 21 consumer modules, from the overlay pollers, the WLED bridge and the feature streams to the keyboard/vision/MIDI surfaces and the stream recorder — in place of per-site copies of the thread + stop-`Event` + `join` boilerplate. Periodic mode calls the target every `period` (with `run_first` picking whether the first call precedes the first wait); `manual=True` hands the worker the stop event and lets it own its pacing (backoff loops, `select` loops) — the constructor rejects a `period` in manual mode and demands one otherwise, so a call site can't half-configure it (and, since the adverse-review pass, `@overload`s two `__init__` shapes so pyright/mypy catch a wrong-arity target at the call site too). The load-bearing details are in the teardown: the periodic wait is `Event.wait`, so `stop()` interrupts a sleeping loop immediately rather than at the next tick, and threads are daemons joined with a bounded `join_timeout` (0.5 s default) — teardown is never hostage to a hung worker.

An abandoned worker (the join times out — a slow poll target, e.g. a network fetch, outliving it) is not silently forgotten: `stop()` keeps the thread reference instead of clearing it, so `is_running()` keeps reporting True for as long as the worker actually runs, and `start()`'s existing "already running" no-op then refuses to spawn a replacement until it does — which also means `start()` never reaches its `self._stop.clear()`, so the abandoned worker's own stop event is never un-set out from under it. Clearing the reference unconditionally used to make both of those lie, which let a `start()` after a timed-out `stop()` resurrect the abandoned worker (via the shared `Event`) *and* spawn a second one on top of it — the top finding of the CORE-1 adverse-review pass. A raised target is also now caught and logged (`log.exception`) rather than left to `threading.excepthook`, which printed straight to raw stderr and bypassed `--log-file`/`SessionLogBuffer` entirely; the loop still stops on an unhandled exception, same as before, just visibly now. `tests/test_pollthread.py` pins the whole contract.

### `_midi.py` — the guarded mido import

mido (+ python-rtmidi) is the optional `midi` extra, so every MIDI consumer needs the same import guard — it had been copied into three modules (one copy's comment promised it mirrored another "exactly"), each with its own 19-line port resolver, until #249 folded them here. Beyond what the docstring says (`mido` typed `Any` to keep pyright off the `None` fallback, `MIDI_AVAILABLE` as the runtime guard), the part that bites is the patch point: consumers re-import `mido` under their own module name, so patching `<consumer>.mido` still works for code *in that module* — but port resolution reads this module's copy, so tests that fake ports patch `c64cast._midi.mido`. `open_input_port` matches a case-insensitive substring of the available names, so nobody has to paste an exact rtmidi port string. Its precondition — the `midi` extra being installed — is a `RuntimeError` naming the extra, not the bare `assert mido is not None` it used to be: an assert is stripped under `python -O` and, even without it, an `AttributeError` on `mido.get_input_names()` names nothing about what a caller forgot to check.

### `_redact.py` — keeping the console token off the durable log paths

The web console's token is logged as a ready-to-open login URL, because that URL is the only entry point a phone gets — so the *terminal* has to keep it. Two other destinations carried the same line and should not have, and they are different enough in kind to be worth naming: `--log-file` writes a file that outlives the run and is not created `0600` (the token's own store deliberately is), and `SessionLogBuffer` is served over the state feed to every client — **including a read-only viewer**, which is the one that actually escalates. A viewer link exists so somebody can watch without being able to stop the show; handing it the admin token in a log tail defeats exactly that. `_LOG_BACKLOG` is 200 and the startup line lands at line ~3, so a viewer connecting to a fresh host received it. The host persists its token across restarts, so neither leak aged out on its own.

The split — terminal keeps, everything durable or shared redacts — is why this is applied at the point of **output** rather than at the `log.info` call. Two consequences worth not re-deriving. First, the file half is a `logging.Formatter` subclass (`cli_commands.RedactingFormatter`) and *not* a `logging.Filter`: a filter mutates the record, which every handler shares, so redacting there would blank the URL out of the terminal too — the formatter belongs to one handler, which is the whole point. Second, the buffer half redacts in `emit`, on the way *in*, so the secret never exists in the deque to be served; a redact-on-read would leave it sitting in memory behind whatever the next reader turns out to be. The pattern matches a `*token=`/`*password=`/`*secret=`/`*api[_-]key=` suffix (`=` or `:`, quoted or not — covers a JSON or TOML rendering, not just the query-string shape) plus a bare `Bearer <value>` header, so `viewer_token` and any later `…_token` are covered without touching this file. `tests/test_redact.py` pins both halves, including an assertion that the terminal handler is *not* redacting — the split regresses in either direction otherwise.

### `_native_io.py` — fd-level stderr muting

Some native dependencies write diagnostics straight to file descriptor 2 — below Python's `logging`, `sys.stderr`, and any library verbosity flag — so an fd-level `dup2` redirect is the only thing that catches them. Three sites use it, each scoped to the one call that emits: MediaPipe's C++/absl chatter (`vision.py`), OpenCV's AVFoundation probe of camera indices past the last valid one (`--list-devices`), and the Obj-C runtime's one-time "class implemented in both" warning when PyAV's bundled libavdevice loads on top of cv2's (`video._ensure_pyav`) — harmless, since the duplicated classes are the AVFoundation capture device neither file-decode path uses, but printed on every video run. The first two silences existed inline; the third made it a shared context manager. The scoping rule is the point: wrap only the emitting import/probe, so real stderr from elsewhere is never swallowed.

fd 2 is process-global, and `video._ensure_pyav` is a lazily-triggered entrant reachable from playlist worker threads (one per system, in an ensemble) — so two overlapping (non-nested) callers were reachable in practice, not just in theory. A module-level depth counter (behind a `threading.Lock`) makes the redirect reentrant across both nesting and overlap: only the outermost `__enter__` actually touches fd 2, and only the matching outermost `__exit__` restores it. Without that, the second caller's own `os.dup(2)` captures the *first* caller's `/dev/null` redirect as its "saved" fd, and whichever caller happens to exit last then `dup2`s that captured `/dev/null` back onto fd 2 — pinning the process's stderr to `/dev/null` for good. The same pass closed the two descriptor leaks on the failure paths (an `os.open`/`os.dup2` raising used to leave `saved`/`devnull` open respectively). `tests/test_native_io.py` swaps real fd 2 for a pipe to pin all three: silencing, no fd growth across ~200 cycles, and the overlapping-threads case restoring cleanly.
